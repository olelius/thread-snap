# 易车限流恢复探针固定为十秒

## Context

ADR 0052与0062把普通帖子任务的429恢复设计为60、120、240、480、900秒递增等待，
并在两次限流之间取得进展时重置为60秒。该策略保留固定候选和平台FIFO，但易车连续
429会把单次等待扩大到数分钟，批次完成时间主要由等待而不是实际采集组成。

现有易车链已经在首次429时按ADR 0061轮换一次当前线程HTTP传输；若新传输仍为429，
Worker会持久保存剩余URL并只恢复一个来源。用户确认该恢复路径改成每10秒一次的实时
探针，并明确要求间隔不随连续429次数上涨。

## Decision

- 本决策只改变`platform_code="yiche"`且错误码为`PLATFORM_RATE_LIMITED`的等待时间；
  每次收到429后，`retry_not_before`固定设为当前时间之后10秒。
- `retry_attempt`和`rate_limit_completed_count`继续写入检查点用于诊断与进展观测，但不再
  参与易车等待时间计算。连续零进展429与有进展后的新429都固定等待10秒。
- 10秒到期后执行的探针就是原任务最早受限来源的原URL复访，不新增独立探测端点；每轮
  只领取一个来源并把实际请求并发收敛为1。成功后沿原任务继续，仍为429则保存下一次
  10秒时间点。
- ADR 0061的一次当前线程传输轮换、固定候选、同平台FIFO、服务重启恢复、腾讯验证码
  分流以及终态判断均保持不变。
- 其他平台继续执行ADR 0052与0062的60、120、240、480、900秒递增冷却和进展重置规则。
  本值为代码常量，不增加新的配置项、数据库字段或前端开关。

## Consequences

- 易车持续受限时最多约每分钟执行6次单来源复访；这比原递增冷却产生更多平台请求，
  但不会形成多来源并发突发，也不占用10秒等待期内的Worker或HTTP槽位。
- 服务重启后仍读取持久化的`retry_not_before`；已经按旧代码写入的未来时间不会被主动
  改写，新一次429由新规则写入10秒时间点。
- 该调整只定义恢复调度，不证明平台429已解除，也不改变易车并发1～8的配置范围或当前
  运行值。正式批次耗时和恢复率仍以运行证据单独报告。

## Rejected alternatives

- **保留60～900秒递增等待**：与本次确认的10秒实时探针行为不一致。
- **把10秒做成新的运维配置**：当前只有易车存在这一明确需求，增加配置面没有必要。
- **每秒复访或恢复全部来源**：会放大请求突发，且破坏现有FIFO单来源恢复合同。
- **把探针改为首页或列表请求**：不同路由成功不等于原受限详情URL恢复，不能驱动原任务续跑。
