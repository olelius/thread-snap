# 限流后的帖子任务在原位冷却续跑

## Context

普通帖子提取已经把瞬时网络错误和人工访问验证建模为原任务可恢复状态，但
`PLATFORM_RATE_LIMITED`仍被当成终态失败。真实汽车之家补提因此出现同一批次部分
来源完成、部分来源限流，用户只能反复创建关联补提批次。新批次会形成新的采集时点，
也不能替代原任务已经冻结的候选与证据。

限流与登录失效不是同一事实。立即刷新Session不能证明限流解除；按普通网络错误的
2秒退避快速重放又可能延长平台控制。系统需要既不强刷，也不把暂时控制变成业务失败。

## Decision

- 普通帖子提取中的 `PLATFORM_RATE_LIMITED` 保持独立错误分类，但进入原圈子任务的
  持久重试检查点，不形成 `failed`、`partial_success` 或新的补提批次。
- 检查点保存已经冻结的剩余URL、来源位置、限流分类、重试次数和下一次允许访问时间；
  服务重启后继续使用同一检查点，不重新发现后续帖子。
- 限流冷却按60、120、240、480、900秒递增，之后保持900秒上限。冷却期间不发平台
  请求，也不占用运行线程或HTTP并发槽。
- 冷却到期后只领取FIFO队首的一个限流来源，并把该次恢复的实际请求并发收敛为1；
  成功后才领取下一个来源。再次限流只更新同一任务的下一次访问时间。
- 验证码和访问验证继续进入 `waiting_for_auth`，真实登录失效继续走Session恢复；限流
  不创建登录窗口，也不被包装成内部错误。
- 接入验收执行器仍遵守自身固定运行窗口和首个控制响应止损规则；本决策只改变普通
  帖子批次的运行时恢复语义，不用跨窗口拼接通过正式500条门禁。

## Consequences

- 用户不再为了暂时限流反复点击“重新提取失败项”；批次在同一任务、同一候选身份上
  延长完成时间。
- 同平台后续批次会继续被该FIFO队首阻塞，这是保留顺序和避免请求突发的预期结果；
  其他平台仍可独立运行。
- 汽车之家升级为 `autohome-club-v6`：详情访问前先完成本轮候选冻结，限流时把当前及
  后续未处理候选交给Worker冷却续跑。共享Worker的同一限流策略也适用于其他平台已经
  返回的精确失败URL。
- 历史终态批次及其补提链保持不可变，不回写为新的运行状态。

## Rejected alternatives

- **限流后立即重试或固定短间隔循环**：会持续制造平台请求并可能延长控制时间。
- **把限流当成登录失效**：重新登录不能证明解除频率限制，还会混淆Session事实。
- **结束批次并要求人工补提**：把暂时平台状态转换成重复操作和新的采集时点。
- **重新读取列表凑足目标数**：会改变固定候选身份，破坏结果与页面清单的对应关系。
