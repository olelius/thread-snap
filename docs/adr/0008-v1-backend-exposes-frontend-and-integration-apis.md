# 第一版独立后端同时提供前端与后续集成接口

第一版采用自建 Web 前端和一个独立提取后端。该后端同时提供两套接口边界：第一版前端使用面向页面的 `/api/v1`；后续客户现有后端使用调用方无关、只在本机开放的 `/internal/v1`。两套接口进入同一应用层，共用采集器、调度、Session、检查点、持久化和批次状态机，不复制业务实现。

这比第一版再增加一个薄应用后端更符合当前成本和复杂度边界：少一个后端进程和一次本机转发，同时仍提前形成后续集成所需的稳定服务契约。后续接入客户现有系统时，停用第一版 `/api/v1` 展示入口，由客户现有后端调用 `/internal/v1`；提取后端及其数据、采集器和任务流程保持不动。

## 接口与代码边界

- 第一版前端只调用 `/api/v1`，不得调用 `/internal/v1`，也不得接触平台接口、Cookie、Profile 或采集器私有结构。
- `/api/v1` 负责页面需要的请求校验、展示模型、文件上传下载和浏览器认证通道；这些控制器调用共享应用层，不另建一套采集业务。
- `/internal/v1` 使用调用方无关的提取业务语义，提供配置、异步批次、状态、结果、导出和平台认证能力，不暴露第一版页面组件或视图状态。
- 创建提取采用异步任务语义：接口返回批次标识，调用方随后查询状态和结果；任何入口都不以长连接同步等待完整采集。
- 提取后端持续拥有提取配置、定时规则、批次、帖子、评论、平台 Session、任务调度、检查点、平台采集器、数据库事务和 XLSX 生成。
- 第一版内网入口可以由同一主机的静态文件服务或反向代理发布前端并只转发 `/api/v1`；`/internal/v1` 继续只监听或仅允许 `127.0.0.1`，不直接暴露给客户浏览器。
- 第一版不为接口边界引入第二个业务后端、服务注册、消息总线、分布式事务或平台采集代理层。

## Python 映射

如果 Candidate A 通过最终技术选型门禁，推荐以一个 Python 后端代码库实现该架构：FastAPI 同时承载 `/api/v1` 和 `/internal/v1` 控制器，Scrapling 实现平台采集与浏览器 Session。API 进程与采集 Worker 可以按运行稳定性拆成同一服务下的独立进程，但它们共用应用契约和领域实现，不形成第二个业务后端。

Python、FastAPI 和 Scrapling 当前仍是最有证据的候选映射，不因本 ADR 自动变成最终技术栈；最终选型仍以目标 Linux 门禁和单独技术栈 ADR 为准。若最终选择 Node.js，同一双接口、单业务层边界保持不变。

## 后续接入

- 客户现有前端调用客户现有后端。
- 客户现有后端承担用户、角色、权限和可选公网访问，并通过 `/internal/v1` 调用原提取后端。
- 第一版 `/api/v1` 和自建前端可以停止部署，不影响 `/internal/v1`、采集任务和历史数据。
- 新鉴权、幂等或调用追踪要求通过版本化接口扩展，不把采集实现搬入客户现有后端。

本 ADR 细化 ADR 0001 的领域所有权与集成边界，不替代其“提取功能服务持续拥有提取数据”的决定。
