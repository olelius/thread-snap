# 云端舆情并发采用有界运行时配置和共享连接池

## Context

舆情 Worker 原先固定两个消费者。2026-08-24 的 150 条现场批次中，AI 从首次开始到最后一次原始完成约 153 秒，单次云端请求 P50 约 2.14 秒、P95 约 2.86 秒，固定值已经成为可见吞吐约束。云端提供方、账号容量和批次规模会变化，因此继续把并发写死在代码中不能满足部署后的实际调节需求；但直接按提供方理论上限创建线程又会放大本机连接、SQLite 写入和失败重试压力。

## Decision

1. “AI 舆情”配置增加“同时分析任务数”，只表示云端模型的最大在途分析请求数，持久化字段为 `cloud_concurrency`，允许 1～64，默认 8。
2. 保存后动态增加 Worker 槽位或暂停序号超出新值的槽位；已经发出的请求继续完成，新任务领取立即服从新值。修改该字段增加配置修订，但不使模型连接验证失效，也不增加判定对象版本。
3. 本地 PaddleNLP 路径固定一个推理槽位，继续由专用线程串行访问 Predictor；已保存的云端值在切换回来时恢复。
4. 云端请求复用一个线程安全的 `httpx.Client`，总连接和保活连接均以 64 为上限；全部槽位继续共享 429 冷却和既有有界重试。
5. 该配置不进入提取规则、批次快照或平台采集并发，也不新增 Redis、Celery、消息总线或第二应用进程。

## Consequences

- 单实例可以按提供方容量和实际批次吞吐在 1～64 之间调节，无需重启服务。
- 64 是 ThreadSnap 当前单进程、线程 Worker 和 SQLite 架构的应用保护上限，不等同于提供方账号上限；提高并发不会保证耗时线性下降。
- 后续若真实 16/32/64 档位出现连接池等待、429、SQLite 忙或失败率上升，应依据同分母耗时与失败分布收紧推荐值，而不是绕过上限。
