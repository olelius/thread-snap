# 将平台风控影响落实为 PoC 结果门禁

需求中使用“必须绕过风控”的说法，同时项目验收要求两个候选在最终 Linux 主机上连续三轮完成 2000 URL/小时、100% 最终完成率和 100% 必需字段完整率。

“绕过风控”如果被理解为必须采用某一种特定对抗技术，会把实现手段与业务结果混为一谈，也无法覆盖平台控制、账号、网络和页面行为持续变化的情况。因此该要求统一落实为可重复验证的结果门禁。

## Decision

- 不单独指定或验收某一种所谓“绕过”技术。
- 限流、验证码、挑战页、登录失效或其他平台控制导致任一 URL 未在一小时窗口内产生完整有效结果时，该轮失败。
- 瞬时错误或平台控制触发后，候选只有在同一小时窗口内自动恢复，并为该 URL 产生通过统一校验的完整结果时，才可计为完成。
- 三轮每轮均有效完成 2000 个不同 URL，且最终完成率和必需字段完整率均为 100% 后，该候选才通过门禁。
- 通过结论绑定候选版本、测试包 SHA-256、URL 清单及哈希、登录或未登录模式、网络出口、最终 Linux 主机、环境快照和测试时间。
- 任一绑定条件发生实质变化后，原通过结论不直接外推，重新执行同等级验证。
- 框架宣传、请求发出数量、排队数量、挑战页响应、人工补齐、窗口结束后补跑和临时人工操作均不作为通过证据。
- 两个候选均未通过时，保持正式技术路线未确认，扩大候选范围、调整采集架构或重新评估数据获取方式后重新执行 PoC。

## Consequences

- “风控是否被处理”成为客观的通过或失败结果，不依赖对实现技术的主观命名。
- PoC 通过证明的是已记录条件下的实际能力，不形成对未来平台变化的永久推断。
- 正式功能开发只在至少一个候选通过全部门禁后开始。
- 平台控制使测试未达标时必须保留真实失败记录，不以估算值或人工处理替代。
