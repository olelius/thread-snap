# 使用全局调度源和平台内 FIFO

第一版使用一个全局调度源维护全部 `HH:mm` 时间节点。每个时间节点最多创建一个顶层定时提取批次，批次再展开为平台和圈子子任务。任务按平台进入各自严格 FIFO；手动、定时和手动补提共用相同队列，不提供插队。

配置分为全局、平台和圈子三层：全局只保存统一提取时间；平台保存自动每圈有效结果数、平台内部总并发和启用状态；圈子归入车型并独立决定是否参加自动提取。任务入队时冻结配置快照，后续修改不改变已排队任务。

## 原因

- 把时间、数量和并发复制到每个圈子会制造大量重复配置，并导致多个定时器无法形成统一运行视图。
- 所有平台共用一条全局 FIFO 会让某个平台的认证等待阻塞其他平台；完全独立的多平台调度器又会失去统一触发和全局资源控制。
- 因此统一创建顶层批次，但在执行层按平台隔离 FIFO 和 Session。认证只阻塞对应平台，其他平台继续运行。

## 执行边界

- 第一版只有懂车帝适配器可运行，后端平台级并发固定为 1。前端可以展示和保存其他平台配置，但其接入状态为 `not_integrated`，不能启用或创建任务。
- 平台内部并发由前端配置并服从后端按平台发布的安全范围；它是该平台全部圈子、请求和自动重试共享的总上限，不是单圈并发。
- 多平台全部接入后，必须经过组合容量验证，再由后端配置可同时运行的平台数、各平台并发上限和全局资源预算；客户前端不控制平台级并发。
- 队列、配置快照、检查点和认证等待状态必须持久化。重启恢复已入队任务；停机错过的定时时间不补跑。
- 普通排队中和提取中的任务不取消。等待认证的任务可以经二次确认结束，以部分成功或失败收口并释放对应平台 FIFO。

## 被放弃的方案

- **每个平台或圈子独立定时器**：配置重复，难以保证统一触发、展示和资源预算。
- **所有平台共用一条执行 FIFO**：任一平台认证等待会无必要地阻塞其他平台。
- **手动任务优先或允许插队**：破坏结果顺序和容量可预测性，也会让定时任务长期饥饿。

本 ADR 只固定业务调度与队列语义，不提前选择调度库、数据库产品或 Worker 进程实现。

后续ADR 0035为每日正式口碑巡检增加了窄范围的非抢占优先级；本ADR对帖子提取、手动任务、补提、口碑失败项补跑和映射验证的普通FIFO语义继续有效。
