# 限流恢复取得进展后重置冷却级别

## Context

ADR 0052把普通帖子任务的限流恢复建模为60、120、240、480、900秒递增冷却，但原实现
只按任务累计`retry_attempt`递增。一个来源在冷却后已经新增大量有效结果，再次遇到429时
仍会升级冷却；这把两个相隔一段成功采集的限流事件误判为“零进展连续失败”。

2026-09-02 同范围易车并发4批次`20260902-133622-001`在完成119条和207条时分别进入
60秒与120秒冷却，最终222条、失败0、服务端耗时249.811秒。其间新增88条已经证明第一轮
冷却恢复成功，第二个429应当作为新的限流事件，而不是失败次数升级。

同日两项反证也修正了此前的归因：全池传输重置批次仍发生60秒与120秒冷却，总耗时
258.950秒；固定0.5秒详情间隔批次同样发生两次冷却，总耗时312.342秒。早期四传输A/B
使用4个不同未解决URL，不能证明同一触发URL通过换传输即可恢复。

## Decision

- `PLATFORM_RATE_LIMITED`首次进入持久恢复时，冷却级别从60秒开始，并记录当时任务的
  已完成结果数。
- 同一任务再次限流时，若本次执行已经把已完成结果数推进到记录值之后，则把它视为新的
  限流事件，`retry_attempt`重置为1，下一次仍冷却60秒。
- 若冷却复访后没有新增有效结果便再次限流，才把`retry_attempt`递增并采用120、240、
  480、900秒退避；900秒继续作为上限。
- 固定剩余URL、来源位置、同平台FIFO、冷却期零请求和恢复时单来源实际并发1保持不变。
  网络重试、认证恢复和验证码状态不复用这一进展计数。
- 进展基线只保存整数`rate_limit_completed_count`，不记录请求URL、Cookie、响应正文或
  平台凭证；任务形成终态后随普通重试检查点一并收敛。

## Consequences

- 对“成功采集一段结果后再次限流”的任务，每一轮从60秒重新开始，避免把有效进展当成
  连续失败；真正零进展的重复429仍会快速增加静默时间。
- 同范围并发4验证批次`20260902-144417-001`在116条时冷却60秒，恢复后新增106条并直接
  完成222条、失败0，服务端耗时124.193秒；相较旧批次249.811秒缩短50.3%。这是一次
  当前出口实测，不外推为固定平台阈值或免控并发配置。
- 易车仍保留ADR 0061的一次传输轮换作为有界前置尝试，但当前证据不再把它描述为通用的
  429解除条件；领导全池重置和固定0.5秒节流均未进入生产实现。

## Rejected alternatives

- **始终按任务累计次数升级**：忽略两次限流之间已经提交的有效进展，产生不必要的长冷却。
- **每次429都固定60秒**：零进展持续限流时静默时间不足，会形成周期性重复请求。
- **全池传输重置**：同范围实测仍发生两次冷却，没有取得优于现有路径的证据。
- **固定0.5秒详情节流**：同范围实测仍发生两次冷却且总耗时更长，不构成有效默认值。
