# 易车429先轮换当前线程HTTP传输再进入持久冷却

## Context

ADR 0052 已把普通帖子限流建模为原任务的持久冷却状态，ADR 0058 也把易车页面和
API 的429统一分类为 `PLATFORM_RATE_LIMITED`。这条路径能够保留固定候选和FIFO，
但它把首次429直接送入60～900秒冷却，没有利用后续对照实验确认的即时恢复条件。

2026-09-01 的固定1000 URL诊断批次处于429冷却时，在同一出口分别新建空Cookie、
仅设备Cookie、账号Cookie加新设备标识以及完整保存Session四组HTTP传输。四组都在约
0.4～0.6秒内取得 `203 -> 写入新动态Cookie -> 200正文`。这排除了账号或出口IP整体
封锁作为该轮429的充分解释，证据更支持状态绑定在活跃 FetcherSession、连接状态或该
传输的近期请求历史。原始对照和脱敏分析分别位于Git外：

- `artifacts/poc/results/yiche-concurrency1/20260901-1000-url/ip-account-cookie-ab-20260901.json`
- `artifacts/poc/results/yiche-concurrency1/20260901-1000-url/root-cause-analysis.json`

腾讯验证码的对照结论不同：同出口、同保存Session的新HTTP传输仍可能进入WAF，因此
传输轮换只处理首次429，不替代ADR 0060的腾讯验证码组件，也不构成免控并发策略。

## Decision

- 易车详情文档或签名API的一个逻辑请求首次收到429时，关闭当前线程持有的
  Scrapling `FetcherSession`，从同一共享 CookieStore 创建全新HTTP传输，并立即复访
  完全相同的URL和业务参数。
- 只替换当前工作线程的传输；其他线程、平台共享并发、平台FIFO、账号Session、固定候选
  和已完成结果保持不变。轮换动作串行进入短临界区，避免同时修改会话池。
- 详情文档在整个逻辑链中最多轮换一次。复访若得到203，继续执行既有动态Cookie计算并
  重载原URL；若得到TencentCaptcha/WAF，继续调用ADR 0060共享纯协议组件、提交
  `WafCaptcha`并校验原URL正文。
- API复访重新生成当前时间戳和签名，不复用第一次请求的时效字段。
- 新传输复访仍为429时，停止即时复访并返回`PLATFORM_RATE_LIMITED`，交回ADR 0052的
  60、120、240、480、900秒持久冷却。一次逻辑请求不循环轮换，也不提高并发。
- 传输统计增加 `http_rotations`，日志只记录平台、动作和次数，不记录Cookie、URL参数、
  签名或账号材料。

## Consequences

- 易车适配器升级为 `yiche-community-v9-rate-limit-transport-rotation`。研究对照中的成功
  恢复约增加1秒以内，但该观测不是服务承诺；生产是否恢复仍由203链、WAF链和最终正文
  身份合同共同判定。
- 首次429不再必然等待至少60秒；若控制确实跨传输存在，原持久冷却继续兜底，因此不会
  丢失原任务或扩大为无界请求。
- 轮换能力属于共享Scrapling传输池的最小操作，但自动触发策略目前只由易车适配器使用；
  其他平台没有对应对照证据，不自动继承该行为。
- 不新增数据库字段、前端配置、代理池或浏览器回退，也不改变易车并发配置范围和当前运行值1。

## Rejected alternatives

- **每次429反复创建新传输直到成功**：没有上限会把一次平台控制放大成连续请求。
- **重建整个Scrapling会话池**：会中断未命中429的其他线程并扩大恢复影响面。
- **清空或替换账号Cookie**：四组对照都成功，Cookie不是本轮即时恢复的必要变量。
- **只保留60～900秒冷却**：正确但遗漏了已有实验证据支持的低成本首选恢复动作。
- **把429直接送入腾讯验证码处理**：429与WAF控制文档是不同响应类别，应由实际复访结果分流。
