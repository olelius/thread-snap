# 正式口碑巡检固定内部并发二

## Context

口碑巡检原先直接冻结懂车帝帖子提取平台配置中的 `internal_concurrency`。当帖子提取为
提高批量吞吐把该值从2调整到8后，次日10:00月末巡检也继承了8，同时创建八个有头
浏览器页面上下文。帖子提取使用直连HTTP且并发面向帖子吞吐，口碑巡检则为每个车型
打开可见页面、稳定测量并截图；两类业务共享同一个数值会把一方的调优意外传播给另一方。

2026-08-31现场批次在并发8下仍然成功，因此问题不是结果错误或浏览器泄漏，而是巡检
桌面负载和平台访问强度不再符合用户确认的固定并发2。需要恢复可预期的巡检边界，且
不增加新的配置面。

## Decision

- 正式日检、月末巡检、同日延迟巡检及其失败项补跑统一使用后端固定内部并发2。
- 新建巡检批次把2写入 `concurrency` 快照；执行入口对修复前遗留或异常写入的非终态
  快照再次收敛为2。已经终态的历史批次及其并发记录保持不变。
- 页面打开、稳定测量、指标请求、截图和即时重试共享这两个执行项槽位，不嵌套扩大。
- 帖子提取继续使用平台配置中的1至8内部并发，修改帖子吞吐不改变巡检并发；巡检不
  新增用户可编辑并发字段。
- 映射验证不是巡检批次，仍按既有平台并发快照执行。本决策只替代ADR 0035和既有
  设计中“巡检继承平台内部并发”的部分，不改变正式巡检的非抢占优先级。

## Consequences

- 懂车帝帖子提取即使配置为8，正式巡检同时也只会处理两个车型页面；27项按两路分批
  完成，窗口数量和平台页面负载稳定可预期。
- 失败项补跑不会继承历史根批次中的8，而以新建补跑批次固定保存2。
- 当前27项全量留证的15分钟目标及45分钟硬上限保持不变；后续真实计划批次继续以
  终态时间和证据完整度验证该目标。

## Rejected alternatives

- **继续继承帖子提取平台并发**：一次HTTP吞吐调优会再次无提示扩大有头浏览器窗口数。
- **新增口碑并发配置项**：当前业务值已经明确为2，增加配置只扩大误操作面。
- **只在本机改成无头浏览器**：会隐藏窗口但不降低并发访问强度，也改变已验证的有头
  浏览器运行条件。
- **只修正当前数据库为2**：后续帖子配置变化仍会在创建新巡检批次时重新传播。
