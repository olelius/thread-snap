# ThreadSnap 当前进度

## 当前阶段

需求与 PoC 设计基线已经收口，等待甲方测试输入和目标 Linux 环境信息。

## 已完成

- 已建立远程仓库连接；
- 已明确产品目标为多平台论坛链接快照提取；
- 已确定第一版只交付一个平台；
- 已确定后续再接入两个平台并预留统一采集器边界；
- 已明确采用前后端模式开发；
- 已形成第一版功能设计基线；
- 已建立项目记忆、技术路线和进度文档的职责边界。
- 已确定第一版为受控内部环境使用的内部验证版；
- 已确定第一版首个平台为懂车帝；
- 已确定公网部署、身份认证和角色权限控制属于后续正式版。
- 已确定正式版集成到客户现有前后端系统中；
- 已确定提取功能服务持续拥有提取配置、定时规则、批次和结果数据；
- 已确定现有后端负责用户、角色、权限和公网访问，并通过本机内部接口调用提取功能服务；
- 已确定当前不考虑 Docker 部署。
- 已确认当前开发环境不是 Linux，日常开发、功能冒烟和中等批量预筛以当前开发环境为准。
- 已确定目标部署环境为 Linux，具体发行版和版本待确认。
- 已确认开发环境的吞吐结果只用于预筛；阶段 3 的三轮 2000 URL/小时硬门禁必须直接在最终部署的 Linux 主机执行。
- 已确认最终技术路线还必须通过 Linux 下的依赖安装、浏览器运行时、路径、权限、进程管理和启动验证。
- 已确认候选方案在当前开发环境完成阶段 1、阶段 2 后，必须先生成最简 `tar.gz` Linux PoC 测试包并通过干净目录部署验证，才能进入阶段 3。
- 已确认 Linux 测试机允许联网，但 PoC 测试包采用应用依赖离线安装：包内提供目标 Linux 对应的离线应用依赖、浏览器运行时、锁文件、SHA-256 清单及安装/启动/健康检查/基准测试脚本。
- 已确认依赖版本稳定性由锁文件、精确版本、测试包版本和 SHA-256 共同保证；离线包用于避免上游变化与下载失败，不能替代版本锁定。
- 已确认阶段 2.5 和阶段 3 不在线下载应用依赖或浏览器运行时；主机级语言运行时和浏览器系统库允许按记录版本在线预装。
- 已确认 PoC 部署人员具有 `sudo` 或 root 权限，可以安装语言运行时、浏览器系统库等主机级依赖。
- 已确认测试包不复制 Windows 虚拟环境、`node_modules`、Windows 浏览器缓存、凭证或机器状态，最终离线依赖必须面向已确认的 Linux 发行版、CPU 架构和 libc 生成。
- 已确认甲方可在目标 Linux 主机上直接执行 `cat /etc/os-release`、`uname -m` 和 `ldd --version` 并提供完整输出；这些命令通常无需额外安装，具体结果待主机确定后采集。
- 已确认最终 Linux 主机上的测试由项目负责人手动上传、校验、解压并触发脚本，Codex 不远程登录或自动操作该主机。
- 已确认人工只负责部署和触发命令；环境快照、计时、完成量、完整率、错误和资源指标由脚本自动记录，测试后生成结果包供评审。
- 已确认 `run-poc.sh` 直接把本次测试产生的数据写入固定轮次结果目录。
- 已确认结果生成过程不扫描服务器文件、不采用文件白名单收集，也不执行额外内容脱敏；结果结构从设计上不包含账号、密码、Cookie 或令牌字段。
- 已确认 Linux 测试结束后，由项目负责人只把完整轮次结果目录复制回当前开发电脑；程序、离线依赖、运行环境、浏览器目录和数据库继续保留在 Linux 主机，不属于回传范围。
- 已确认原始 `results`、URL 明细、运行日志和包含离线依赖的 Linux 测试包只在本地保存，不提交 Git。
- 已确认 Git 只保留 PoC 汇总报告、技术选型结论、ADR、必要汇总表和关联本地原始结果的 SHA-256。
- 已确认所有本地 PoC 产物统一放在 `artifacts/poc/`：甲方真实清单放在 `inputs/`，测试包放在 `packages/<candidate>/`，各轮结果放在 `results/<candidate>/<round>-<timestamp>/`，同一轮的不同结果文件不得散落到其他路径。
- 已确认 Linux PoC 测试包和原始测试结果都至少保留到第一版验收完成，之后由项目负责人手动决定继续保留或删除，不自动清理。
- 已确认输入清单和逐 URL 测试结果保留实际完整 URL，不使用哈希替代；清单哈希只用于一致性校验，Git 汇总报告不列出完整 URL 清单。
- 已确认每轮结果固定包含：JSON 格式的环境和汇总、JSONL 格式的逐 URL 结果和请求事件、CSV 格式的资源时序指标、纯文本 URL 清单与运行日志，以及 `SHA256SUMS`。
- 已确认所有结果文件统一使用 UTF-8，时间字段使用带时区的 ISO 8601 格式，两个候选使用相同文件结构和字段定义。
- 已生成甲方 PoC 输入模板：吞吐 URL 使用每行一个完整 URL 的 TXT，功能样本使用带模块、预期状态、评论档位和确认时间的 CSV，并提供独立填写说明。
- 已生成 `threadsnap-poc-client-input-templates-v1.0.zip`，包含填写说明、吞吐 URL 模板和功能样本模板，可直接发送给甲方。
- 已确认模板文件进入 Git；甲方填写后的真实清单固定放入本地 `artifacts/poc/inputs/`，不覆盖模板，不提交 Git。
- 已建立 `.gitignore` 规则统一忽略 `artifacts/poc/`，避免原始测试结果和大型 PoC 测试包误入仓库。
- 已确认 Linux 打包部署验证属于正式业务功能开发的前置 PoC 门禁；PoC 原型本身仍然需要先开发，不能把该门禁表述为“所有代码开发之前”。
- 已确认需求中的“必须绕过风控”按 PoC 结果门禁执行：限流、验证码、挑战页、登录失效或其他平台控制导致任一 URL 未在一小时内完整完成时，该轮失败；在同一窗口内自动恢复并完整完成时可计为通过。
- 已确认不单独验收某种所谓“绕过”技术；三轮通过结论绑定候选版本、测试包、样本、访问模式、网络、最终 Linux 主机和测试时间，条件实质变化后重新验证。
- 已完成 `grill-with-docs` 需求与设计访谈；后续 Linux 环境值、甲方真实清单、平台接口和技术栈结论属于 PoC 输入或实测结果，不属于尚未回答的产品设计问题。
- 已新增 `docs/README.md` 统一文档索引，并在 `AGENTS.md` 中建立按任务类型强制读取 Git 状态、领域词汇、产品设计、技术路线、当前进度、相关 ADR 和 PoC 计划的顺序。
- 已明确当前分支的 Git 状态和仓库文档优先于历史对话、全局记忆和旧分支内容；调研、模板与 ZIP 不自动成为实现规范。
- 已确定现有后端通过监听 `127.0.0.1` 的 `/internal/v1` HTTP/JSON 接口调用提取功能服务。
- 已确定本机内部接口不额外使用共享令牌，并接受同机其他进程可能调用的剩余风险。
- 已确定第一版需要逐条访问帖子链接，并提取帖子正文及评论等相关内容。
- 已确定第一版每个帖子按平台返回顺序最多采集十条主评论，不采集楼中楼回复。
- 甲方说明当前没有可用的官方数据接口；该信息尚未通过平台文档或书面回复独立验证。
- 已形成 Web 采集、浏览器自动化、会话、代理、验证码、协议分析及主要爬虫框架的技术版图调研；调研结论不代表框架已经选定。
- 已将技术选型候选缩小为 `Python + FastAPI + Scrapling` 和 `Node.js + TypeScript + Fastify + Crawlee + Playwright`；
- 已确定两个候选的真实样本对比 PoC 是正式功能开发前的强制前置门禁，不再把 `Scrapy + Playwright` 作为本项目候选；
- 已建立技术栈对比 PoC 计划，最终技术路线必须依据统一样本、统一输出契约和实测指标确定。
- 已更正每小时 2000 个 URL 的定位：这是项目真实交付硬要求，也是候选技术栈进入正式开发的硬门槛，不是仅供观察的 PoC 目标值；
- 已确定任一候选未达标即淘汰；两个候选都未达标时扩大候选范围、调整采集架构或重新评估数据获取方式后再次 PoC，不选择“相对更快”的失败方案；
- 已明确排队未执行、主动跳过、测试窗口外补跑、无限重试、验证码或登录页、未确认空数据、预置缓存、人工修补、重复少量 URL 和短样本外推均不得计入 2000 个有效完成量；
- 已确定 PoC 由甲方提供按功能模块组织的固定清单模板；测试从清单中随机抽样，两个候选使用相同抽样结果并保存随机种子；只有一条样本的模块只能证明该样本可处理；
- 已区分功能覆盖样本与吞吐样本；甲方确认可提供至少 2000 个不同的真实帖子 URL，不能通过重复少量 URL 达标。
- 已确认吞吐 PoC 连续执行三轮独立测试，三轮每轮都必须在一小时内有效完成 2000 个 URL；任何一轮未达标，该候选即未通过吞吐门禁。
- 已确认吞吐 URL 均由甲方从已知有效链接中提供；每轮 2000 个输入必须全部有效完成，最终完成率为 100%，不允许存在最终失败、部分成功或未完成结果；
- 已确认“零失败”指零最终失败：瞬时错误必须记录，只要系统在同一小时窗口内自动恢复并产生通过校验的完整结果，即计为通过；
- 已确认必需字段完整率为 100%：可见帖子必须取得正文，一级评论不足十条时全部取得，达到或超过十条时按平台顺序取得前十条；平台未提供的可选字段允许为空，但解析失败不得冒充平台缺失；
- 已确认正文中的图片和视频只保存平台实际提供的 URL，不下载、转存或代理媒体文件；
- 已确认导出从数据库中的独立批次快照生成，不在导出时重新访问平台；主要格式为 XLSX，至少包含帖子表和评论表；
- 已确认历史批次不自动过期，持续保留到用户人工删除；删除批次时同步删除所属帖子、主评论和相关临时导出文件；
- 已确认用户可见批次编号采用 `YYYYMMDD-HHmmss-NNN`、`Asia/Shanghai` 时区和秒级精度，同秒使用三位递增序号；数据库内部批次主键采用 UUIDv7；
- 已确认访问策略为未登录优先：匿名状态满足正文和主评论完整率时不使用账号；确需登录时由甲方提供合法会话，两个候选使用相同授权条件并重新开始测试轮次；
- 已按极简原则确认内部验证版凭证方案：确需登录时通过配置页面录入，账号密码保存到本地数据库，密码允许明文持久化但接口不回显，且不得进入列表、日志、错误、导出或 Git；
- 已确认内部验证版只保存一套全局懂车帝账号，所有提取配置共用，不实现多账号选择、绑定或轮换；
- 已明确明文凭证是内部验证版安全降级；正式公网版本必须改为加密持久化和权限控制，并加密迁移或清除遗留明文凭证；
