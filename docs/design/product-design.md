# ThreadSnap 功能设计

## 1. 文档状态

- 状态：初版功能基线
- 目的：规定产品功能、业务边界、分阶段交付和验收口径
- 不包含：具体编程语言、前后端框架、数据库、调度组件和部署方案

具体技术路线将在 `technical-route.md` 中单独评审和确认。

## 2. 产品定位

ThreadSnap 用于按需或按固定周期提取论坛、车友圈等社区版块中的帖子链接，并按执行批次保存结果。

每次提取都是一份独立快照。系统不持续跟踪单个帖子的后续变化，不覆盖旧批次，也不把不同批次自动合并为一条长期记录。

新增舆情反馈能力在帖子快照入库后调用已选的受控模型，忠实保存模型对指定品牌对象的情感、负面类型和依据；千问云端多模态模型额外保存图片、视频画面和音频覆盖，DeepSeek 云端文字模型与本地轻量模型只分析文字。单一内部使用者可随机人工修正；它不改变快照不可变边界，也不把模型反馈声明为客观事实。

## 3. 交付阶段

### 3.1 第一版：内部验证版

第一版只在受控内部环境中使用，以懂车帝为首个平台形成完整业务闭环：

- 配置每周计划节点、循环计划节点、可复用自动提取规则、平台运行参数、来源名称与平台圈子来源；
- 第一版只执行懂车帝采集，但前端展示后续平台并明确标记“暂未接入”；
- 导入已知帖子 URL 清单并手动发起提取；
- 从自动圈子、手动圈子历史或新输入圈子中选择多个圈子，配置本次统一数量后手动提取；
- 按每周计划节点或循环计划节点选择的自动提取规则，对符合条件的平台圈子自动提取；
- 查看提取批次及状态；
- 逐条访问帖子链接并提取帖子正文及评论等相关内容；
- 查看、搜索、复制和导出链接及提取内容；
- 记录基础错误信息；
- 为后续平台预留统一采集器接口。

懂车帝的具体列表与详情接口、访问条件、分页规则、评论加载规则和状态字段仍须通过真实样本验证，不得因平台名称已经确定而假定接口可用。

第一版同时保留两种输入方式：“圈子发现提取”负责从圈子列表分页发现帖子 URL；“URL 清单提取”负责直接处理用户导入的已知帖子 URL。两种方式必须复用同一平台详情采集、标准化、存储和批次流程。

第一版使用自建 Web 前端和一个独立提取后端形成完整调用闭环。该后端同时提供面向第一版前端的页面 API 和面向后续客户现有后端的稳定集成 API，两套接口共用同一应用层、采集器、调度、Session、批次状态和提取数据库，不复制业务实现。这样后续接入客户现有模块时，只需停用第一版前端入口并让客户现有后端调用集成 API，提取后端本身不迁移、不重写。

新增的舆情反馈作为第一版提取闭环之后的独立增量工作线：真实图文和视频样本的在线多模态 API PoC 已完成，数据库、持久队列、独立 Worker、接口、配置页、列表/详情和人工修正闭环也已实现；同一闭环增加只处理标题和正文的 DeepSeek 云端文字选项与本地轻量选项。生产环境真实模型调用、部署升级和目标环境验收仍与本地功能完成分开记录。

### 3.2 后续正式版

在不重复建设公共功能的前提下，再接入汽车之家和易车。第一版基线允许选择和保存其他平台的配置与圈子链接，但尚未完成本地适配器交付的平台必须显示“暂未接入”并禁止启用、手动提取或创建空任务。当前汽车之家与易车本地适配器均已发布为 `available`、默认停用；后续平台原则上只新增平台采集器、字段映射、平台安全上限及相应测试。

后续平台以外部配置说明中的社区页面作为发现种子，由项目通过实际点击或页面导航取得最新回复、最新发布入口并分别保存为独立来源。圈子发现冻结该来源实际返回的有序帖子；平台把其他原始论坛帖子明确聚合到当前列表时，分别保留发现来源和详情原始归属，不因两者不同而过滤或向后补量。易车已标记缺失的社区来源按真实缺失保留，不要求补齐，也不创建占位来源。项目从每个平台的真实社区发现结果中分别生成、现时复核并事前冻结500个不同帖子URL，同时自行形成分层功能样本和访问条件证据；不再要求外部为这两个平台另行提供2000条帖子URL或功能样本表。

500条是汽车之家、易车各自新增适配器的接入验收分母，只验证该平台的来源发现、详情、主评论、媒体、状态、认证和控制分类闭环。懂车帝既有2000条技术选型证据与目标CentOS连续三轮门禁保持不变，不因后续平台验收量调整而追溯降低。

如果后续平台必须依赖验证码处理、复杂动态签名、代理池或浏览器自动化，应重新评估范围和成本，不能默认视为普通适配。

若后续明确选择公网部署，必须增加身份认证和角色权限控制。具体管理框架暂不指定；业务接口和领域逻辑不得绑定到某个前端管理框架，以便后续替换管理界面或权限实现。

正式版集成到客户现有前后端系统中作为一个功能点：

- 正式前端在现有系统中新增业务界面；
- 正式前端只调用现有后端；
- 现有后端负责用户、角色、权限和公网访问；
- 现有后端通过仅限本机访问的内部接口调用提取功能服务；
- 提取功能服务持续拥有每周计划节点、循环计划节点、自动提取规则、平台采集配置、圈子列表来源、提取批次和提取链接。
- 第一版前端使用的页面 API 可以退出正式部署；客户现有后端复用同一提取后端的版本化集成接口。

## 4. 用户与访问边界

- 第一版只面向单一内部使用者或受控网络环境，不部署到公网。
- 第一版不建设应用内登录、用户、角色和权限管理。
- 第一版自建基础 Web 前端和独立提取后端，用于验证完整前后端闭环；前端只调用该后端的页面 API，不调用后续集成 API，也不接触平台私有接口和认证数据。
- 正式版部署到公网前，必须完成身份认证、角色权限控制和必要的外围访问保护。

第一版的平台人工认证入口同样只在上述受控内网中使用：客户使用现有浏览器，在第一版前端的页面或弹窗中直接操作提取后端控制的服务器浏览器，不安装远程桌面客户端，不接触 SSH、CDP、VNC 地址或第二层远程桌面登录。入口通过页面 API 使用短期、一次性随机票据绑定当前认证任务，并在完成、结束、断开或超时后失效。该票据只缩小内网误用窗口，不替代公网身份认证。

公网访问属于后续可选部署增强，不是第一版交付或验收前提。只有客户以后明确需要公网部署时，才把正式前端接入客户现有身份系统，由现有后端承担用户、角色、权限、敏感操作重新认证以及 HTTPS/WSS、WAF 或等价外围保护；不得因此提前扩展第一版功能。

## 5. 核心业务对象

### 5.1 配置与采集来源

第一版将自动提取配置拆成每周计划节点、循环计划节点、自动提取规则、平台采集配置、来源名称和平台圈子来源六个职责层。两类时间节点只引用规则，不复制数量等规则参数；平台页不再保存自动提取数量；来源与圈子页不保存时间、规则或平台运行参数。

#### 5.1.1 每周计划节点与自动提取规则

- 用户先维护带名称的可复用自动提取规则，再为每条每周计划节点选择一个或多个星期、24 小时制 `HH:mm:ss` 时刻、启用状态和一条或多条规则；
- 循环计划节点选择一个或多个星期、同一自然日内的开始与结束 `HH:mm:ss`、1 到 1440 的正整数分钟间隔、启用状态和一条或多条规则。开始必须早于结束且不跨午夜；实际触发点为“开始 + n × 间隔”，开始始终采集，结束只有被该序列恰好命中时才采集；
- 自动提取规则的可编辑字段为规则名称、明确选择的平台圈子、各已选平台统一的每圈有效结果目标数、AI 舆情分析开关和圈子页面截图开关；规则 ID、版本和更新时间由系统生成并只读展示。同一规则可以被多个计划节点引用，计划节点不复制规则字段；
- 规则按“平台 → 列表顺序 → 来源”两级折叠分组多选具体来源；平台和列表顺序复选框只用于各自范围内批量选择，保存时展开为明确来源 ID，每级标题显示已选数与总数。列表顺序分类默认收起，即使分类中已有选中来源也只在用户主动展开后显示来源项；切换规则时重新回到收起状态。同一圈子的“最新回复”和“最新发布”沿用相同提取参数与采集流程，但作为两条来源分别选择、分别发起批次；规则区只列出已经全局启用的来源，最内层来源以紧凑的满宽网格行展示，不重复展示验证状态、列表顺序徽标或全局启用状态；未全局启用来源只在“来源与圈子”管理，不进入规则选择列表。新平台或新来源默认不加入既有规则，不能因为曾经执行“全选”而动态扩张旧规则范围；
- 每周节点按“星期 + 时分秒”规范化；循环节点按星期、开始、结束和间隔展开实际触发秒；两类节点统一使用 `Asia/Shanghai` 时区；没有启用节点表示关闭定时提取；
- 所有启用节点按计划类型分别保持展开后的“星期 + `HH:mm:ss`”唯一：两个每周节点或两个循环节点发生任一实际触发点重叠时整次保存失败，并同时定位计划类型、冲突节点、星期、时刻和规则名称。每周节点与循环节点允许同秒触发并分别创建独立类别批次；仅时间段重叠但循环触发序列不相交不算冲突。停用节点可以保留同类型冲突，但重新启用时执行相同校验；系统不合并、覆盖或跨批次去重同秒的跨类型节点；
- 所有节点由一个全局调度源统一管理，不创建平台或圈子私有定时器；
- 服务停机期间错过的时间节点不补跑，只记录中文调度事件；已经持久化入队的任务在重启后继续处理。

“自动提取规则”“每周计划”和“循环计划”是配置管理中的三个同级编辑标签。用户先在规则标签维护并保存规则，再在任一计划标签选择已经保存的规则；三个标签分别保存当前职责范围，但后端继续使用同一提取配置 revision，并在单次事务中把当前标签草稿与服务器已保存的其他部分合并校验，避免节点引用尚未保存或已删除的规则。框架没有单一的计划成品控件，前端使用统一组件体系中的星期多选、24 小时时间输入、分钟间隔输入、规则选择、按钮、标签和 Alert 组合为应用级计划编辑器，不另起视觉体系。

计划节点实际触发时冻结全部所选规则的版本、已选圈子 ID、各平台数量、两个输出开关、实际可执行来源和运行配置快照，并把这些规则合并为一个定时批次；重复圈子只创建一个圈子任务，目标数采用所有包含该圈子的规则中最大值，AI 分析与页面截图分别按“任一贡献规则开启即开启”合并，同时在批次和圈子任务快照中保留来源规则。后续修改规则、平台状态或圈子状态不改变已经创建的批次。提取计划不复制平台启用状态或圈子全局自动提取开关，而是逐规则以“规则已选圈子 ∩ 已接入且启用平台 ∩ 已验证且全局启用圈子”形成来源后再求并集。

规则中的平台数量与所选圈子范围严格对应：只有至少选中一个圈子的平台才显示并保存该平台的每圈数量；取消该平台最后一个圈子时同时移除其数量。暂未接入平台只显示接入状态并禁止选择；后续平台正式接入后默认不进入既有规则。平台并发、启用状态、Session、重试与安全限制、评论数量、发现顺序、星期、时刻、时间段和间隔仍不进入规则；规则本身不设置启用开关，是否触发只由每周计划节点或循环计划节点的启用状态决定。

规则采用逻辑 ID 与不可变版本：编辑并保存规则时生成同一逻辑规则的新版本，引用该逻辑规则的计划节点无需逐条修改，下一次触发自动读取最新版本；已经创建、排队、运行或结束的批次继续使用并展示其冻结版本。任何启用或停用的计划节点仍引用规则时，归档和删除操作均被阻止并列出引用节点，用户必须先切换或删除这些节点。从未产生批次且没有节点引用的规则可以永久删除；已有历史批次但已解除全部节点引用的规则只能归档，归档后退出新节点选择器但历史仍可查看，并允许恢复为可选规则。

第一版不自动生成默认规则或计划节点。首次使用时“自动提取规则”“每周计划”和“循环计划”均为空，用户先创建并保存至少一条规则，再创建引用它的任一类计划节点；只有规则而没有启用节点时，定时提取保持关闭。

#### 5.1.2 平台采集配置

| 字段 | 说明 |
|---|---|
| 平台代码 | 稳定英文代码，例如 `dongchedi` |
| 接入状态 | `available` 或 `not_integrated`；由后端能力决定 |
| 平台内部并发 | 该平台全部圈子和自动重试共享的总并发上限 |
| 平台启用状态 | 是否允许创建该平台的新手动和定时任务 |
| Session 状态 | 当前保存状态、最近保存时间和获取或更新入口；不表示采集端点已经验证 |

平台内部并发由前端配置，但必须服从后端按平台发布的最小值与最大值。当前三个已接入平台统一允许保存 1～8；前端限制输入范围，绕过前端提交的值由后端自动收敛到范围内，并在响应中返回实际保存值。该值是平台全部来源、帖子请求和即时重试共享的总并发，不是每个圈子的独立并发；修改只影响之后创建的批次。自动每圈提取数只在“自动提取规则”标签维护，手动提取数量只属于当前手动提交，两者都服从对应平台经 PoC 和容量验证确定的安全范围。

平台停用后不再加入新的定时任务，也不接受新的手动任务；已入队、运行中或等待认证的任务仍按入队快照完成。历史结果仍可查看、导出和删除；重新启用前不得创建手动补提。当前懂车帝、汽车之家与易车均为 `available`；后两个平台完成本地发布后继续默认停用，由用户显式启用。

后续平台从 `not_integrated` 变为 `available` 时默认保持停用，现有自动提取规则也不自动选择该平台或其圈子。平台启用只开放该平台创建新任务的全局资格，不改变规则范围；用户在“自动提取规则”标签为某条规则选择该平台圈子时，必须同时填写该平台的每圈数量。平台配置页不重复编辑规则范围或数量。

#### 5.1.3 来源名称与平台圈子来源

- 来源名称由用户填写，用于规则选择、批次“提取范围”和结果来源展示；名称属于当前来源的可变展示属性，保存修改后，仍关联该来源的历史批次列表、详情和之后生成的导出均显示当前名称，批次任务继续保留创建时名称快照供来源删除后的回退与追溯。平台返回圈子名称继续独立保存，不用它代替用户名称。历史 API 与数据库中的 `vehicle`/`vehicle_name` 字段只作兼容保留；同一圈子的不同列表顺序必须使用不同来源名称以便识别；
- 平台圈子来源以“平台代码 + 平台圈子 ID + 版块 + 列表顺序”全局唯一，保存平台返回名称、规范化链接、验证状态和自动提取启用状态；同一圈子的“最新回复”与“最新发布”是两个独立来源，可以使用不同来源名称并进入不同规则或批次；
- 平台明确返回在当前来源列表中的跨论坛聚合帖仍属于该次来源快照：批次和结果保留当前发现来源，帖子原始状态另存详情原始论坛身份和跨论坛标记。只有列表响应不属于请求来源、帖子ID或URL身份不一致，或列表已声明的原始归属与详情再次冲突时才判为错帖；不得仅因发现来源与原始归属不同而过滤并向后补量；
- 第一版懂车帝实现动态版块的“最新回复”和“最新发布”两种列表顺序；规范化链接分别为 `/community/<id>` 与 `/community/<id>/dongtai-release`，分页继续附加 `/<page>`；其他版块暂不开放；
- 删除来源配置只影响后续选择和自动提取，不删除历史批次、结果或已有模板引用；来源仍被任一未归档规则的当前版本选择时阻止删除，用户需先保存移除该来源的规则新版本；
- 多条来源允许在前端表格中连续编辑后整批提交。整批先做格式、平台归属、圈子 ID、列表顺序和复合重复校验；任一行错误时整批不保存，一次返回全部中文定位错误；全部通过后在同一事务中保存。

圈子来源允许先保存为 `unverified`。用户可以单条验证，也可以把全部未验证来源一次提交到持久 FIFO；页面持续显示总数、完成数、成功、失败和等待平台会话数量。验证确认圈子身份、动态版块、所选列表顺序、至少一个真实帖子 URL 和一条有效帖子结果。系统先使用现有访问条件；只有明确识别为账号登录要求或访问会话异常时才进入对应的平台会话流程，更新后自动重试原验证。普通来源验证与帖子提取只使用平台 Session 的直连 HTTP，不启动 Chromium；浏览器只属于共享认证状态机中的人工登录/有界Session刷新，或用户明确开启且平台支持的页面证据，不作为采集失败回退。网络错误、限流和平台控制按各自中文错误返回，不直接推断为需要登录。

配置圈子第一次验证成功时自动开启全局自动参与资格，并永久记录首次验证时间。用户此后可以手动关闭自动参与；重新验证、重新认证、圈子链接或适配器变化导致的再次验证都只刷新验证结果，不得把用户已经关闭的开关再次开启。手动圈子历史不适用首次验证自动参与。只有验证通过且全局自动参与开启的配置圈子才具备定时执行资格，具体规则范围仍须由用户明确勾选，不因验证成功自动扩张。

#### 5.1.4 手动圈子历史

用户手动输入的新圈子在验证通过后保存到手动圈子历史，记录平台、圈子 ID、平台返回名称、规范化链接和最近使用时间；不自动创建车型、不自动绑定车型，也不加入定时提取。历史永久保留到用户单条删除或清空，下次手动提取可以再次选择。以后加入自动提取时，用户必须明确选择已有车型或新建车型。

### 5.2 提取批次与来源任务

每次手动触发、每周计划节点或循环计划节点的实际触发点均创建一个独立提取批次。每周节点创建 `scheduled` 定时批次，循环节点创建 `recurring` 循环计划批次；两类节点同秒时分别创建批次，定时批次先于循环批次入队，同一平台仍按 FIFO 顺序执行而不增加平台采集并发。手动与定时批次只进入侧边栏“提取列表”，循环计划批次只进入独立侧边栏“循环计划列表”，不得依赖同一列表中的触发方式筛选完成分隔。两个列表及其详情路由复用完全相同的字段组件、状态机、任务进度、认证、重试、导出和删除交互。一个计划批次合并使用该节点引用的全部自动提取规则；本次新增的同圈多列表能力只改变来源校验和寻址，不把“最新回复”与“最新发布”自动合并为一个来源或一个结果集合。两类来源分别提交时创建独立批次，不因平台圈子 ID 相同而互相覆盖。一次手动批次只选择一个已接入平台，可以选择该平台的一个或多个来源，并为所有选中来源填写本次统一目标数，同时明确选择本批次是否执行 AI 舆情分析、是否生成圈子页面截图。新建手动提取按“最新回复、最新发布”把已配置来源分组；分类标题显示已选数与总数，提供全选、取消全选和半选状态，分类默认收起且不同分类独立选择。URL 清单同样可选择 AI 分析，但因没有圈子列表页面，页面截图固定不适用。手动数量和两个开关不修改自动提取规则，也不写入平台配置。

批次创建入队时冻结平台、圈子、每圈数量、AI 分析开关、页面截图开关、平台内部并发和触发时间等业务配置。后续配置修改、停用或删除不改变已经入队的批次；执行时如后端安全上限降低，则自动收敛并记录中文说明。

建议字段：

| 字段 | 说明 |
|---|---|
| 批次 ID | 数据库内部 UUIDv7 唯一标识 |
| 批次编号 | `YYYYMMDD-HHmmss-NNN` 格式的用户可见编号 |
| 输入方式 | 圈子发现或 URL 清单 |
| 触发方式 | `manual`、`scheduled` 或 `recurring` |
| 创建、排队、开始、结束时间 | 用于展示队列和运行阶段 |
| 状态 | `queued` / `running` / `waiting_for_auth` / `success` / `partial_success` / `failed` |
| 平台、圈子、计划和完成数量 | 由圈子子任务汇总 |
| 错误详情 | 后端生成、可直接展示的中文说明 |
| 配置快照 | 本批次实际采用的业务配置 |
| 补提来源 | 手动补提时关联原批次 |

前端中文状态为“排队中、提取中、等待平台会话、成功、部分成功、失败”，触发类型为“手动触发、定时提取、循环计划”。第一版不显示操作人，也不建设人员权限。

所有用户可见的创建、排队、开始、结束、发布和验证时间统一按 `Asia/Shanghai` 展示，不随部署服务器或访问浏览器的系统时区变化。后端接口时间使用带 UTC 时区标识的 RFC 3339 字符串，前端完成 UTC 到北京时间的显示转换；不得把无时区字符串直接当作北京时间展示。

提取后端使用一个全局调度源，但按平台维护严格 FIFO 队列。平台会话异常只阻塞对应平台：该平台后续任务继续持久化排队，其他平台可以运行；账号登录认证或访问会话更新通过后先续跑原任务，再处理该平台后续任务。第一版后端平台级并发固定为 1；后续多平台全部接入并完成组合容量验证后，平台级并发、各平台内部并发和全局资源预算作为后端重要配置重新确定，不由客户前端控制。

同一平台的多个圈子来源可以并行推进，但圈子列表和帖子请求、自动重试合计不得超过平台内部总并发。每个来源保持其已冻结的“最新回复”或“最新发布”顺序。来源内按平台帖子 ID 或规范化 URL 去重；同一帖子出现在不同来源时保留各来源归属，可以复用同一批次内已取得的详情响应，但不能删除任一来源的结果记录。

每圈提取数用于从来源冻结顺序中确定前 N 个去重固定候选，不再按最终成功帖子数向后补位。列表确实不足 N 条时按实际冻结清单结束并显示中文原因；固定候选的网络访问错误只重试原来源或原帖子 URL，不能发现 N+1 候选替换。平台明确证明帖子删除、身份冲突或内容不成立等终态错误时，有部分结果为 `partial_success`，没有结果为 `failed`。

自动重试属于原任务的持久状态，不创建新批次，也不把任务放到同平台 FIFO 队尾。瞬时网络错误不进入终态或 `failed_count`，Worker 按有界退避反复访问完全相同的来源 URL 或固定候选 URL；服务重启后从检查点继续，成功后才释放该平台 FIFO。登录失效、验证码或需要人工完成的访问验证进入既有 `waiting_for_auth` 恢复状态，不直接结束为失败；系统保存原始触发 URL，用户保存结构有效的 Session 后恢复同一任务，并由原任务在原 URL 判断采集访问条件。平台限流不伪装成登录问题，也不结束批次要求人工补提；系统保存本轮已经冻结的剩余 URL，按 1、2、4、8、15 分钟且最高 15 分钟的冷却间隔留在同平台 FIFO 队首自动续跑，冷却复访一次只执行一个来源并把实际请求并发收敛为 1，避免冷却结束后再次形成请求突发。只有平台明确证明删除、身份冲突、正文或媒体不成立等非网络终态错误，才把固定候选计入最终失败数。终态 `partial_success` 只手动补提失败圈子，终态 `failed` 手动补提原全部圈子；手动补提创建新的 `manual` 批次、冻结新的候选与证据并进入对应平台 FIFO，不改写原批次候选或截图。前端把原批次和后续补提中每个圈子的最新成功结果关联汇总，但不物理合并原始快照。删除任一补提批次后立即按剩余批次更新汇总，并恢复仍缺失圈子的“重新提取失败项”操作。

第一版普通 `queued` 和 `running` 不提供取消。`waiting_for_auth` 提供“结束本次提取”以解除平台队列阻塞；二次确认后按已有结果结束为部分成功或失败，关闭认证入口并允许后续手动补提。

批次数据不自动过期。只有终态可以在二次确认后永久删除；删除时在同一事务中删除该批次的圈子任务、帖子、主评论、检查点、错误明细、导出记录和文件，不影响其他批次、配置或手动圈子历史。删除配置不删除历史批次。

批次编号使用 `Asia/Shanghai` 时区，时间精度为秒；同一秒创建多个批次时，通过三位递增序号 `NNN` 区分。

### 5.4 提取评论

第一版需要采集目标帖子下可合法访问的主评论。主评论指直接回复帖子正文的一级评论；每个帖子按平台返回顺序最多保存十条，不采集楼中楼回复。评论属于对应提取批次和帖子快照，不在后续批次中覆盖旧数据。

主评论采集不作为整条帖子是否有效的门禁。帖子身份成立且正文或媒体有效时，平台当前返回多少条一级评论就保存多少条，最多十条；评论为空、列表回复数与详情评论数不同、仍声明后续页、缺少分页终止标记或评论响应不可用时，帖子仍作为正常结果保存和展示，不增加批次失败数、不向后补量，也不显示评论异常或待确认状态。评论响应身份与帖子不一致时只丢弃该次评论数据。登录失效、验证码、限流等平台控制仍按统一控制状态机处理。

建议字段：

| 字段 | 说明 |
|---|---|
| 批次 ID | 所属提取批次 |
| 平台帖子 ID | 所属帖子 |
| 平台评论 ID | 平台提供时保存 |
| 评论作者 | 平台提供时保存 |
| 评论内容 | 平台提供时保存 |
| 评论时间 | 平台提供时保存 |
| 点赞数 | 提取时的平台数值 |
第一版不要求采集楼中楼、超出十条的后续评论或平台未正常返回的折叠评论；这些未采集内容不影响帖子快照的正常结果状态。

### 5.5 舆情反馈

每条提取链接快照可以形成一份 AI 舆情反馈。千问云端多模态模型的判定输入包含该快照的完整标题、正文、全部图片 URL 和全部视频 URL；DeepSeek 云端文字模型与本地轻量文字模型只读取完整标题和正文，不刷新或提交任何媒体 URL。三种模型都不包含主评论、楼中楼、作者历史或其他帖子。千问多模态路径对同一稳定媒体去重，视频反馈必须同时说明画面和音频的实际处理情况；两个文字路径把存在的图片、视频画面和视频音频统一标记为“未参与分析”，该明确跳过不会使任务变为部分完成。

帖子详情不直接播放快照中可能已经过期的视频地址。打开含视频的详情 Sheet 时，系统自动使用快照中保存的平台视频 ID，通过平台网页同款的授权接口与播放信息接口发起两次直接 HTTP 请求，选择当前最高码率播放 URL；同一清晰度优先采用支持浏览器连续字节范围播放的备用 CDN 地址，备用地址缺失时回退主地址。该过程不加载原帖页面或启动浏览器。播放器先请求同源的无正文重定向，由其设置不发送 Referer 后再让浏览器直接访问媒体 CDN，避免 CDN 因本地页面来源拒绝请求。播放器取得当前地址后使用 `preload="auto"` 提前缓冲并启用行内播放，但仍由用户主动开始播放；用户可以显式刷新播放地址。刷新结果只用于当前播放且有短时缓存，不回写帖子快照，不下载、转存或代理视频文件。解析失败时展示中文原因、重试入口和原帖入口，不把失效历史地址伪装为可播放媒体。

一个 ThreadSnap 实例只维护一个可配置、可版本化的舆情判定对象，不按平台、来源或提取规则分别配置。首版配置面保持最小，只填写一个目标品牌、一组重点产品/车型和一段选填补充说明。千问与 DeepSeek 云端模型由模型结合所收到的语境判断常见别名、品牌服务和实际相关性，后端不以关键词重判；DeepSeek 只依据文字语境。本地轻量模型使用配置品牌/产品作为 UIE 评价维度，保留模型抽取的观点与依据，并由 UTC 执行情感和负面类型分类；对模型未抽取到观点的文本，只能依据配置名称的明确出现判定相关。因此其别名、隐含指代和复杂语境能力弱于云端模型，用户需把必须覆盖的别名作为独立重点产品填写。用户保存修改时生成新版本，只供之后创建的分析任务使用；旧任务和历史反馈继续引用原版本。初始目标品牌为“奇瑞”，重点车型为 `A9`、`A9L`、`QQ3 EV`、`T9L`、`T11`、`T9`、`艾瑞泽8`、`艾瑞泽8PRO`、`瑞虎8`、`瑞虎8PLUS`、`瑞虎8PRO`、`瑞虎9`、`瑞虎7L` 和 `风云T7`，后续可在同一配置区调整。每次反馈同时冻结提示词版本和模型版本，以便后续解释同一帖子为何得到不同反馈。首批负面类型采用稳定代码，并允许一个主要类型和零个或多个次要类型：

“AI 舆情”配置为云端模型提供“同时分析任务数”，表示最多同时发出的云端模型请求，允许范围为 1～64，默认 8，并提供 4、8、16、32 快捷值。保存后只约束后续领取任务，不中断已经发出的请求，也不使连接验证失效或生成新的判定对象版本；本地模型始终使用单路推理，切回云端后恢复已保存值。界面不得把该字段称为线程数，也不得与平台采集并发混用。

| 稳定代码 | 中文含义 |
|---|---|
| `product_complaint` | 产品客诉：车主对真实故障、质量或设计缺陷的反馈 |
| `product_criticism` | 产品吐槽：非真实车主发言，或缺少明确维权诉求的用料、体验等负面评价 |
| `service_complaint` | 服务投诉：对售后、门店或服务质量的负面反馈 |
| `brand_criticism` | 品牌吐槽：针对品牌形象、经营或相关言论的负面评价 |
| `competitor_attack` | 竞品攻击：以贬损本品牌为目的的竞品水平恶意言论 |
| `other` | 其他：突发舆情、线下集体维权等未落入上述类型的场景 |

AI 反馈至少保存对象相关性 `subject_relevance`、相关对象与依据、情感倾向 `negative` / `non_negative`、负面类型、文字/图片/视频画面/视频音频的覆盖状态与依据，以及模型原生返回。`subject_relevance=false` 时有效舆情结果为 `unrelated`，情感和负面类型字段为空；相关内容只有 `negative` 继续填写一个主要类型和零个或多个不重复的次要类型，`non_negative` 的类型字段为空。结构化输出按模型能力独立适配：千问继续使用 JSON Object 并由后端严格校验完整多模态合同；DeepSeek 使用 Beta Strict Tool Calling 的单一强制函数，模型只返回相关性、命中对象、情感、分类、文字依据和总结，文字处理状态及全部媒体数量与“未参与分析”状态由后端根据实际输入确定性补齐；本地路径保存 UIE-Senta 和 UTC 原生输出，再以固定映射生成统一结果和中文模板总结。提供方结构约束不是最终信任边界，任何云端原生结果仍须从零通过本地字段、类型、枚举和业务关系校验。DeepSeek 严格工具参数发生 JSON 语法错误时，后端可以构造通用结构候选，但候选相对原文只能改变 JSON 标点、引号、转义符和空白，并且必须是唯一通过精确七字段、禁止额外或重复字段、类型、枚举和业务关系校验的结果；任何语义字符变化、候选不唯一或合同不完整都不得本地恢复。后端不替换同义枚举、不把字符串改成数组，也不通过关键词或业务常识重判结论。千问合同违约时保存候选和具体错误，并在不携带错误 assistant 候选的干净上下文中纠正一次；DeepSeek 只有在无唯一无损结构候选或业务关系违约时才在同一强制函数和原 Schema 下纠正一次。模型调用保持有界，不进行无限重试；DeepSeek 文字流使用 30 秒逐块读取边界和 60 秒单次绝对总时限，千问多模态保持 600 秒逐块读取边界，流式传输缺少正常结束标志或明确因长度限制结束仍按传输故障完整重请求一次，并与合同纠正分别审计。

分析状态与提取状态分离。状态包含 `analysis_queued`、`analysis_running`、`analysis_completed`、`analysis_partial`、`analysis_failed`、`analysis_paused` 和 `analysis_disabled`。不存在的模态不影响完成；帖子存在媒体而任一必要媒体无法访问、无法辨认或未被处理时，状态为 `analysis_partial`，可以保存暂定反馈但不形成有效舆情结论。全部必要模态处理成功且结构有效时才是 `analysis_completed`；失败、部分、暂停或禁用不改变提取批次及帖子快照的成功状态。解析、结构修正或结果保存阶段的未预期内部异常必须结束 `analysis_running` 并记录稳定错误码；运行任务失去执行线程时只允许自动恢复排队一次，重复失联转为失败，避免永久显示“分析中”或无界重复付费。

当前有效舆情结论按以下优先级确定：当前快照的人工修正 > 内容未实质变化时继承的人工判定记忆 > 当前完整 AI 反馈。没有人工结果时，只有输入、舆情判定对象版本、提示词版本和模型版本完全一致的完整 AI 反馈可以复用；部分或失败结果不作为缓存命中。

人工复核为可选操作。单一内部使用者可以随机查看帖子并把结果修正为 `negative`、`non_negative` 或 `unrelated`；负面结果必选一个主要类型，次要类型可多选且不得与主要类型重复，修正备注选填，非负面或不相关结果清空负面类型。系统保留原始 AI 反馈并追加人工修订记录，不覆盖原始返回；同一快照可以多次修订，最新有效人工修订优先。用户可以通过追加撤销事件恢复完整可用的 AI 结果，历史记录始终只读。人工判定只对当前快照和内容实质未变化的未来同帖快照生效，不回写其他历史批次；内容变化后重新取得 AI 反馈，并仅把旧人工结果作为参考。

### 5.6 圈子页面原始证据与关联截图成果

只有批次快照中开启“圈子页面截图”的圈子发现任务才同步冻结圈子页面原始证据。任务使用哪个来源链接，就只截取该任务实际访问的页面；同一圈子的“最新回复”和“最新发布”只有在本批次分别执行且截图开启时才分别形成成果，未执行来源和关闭截图的任务不补拍。URL 清单提取没有圈子来源页面，不进入该流程。

圈子页面清单是页面证据与帖子详情采集共同使用的有序帖子集合。系统在同一个已渲染页面状态中冻结帖子 ID、顺序、卡片范围和原始分页证据，再按配置数量从中确定前 N 个去重固定候选；不得让截图链路和帖子链路各自重新发现列表，也不以时间差很短推定两者一致。固定候选访问失败只重试原 URL，不继续冻结或使用后续帖子补位。

每个物理分页的原始证据保持页面原貌，捕获链路不得注入隐藏滚动条、禁用动画、改变定位或其他会改写页面布局/像素的 CSS。实际入库帖子只有在同次页面清单和完整原始证据中存在可追溯卡片时才成为证据化帖子。卡片文字、媒体和布局必须完成加载并在平台原始页首状态稳定，最终卡片矩形与原始 PNG 使用同一像素坐标系；首部、中部与末部抽样均应完整包含卡片底部操作栏。仍处于空白、破图或加载状态的必需卡片不形成完整证据。平台页面明确显示媒体失效或无内容属于真实页面状态，侧栏广告等非帖子资源不影响卡片门禁。原始证据只允许在当次浏览器上下文内有界即时重试；上下文结束后不得重新访问平台并把新页面伪装成原采集时刻，恢复必须创建新的关联采集。

一个原批次及其全部补提批次中的同一实际执行来源组成稳定的关联圈子成果组。当前关联结果沿用现有跨补提去重和稳定来源位置；成果按这些结果首次引用页面证据的顺序，为每张被引用的原始物理分页生成完整标注副本并组成唯一逻辑截图成果。副本保持原图宽高、布局和页面内容，不裁取、不缩放、不重排卡片，也不增加成果标题栏；允许产生变化的像素只有负面红框。若不可变原始证据完整而历史卡片矩形与 PNG 像素发生可验证的布局漂移，成果渲染允许从原图恢复可见卡片边界并创建新的不可变版本，但不得修改原图、原清单或历史成果。跨批次成果必须在查看器摘要和成果清单明确标注派生性质、贡献批次、采集时间范围以及每张页面和卡片的来源批次与捕获时间，不称为单时点原始全页截图。

关联截图成果直接复用帖子的当前有效舆情结论，不对截图执行 OCR、第二次模型分析或关键词重判。有效结果为 `negative` 时沿用现有边界恢复和框线样式，在完整原页副本上以红框覆盖整张帖子卡片；`non_negative` 和 `unrelated` 不框选。截图开启而 AI 分析关闭时不等待或伪造舆情结论，成果直接使用原始页面文件且不加红框；后续人工结论存在时仍按其当前有效结果生成新版本。没有任何负面框的页面直接复制原始 PNG，不重新编码。

批次开启 AI 时，只有当前关联结果中的全部证据化帖子都取得有效舆情结论后，截图才成为最终成果；分析失败、部分完成或暂停保持“等待判定”，使用者可以通过现有人工判定补齐。批次关闭 AI 时不等待模型，直接形成无红框原图成果，后续人工有效结论可以触发新版本。零条负面仍生成包含全部卡片的无红框成果；平台明确正常返回空列表时生成零结果成果；错误导致零条时只保存失败诊断，不生成最终成果。功能上线前的历史帖子不补拍；历史原批次之后的新补提可以形成新证据，但成果只覆盖证据化帖子并明确覆盖缺口。

提取状态、舆情状态和截图成果状态分别表达。截图异常不改写帖子提取状态，也不触发“重新提取失败项”；原始证据完整而本地标注或写文件失败时允许只重新生成成果，原始证据缺失时只能通过新的关联采集恢复。补提、删除贡献批次或有效舆情结论变化都会生成新的成果版本；前端只把最新版作为当前成果，历史版本保留生成时间、结果数、负面数和文件校验值。删除任一贡献批次后按剩余数据重建，最后一个贡献批次删除后才清理整个成果组。

正常尺寸成果使用一张无损长图；超过已验证的单图像素或内存边界时，按完整帖子卡片边界形成连续无损分片。分片只承载同一个逻辑成果，不切断卡片、不降低现有每圈采集上限，前端连续展示并以一个成果包下载。页面证据、卡片信息、成果分片和历史版本与贡献批次同寿命，进入持久数据备份，不按天自动过期或静默清理。

## 6. 功能模块

第一版界面以中文为主。导航、页面标题、按钮、表单标签、帮助说明、表头、分页、状态、空状态、加载提示、弹层、确认信息、校验错误和无障碍名称均使用自然中文，不沿用上游框架的英文示例文案。只有品牌名、文件格式、协议、接口和业内通用缩写等专业术语保留英文，例如 URL、ID、Session、API、SSE、WebSocket、Excel 和 XLSX；操作名称采用中文动词与必要术语组合，例如“导出 Excel（.xlsx）”和“更新 Session”。平台原有名称按其正式写法展示。

第一版采用中文直接实现，不设置语言切换入口。公共状态、分页、主题、空状态、确认和反馈文案集中维护，页面专属说明使用自然中文；日期、日历和时间格式使用 `zh-CN` 与 `Asia/Shanghai`。UI 验收必须扫描可见文字、占位文字、提示、无障碍名称、Toast 和弹层中的英文残留，只有确认过的专业术语和平台正式名称进入允许清单；帖子标题、正文、评论等平台原始内容不按 UI 文案处理。

界面主题初次访问跟随操作系统设置，顶部提供“浅色、深色、跟随系统”切换，用户选择保存在当前浏览器。导航、表格、表单、状态色、Sheet、Dialog、认证画面、加载状态和动态效果必须在浅色与深色主题下保持一致的信息层级、对比度和可用性。

第一版主视觉暂定为冷调科技方向：浅色使用冷白与淡蓝灰表面，深色使用深海军蓝与蓝黑表面，靛蓝作为主操作色，青色只承担动态指示、焦点和少量高光，成功、等待、失败和未知继续使用稳定语义状态色。轻量靛蓝到青色渐变仅用于品牌、当前导航、主操作或连接进度等有限位置，数据表格、表单和状态徽标保持清晰实色。该配色属于实施前视觉假设，允许在第一版真实 React 页面评审后整体调整，不改变页面结构和交互规则。

第一版不制作 Figma 设计稿，以真实 React 页面、组件状态和运行交互作为视觉验收对象。三个平台全部开发完成后再建立 Figma 设计稿；届时以实际前端代码、路由、组件、语义 Token、响应式断点、真实数据形态和可运行交互为来源，设计稿中的每个页面、状态和动作都必须能映射到现有前端能力或附带已通过技术评审的实现变更，不增加脱离前端组件、后端接口或运行约束的效果。

第一版不设置独立的主观视觉确认阶段，交付优先级依次为真实功能闭环、功能完整性、可用性和 UI 一致性。未来感通过统一主题 Token、公共组件和有限的命名变体实现：同一种组件、同一规格和同一用途必须使用相同的颜色、字体、间距、圆角、阴影、层级与动态；不同用途通过事先定义的变体表达，不在单个页面为某一个 Dialog、Sheet、按钮或表格临时创造一套样式。

页面反馈、加载、空状态、提示、确认和进度优先使用统一组件体系中的现有组件及其正式变体。只有现有组件无法表达真实业务语义时才增加新的应用级组合组件，新组件仍复用同一 Token、排版、图标、动态和无障碍规则，不在页面中直接拼装一次性的彩色提示块、弹窗或加载效果。

批次列表与批次详情的首次查询必须区分“正在加载”“加载失败”和“查询成功但结果为空”。加载期间不得把缺失响应显示为 0 条；请求在 20 秒内未返回时结束当前加载并提供中文错误与重试入口。运行中批次的帖子列表即使首次返回 0 条，也要跟随批次数据版本继续刷新；数据版本变化后立即查询新快照，避免把提取尚未入库误呈现为长期空列表。

第一版响应式定位保持桌面优先：1280px 及以上展示完整布局；批次详情筛选栏在内容宽度充足时以紧凑间距单行展示全部搜索、筛选、排序和导出控件，任一搜索框不得被压缩到不可辨认，也不得在超宽屏无限拉长，剩余空间用于分隔筛选组与右侧操作区；宽度不足时按四列、两列逐级换行。1024px 至 1279px 收敛次要信息，明确操作可切换为图标；768px 至 1023px 使用框架已有的动态导航 Sheet，筛选栏自动换行，数据表格保持列结构并允许横向滚动，关键标识列和操作列保持可达；低于 768px 保证基础查看与必要操作，但不另建手机卡片版。平台认证 Dialog 在各断点都使用接近全屏的操作区域。

### 6.1 配置管理

- 管理可复用自动提取规则以及引用规则的每周计划节点和循环计划节点；
- 查看平台接入状态，配置已接入平台的内部并发、启用状态和 Session；
- 以前端表格批量管理来源名称、圈子链接和列表顺序，整批原子保存并展示后端中文校验错误；
- 单条或批量验证未验证圈子；配置圈子首次验证成功自动参与，此后重新验证保持用户当前开关；
- 查看、删除或清空手动圈子历史；
- 查看全局平台 Session 状态和最近验证时间；
- 启动官方页面人工认证、更新 Session 或清除 Session；
- 管理多个命名 XLSX 模板及其不可变版本；
- 配置并启停 AI 舆情服务，维护云端同时分析任务数、目标品牌、重点产品和选填补充说明，并显式测试模型连接。

配置管理页使用八个横向标签组织上述能力：

1. “自动提取规则”承载规则名称、范围、平台数量、版本与归档；
2. “每周计划”承载星期、时刻、启停状态和已保存规则引用；
3. “循环计划”承载星期、开始时刻、结束时刻、间隔分钟、启停状态和已保存规则引用；
4. “平台配置”承载平台接入状态、平台内部并发、启用状态、Session 状态和认证入口；
5. “来源与圈子”承载用户来源名称、多个平台圈子来源的批量表格编辑、来源验证和自动提取开关；
6. “手动圈子历史”承载历史查看、选择、单条删除和清空；
7. “导出模板”承载模板上传、不可变版本、字段标签和删除；
8. “AI 舆情”承载分析启停、受控模型选择、云端同时分析任务数、模型测试状态、目标品牌、重点产品和选填补充说明；API Host 和 API Key 只在云端模型下显示，本地模型明确显示固定单路推理。

配置项遵循唯一编辑归属：一个字段只在上述一个标签中提供编辑器，其他标签需要上下文时只显示只读摘要和“前往配置”链接。平台配置不编辑定时数量或时间，来源与圈子不编辑规则参数或平台并发，自动提取规则不编辑星期和时间，两类计划不编辑规则范围、平台 Session、来源资料或验证状态，AI 舆情配置不进入来源、规则或单次提取界面。手动提取中的数量只属于本次提交，不回写任何自动提取规则。

“来源与圈子”按平台显示可折叠分组，组标题同时展示来源总数、已验证数量和未保存数量；首次进入默认展开第一个平台，并提供展开全部、收起全部以及组内新增来源入口。分组只改变长列表的浏览和编辑方式，不改变来源身份、跨平台批量保存事务、验证状态或自动参与规则；来源行仍可修改平台归属，修改后立即进入目标平台分组。

标签使用动态指示条和轻量内容过渡，切换时保持页面标题和主操作位置稳定。当前标签写入页面 URL 状态，刷新、前进和后退后仍回到相同标签；这些标签属于配置页内部区域，不增加新的顶层业务页面或第二层侧边导航。配置页的应用标题栏、页面说明、标签栏以及当前标签的标题和主操作保持在工作区顶部，只有当前标签的数据卡片、表格或表单内容纵向滚动。置顶区使用紧凑的标题、标签和卡片式工具栏间距，在保持分组边界与按钮换行空间的前提下降低纵向占用；当前标签工具栏依靠圆角、边框、轻阴影和必要摘要与页面背景建立层级，不使用横贯内容区的单色平条。

“自动提取规则”“每周计划”“循环计划”“平台配置”“来源与圈子”“AI 舆情”分别维护独立的未提交编辑状态，并由当前标签的显式“保存当前标签”按钮统一校验和提交；切换配置标签时保留各标签在本次页面会话中的编辑内容，保存当前标签不提交或清除其他标签的暂存内容。未保存状态按“标签汇总、工具栏计数、实体汇总、具体编辑项”分层呈现：规则索引项、两类计划节点标识、平台卡片、圈子行和 AI 配置卡片负责指明发生修改的实体；输入框、复选框、开关、星期按钮或规则多选器只有在自身规范化值偏离最近一次服务端基线时才显示琥珀色边框或实线外环，恢复原值后立即清除；新增实体使用紧邻序号或名称的新增圆点，删除项由区域计数汇总。六个受控配置标签都在保存按钮旁提供“放弃修改”，只把当前标签恢复到最近一次服务端基线，不提交或清除其他标签的暂存内容。页面通过 SSE 使 TanStack Query 取得服务器新版本：当前标签没有本地编辑时直接替换草稿与基线，不产生“未保存”标记；确有本地编辑时保留草稿并以 revision 冲突流程阻止静默覆盖。页面标题与标签之间不插入占高的全局提示条；“来源与圈子”存在草稿时直接禁用批量验证，并依靠标签圆点、工具栏计数、实体标识、保存按钮和字段外环表达原因，不再额外插入重复的保存提示卡。离开配置页面或刷新时，任一标签仍有未保存内容则提示确认；确认离开后放弃全部未保存配置。保存成功后以服务端返回的数据刷新当前标签、清除其未保存状态并显示短暂成功反馈。“手动圈子历史”和“导出模板”的上传、删除、清空等独立操作即时提交，不产生表单 dirty 标识，也不显示“放弃修改”，并按各自危险程度执行确认。

“自动提取规则”采用占满当前标签剩余工作区的主从编辑区：左侧为可按规则名称、ID 和圈子搜索的紧凑规则索引，只展示版本、圈子数、已保存计划引用数与未保存标识；右侧只渲染当前选中规则的名称、平台数量和圈子选择编辑器。桌面端由固定工具栏和弹性主从网格共同继承标签内容区高度，不以视口比例或固定像素强制撑高外层；只有规则索引或当前规则正文真实溢出时，左右面板各自滚动。切换规则只切换编辑上下文，不提交或丢弃其他规则草稿；规则数量增加时左侧索引独立滚动，不继续增加整个规则区高度。窄屏时规则索引和单规则编辑器顺序堆叠并按内容自然增长，不恢复多卡片并排。“每周计划”和“循环计划”使用一致的固定卡片式工具栏、节点卡片、星期与规则控件；循环卡片只把单一时刻替换为带可见标签的开始、结束和间隔分钟字段，不把计划节点继续附着在规则编辑器下方。

提取规则与两类计划节点继续使用同一个全局 `revision` 和 `/extraction-plan` 单事务校验，不改为逐规则即时写入，也不新增第二套业务保存端点。前端以服务器最近一次成功响应作为共同基线，分别维护规则、每周计划和循环计划草稿；保存当前标签时只提交该标签草稿并合并服务器已保存的其他部分，因此不提交或清除其他标签的未保存内容。计划多选器只显示已保存规则且至少保留一条选择，新建规则必须先保存后才能被计划引用。没有实际差异时保存按钮禁用，按钮显示当前标签待保存项总数。保存请求期间锁定当前标签的编辑控件；失败时保留草稿，并按后端明细切换到对应标签和定位规则或节点。遇到版本冲突时明确提供“保留当前草稿”和“放弃规则及计划草稿并加载服务器版本”两种选择，不静默覆盖任一侧。恢复归档规则属于即时服务器操作，存在任一规则或计划草稿时必须先保存或放弃，不能用恢复响应覆盖当前编辑。

“平台配置”中的 Session 区域保持为紧凑状态卡片，只展示平台、当前状态、最近保存时间和获取、更新、清除等入口，不承载服务器浏览器画面。平台注册项仍可区分 `account_login` 与 `access_session`：账号模式在服务器浏览器导出结构有效的 storage state 后显示“Session 已保存”，操作为“获取 Session / 更新 Session / 重新获取 Session”；保存操作不判断当前页面是否已登录。访问会话沿用“可用”语义并按状态显示“初始化/更新会话/重新初始化”。“Session 已保存”不等于圈子、帖子、评论或受保护字段访问已经验证，实际采集任务在原 URL 上执行采集访问门禁。配置卡片和提取列表中等待平台会话的“处理会话”操作调用同一个交互会话组件；两处入口共享连接、画面、输入和完成状态逻辑，但入口所在卡片或表格行保持各自页面布局。

“AI 舆情”允许先保存配置而不发起模型请求；只有用户点击测试才会执行一次最小文字推理。云端选项按各自生产输出协议测试 API 连接：千问验证 JSON Object，DeepSeek 验证 Beta Strict Tool Calling；本地选项直接在 ThreadSnap 进程内加载模型并推理。该页面只表达模型是否就绪，不提供全局业务启停；API Key 只允许写入或替换，保存后不返回明文。API Host、API Key 或模型变化使既有测试结果失效，并把要求 AI 的排队任务置为暂停，测试成功后恢复。受控下拉提供 `qwen3.5-omni-plus-2026-03-15`、`deepseek-v4-flash` 和 `paddlenlp-local-text-nano-v1`，不接受自由模型名或自由本地端点。千问和 DeepSeek 分别保存独立的加密 URL/Key，切换模型不会把一方连接覆盖给另一方。页面不展示单次 Token、预估费用或账户余额，也不配置费用查询凭证。

API Host 可以使用所选云端模型的官方地址，也可以使用实现该模型当前生产输出协议的公网 HTTPS 代理；千问代理须兼容其 JSON Object 请求，DeepSeek 代理须兼容 `/beta/chat/completions`、Strict Tool Schema、强制函数选择和流式工具参数。界面按模型明确提示千问或其代理会接收 API Key、帖子文字和媒体 URL，DeepSeek 或其代理只接收 API Key、判定对象和帖子文字。连接区域在本地模型下隐藏，切回任一云端模型时恢复该提供方原有加密密钥与地址。连接测试或本地模型测试失败时保留已保存配置但保持分析关闭；系统不把 DeepSeek 严格工具失败静默降级为弱 JSON 约束，本页不发起任何费用或余额查询。

### 6.2 手动提取

1. 用户选择一个已接入且启用的平台；
2. 从自动圈子、手动圈子历史中选择一个或多个圈子，或者输入一个或多个新圈子链接；也可导入已知帖子 URL 清单；
3. 圈子发现方式为本次所有选中圈子填写一个统一每圈提取数，后端按平台范围收敛；
4. 新圈子先完成验证并写入手动圈子历史，同一次提交中的重复圈子链接自动去重；
5. 系统持久化配置快照并创建 `queued` 批次；
6. 圈子发现方式分页取得候选 URL，URL 清单方式直接校验、标准化并批内去重；
7. 调用统一详情流程保存帖子、媒体 URL 和最多十条主评论；
8. 达到有效结果数、没有下一页或触发安全停止条件后汇总状态。

一次手动提取只能选择一个平台，但可以选择该平台多个圈子。尚未接入或已停用的平台不能创建手动批次，并返回后端中文错误。

手动提取的前端入口固定在“提取列表”页右上角，以“新建提取”作为该页唯一主操作。点击后从右侧打开全高动态 Sheet，背景保留当前提取列表和浏览上下文；Sheet 内在“圈子发现”和“URL 清单”两种输入方式之间切换，不新增独立业务页面。提交期间主按钮显示进行中状态并防止重复触发；提交成功后 Sheet 退出，新批次以有界高亮过渡插入列表顶部。字段或业务校验失败时 Sheet 保持打开，后端中文错误显示在对应区域并聚焦首个错误。

Sheet 内采用单页渐进式表单，不使用多步骤向导。顶部为输入方式切换和平台选择，中部只展开当前模式需要的圈子选择、新圈子输入、统一数量或 URL 清单，并就地展示异步验证、去重和解析结果；底部显示本次任务摘要以及固定的取消、提交操作栏。模式切换、字段展开和验证结果使用保持空间连续性的过渡。

同一次打开 Sheet 期间，“圈子发现”和“URL 清单”分别保留各自的未提交输入，来回切换不清空另一模式；点击提交时只校验并提交当前选中的模式。关闭 Sheet、返回或切换页面时直接放弃全部未提交输入，不显示放弃确认，也不在页面刷新后恢复草稿。

### 6.3 定时提取与循环计划

- 一个全局调度器加载全部启用的每周与循环计划节点；每个节点引用一条或多条自动提取规则，并在一次实际触发点最多创建一条合并计划批次；每周与循环节点同秒时分别创建“定时提取”和“循环计划”批次，两者不跨节点合并并复用同一批次处理能力；
- 到点解析节点引用的全部有效规则，读取符合各自规则范围、已接入、平台已启用且圈子已启用自动提取的来源，按圈子求并集并对重复圈子采用最大目标数，同时冻结全部规则版本、参数、来源映射和运行配置快照；
- 没有可执行圈子时不创建空批次，只记录中文调度事件；
- 同一“计划节点 + 计划触发时刻”通过稳定幂等键防止服务抖动产生重复批次；
- 调度器加载配置时再次检查同类型启用节点的星期与实际触发时刻重叠；发现同类型持久数据异常时不选择其中一条继续执行，而是逐节点跳过冲突触发并记录可定位的中文配置错误；跨类型同秒节点按“每周在前、循环在后”的稳定顺序分别创建批次；
- 节点触发前校验全部所选规则是否为各自已选平台保存数量；任一规则异常缺失时停止该节点整次触发并记录中文配置错误。规则已选但当前全局停用、未验证或所属平台停用的圈子不创建任务；合并后没有可执行圈子时不创建空批次，并记录中文调度事件；
- 定时、循环、手动和手动补提都进入同一持久化平台 FIFO；不允许手动任务插队；
- 服务重启后恢复已入队任务，停机错过的历史节点不补跑；
- 与手动提取复用同一采集和结果流程；
- 第一版不包含邮件、短信或企业微信通知。

### 6.4 提取列表、循环计划列表与批次详情

“提取列表”一行代表一次手动或每周定时批次；独立的“循环计划列表”一行代表一次循环计划批次。两个列表通过独立侧边栏入口和独立路由访问，复用同一列表组件；详情也使用对应独立路由进入同一详情组件，并按平台和圈子展示子任务。列表至少展示批次编号、提取类型、创建/排队/开始/完成时间、状态、排队位置、平台数、圈子数、计划数、完成数、失败数和后端中文错误或等待认证原因。

提取列表采用数据表格，不使用卡片网格或行复选框。默认列按信息关系合并为六组：“批次编号、提取范围、状态、进度、时间、操作”。批次编号单元格次行显示触发类型和输入方式；提取范围优先显示用户填写的来源名称，多个来源并列或以数量摘要，平台圈子名称只作辅助信息，并以独立短标签展示来源冻结的“最新回复”或“最新发布”，不依赖用户名称表达列表类型；筛选区提供服务端“列表类型”筛选，URL 清单批次不归入任一列表类型。状态单元格按需显示排队位置、等待平台会话或失败简因；进度单元格显示完成数、计划数、失败数和动态进度条；时间单元格以创建时间为主，并按状态补充开始时间、完成时间或运行时长；操作列只展示当前状态有效的查看、处理会话、重新提取失败项或删除操作。点击普通行区域进入批次详情，行内操作独立触发且不同时进入详情。

操作按钮优先使用中文文字配合图标；当图标含义明确、框架已有一致图标或操作列空间不足时，可以使用仅图标按钮，但悬停和键盘聚焦时必须显示中文 Tooltip，并提供中文无障碍名称。业务含义特殊的“处理会话”和“重新提取失败项”优先保留文字；删除等危险操作放入带文字的“更多”菜单并二次确认。次要操作较多时优先收敛到“更多”菜单，不把大量相近图标并排堆放。

列表工具栏提供批次编号搜索、状态筛选、触发类型筛选和创建时间范围，右侧提供“重置筛选”、手动刷新和“新建提取”主按钮。页面标题、主操作和筛选工具栏以紧凑间距固定在工作区顶部，筛选卡片不叠加无业务内容的外层纵向留白；批次列表固定表头和分页底栏，只有中间数据行区域纵向滚动。筛选作用于完整批次集合并在变化后回到第一页；筛选、页码和每页数量写入 URL，刷新、前进和后退时恢复。第一版只有一个实际接入平台，列表暂不增加平台筛选。

- 所有圈子成功时为 `success`；
- 部分圈子成功、部分失败时为 `partial_success`；
- 所有圈子失败时为 `failed`；
- 任一平台等待认证且批次未结束时为 `waiting_for_auth`，详情保留其他平台真实状态；
- `partial_success` 和 `failed` 提供手动“重新提取失败项”；
- 关联补提全部完成时允许显示衍生提示“重新提取完成”，但不篡改原批次状态；
- 终态支持二次确认后的永久删除；提交后确认 Dialog 保持打开并显示删除与关联内容整理状态，禁用重复提交和取消，后端完成数据库级联、关联文件清理及必要的截图成果重建后自动返回列表；普通排队和运行中不提供取消；等待认证可以结束本次提取以解除平台阻塞；
- 第一版不提供复杂统计图表或操作人字段。

提取列表以服务端事件通知驱动刷新：后端在批次、圈子任务、排队位置或 Session 状态提交变化后，通过 SSE 向前端发送只含资源类型、资源 ID 和版本的轻量变化信号；圈子任务采集期间按小批量持久化已完成快照并发送变化信号，认证续跑继续沿用原批次累计进度。前端收到信号后查询当前可见列表或对应详情，以 HTTP API 返回的数据作为权威状态。SSE 重连成功、页面重新获得焦点、网络恢复或完成新建、补提、结束认证等待、删除等操作后立即刷新；含排队、运行或等待认证批次的当前视图每三秒兜底回查，全部为终态时恢复每六十秒低频兜底，并保留手动刷新。状态、数量和排队位置变化使用短暂过渡，不使用持续闪烁的运行效果。

“重新提取失败项”打开确认 Dialog，显示原批次编号和本次失败项数量，并说明该操作会创建新的关联批次、只处理尚未成功的 URL、原批次状态与快照保持不变。确认后提交，成功时关闭 Dialog，并在列表中展示新关联批次。

平台交互会话操作使用接近全屏的动态 Dialog。顶部按平台注册模式显示“平台登录认证”或“访问会话初始化”，并展示关联任务、处理阶段、剩余时间和连接状态；中部展示服务器浏览器画面并转发鼠标与键盘输入，底部承载重新连接、关闭窗口以及任务场景下的“结束本次提取”。画面操作必须覆盖持续鼠标移动、悬停反馈、按下、释放、拖动、滚轮、键盘组合键和粘贴，并保持输入坐标与服务器浏览器视口一致；不得退化为只有点击后才更新的静态截图。会话通过后端门禁后 Dialog 自动退出，原批次恢复并以有界高亮展示状态变化。

中继连接状态与平台页面状态必须分开显示；WebSocket 已连接不等于平台页面可操作。只有官方页面形成非空、可交互 DOM 后才显示“页面可操作”并开放输入与“保存 Session”，HTTP 错误、零字节响应或空 DOM 必须在 Dialog 内显示稳定错误码和中文原因，不得继续展示空白画布。页面加载、Session结构检查和加密持久化属于不同阶段；保存操作不判断页面登录状态，也不访问圈子、首帖、评论、点赞或其他采集端点，失败提示必须按实际阶段和平台注册模式分类，合法空值Cookie不得被结构检查误判。从 `waiting_for_auth` 批次的“处理会话”入口打开 Dialog 时必须按检查点错误分流：`AUTH_REQUIRED` 使用不继承正式 Profile 的全新环境打开官方登录入口；`PLATFORM_CHALLENGE` 或 `PLATFORM_CAPTCHA_REQUIRED` 继承当前已登录 Profile 并直接打开原始触发 URL，避免把验证码恢复错误地变成重新登录。系统观察到验证页后，页面返回原站即自动保存更新后的 Session/Profile、关闭 Dialog、恢复同一等待任务，并由原 URL 的实际采集请求决定是否通过采集访问门禁；页面未发生可确认的验证跳转时仍保留“保存 Session”作为人工完成入口。平台配置中的主动处理仍默认复用既有 Profile 并打开平台注册登录入口。

### 6.5 链接结果

- 表格展示基础字段；
- 标题可点击跳转到原始帖子；
- 支持标题关键词搜索；
- 支持单条复制和批量复制链接；结果表格不提供复选框，单条复制只写入该帖的规范化原帖 URL，批量复制写入当前标题搜索、来源多选和可见状态筛选共同命中的全部结果，不受当前分页限制；
- 支持查看帖子正文和最多十条主评论；
- 支持按来源和可见状态筛选；来源筛选只列出当前批次及其关联补提实际包含的来源，选项同时显示来源名称、圈子名称和“最新回复/最新发布”列表顺序，允许多选，不选表示全部来源；
- 导出只读取数据库中已经持久化且不会再变化的终态结果，不重新访问平台。

批次详情页上方以紧凑布局展示返回入口、批次标题与操作、摘要和搜索筛选工具栏，下方展示链接结果表格。圈子任务不再占用置顶区独立行；“圈子任务 N”按钮紧邻刷新操作，点击后打开按平台分组的可滚动 Dialog。Dialog 顶部汇总任务总数、成功数、结果进度和异常数，各平台分组只展示一次平台名称与聚合进度；圈子行展示名称、原帖入口、状态、结果进度和必要结果说明，不重复平台列，也不把正常终止说明误标为错误详情。批量复制与导出模板选择共同位于筛选工具栏右侧，作为相邻的结果输出操作，不在列表底部另设孤立导出行。桌面布局中上述上下文保持在工作区顶部，链接结果区同时固定表头与分页底栏，只有中间数据行区域纵向滚动；横向滚动与数据行共用同一视口，避免表头和数据列错位。窄屏内容超过可用高度时回退为整页顺序滚动，但结果区仍使用内部滚动保留表头和分页操作。帖子标题作为平台原帖链接并在新标签打开；每行另设“查看”操作，从右侧打开约占页面宽度 50% 至 60% 的大型动态 Sheet，展示本批次数据库快照中的标题、作者、时间、可见状态、正文、图片与视频 URL、回复数、点赞数、最多十条主评论、原始状态和诊断信息。两种操作必须使用不同的可见文案和图标，避免把本地快照误解为平台实时页面。

配置页中具有列标题的数据列表复用同一滚动约束：表头固定，仅数据行区域滚动；桌面端“来源与圈子”列表视口占满工具栏和验证提示以下的全部剩余高度，不再使用独立视口比例制造外层页面滚动；没有分页的列表不额外制造空白底栏。基础表格组件不自行创建第二层横向滚动容器，每个页面的数据视口统一承载纵向和横向滚动，保证粘性表头始终与内容使用同一个滚动参照。

所有数据表格的第一列统一显示“序号”。提取列表和批次结果等请求分页列表按当前筛选与排序后的完整结果集连续编号，翻页后从上一页末尾继续；来源与圈子、手动圈子历史、导出模板字段等不分页配置列表按当前展示顺序从 1 编号。序号仅用于界面定位，不写入数据库、接口、URL 状态或导出字段。

帖子结果表默认列为“标题、来源、作者、发布时间、可见状态、评论数、点赞数、操作”。来源列显示来源名称并以标签标明“最新回复/最新发布”；标题列获得主要可用宽度，操作列固定在右侧并提供“查看”和“复制链接”；第一版的平台名称放在批次摘要中，不在每一行重复展示。完整 URL、正文、媒体 URL、评论内容、原始状态和诊断信息只在快照详情 Sheet 中展开。

帖子结果表复用统一分页控件并采用请求分页：默认每页 50 条，可切换 20、50 或 100 条；页码、每页数量、标题搜索、来源多选、可见状态筛选和排序变化共同触发后端查询，搜索、筛选或排序变化后回到第一页。后端返回当前页结果、完整筛选结果总数，以及不受当前来源选择影响的批次实际来源选项；关联补提中同一平台、来源 ID、版块和列表顺序一致的任务复用同一选项。界面显示当前范围及总数；翻页加载期间保留上一页布局并显示轻量加载状态。打开含视频的详情 Sheet 时自动获取当前临时 URL 并创建浏览器播放器，加载期间显示局部进度，失败时显示原因与重试入口，成功后保留刷新入口；播放器不自动播放。

帖子结果表默认使用稳定的来源顺序：URL 清单保持用户输入顺序；圈子发现保持平台列表发现顺序；多个圈子按本次提交时的圈子顺序排列；补提成功结果回到原失败 URL 的逻辑位置，而不是追加到结果末尾。用户可以切换按发布时间、评论数或点赞数排序，排序作用于完整筛选结果并在变化后回到第一页；值相同时仍以稳定来源顺序裁决。批量复制沿用当前有效排序。

帖子结果页把标题搜索、来源稳定标识多选、可见状态、排序字段与方向、页码、每页数量和当前查看的帖子 ID 写入 URL 查询状态。刷新、前进、后退和复制页面地址后重新打开时恢复相同上下文；同一路由内的搜索、筛选、排序和分页只更新查询参数与结果查询，不触发整页重新加载，也不重置当前滚动区位置。打开快照详情 Sheet 会增加帖子 ID，浏览器返回可关闭该 Sheet。URL 只保存筛选条件和资源标识，不包含帖子正文、评论、平台凭证或其他快照内容。

快照 Sheet 打开时保留背景表格的分页、筛选、搜索和滚动位置；关闭后保留关闭瞬间的背景滚动位置，不回到首次打开 Sheet 时的位置。遮罩区域的鼠标滚轮和触控板滚动不得驱动背景表格，Sheet 内容区域的滚动只作用于详情。Sheet 内提供上一条、下一条和关闭操作，顺序以当前筛选与排序结果为准；当前查看的帖子在背景结果表中以文字标签、浅色行面和左侧液态光晕共同标示。同页相邻切换时光晕按实际行位置上下过渡，目标行已经可见时背景不滚动，越出可视边界时只最小距离平滑滚动至可见；跨页加载后在目标行重新出现标示。关闭 Sheet 时，焦点交还给当前帖子行的“查看”按钮，当前行以“刚刚查看”标签、浅色行面和左侧光晕保留约 1.8 秒；标签出现和消失采用横向推入推出，并同步过渡所占宽度与标题左侧间距，使标题连续跟随移动而不是在标签卸载时跳位；启用系统“减少动态效果”偏好时立即切换。该短暂定位提示不写入 URL，也不形成永久选中态。切换记录时保留当前快照直至新快照返回，由被点击的箭头显示局部等待状态，两个按钮的尺寸、位置和背景状态保持稳定，正文、媒体和评论使用轻量内容过渡，不重新访问平台。

批量复制使用当前批次与关联补提汇总后的稳定结果顺序，优先按平台帖子 ID 去重，缺失时按规范化 URL 去重；每条链接占一行，不添加编号、标题、引号、额外空白或末尾空行。零条结果时批量复制禁用，成功后显示实际复制数量。浏览器剪贴板写入受限时，打开手动复制 Dialog，在只读文本区域中展示并自动选中相同内容，供用户使用系统复制快捷键；模板字段标签复制复用相同的剪贴板回退行为。该规则作为第一版暂定口径，后续只有出现真实的任意选择或其他输出格式需求时再扩展。

### 6.6 XLSX 模板与导出

系统允许保存多个命名模板；同名模板重新上传时创建不可变新版本，不覆盖旧版本。可用模板卡片显示当前最新版本，并提供原始 XLSX 下载入口，下载不创建导出记录也不改变模板状态；导出时选择模板，而不是在创建批次时绑定模板；同一批次可以使用不同模板重复导出。

模板字段标签必须是稳定英文标识：

```text
s.<source_key>.<field>
```

`source_key` 是来源创建时生成并持久化的 10 位导出键，在所有平台来源之间全局唯一，可以定位来源并区分同一个平台圈子的最新回复与最新发布。标签不包含平台代码或来源 UUID；例如来源名称为 `s.<source_key>.name`，帖子与圈子字段使用 `post.title`、`circle.id` 等清晰后缀。标签不使用中文来源名称、工作表名称或数据库物理字段名。前端提供可用标签、数据类型、说明和复制入口，并允许标签文本自然换行。上传时只解析该短标签格式；无效标签拒绝保存，并一次返回中文的工作表、单元格、字段和原因。

第一版正式数据会在交付前清理，不保留 `source.<22位来源键>.<field>`、`platform.<platform_code>.source.<source_id>.<field>`、`platform.<platform_code>.circle.<circle_id>.<field>` 或 `vehicle.name` 的模板兼容分支。所有平台共用下列字段后缀注册表；平台暂时缺少的字段按既有字段契约留空，不另建平台专属标签规则。前端按当前已保存来源生成模板标签，例如 `s.<source_key>.post.title`，每个标签单元格只能绑定一个注册字段。

| 字段后缀 | 类型 | 导出内容 |
|---|---|---|
| `source.id` | 文本 | 稳定的圈子来源配置 ID |
| `source.name` | 文本 | 来源当前用户名称；来源已删除时回退批次名称快照 |
| `source.list_order` | 文本 | `latest_reply` 或 `latest_publish` |
| `source.list_order_name` | 文本 | “最新回复”或“最新发布” |
| `circle.id` | 文本 | 平台圈子 ID |
| `circle.name` | 文本 | 批次快照中的平台圈子名称 |
| `circle.url` | 文本 | 批次快照中的圈子规范化链接 |
| `post.platform_post_id` | 文本 | 平台帖子 ID |
| `post.url` | 文本 | 帖子规范化链接 |
| `post.title` | 文本 | 帖子标题或已确认的正文首句回退值 |
| `post.author` | 文本 | 帖子作者 |
| `post.published_at` | Excel 日期时间 | 帖子发布时间 |
| `post.content` | 文本 | 帖子正文 |
| `post.image_urls` | 集合文本 | 编号后的图片 URL，中文分号和单元格内换行分隔 |
| `post.video_urls` | 集合文本 | 编号后的视频 URL，中文分号和单元格内换行分隔 |
| `post.reply_count` | 数值 | 提取时回复数 |
| `post.like_count` | 数值 | 提取时点赞数 |
| `post.section` | 文本 | 来源版块；第一版懂车帝为 `dynamic` |
| `post.visibility` | 文本 | `visible` / `hidden` / `unknown` |
| `post.raw_status` | 文本 | 平台原始状态值 |
| `comments.content` | 集合文本 | 编号后的主评论作者、时间和正文 |
| `comments.content_with_likes` | 集合文本 | 编号后的主评论作者、时间、正文和可用点赞数 |

数据库可以在不改变这些标签的前提下调整物理表名或列名。后续新增字段只能增加新的稳定后缀；已有后缀含义发生不兼容变化时必须新增标签版本，不能静默改义。

字段标签所在单元格就是第一条帖子数据位置，导出后标签不保留，最终文件为用户表头和数据；后续帖子按各圈子结果顺序向下写入。一个帖子占一行。同一工作表可以包含多个圈子的列，各圈子第 N 条结果横向写入第 N 个数据行，数量较少的圈子对应列留空，这种并排不表示帖子之间存在业务关联。工作表数量、名称、表头、列顺序和样式由用户模板决定，后端不按工作表名称推断圈子。

字段标签不得位于合并单元格。后续数据单元格复制标签单元格的字体、填充、边框、对齐和数字格式，只复制对应单元格样式，不复制整行或移动其他区域。所有导出字段的数据单元格统一启用自动换行；实际写入的列依据表头和本次内容估算列宽并限制最大宽度，实际写入的数据行清除模板固定行高，使表格软件按换行内容自动调整行高。预计写入范围内已有文字、公式或其他内容时停止导出并返回中文冲突错误；第一版不自动扩展公式，范围外的公式、图表、图片和说明保持不变。

一个帖子仍只占一行。图片和视频 URL 分别按平台顺序在各自单元格内编号，以中文分号和换行分隔。主评论默认集合字段包含作者、上海时区时间和评论正文；带点赞版本额外包含点赞数。格式示例：

```text
1. 作者：作者甲
   时间：2026-08-14 10:30:00
   评论：第一条评论；

2. 作者：作者乙
   时间：2026-08-14 10:35:00
   评论：第二条评论
```

点赞数为 0 时显示“0赞”，平台未返回点赞数时省略点赞行；作者或时间未返回时对应值留空。单值时间以 Excel 日期时间值写入，显示为 `yyyy-mm-dd hh:mm:ss` 并统一转换到 `Asia/Shanghai`；集合中的时间使用同格式文本，不以导出时间填补缺失发布时间。

相同结果版本和模板版本重复导出时复用已有文件；结果汇总变化或模板版本变化时生成新导出记录。导出记录保存批次或补提汇总版本、模板 ID、模板版本、生成时间、状态和文件哈希。`success`、`partial_success` 和有已持久化数据的 `failed` 允许导出；`queued`、`running` 和 `waiting_for_auth` 不允许导出。删除批次时删除其导出文件；删除模板仅从可选列表隐藏，被历史导出引用的版本继续保留。

### 6.7 舆情反馈与人工复核

- 帖子快照持久化后，在分析开启且当前配置已测试通过时自动创建独立舆情任务；提取页面继续以提取状态为准，舆情区域单独显示等待、分析中、完成、部分完成、失败、暂停和禁用；第一版上线不自动分析已有历史快照，也不提供批量历史回刷。
- 选择云端 Omni Plus 时分析文字、图片和视频；选择 PaddleNLP 本地 Nano 时后端只把标题和正文交给本地模型，不调用云端 API，不解析媒体播放地址，不产生 Token 用量。详情仍展示快照图片和视频供人工查看，但模型覆盖明确显示“未参与分析”。
- 批次关闭 AI 时，该批次新入库帖子进入 `analysis_disabled`，不因模型配置恢复而回刷；批次开关不取消其他批次已经发出的模型请求。`analysis_paused` 表示批次要求 AI 但模型服务未验证或运行配置失效，既有排队任务和失效期间继续入库的新任务都等待重新测试成功后恢复，与批次主动禁用严格区分。
- 帖子列表增加“舆情结果”列：有效结果显示“负面”“非负面”或“不相关”，并在同一单元格下用小标签标明“AI”“人工”或“继承人工”；分析状态不是独立列，非完成状态继续在该单元格内显示状态标签，没有有效结论时只展示真实分析状态，不把部分反馈当作有效结果。列表操作仍只保留查看和复制链接，不放人工修正按钮。
- 列表提供两个互不混用的服务端下拉筛选：“舆情结果”筛选负面、非负面和不相关，“分析状态”筛选等待、分析中、完成、部分完成、失败、暂停和禁用；筛选使用当前有效结论，并与现有搜索、排序和分页共同写入 URL 状态。
- 帖子详情继续使用现有 Sheet，新增舆情结论、结论来源、分析状态、中文总结、文字依据、逐图片依据、逐视频画面依据、逐视频音频依据、模型和反馈时间。正常界面不展示 SSE 分块、英文 JSON、单次 Token 或预估费用；中文内容按模型返回的段落分段显示，失败或部分完成展示可理解的中文原因及缺失模态。
- 详情同时展示已保存的图片和视频 URL：图片懒加载并可放大；视频取得当前临时播放地址后由浏览器以 `preload="auto"` 直接预缓冲并保持用户主动播放，ThreadSnap 后端不下载、不代理。媒体 URL 失效、防盗链或浏览器不支持时显示“媒体暂不可用”并提供原帖入口。
- 人工入口只位于帖子详情。没有任何有效舆情结论时显示“人工判定”，已有 AI、继承人工或人工结论时显示“人工修正”，Dialog 标题、备注和保存按钮同步使用相同语义。点击后通过全局 Portal 打开 Dialog，不局限在 Sheet 内容区；Sheet 保持打开，关闭 Dialog 后回到原详情位置和焦点。等待、分析中和暂停状态禁止人工操作；完成、部分完成、失败和禁用状态允许，人工结果始终优先。
- 人工修正允许负面、非负面和不相关。负面必选一个主要类型，次要类型可多选且不得与主要类型重复；非负面和不相关清空类型，备注选填。每次保存追加一条只读修订，最新有效人工修订生效；存在完整可用 AI 反馈时可以通过追加撤销事件恢复 AI 结果，不删除任何历史。
- 详情允许用户随机复核任意帖子，不设置强制复核比例、每批复核数量、召回率、误判率、最多漏判数或多人一致性流程；同一平台帖子在新批次出现且内容未实质变化时，界面显示继承人工结论及来源快照，内容变化后重新取得 AI 反馈并只把旧人工结果作为参考。
- 第一版不提供“重新分析”按钮。Worker 按既定有界重试处理暂时错误；失败和部分反馈保留证据并允许人工修正，暂停任务等待配置恢复。任何分析终态都不要求重新采集帖子，也不影响已完成提取批次的查看、复制、导出和删除。

### 6.8 页面截图成果

- 页面截图能力不新增顶级导航或额外批次列表；既有“提取列表”和“循环计划列表”都在进度或状态区域显示截图成果摘要。
- 批次详情在现有摘要下增加“链接结果”和“页面截图”同级标签。“页面截图”按关联圈子成果组一行展示实际来源、列表类型、证据化帖子数、已判定数、负面数、贡献批次数、当前版本和成果状态；同圈不同实际执行来源分别展示。
- 原批次和补提批次详情指向同一关联成果组。查看器默认打开当前负面标注成果，并允许切换底层原始分页证据、上一分片和下一分片；分片在视觉上连续排列，不把每个分片表现为独立成果。
- 成果查看器摘要显示贡献批次数、采集时间范围、当前版本、实际结果数、有效判定数和负面数；逐卡来源批次与捕获时间保留在成果清单和审计数据中，不写入图片像素。点击红框或卡片可以进入对应帖子详情，帖子详情提供返回所在成果的入口。
- 状态至少区分原始证据采集中、等待舆情判定、成果生成中、已完成、零结果和失败。提取成功但截图失败时同时展示两个真实状态，不把截图失败写成提取部分成功。
- 历史批次没有同期页面证据时显示“该批次创建时尚未启用页面证据采集”，不记为截图失败，也不提供历史补拍。
- 当前成果和原始证据分别提供下载；超长成果下载为一个包含有序无损分片、清单和校验值的成果包。正常页面不公开服务器文件系统路径。

### 6.9 垂媒口碑巡检扩展

- 当前已接入平台的业务排名明确为车型口碑页“同级车评分”卡中当前车型的一基位置，不使用页面顶部 `No.N` 全站榜。平台明确暂无评分时口碑分和同级排名均展示“暂无”，口碑量仍按页面可见评价人数独立保存；车型基础页没有评价人数时口碑量也展示“暂无”，不得以历史截图数字填充。口碑评价篇数取同一车型评分页“全部评分”的文章总数，与口碑评价人数分开保存和比较，不再访问车型圈子页。差评率复用同一平台车型ID作为APP接口 `series_id`，由接口返回的优点数和缺点数按 `缺点数 ÷（优点数 + 缺点数）` 取整数百分比，不使用低星评分占比替代。

- 垂媒口碑巡检与帖子链接提取是两个独立业务模块。每次计划触发或失败项补跑都创建独立、不可变的口碑巡检批次，不复用现有提取批次作为领域对象，也不把口碑排名数据添加为帖子批次详情的第三种结果。
- 前端在现有应用外壳中增加独立的“口碑巡检”一级入口。入口包含口碑巡检批次列表和批次详情；详情使用“排名数据”“页面证据”“汇报结果”三个同级视图，不增加第二套前端或第二个业务后端。
- “巡检批次”顶层列表一行只对应一个每日正式巡检批次根节点；其关联失败项补跑在该行展开区或批次详情中展示，不与每日正式批次作为同级行铺开。删除后的日期墓碑继续占一行并显示“已删除”。列表必须分别展示原批次真实状态和关联结果完整度，不得因补跑已补齐而把原批次状态改为成功。
- 列表默认限定当前 `Asia/Shanghai` 自然月并按计划巡检日期倒序，计划日期相同时使用稳定批次编号排序；延迟批次仍归属其计划日期，不按实际创建时间挪到其他日期。首版筛选只包含日期范围、批次类型（日检或月末）、原批次状态（运行中、成功、部分成功、失败、已删除）和批次编号搜索，不在顶层增加车型、单项指标或平台明细筛选。巡检批次固定每页20条并使用服务端 `offset/limit` 分页，页码写入URL；只有结果超过一页时才显示当前页与上/下一页操作，单页不显示纯总数底栏、分页导航或每页数量选择器。
- 每行至少组合展示计划日期与日检或月末标识、原批次真实状态、关联结果完整度、车型平台完成分母、页面证据完成度、汇报状态和延迟标识。车型与平台指标、单项错误、贡献补跑批次及每次真实采集时间进入批次详情；初始化或新映射基线作为批次或执行项标识展示，不扩张顶层批次类型筛选。
- 运行中口碑批次按车型平台执行项逐项提交权威进度：一个执行项成功、部分成功或在有界重试后失败时，后端必须在独立事务中同时持久化指标、证据、完成或失败计数，并在提交后通知前端回查；暂时错误在自动重试结束前不增加完成或失败数。列表和详情沿用现有进度条、三秒活动态回查与SSE刷新，允许逐步显示已经提交的排名行和证据数；批次在全部执行项终态前保持运行中，汇报继续只读取最终冻结结果。
- 批次类型只用“日常巡检”或“月末巡检”徽标表达；月末不拆成第二份列表或二级导航，也不使用整行底色。基线初始化和延迟执行使用独立附加徽标，成功、部分成功、失败继续使用状态色，避免类型、运行状态和指标涨跌共用颜色语义。月末类型徽标同时出现在列表行、批次详情标题和汇报结果标题，三处文案保持一致。
- 点击批次行主体默认进入“排名数据”；点击行内页面证据完成度直接进入“页面证据”，点击汇报状态直接进入“汇报结果”。三个详情视图使用URL参数 `view=ranking|evidence|report`，刷新、复制链接、浏览器前进后退和从详情返回时保持当前视图；未知参数回退到 `ranking`，不产生空白页。
- “排名数据”默认严格沿用该批次冻结范围版本中“车型与映射”的完整显示顺序，不因重点或竞品角色、当天涨跌、异常或补跑完成时间另行分组或重排；页面证据复用同一结果顺序。用户可以临时按平台指标、变化方向或执行状态排序，排序仅属于当前页面查询状态，不回写范围配置或历史批次。初始化、无前日基线、排名或数量口径变化、新映射基线、历史未采集、`not_available`、`unknown`、`auth_required` 和 `timeout` 必须在对应车型平台单元格直接显示，不只藏在证据或汇报视图。
- “排名数据”表格左侧固定并吸附角色、车系和车型三列，只为批次冻结的实际平台生成列组，不预留未接入平台。每个平台固定口碑分、排名、口碑量、口碑评价篇数、差评率、状态或证据六列；当前单平台显示一个六列组，未来三平台显示十八个平台列并使用横向滚动，表头和身份列保持可见。平台列组不可由用户拖散或跨组重排。
- 每个指标单元格紧凑展示当日平台原始值、“较昨日”差值或升降、红绿底色及无基线、历史未采集、`not_available`、`unknown`、`not_comparable` 等状态；前日值、差值、单位和比较状态不分别扩张为独立列，完整原文与来源通过悬停提示或点击项详情查看。每个平台的“状态/证据”列显示执行状态、实际采集时间和证据入口，并可直接深链到该车型平台项。XLSX使用同样的五个指标列和每车型一个备注单元格。
- “口碑巡检”模块内部使用“巡检批次”和“车型与映射”两个同级页面。“车型与映射”是车型身份、项目组归属、重点或竞品角色、当前平台页面映射、映射验证和历史范围版本的唯一编辑归属；现有“配置管理”继续负责帖子提取规则、计划、圈子、模板和共享平台运行配置。共享平台 Session 或连接能力仍由现有平台配置唯一编辑，口碑巡检只读显示连接状态并引用，不复制凭证或编辑入口；固定10:00巡检和终态立即汇报规则也只读展示。已经成为正常运行前提的真实采集器接入状态不占用常驻成功提示区，只有适配器尚未就绪等阻断状态才在车型与映射页显示异常提示。
- 范围草稿 `revision` 只用于保存、验证和发布请求的并发冲突控制，不作为业务变化数量展示，也不在车型表格上方常驻显示“当前范围草稿”或操作说明。重新验证可以递增该技术修订号，但不得因此暗示发生了车型新增、停用或删除；真实的新增、停用、角色和映射变化只在确有差异时进入发布影响预览并显示对应数量。
- “巡检批次”和“车型与映射”都使用上下分离的两张卡片：上方固定摘要/操作卡与下方独立表格卡之间保留12px页面间距，不把头部和表格塞进同一卡片形成无语义的内部空带。“车型与映射”不再用独立统计卡展示已发布版本号、范围分母或验证分母；其上方卡左侧展示模块名称、启用及停用数量和简短维护说明，右侧按“验证、新增车型、批量映射、发布变更”组织操作。“巡检批次”上方卡展示固定巡检时点、终态汇报规则和最近计划事件。两页下方表格正文独立滚动且表头吸附，上方卡和列头均不随长列表滚出视口；车型表格底部不重复展示验证分母或删除规则说明，相关状态由头卡、行操作及确认框就地表达。版本号、发布时间和技术revision继续由后端保留供审计与并发控制，但不作为日常维护页常驻信息；发布确认框只展示本次真实变更和未来范围。
- 页面提供显式“新增车型”、逐行“修改”和逐行移除入口。新增时由服务端生成从不复用的内部车型ID，并一次保存车系、车型、项目组归属、重点或竞品角色和当前平台稳定映射，初始状态为待验证；项目组归属不预填默认值，去除首尾空白后必须为1至80个字符，当前既有27款统一初始化为“奇瑞项目组”。逐行修改复用新增车型对话框并预填车系、车型、项目组、角色、平台车型ID、页面URL和平台展示名，内部车型ID保持不可变；列表单元格继续只读展示，不放置行内输入框。只修改身份展示、项目组或角色时保留当前映射验证，任一平台映射字段变化时该车型立即回到待验证；修改只进入当前范围草稿，发布后影响未来巡检，不改写历史版本或批次。从未进入任何范围版本或批次的新增草稿车型可以二次确认后永久删除。已经进入范围版本或批次的车型使用相同移除入口时必须明确提示“停用并保留历史”，只从未来发布范围排除并提供恢复入口，不删除身份、映射历史、既有版本或批次。
- 口碑巡检新增表格必须复用应用现有表格视觉合同：表头统一使用低对比度灰底，卡片边框、阴影、单元格内边距和行悬停反馈与提取批次等既有表格一致；表格首列左侧和末列右侧固定保留16px边距，与同一卡片工具栏、说明区的内容边线对齐，中间单元格继续使用8px水平内边距。可点击整行同时提供键盘焦点与回车进入能力。角色及组内顺序属于普通身份字段，使用低强调圆点、文字和等宽数字展示，不使用容易被误认为状态的实心徽标。口碑分、排名、口碑量、口碑评价篇数和差评率等数值列右对齐并使用等宽数字，独立图标操作列居中，文字操作列右对齐；冻结列必须延续表头底色和整行悬停底色，不形成白色断层。
- 应用外壳、状态展示、数据表格、页面证据查看器、服务端事件刷新和下载交互可以复用；车型指标、跨期比较、巡检证据和汇报使用独立接口与前端特性模块，现有帖子批次的“链接结果 / 页面截图”语义保持不变。
- 每个自然月最后一天只创建一个月末巡检批次，不再为同一天另建日常巡检批次。该批次只执行一次“全部启用车型 × 批次冻结平台范围”的数据采集，继续生成前一日比较，页面证据覆盖该范围的全部车型平台组合，批次终态后立即生成当日汇报；不得为日检和月检重复访问平台并形成两套当天指标。
- 当前版本不提供通用“立即巡检”或人工完整巡检。每日计划只创建一个正式完整巡检批次；配置阶段只提供平台映射验证，终态部分成功或失败后只提供“重新巡检失败项”。映射验证和关联补跑都不成为新的当日正式完整批次，不单独触发正式汇报，也不改变已经冻结的前日基线。
- 首次真实联调允许由后端运维命令把同一已发布范围下已经完成且证据校验通过的映射验证成功项冻结为一次来源明确标记为“真实验收”的基线初始化批次。该操作只复用既有真实指标和口碑指标区域截图，不再次访问平台；缺少任一车型成功项、映射内容哈希不匹配或证据文件校验失败时整批不创建。真实验收批次进入巡检列表并生成TXT、XLSX和证据下载，不冒充10:00计划批次且不消费正式日期幂等键；但它承载的真实初始化结果就是后续前日比较基线，若其日期恰为下一次正式巡检的前一自然日，调度批次必须冻结该批次的最终有效结果并直接执行日常比较，不能仅因来源类型不同再次初始化。
- 为开发和验收提供的“手动运行测试”是严格隔离的测试能力，不是上述生产立即巡检入口。只有后端处于显式测试运行模式并使用隔离测试数据库时，前端才显示该按钮；点击后先选择确定性场景，再创建带“合成测试”标识的测试运行。测试运行使用虚拟当前值、虚拟前日基线和测试PNG证据，不访问真实平台、不读取共享Session、不消费正式巡检日期与类型幂等键、不进入前日基线、不触发正式终态汇报，也不出现在生产环境。首版固定提供“基线初始化”“日常混合变化”“月末混合变化”三个场景，覆盖口碑分、口碑量、口碑评价篇数和差评率升降、排名数值降低为改善和升高为下降、方向冲突、全无变化、单项数量变化、无前日基线、`not_available`、`unknown`、`auth_required`、部分成功，以及三个场景均为27项全量证据。
- 合成运行必须复用正式的比较、证据聚合、结构化汇报快照、页面渲染、TXT和XLSX生成代码，不能通过直接写最终颜色或最终汇报文本伪造通过。验收颜色只存在于网页排名数据和XLSX单元格：口碑分、口碑量或口碑评价篇数增加为绿色、减少为红色，排名数字和差评率减少为绿色、增加为红色，无变化和不可比较不着红绿；方向冲突的正文表达为“表现分化”。TXT和页面复制正文是纯文本，不含颜色，只校验实际变化、平台分组、异常与缺失及场景标识。测试运行可以重复和删除，但只能影响隔离测试数据。
- 当前版本固定使用 `Asia/Shanghai`：每日10:00创建每日正式巡检批次，批次达到成功、部分成功或失败终态后立即生成对应汇报；月末最后一天仍在10:00创建月末巡检批次并替代当日日常巡检。前端只读展示巡检时间、终态汇报规则和北京时间，不提供用户编辑入口，也不把口碑巡检日程放入帖子提取的每周计划节点；后端只复用通用调度基础设施。
- 服务不可用导致当日10:00口碑巡检未触发时，服务在同一 `Asia/Shanghai` 自然日恢复且当日尚无每日正式巡检批次，立即补建唯一“延迟巡检批次”；巡检终态后立即生成汇报，并显示计划巡检时间、实际创建时间、实际汇报时间和延迟巡检标识。月末当天的同日补触发仍创建月末巡检批次，不另建普通日检。调度以“巡检日期 + 当日计划批次类型”的稳定键幂等去重，重启或重复恢复检查只返回既有批次。服务跨过自然日后不再补采错过日期的历史页面，只记录可定位的漏触发事件；下一个正式批次因严格前日数据缺失而按“无前日基线”处理。该规则只处理调度服务不可用造成的漏触发，不把范围未发布、映射门禁失败等已执行的配置错误重新解释为停机补触发。
- 每日正式巡检冻结计划时刻10:00当时生效的已发布范围版本，而不是任务实际开始或服务恢复时的当前版本。同日延迟批次必须通过版本发布历史还原并冻结10:00生效版本；10:00之后、恢复之前发布的新版本只影响下一次正式巡检。10:00当时没有已发布范围版本时，即使当天稍后发布并恢复服务，也只记录当日配置错误而不补建批次。计划时刻、实际创建时刻和冻结范围版本继续由后端持久化并通过API保留审计能力，但不在日常详情首屏增加独立信息卡；页面以结果、证据和汇报为主。
- 每个车型、平台和指标的前日比较基线严格取前一个自然日的最终有效巡检结果。前一自然日缺少对应有效值时标记“无前日基线”，不跨日改用更早成功值；该项不计算变化、不标红绿，也不以数值变化触发页面证据，缺失本身作为独立异常进入页面和汇报。
- 旧数量指标及其派生TXT、XLSX已清除，不映射为口碑评价篇数。历史结果在该列显示“历史未采集”；首个包含口碑评价篇数的新批次显示“暂无基线”，不按当前文章总数反推或回填历史值，从下一自然日开始与前日冻结值正常比较。
- 差评率上线前形成的历史结果保持不可变，详情该列显示“历史未采集”；首个包含差评率的新批次保存整数百分比、优点数、缺点数和接口来源URL，对该指标显示“暂无基线”，不按当前接口结果反推或回填历史值。从下一自然日开始与前日已冻结差评率正常比较。
- 系统首次没有任何可用前日基线时，每日正式巡检批次标记为“基线初始化批次”：采集全部启用车型在批次平台范围内的指标，不计算差值、不标红绿，汇报明确显示“首次基线初始化，无前日变化可比较”，并对全部车型平台组合保存口碑指标区域截图。当前单平台阶段分母为27；第二天开始正常比较，但证据范围继续保持冻结范围全量。首次运行若恰逢月末，仍只创建一个月末巡检批次，同一份全量证据同时承担基线初始化和月末证据，不重复访问或截图。
- 首个范围版本发布后不创建人工正式首跑，只由下一个北京时间10:00计划事件创建首批正式批次。若前一自然日没有真实验收或正式巡检形成的可用基线，该批次才标记为“基线初始化”；若前一自然日已有真实初始化基线，则该批次直接按日常巡检比较，但两者都要求逻辑页面证据 `27 / 27`。正式首跑验收要求当天只有一个正式根批次并冻结当前单平台27项，原批次27项均取得可靠成功终态（平台明确 `not_available`允许成功），正常完成时间不超过15分钟，并在终态后立即生成正文、UTF-8 TXT和固定版式XLSX；真实前端必须核对基线来源、排名数据、全量页面证据、汇报结果和下载入口。原批次部分失败时只补跑失败项，不人为重复整批27项，且该原批次不算正式首跑验收通过；下一个自然计划批次用于重新关闭正式运行门，不新增人工完整巡检入口。合成验收运行只用于提前验证处理逻辑，不能替代这次真实计划运行。
- 范围版本变化不自动把整个批次重新标记为初始化。某车型首次进入一个平台，或其平台稳定车型ID相对前日发生变化时，仅该“车型 × 平台”项形成“新映射基线”：首日保存指标但不计算差值、不标红绿，并不论重点或竞品都保存口碑指标区域截图；同批次其他稳定身份连续的项继续正常前日比较。仅页面URL、平台展示名称或重点/竞品角色变化且平台稳定车型ID不变时延续原指标序列，当日冻结的新角色决定当日是否属于重点车型变化证据范围。
- 平台没有稳定车型ID时，适配器必须使用验证通过的规范页面身份判断连续性；身份连续性无法证明时按新序列处理，不通过名称相似推断。旧映射版本及旧序列继续保留在历史批次中，不追溯连接到新序列。汇报把局部首日项列入“新映射基线”，不描述为指标无变化，也不把它计入改善、下降或表现分化。
- 口碑巡检批次创建时冻结前一自然日当时可用的关联结果版本、基线指标和冻结时间。创建前完成的失败项补跑可以进入该基线；创建后完成的晚到补跑只更新前一日的关联结果，不追溯修改已经创建批次的差值、颜色、页面证据触发或汇报输入。基线日期、冻结时间和来源批次保留在API与派生产物输入中供审计，不在日常详情首屏重复展示，也不提供事后自动重算。
- 口碑分、排名、口碑量、口碑评价篇数和差评率逐指标独立比较与着色，不给车型整行或平台结果强制合成总体提升或下降。口碑分、口碑量和口碑评价篇数数值上升为浅绿、下降为浅红；排名名次数值和差评率变小为浅绿、变大为浅红；不变不着色。多个指标方向冲突时各单元格保留自身方向，汇报表述为“表现分化”并分别列出改善项和下降项，不引入加权或指标优先级。
- 口碑分、排名、口碑量、口碑评价篇数和差评率同时保存各自来源的原始文字及其十进制规范值，变化严格按当日可见精度计算并使用Decimal语义，不使用二进制浮点或接口未展示的更高精度。`4.5`与`4.50`等格式差异、以及单位换算后规范值相同的数量不算变化；显示值未变化时，即使底层计数变化也不着色、不进入汇报。口碑分、排名和口碑量仍按全量证据规则保存同期指标区域截图；口碑评价篇数保存同一评分页来源URL和服务端状态原值；差评率另存APP接口来源URL和优缺点原始计数。
- 口碑量规范单位统一为“条”，支持数字分组符以及页面明确显示的“万”“亿”等单位并以Decimal换算，例如 `12,345` 为 `12345`、`1.23万` 为 `12300`、`1.2亿` 为 `120000000`；换算不意味着平台提供了更细精度，原始文字、原始单位和显示小数位必须继续保存。数量语义区分确定值 `exact`、按万或亿展示的可见舍入值 `rounded`、带“+”“以上”等含义的下限值 `lower_bound`，平台暂无和采集异常继续使用 `not_available` 与 `unknown`。
- 口碑量只在前后数量语义相同且都有规范值时比较：`exact` 对 `exact`、`rounded` 对 `rounded`、`lower_bound` 对 `lower_bound`；变化仍按平台可见规范值判断。语义变化，例如精确数字变为 `1.2万+`，比较状态记为 `not_comparable`，不计算差值、不标红绿，并在汇报“口碑量展示口径变化”中单列。格式或单位不同但语义兼容且规范值相同仍视为无变化；不得推算页面未显示的个位数。该比较规则不改变每个执行项都要保存同期截图的证据范围。
- 排名除数值外必须保存平台榜单名称、分类或稳定榜单ID/URL形成的排名范围身份。只有同一内部车型、同一平台且前后两日排名范围身份一致时才比较名次数值；范围变化时比较状态为 `not_comparable`，不标红绿、不描述排名上升或下降，并在汇报“排名口径变化”中单列。平台页面不显示范围文字时必须由稳定榜单身份证明，无法证明时排名范围为 `unknown`，不得只比较数字；上述状态均保留同期截图。
- 每个新建口碑巡检批次都对冻结范围内全部启用的“车型 × 平台”执行项取得页面证据，不再以车型角色、指标变化、无基线、普通日检或月末类型筛选截图对象。当前单平台27款车型的证据分母为 `27 × 1 = 27`；三个目标平台全部接入并纳入巡检后才为 `27 × 3 = 81`。
- 所有执行项直接使用受控浏览器打开冻结口碑URL，在同一页面上下文中完成身份核对、口碑分、排名、口碑量和口碑评价篇数读取、连续三次稳定DOM边界测量，并截取唯一不可变的口碑指标区域PNG；不再先做HTTP预取或访问车型圈子页。口碑评价篇数从该评分页服务端状态的 `reviewListData.total_count` 读取，并固定使用同一平台车型ID作为APP接口 `series_id` 取得优点数、缺点数和差评率。截图保留车型名称、口碑分、排名、口碑量及必要上下文；评价篇数由同页状态与来源URL证明，不伪装为截图可见文字。记录口碑URL、冻结车型映射、差评率接口URL及优缺点计数、采集时间、页面尺寸、截图矩形、截图尺寸和SHA-256，不生成第二张图片。
- 一个“车型 × 平台”组合只有一张指标区域截图和一个逻辑页面证据。前端查看、表格嵌入、单项下载和批次ZIP均使用同一PNG，不提供完整原页切换或下载入口。
- “页面证据”视图允许按单个车型平台项在站内大图Dialog查看指标区域PNG，并提供批次级独立ZIP证据包；排名表与证据卡片都复用同一Dialog，不打开新标签页。Dialog按图片内容自适应高度并只使用应用主题语义色：浅色主题下为白色标题区、浅蓝灰画布和白色信息侧栏，切换深色或系统主题时同步使用对应的`background`、`card`、`muted`、`border`和`foreground`色值；品牌色只用于图标、标题眉题和焦点状态。独立侧栏展示三项指标、车型角色、采集时间、文件格式和完整SHA-256，不以固定全屏高度制造无内容区域。证据包覆盖批次冻结的全部车型平台项，包内按平台代码和内部车型ID组织单一 `region.png`，附 `manifest.json` 与 `SHA256SUMS`，清单记录车型与平台身份、冻结映射与范围版本、来源URL、采集时间、页面尺寸、截图矩形、截图尺寸、SHA-256及缺失原因。缺失项只进入清单，不生成占位图片。
- 页面证据的统计单位始终是一个“车型 × 平台”逻辑项。普通日检、月末、首次基线和新映射基线均使用批次冻结的全部车型平台项作为分母，当前单平台通常为27、三个目标平台全部接入后通常为81；任何页面都不得把目标81写成当前固定值，也不得按角色或指标变化缩小新批次证据分母。
- 批次列表的证据摘要只显示“截图完成数 / 本批次要求留证总数”。“页面证据”详情显示可靠指标数与指标区域截图成功数，并按平台分组展示完成、处理中、失败和缺失。`not_available`在截图成功时计为证据完整；`unknown`只有实际取得截图时计入证据完整数，但不计入可靠指标完成数。
- 证据包只复制已持久化的不可变PNG字节，不在下载时访问平台、重新截图、重新裁切、标注或重压缩；同一批次证据版本与清单版本相同时复用同一不可变ZIP及其SHA-256。该ZIP属于页面证据交付，不与TXT汇报正文、XLSX数据证据或预览图自动混装。
- 批次终态时只冻结证据包清单版本和输入哈希，不自动压缩ZIP，也不让终态汇报、TXT或XLSX等待证据包。用户首次点击“下载证据包”后创建唯一按需生成任务，页面显示“证据包生成中”并在完成后提供下载；相同输入与生成器版本的并发或重复点击复用同一任务或已生成文件。部分成功批次同样允许生成，缺失项继续只写manifest。已生成ZIP随批次保留并进入整体删除；生成器升级后的人工重建按既定派生版本规则追加文件。当前不定时预生成或夜间批量打包。
- 指标可用状态与指标区域截图状态分别持久化。指标已经可靠取得但必需截图失败时，指标保持成功，证据单独标记失败，批次总体为部分成功；详情必须明确显示“指标成功 / 截图失败”，不得笼统改成数据采集失败。截图缺失时原批次不事后补拍，只能通过新的关联补跑批次形成新时点指标和证据，新证据不得冒充原采集时刻。
- 车型巡检范围不硬编码在前端或采集器中。第一版通过一次性命令导入一份人工复核的结构化初始化清单，建立附件所述14款重点车型和13款竞品车型；附件截图只作人工核对参考，不直接通过OCR建库。清单必须包含稳定初始化键、车系、车型展示名、角色、组内顺序，以及当前已接入平台的车型ID、页面URL和平台展示名；导入前全量校验27款、`14 + 13`角色分母、键值唯一和顺序完整，并记录源文件SHA-256与结果摘要。导入的平台映射初始仍为待验证，逐项通过真实页面门禁并发布首个范围版本后才进入正式巡检。初始化完成后的车型与映射维护只走本模块草稿和版本发布，不建设长期初始化上传页面；其他目标平台映射在对应平台正式接入后补充。全部启用车型参与每次指标采集和全量页面证据。
- 初始化清单交付为一行一车型的UTF-8 CSV，允许可选BOM并使用固定表头 `schema_version,seed_key,series_name,vehicle_name,role,role_order,platform_code,platform_vehicle_id,platform_url,platform_display_name`。`seed_key`是跨平台内部车型身份，必须使用平台中立且全局唯一的稳定值，不得编码平台代码或平台车型ID；`role`只接受 `focus | competitor`，`role_order`分别在两个角色组内从1连续编号；URL、逗号和中文按标准CSV引号规则解析。仓库只保存不含实际业务值的空模板、Schema和校验说明，实际填充文件由一次性命令按路径读取，不嵌入前端或程序代码；数据库只保存输入SHA-256、Schema版本和导入摘要，不保存原CSV副本。
- 车型、角色或平台映射变化时生成新的口碑巡检范围版本，未来批次使用最新版；已经创建的批次冻结创建时版本，后续修改或删除配置不改变历史指标、车型角色、平台映射和证据分母，也不删除历史批次。
- 车型与映射编辑形成独立草稿，映射可以分批验证；当前已经接入平台的全部启用车型映射通过门禁后才开放“发布新版本”，但验证通过本身不自动生效。用户确认变更摘要和未来巡检分母后原子发布为唯一当前版本，旧版本进入只读历史；每日10:00只读取触发瞬间的已发布版本，未发布草稿不影响批次。没有可用已发布版本时不创建空巡检批次，只记录可定位的中文配置错误；发布不修改已经创建、排队或运行的批次。
- “车型与映射”只对尚未成功提交到服务端草稿的本地改动启用离开保护。站内导航时提供“保存草稿并离开”“放弃改动并离开”“继续编辑”；保存或映射验证请求进行中时暂时阻止离开并显示当前动作，刷新或关闭标签页时使用浏览器原生未保存提示。服务端已经保存但尚未发布的草稿可以直接离开，返回后继续编辑，不因此自动发布或丢弃。点击“发布新版本”时若仍有本地改动或进行中请求，必须先完成草稿保存，再基于保存后revision重新取得发布影响预览，禁止发布未进入预览的浏览器内数据。
- “车型与映射”草稿使用单一完整车型序列展示，重点或竞品由行内角色标签表达，不把同类角色强制归并。顺序维护提供拖拽手柄以及键盘可操作的上移、下移，不提供排序数字输入；角色变化不自动移动该车型。存在搜索或筛选时禁用拖拽和顺序移动并解释原因，避免把局部结果顺序误写为完整配置；车型字段和映射仍可编辑。
- “车型与映射”提供按单个平台批量粘贴映射的辅助入口，不建设长期通用文件上传解析器。用户从表格粘贴“内部车型ID、平台车型ID、页面URL、平台展示名”四列，车型名称只作同屏核对，系统不得按名称自动绑定。预览必须列出新增、修改、重复内部车型ID、重复平台车型ID、未知车型、URL格式错误和未包含车型；本次粘贴范围全部有效才在一个事务中保存，未包含车型保持原草稿值不变。保存后的映射仍为未验证，用户可以选择“保存并验证”，按该平台批次冻结的内部并发验证本次实际变更项；每项独立记录成功或中文失败原因，失败不回滚已保存草稿，也不影响其他项完成。只有当前实际平台全部启用车型映射满足既定门禁后才可以预览并发布范围版本。
- 角色和组内顺序属于范围草稿，必须发布新版本后才影响未来批次；单纯角色或排序变化不使已验证平台映射失效，也不要求重新访问平台，但发布预览必须逐项显示。批次冻结发布版本中的角色与顺序，历史排名表、XLSX和汇报不随以后调整。已有历史批次引用的车型只允许停用并保留身份，从未进入批次且没有任何版本引用的草稿车型才允许永久删除；新车型不得复用旧内部车型ID。
- “发布新版本”确认框必须展示新增、停用、重点或竞品角色变化、平台映射变化数量，下一次正式巡检生效日期与时间，预计车型平台分母，以及将因首次接入或稳定身份变化形成“新映射基线”并全量留证的执行项数量。日常维护页不常驻展示版本号和发布时间；是否存在可发布变更由工具栏“发布变更”按钮状态和本次影响预览表达。存在新映射基线时在发布确认与后续批次中明确提示“首日建立基线，不计算涨跌”。
- 发布首个范围版本时复用同一确认框并切换为全量复核模式，不新增独立审批页面。确认框先展示总车型27、重点14、竞品13和当前平台已验证映射 `27 / 27`，再按车型与映射的完整显示顺序列出全部车型；每行显示内部车型ID、车系、车型名、平台车型ID、平台展示名、验证时间、验证状态，以及打开该次指标区域截图的入口。名称不一致、验证已不再绑定当前映射内容或其他复核警示必须醒目集中列出。首发要求没有本地未保存改动或进行中验证，27项全部通过当前映射内容的验证，并由用户主动勾选“已核对车型身份、角色、顺序和平台映射”后再次点击“发布首个范围版本”；确认框不得默认勾选，也不增加双人审批、电子签名或独立权限流。
- 范围发布事务在调度冻结范围之前提交成功才可以进入当天10:00正式批次；正式批次已经创建后发布只影响下一天。界面不提供“立即应用到运行中批次”“重算今天结果”或以新范围重建当天正式批次。延迟补触发继续按计划时点发布历史选择版本，不因当天稍后发布而改变。发布失败时当前指针和生效说明保持原版本，不展示部分生效。
- 每个业务统计车型使用不可变内部车型 ID，名称只用于展示和人工辅助匹配。每个平台映射独立保存平台车型 ID、页面 URL 和平台展示名称；平台改名或增加年款后缀只更新映射版本，不改变内部车型身份。同名但属于不同代际或不同业务统计对象时新建内部车型 ID，禁止按名称、空格或后缀规则自动认定为同一车型；配置界面可以提示候选，但必须由用户明确绑定。前日比较要求内部车型ID、平台和稳定平台车型身份连续；历史批次保留当时名称、映射快照和序列身份。
- 平台车型页面不存在、跳转到其他车型或稳定身份校验不一致时，当前执行项以“平台车型映射失效”失败并保留失效 URL 和同期诊断证据；该映射进入“映射待修复”，未来巡检不再持续访问已确认失效的旧 URL，而是直接把对应执行项标记为待修复，其他车型继续执行。
- 系统可以搜索并展示可能的新页面候选，但不得自动改绑。用户必须明确确认内部车型身份并通过真实页面验证，保存后生成新的口碑巡检范围版本且只影响未来批次；不得用名称相似、同名年款或跳转落地页静默替换历史映射。
- 平台车型映射验证必须在一次受控页面访问中同时通过三类门禁：车型身份门禁证明平台、稳定车型ID或页面身份、可见车型名称与用户确认对象一致，并排除登录页、错误页、搜索页和其他车型跳转；指标门禁取得口碑分、排名、口碑量的可解析数值或页面明确 `not_available` 状态，保存平台原始文字与适配器版本，选择器缺失不得冒充平台暂无；证据门禁等待字体和关键资源终态，在同一页面上下文连续三次取得稳定的车型身份、指标值和区域矩形，指标矩形位于页面内，直接截取的单张区域图可解码并包含车型身份与三个指标区域，文件记录SHA-256。连续三次稳定是同一页面访问内的测量，不重复访问平台三次。
- 映射验证不按7天、30天或其他经过天数自动过期，页面持续展示实际验证时间供人工判断。内部车型绑定、平台代码、平台车型ID、页面URL、平台展示名任一变化，或适配器明确提升映射验证合同版本时，对应验证立即失效并要求重新验证；重点或竞品角色、组内顺序和共享Session变化不使映射失效。人工重验遇到单次网络超时或认证失败时记录本次尝试失败，但不撤销仍绑定当前映射内容与合同版本的既有成功验证；真实页面不存在、跳转到其他车型或稳定身份不一致时按既定规则立即进入“映射待修复”。
- 批量映射验证完成后只为终态失败项提供“重试失败项”，成功项默认不重复访问，同时保留每行显式“重新验证”。暂时性网络错误或页面超时在每次用户操作内最多自动重试1次；`auth_required`不自动重试，用户更新共享Session后再重试；页面不存在、跳转到其他车型或稳定身份不一致的项进入“映射待修复”，必须修改并保存映射后才可验证；指标解析或证据门禁失败保留具体阶段原因，可以直接重试。人工点击次数不设额外产品上限，但每次操作始终有界，不循环请求。每次尝试都保留时间、映射内容哈希、各门禁结果和本次证据，单次成功必须在同一次受控页面访问中关闭全部门禁，不跨尝试拼接。映射验证及其重试不是口碑巡检批次，不触发正式终态汇报、不改变已发布范围或历史批次。
- 当前阶段只处理已经接入的一个平台；范围版本只要求该平台映射完整且验证通过即可启用，尚未接入平台的缺失映射不阻塞当前巡检。三个目标平台全部接入后，第一优先级是启用“每个启用车型必须具有三个平台稳定映射且全部验证通过”的范围版本门禁；门禁完成前不得宣称三平台巡检闭环或使用81作为验收分母。
- 一个口碑巡检执行项对应一个“车型 × 平台”组合。暂时性错误只执行有界自动重试；重试耗尽后该项记录失败并继续其他执行项，不用历史值冒充当天结果。全部执行项成功时批次为成功，存在部分成功或失败项且仍有可靠结果时为部分成功，没有任何执行项取得可靠结果时为失败；已经取得的成功指标保持不可变，不因其他执行项异常而丢弃。
- 当前单平台阶段每次车型页面访问使用90秒绝对上限，网络中断、暂时加载失败等可恢复错误最多自动重试1次；身份不一致、映射待修复、明确验证页等确定性或需人工处理状态不消耗自动重试。整个批次从实际开始执行时间计算45分钟绝对上限，延迟补触发不从计划10:00倒扣预算。达到批次上限后停止领取新执行项，终止或收敛仍在运行的访问，所有未完成项记录为 `timeout`，批次立即按已有可靠结果汇总为部分成功或失败并触发既定汇报流程。运行预算由后端固定并在前端只读展示，不增加用户配置。
- 口碑巡检执行项允许在平台容量门禁内受控并发，不要求逐车型串行完成。批次创建时冻结现有共享平台配置中的内部并发值，当前默认2、允许范围1至8；浏览器页面打开、稳定测量、截图和即时重试都服从同一冻结并发，不另建浏览器并发配置。所有巡检类型都因全量留证直接进入浏览器；口碑巡检与帖子提取合计不得超过该平台总容量，运行中修改平台配置只影响未来批次，不改变当前Worker数。当前单平台27项全量留证验收目标统一为实际开始后15分钟内终态并具备汇报输入；90秒单次和45分钟整批仍是异常保护边界，不是预期耗时。
- 每日正式口碑巡检批次，包括普通日检、月末和同日延迟补触发，在对应平台使用非抢占高优先级：已经开始的帖子请求继续完成，不中断或取消；之后释放的平台容量优先分配给正式口碑执行项，尚未开始的帖子执行项暂停领取，口碑批次终态后按原FIFO相对顺序继续。失败项补跑和映射验证保持普通优先级，不插队。未来多平台按各自队列独立应用该规则，不阻塞无关平台；页面必须区分“等待平台容量”和“正式口碑巡检优先执行中”，不能把排队时间表现为页面采集耗时。
- 共享平台Session失效时，受影响执行项快速标记为 `auth_required`，当前单平台批次据已有可靠结果汇总为部分成功或失败；未来多平台阶段只结束失效平台的未完成项，其他平台继续。口碑巡检不进入长期 `waiting_for_auth`，不提供普通排队或运行中批次的人工取消，也不在本模块复制认证入口。用户到现有共享平台配置完成认证后，通过“重新巡检失败项”创建关联补跑，原批次和失败时间保持不变。
- 终态为部分成功或失败的口碑巡检批次提供“重新巡检失败项”。该操作创建具有独立编号、时间、状态和证据的关联补跑批次，只处理原关联链中尚未成功的车型平台执行项；原批次状态、成功指标、失败记录和页面证据保持不变，已经补跑成功的执行项不再进入下一次补跑。
- 补跑的最小范围是完整“车型 × 平台”执行项，而不是单个缺失指标或单张证据。一次补跑访问必须重新取得该执行项当时的口碑分、排名、口碑量及本次要求的页面证据；不得把原批次的口碑分、第一次补跑的排名和第二次补跑的口碑量拼成一个不存在的页面时点。每次尝试保留独立编号、采集时间、指标和证据，页面可以逐次查看真实差异。
- 页面按车型平台执行项汇总原批次及全部补跑批次的当前关联结果，但每个车型平台只选择一个完整执行项版本：完整成功优先于部分成功，部分成功优先于失败；完整度相同时选择采集时间最新的一次。选中完整成功后该项不再进入下一次补跑；没有完整成功时，未可靠指标继续作为异常，不从其他尝试补齐。关联汇总不得物理合并数据库记录、覆盖贡献批次或把原批次状态改成成功，列表和详情必须区分原批次真实终态与关联汇总状态，并标明每个选中结果的贡献批次和采集时间。下一批次冻结前日基线时只读取冻结时刻选中的单个执行项版本。
- 平台页面明确显示“暂无评分”“暂无排名”或等价状态时，对应指标保存为 `not_available`；它是已确认的平台事实，允许执行项成功，但没有可比较数值，不计算变化或着色，汇报显示“平台暂无数据”。未开售或零评价车型即使没有独立的评分空态文案，也只有在页面车型身份通过、口碑分、排名、口碑量和评价篇数全部为空、同页服务端状态同时给出总评分0与评价人数0，并由差评率接口再次确认评价总数0时，才把五项统一保存为 `not_available` 并正常留证。任何一项已有值、零评价信号缺失或两处来源矛盾时仍按解析异常处理。页面加载不完整、DOM 变化或解析器未取得可靠字段时保存为 `unknown` 并记录中文原因；取得部分可靠指标时执行项为部分成功，三项均未可靠取得时执行项失败，汇报显示“数据采集异常”。两种状态都不得用历史值填充或统一显示为无差别斜杠。
- 所有巡检类型都尽力对 `not_available` 和 `unknown` 保留同期页面证据：前者证明平台当时明确暂无，后者用于定位页面或采集异常；截图失败则按既有证据缺失规则记录，不伪造占位图。
- 成功批次到达终态后立即生成正常汇报；部分成功批次仍使用真实成功数据立即生成汇报，但开头必须醒目标记“数据不完整”，并单列失败项、`unknown` 和无前日基线的车型平台组合。缺失项不参与改善、下降或表现分化统计，不使用历史值或推测值补齐。全部失败时不生成普通排名汇报，只形成包含中文原因摘要的巡检失败记录。
- 汇报绑定生成时的不可变巡检批次数据和冻结基线；后续失败项补跑成功不自动改写已经生成的汇报。汇报不设独立计划时刻，也不强行截断巡检；批次尚未终态时不生成，批次终态后立即生成并记录实际生成时间，不读取运行中数据生成半成品。巡检状态与汇报状态分别展示，巡检自身必须通过有界总时限和异常终态保障避免汇报永久等待。
- 日报按平台分组，只列口碑分、排名、口碑量、口碑评价篇数或差评率至少一项相对冻结前日基线发生变化的车型平台组合，并且只描述实际变化指标；变化条目均可附该项同期口碑页面证据入口。五项均无变化的车型不逐条列出，全部车型均无变化时明确输出“今日无口碑指标变化”；失败、`unknown`、历史未采集和无前日基线统一进入独立“异常与缺失”部分，不混入正常变化列表。
- 汇报按批次冻结平台顺序始终保留每个实际平台分组。该平台存在正常变化时列变化项并把异常与缺失另列；存在可比较结果但没有任何指标变化时显示“今日无口碑指标变化”；平台全部执行项都因无前日基线、`unknown`、`auth_required` 或失败而不可比较时显示“本平台今日无可比较结果”，并在异常与缺失中解释原因。只有所有平台都存在可比较结果、都无变化且没有异常与缺失时，汇报顶部才显示一次全局“今日无口碑指标变化”；不得把全量异常或混合异常概括成无变化。
- 月末汇报沿用日报的冻结前日基线和变化条目规则，额外标记“月末巡检”并展示本批次全量页面证据完成摘要及入口。当前版本不计算整月趋势、月均值、最大涨跌、波动次数或月初月末比较；后续只有取得明确业务公式和验收条件后才增加月度分析。
- 终态汇报只在系统内生成。“汇报结果”视图展示最终正文、实际生成时间、完整度和来源批次，并提供一键复制与文件下载；当前版本不自动发送企业微信、邮件、短信或其他外部渠道，也不增加接收人、发送凭证、送达、撤回、重发和外发审计状态。后续自动外发必须在渠道、接收对象、凭证归属、失败重试和重复发送规则明确后作为独立功能扩展。
- 汇报正文下载为UTF-8编码的 `.txt`，内容与页面“一键复制”完全一致，保留平台分组、实际变化指标、异常与缺失、普通或月末标识及延迟信息；不另行生成DOCX、PDF或HTML版本。数据与证据继续通过独立 `.xlsx` 下载，指标区域截图从“页面证据”入口查看，当前不把三者自动打成ZIP汇报包。TXT和XLSX文件名都包含巡检日期、普通或月末类型及批次编号，文件记录绑定来源批次或关联结果版本并保存SHA-256。
- 巡检状态、汇报正文、TXT、XLSX和页面证据ZIP分别持久化生成状态。临时写文件、表格渲染或压缩错误自动重试1次；仍失败时保留其他成功产物，在对应入口显示“生成失败”和中文原因，并提供“重新生成失败产物”。正文成功而全部文件失败时仍允许页面查看和复制，原巡检批次状态不降级，仅交付产物汇总显示部分成功或失败。
- 重新生成只读取批次已冻结指标、比较结果、证据和汇报快照，不访问平台、不重新选择前日基线，也不纳入晚到补跑。相同输入与相同生成器版本复用既有文件和SHA-256；生成器升级后重建历史产物创建新的派生版本并保留旧成功文件，不覆盖或删除旧版本。晚到补跑不自动触发成功正文、TXT、XLSX或证据包重建。
- 每种派生文件类型的第一个成功版本成为该历史批次的“首次成功发布版”，默认查看和下载始终指向它；此前全部尝试失败时，首次重建成功的版本自然成为发布版。生成器升级后形成的文件标记为“重建版”，版本列表显示生成时间、生成器版本、冻结输入版本、SHA-256和重建原因，用户可以显式选择下载，但当前不提供“设为默认”或替换发布版。相同输入、相同生成器版本的故障重试复用同一产物记录，不增加版本。页面正文、一键复制和终态当日汇报继续绑定原始汇报快照，不随文件版本切换。
- 口碑巡检XLSX使用系统固定版式，不复用帖子导出的用户上传模板和 `s.<source_key>.<field>` 标签，也不增加口碑模板管理页面。每行对应一个车型，左侧为日期、车系和车型，按批次冻结平台范围动态生成平台分组，每个平台包含口碑分、排名、口碑量、口碑评价篇数和差评率；当前单平台阶段只生成已接入平台列，后续平台正式接入并进入批次后再增加对应分组，不预放空平台列。
- XLSX按已确认变化方向填充浅绿或浅红，备注列对所有巡检类型嵌入批次平台范围内的同源指标区域证据。文件只读取批次冻结指标和已持久化证据生成，不重新访问平台；绑定批次与关联结果版本并保存文件哈希，相同输入重复下载复用同一不可变文件。可以复用现有文件记录、生成、下载和清理基础设施，但不得复用帖子模板字段合同。
- 每个车型行只使用备注列的一个单元格承载证据。当前单平台阶段把一张指标区域图锚定到该单元格；未来多个平台具有证据时，导出器按冻结平台顺序把1至3张指标区域图横向排成一张带平台名称的口碑证据预览图，只缩放、不再次裁切指标内容，再把这一张图锚定到备注单元格并统一控制列宽、行高。预览图保存引用证据ID和自身SHA-256，只是XLSX展示产物，不合并或替代独立平台证据，也不增加逻辑证据分母。
- 必需证据缺失时XLSX仍允许生成，但文件和汇报明确标记“数据或证据不完整”，备注列显示中文证据失败原因，不插入占位假图。
- 口碑巡检指标、指标区域截图、汇报和XLSX不自动过期。只有终态每日正式巡检批次允许二次确认后的人工删除；删除以该正式批次为根，整体删除其全部关联补跑批次以及关联链中的指标、证据、汇报、预览图和XLSX，不提供只删截图、只删汇报或只删某个补跑的局部操作。范围配置归档或删除不删除历史巡检。
- 人工删除进入可观察的删除作业。作业生成完整关联链与文件清单后标记“删除中”，期间禁止查看、下载、重复删除和修改该关联链；全部文件先移动到同文件系统隔离区，不立即永久清除。任一文件移动失败时按清单恢复已移动文件，数据库保持原状并显示“删除失败”；文件全部隔离后才在单个数据库事务中删除领域数据并写入墓碑，事务失败时从隔离区恢复文件。删除作业和恢复操作必须幂等，重试不得创建第二个墓碑或遗漏文件。
- 数据库删除事务提交是逻辑删除的不可逆边界。提交后再清理隔离区；清理失败只显示“存储清理待重试”并持续按清单重试，不恢复已经删除的业务数据，也不把逻辑删除标成失败。删除历史关联链不追溯重算后续批次已经冻结的前日基线、颜色、证据触发和汇报；后续批次保留最小来源墓碑，只包含原批次编号、日期、删除时间和原结果哈希，并显示“基线来源批次已删除”，墓碑不保留已删除指标、证据或文件，也不用于恢复数据。
- 删除墓碑继续持有原“巡检日期 + 计划批次类型”的正式日期身份和幂等键，列表在原日期显示“已删除”，不把它解释为从未执行。删除后即使仍在同一自然日，调度恢复检查也不得重新创建或补触发该日期正式批次；人工删除不是重新采集入口。下一日批次尚未创建时，被删除日期没有可用结果，下一日按“无前日基线”处理；下一日批次已经冻结该来源时保留其冻结指标和派生结果，只把来源显示为“基线来源批次已删除”。

本功能当前复用已经接入平台的连接与受控浏览器能力，不单设多轮口碑采集PoC或P95/P99性能定标阶段。实现验收至少执行一次真实27车型完整闭环，覆盖指标、比较、全量证据、汇报、XLSX及上述15分钟目标，并使用自动化故障测试覆盖并发门禁、认证快速失败、90秒单次上限、一次重试、45分钟批次收敛及 `timeout` 状态；以后只有真实运行持续接近预算时，才基于运行记录调整后端固定值。

## 7. 平台采集器功能契约

所有平台采集器都应具备相同的业务能力：

1. 验证配置和访问条件；
2. 根据圈子、版块和分页参数获取一页数据；
3. 判断是否存在下一页；
4. 将平台字段转换为统一字段；
5. 返回可诊断的错误类型；
6. 保留必要的原始状态；
7. 遵守统一的数量上限、超时、重试和停止规则。

公共业务只依赖统一结果，不直接读取平台私有字段。具体接口形式和代码契约留待技术路线文档确定。

## 8. 可见状态规则

- `visible`：已有样本和字段规则证明帖子正常展示；
- `hidden`：已有样本和字段规则证明帖子被隐藏、删除、审核或不可正常展示；
- `unknown`：字段缺失、新状态值或证据不足。

需求中出现的 `status`、`visible`、`audit_status`、`fold_type` 等名称只是候选线索，不是已确认字段。

懂车帝当前人工核对样本已经确认 `operation_status=2` 的帖子页面可正常展示，因此当前适配器将已验证的原始值 `0` 和 `2` 映射为 `visible`，同时保留原始值。该结论是样本验证规则，不等同于平台官方枚举说明；遇到其他新值仍标记为 `unknown`，直到重新取得证据。

第一版因正文和评论需求需要逐条访问详情接口或详情页。可见状态判断应优先复用该次详情访问结果，不为状态判断额外重复请求。

## 9. 页面范围

现有帖子提取范围包含四个基础页面：

1. 配置管理页；
2. 提取列表页；
3. 循环计划列表页；
4. 批次链接详情页（两个列表入口复用同一组件）。

页面截图成果属于批次链接详情页的同级结果视图，不新增第五个基础页面或第三份批次导航。

已确认的垂媒口碑巡检扩展在同一应用外壳中增加独立的“口碑巡检”一级入口及其批次列表、批次详情；它不改变上述三个帖子提取页面的职责，也不与提取批次共用详情导航。

配置管理页使用八个同级标签承载自动提取规则、每周计划、循环计划、平台配置、来源与圈子、手动圈子历史、XLSX 模板和 AI 舆情，不因此增加独立业务页面或第二层侧边导航；规则定义“提取什么”，两类计划定义“何时使用哪条已保存规则”，各自按唯一编辑归属分开。

第一版前端定位为现代、数据密集、桌面优先的内部运营控制台。四个基础页面共享同一个应用外壳和可收缩的左侧导航；导航展开、收缩、当前项切换以及由此产生的内容区变化必须有连续、可感知且不阻塞操作的过渡，避免以瞬间跳变代替状态反馈。

页面以信息清晰和操作可用为目标，采用克制卡片、清晰表格、稳定状态色和一致的间距、圆角、阴影及图标体系。动态效果必须服务于导航、加载、展开收起、状态变化、提交结果和错误恢复等真实因果关系；不采用持续漂浮、粒子背景、大面积视差或遮挡任务信息的装饰性动画。所有关键操作在动画过程中保持可用，并为系统减少动态效果偏好提供等价的弱化表现。

第一版不要求品牌级视觉设计或移动端专项适配，但常用桌面宽度下必须保持信息层级、表格可读性和完整操作路径；缩窄窗口时不得因导航和固定区域导致主要操作被遮挡。

## 10. 第一版验收条件

第一版至少满足：

1. 懂车帝已经完成真实样本、动态/最新回复圈子发现和 Windows 后端闭环验证；目标 CentOS 三轮门禁暂缓，仍是最终 Linux 部署验收项；
2. 可以配置可复用自动提取规则、引用规则的每周与循环计划节点、平台运行参数及多个圈子列表来源，未接入平台明确显示且不能创建任务；同一圈子的最新回复和最新发布可以分别保存为来源并使用相同规则参数，同一配置项不在多个标签重复编辑；
3. 圈子可以先保存为未验证，测试通过后才能启用自动提取；
4. 可以从自动圈子、手动圈子历史或新输入圈子手动提取，也可以导入已知帖子 URL 清单；
5. 手动提取一次选择一个平台、多个圈子和一个统一数量且不回写自动规则；每周或循环计划节点按所选规则创建一条覆盖其可执行来源的批次，循环计划批次与定时批次类型分开但页面能力一致；
6. 定时、循环计划、手动和补提任务持久化排队，不插队，重启后恢复；平台会话异常只阻塞对应平台；
7. 每圈数量按有效结果计，达到数量或平台明确没有更多内容时正常停止；
8. 提取列表和圈子详情显示中文类型、状态、数量和后端错误详情；
9. 可以逐条访问帖子并保存真实可获取的正文、媒体 URL 和每帖最多十条主评论；
10. 终态部分成功和失败可以手动补提，自动重试仍属于原批次，补提关联展示不改写原快照；
11. 终态可以二次确认永久删除，等待认证可以结束本次提取，普通排队和运行中不能取消；
12. 可以上传、校验和版本化多个标签驱动的 XLSX 模板，并在导出时选择模板；一个帖子一行；
13. 成功、部分成功和有数据的失败结果可以查看、搜索、复制并从数据库快照导出；
14. 所有可展示错误由后端返回稳定英文错误码和中文详情，前端不维护错误文案映射；
15. 不同批次互不覆盖，平台缺失字段和未知状态不会被伪造；
16. 已预留后续两个平台的统一适配器、平台队列和组合容量控制边界；
17. 在约定的部署环境、网络条件、合法访问条件和统一测试数据集下，一小时内有效完成 2000 个帖子 URL 的访问与结果处理；
18. 连续三轮吞吐测试均满足上述条件；任何限流、验证码、挑战页、登录失效或其他平台控制导致未能完成约定结果时，该轮验收失败。

“有效完成”必须满足：系统在测试时间窗口内实际访问该 URL，正确识别平台响应，并保存通过字段校验的帖子快照或有证据支持的平台终态。排队未执行、主动跳过、超时、验证码或验证页、无法确认的空数据、测试窗口结束后的补跑以及人工修补结果均不计入完成量。

每小时有效完成 2000 个 URL 是真实交付要求，不是仅供观察的性能目标。最终验收仍需同时报告自动成功率、正文完整率和主评论完整率，不能仅以请求发出数量证明达标。

需求中所称“必须绕过风控”按上述结果门禁理解：项目不单独验收某种对抗技术名称，只验证实际访问条件下是否按时产生 2000 个完整有效结果。通过结果只证明对应版本、样本、账号、网络和测试时间窗口内达到门槛；运行条件实质变化后需要重新验证。

吞吐测试输入由甲方从已知有效链接中提供。每轮输入 2000 个不同 URL，要求 2000 个全部有效完成，最终完成率为 100%，不允许存在最终 `failed`、`partial` 或未完成结果。

必需字段完整率要求为 100%：可访问帖子必须取得正文文字或至少一个平台实际返回的图片/视频 URL；纯媒体帖子允许正文为空。标题优先采用平台标题，平台无标题时取正文第一句话，标题和正文都没有时标题为空。一级评论以评论接口本次实际返回为准，达到十条时按平台顺序保存前十条，不足十条且接口明确 `has_more=false` 时保存实际返回结果并视为本次结束。详情回复数、评论接口总数与实际返回数量不一致时保留诊断字段，不据此虚构缺失评论；`has_more=true` 但游标缺失、评论接口失败或控制响应仍属于不完整。作者、发布时间、点赞数等平台本身未提供的可选字段允许为空，但系统不得因为解析失败而把已有字段静默保存为空；已证明匿名占位与登录真实值不同时，必须使用登录模式取得真实值，匿名占位不属于平台实际字段值。

字段完整率以测试时点能够取得帖子详情的结果为分母；详情已经不存在的输入单独计入“来源缺失”和“输入解析率”，不伪装成字段解析失败。正式每轮 2000 条验收仍要求事前固定 2000 条有效输入，运行时出现来源缺失仍会使该轮 2000/2000 有效完成门失败，不能通过事后缩小分母通过吞吐验收。

上述是第一版完工验收。根据 ADR 0011，圈子列表、主评论、数据库、队列、导出以及自建 React 前端已经完成 Windows 实现与真实页面联调；目标 CentOS 三轮 2000 条门禁暂缓，但仍是最终 Linux 部署验收的独立项，当前不记为已通过。

平台在正文中实际提供图片或视频地址时，应保存其 URL；媒体文件本身不进入下载和吞吐验收范围。

### 10.1 新增舆情反馈验收边界

舆情反馈增量完成时至少满足：

1. 每条新入库帖子快照独立触发舆情任务，不阻塞或改变提取批次状态；
2. 云端模型输入使用完整标题、正文、全部图片 URL 和全部视频 URL；本地模型输入只使用完整标题和正文，两者都不把评论混入判定；
3. 云端 AI 根据“目标品牌 + 重点产品 + 选填补充说明”结合语境判断相关性；本地模型以该对象执行 UIE 抽取并明确告知别名和隐含语境限制；
4. 云端模型对视频分别记录画面和音频覆盖，必要媒体未处理时只保存部分反馈；本地模型对所有媒体记录“未参与分析”并仍允许文字分析形成完整结论；
5. 保存模型原始返回、结构化字段、模型/提示词/判定对象版本、请求追踪、用量、耗时和失败原因；
6. 只有完整结构化 AI 反馈或人工结果成为负面、非负面或不相关的有效结论，且人工结果优先；
7. 同帖内容未实质变化时可以继承人工判定或精确复用完整 AI 结果，内容变化后重新分析，不回写历史批次；
8. 单一使用者可以在允许状态下从详情 Dialog 随机复核并追加修订，系统不强制每条复核，也不设置复核比例；
9. 模型配置保存不调用 API，显式连接测试成功后才能开启；关闭、暂停、禁用和运行中任务按已确认状态规则执行；
10. 图片与视频由浏览器按需直连保存 URL，ThreadSnap 不为详情展示下载或代理媒体；
11. 网络、限流、外部服务错误、媒体 URL 失败和结构错误均按已确认边界有界处理，最终状态可追溯且不影响提取数据。

正式实现前的真实样本 PoC 只回答外部服务是否能够访问媒体 URL、分别处理视频画面与音频、返回约定结构，以及实际耗时、用量、成本和失败分布。PoC 不设置 AI 准确率、召回率、误判率、漏判上限、人工一致率或类别正确率门槛，也不以单个标注者结果充当客观真值。

### 10.2 新增关联圈子截图成果验收边界

关联圈子截图成果增量完成时至少满足：

1. 所有截图开关开启的新圈子发现任务进入页面证据流程，实际来源链接与任务冻结的来源、版块和列表顺序一致；截图关闭、URL 清单和未执行来源不产生截图；
2. 每个物理分页在同一个渲染状态中冻结原始证据和有序页面清单，清单内帖子 ID、顺序、卡片范围与截图逐项一致，详情采集只处理该清单；
3. 每条进入当前关联成果的帖子都有实际入库快照、完整卡片证据、来源批次和捕获时间，历史无证据帖子、详情失败项和重复项不伪装为证据化帖子；
4. 原始证据门禁覆盖卡片文字、媒体、字体和稳定布局，未完成加载的必需卡片使证据失败，非帖子侧栏资源不扩大分母；
5. 原始证据只在当次上下文内有界重试，事后恢复创建新关联采集并保留新时间，不改写旧证据；
6. 原批次及其全部补提批次按同一实际执行来源合并为一个稳定成果组，去重和顺序与现有关联结果一致；删除任一贡献批次后当前成果只包含剩余数据；
7. AI 分析开启时，当前关联结果全部具有有效舆情结论后才形成最终成果；AI 分析关闭时直接形成无红框原图成果。负面框数严格等于当前有效负面帖子数，红框覆盖整张对应卡片且不产生第二套舆情结论；
8. 零负面生成无红框成果，平台明确空列表生成零结果成果，错误导致零条和原始证据缺失不生成最终成果；
9. 人工修正、恢复 AI、补提或删除导致结果变化时生成新版本，当前入口唯一指向最新版，历史版本、生成时间、数量和文件哈希可追溯；
10. 原始证据哈希在任何成果生成前后保持不变；每张成果页与其来源原图宽高一致，除负面红框覆盖像素外的页面像素一致，不裁切、缩放、重排或增加标题栏；跨批次成果明确展示来源与时间，不冒充单时点原图；
11. 一张原始物理分页对应一张成果页，多页由前端连续展示；Windows 和目标 Linux 分别验证最大原页的编码、解码和内存边界，成果包清单、页面顺序、数量和哈希完整；
12. 截图成果状态不改变提取和舆情状态，文件进入备份并随贡献批次和成果组按已确认规则删除，不存在独立自动过期或静默清理。

### 10.3 后续两个平台本地发布与正式验收边界

平台“已接入”表示对应适配器已经完成本地实现、公共业务闭环与自动化验证，可由用户显式启用；它不等同于正式环境大样本验收完成。汽车之家与易车均已满足本地发布条件，注册为 `available` 且默认保持停用。以下条件整体用于正式环境发布、规模运行和完整验收声明；其中第4项及已确认的平台真实样本也是本地发布的必要证据：

1. 项目已从每个真实存在的社区页面取得并验证最新回复、最新发布入口；两个列表顺序分别保存，易车真实缺失来源不进入配置或验收分母；
2. 项目已为该平台生成、规范化、去重、现时复核并在运行前冻结500个不同帖子详情URL，保存来源分布、生成规则、访问模式和清单SHA-256；
3. 项目已从真实发现池自行形成分层功能样本，按实际可观察情况覆盖正文、媒体、评论数量、状态、认证和平台控制，并明确记录未观察到的场景；
4. 新平台实现统一采集器契约和公共行为测试，复用既有平台FIFO、批次、Session、存储、API、前端及XLSX，不复制公共业务链；
5. 正式验收运行对事前冻结的500个输入形成 `500 / 500` 唯一有效终态，帖子身份、正文或媒体、最多十条一级评论、原始与标准化状态均满足统一合同；本项不回退已经关闭的汽车之家与易车本地发布状态；
6. 登录页、验证码、挑战、限流、异常空响应和真实错帖不计为有效结果；已证明的跨论坛聚合帖不是错帖。访问条件变化、适配器修复或样本失效后必须完整重跑，不通过人工补值、重复URL、跨平台补量或事后缩小分母通过；
7. 每个平台分别报告耗时、有效URL/秒、请求放大率、P50/P95、资源、访问模式、控制事件与恢复结果，但不把500条接入验收表述为2000条/小时或目标CentOS连续三轮性能验收；
8. 汽车之家和易车的27款口碑车型映射候选由项目依据稳定平台身份与页面证据生成，并继续经过现有草稿、真实验证和显式发布门禁；不按名称相似度自动绑定；
9. 两个平台的口碑评价篇数、差评率来源与语义暂缓确认。在完整五指标和同期证据合同通过前，即使帖子适配器或车型映射已完成，也不启用对应平台的正式口碑巡检，三平台全量证据分母仍不表述为81。

## 11. 第一版不包含

- 应用内登录和权限系统；
- 第二、第三个平台的实际采集器；
- 自定义 Cron；
- 独立代理池管理、验证码识别服务和反风控运营后台；
- 默认使用浏览器自动化；
- 数据趋势、敏感词和高频账号分析；
- 邮件、短信和企业微信通知；
- 长期追踪帖子变化；
- 历史数据回刷；
- 通用本地大模型端点、Agent 框架、多轮对话、RAG、联网搜索、工具调用或第二模型复核；
- 由 ThreadSnap 下载、中转、转码、抽帧或语音转写帖子媒体；
- 把主评论、楼中楼或作者历史作为舆情判定输入；
- 强制人工复核、多人一致性流程和 AI 准确率承诺；
- 自由输入未经验证的模型名，或在线编辑提示词、分类体系和结构化输出协议；
- 平台改版后的长期免费维护。
