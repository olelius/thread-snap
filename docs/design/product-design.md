# ThreadSnap 功能设计

## 1. 文档状态

- 状态：初版功能基线
- 目的：规定产品功能、业务边界、分阶段交付和验收口径
- 不包含：具体编程语言、前后端框架、数据库、调度组件和部署方案

具体技术路线将在 `technical-route.md` 中单独评审和确认。

## 2. 产品定位

ThreadSnap 用于按需或按固定周期提取论坛、车友圈等社区版块中的帖子链接，并按执行批次保存结果。

每次提取都是一份独立快照。系统不持续跟踪单个帖子的后续变化，不覆盖旧批次，也不把不同批次自动合并为一条长期记录。

## 3. 交付阶段

### 3.1 第一版：内部验证版

第一版只在受控内部环境中使用，以懂车帝为首个平台形成完整业务闭环：

- 配置目标圈子与版块；
- 手动发起提取；
- 按固定周期自动提取；
- 查看提取批次及状态；
- 逐条访问帖子链接并提取帖子正文及评论等相关内容；
- 查看、搜索、复制和导出链接及提取内容；
- 记录基础错误信息；
- 为后续平台预留统一采集器接口。

懂车帝的具体列表与详情接口、访问条件、分页规则、评论加载规则和状态字段仍须通过真实样本验证，不得因平台名称已经确定而假定接口可用。

### 3.2 后续正式版

在不重复建设公共功能的前提下，再接入两个平台。后续平台原则上只新增平台采集器、字段映射、配置选项及相应测试。

如果后续平台必须依赖验证码处理、复杂动态签名、代理池或浏览器自动化，应重新评估范围和成本，不能默认视为普通适配。

正式版面向公网使用，必须增加身份认证和角色权限控制。具体管理框架暂不指定；业务接口和领域逻辑不得绑定到某个前端管理框架，以便后续替换管理界面或权限实现。

正式版集成到客户现有前后端系统中作为一个功能点：

- 正式前端在现有系统中新增业务界面；
- 正式前端只调用现有后端；
- 现有后端负责用户、角色、权限和公网访问；
- 现有后端通过仅限本机访问的内部接口调用提取功能服务；
- 提取功能服务持续拥有提取配置、定时规则、提取批次和提取链接。

## 4. 用户与访问边界

- 第一版只面向单一内部使用者或受控网络环境，不部署到公网。
- 第一版不建设应用内登录、用户、角色和权限管理。
- 第一版提供基础测试界面，用于直接验证提取功能服务的完整业务接口，不作为正式系统界面。
- 正式版部署到公网前，必须完成身份认证、角色权限控制和必要的外围访问保护。

## 5. 核心业务对象

### 5.1 提取配置

一条配置对应一个平台、一个圈子和一个版块。

建议字段：

| 字段 | 说明 |
|---|---|
| 配置名称 | 便于识别的名称 |
| 平台 | 第一版只有一个可选平台 |
| 圈子 URL | 用户提供的目标地址 |
| 圈子标识 | 从 URL 解析或验证后保存 |
| 版块 | 最新发布或最新回复 |
| 访问模式 | 默认未登录；平台确需登录时使用甲方提供的合法会话 |
| 单次提取上限 | 默认 200 条 |
| 定时规则 | 第一版提供固定预设 |
| 启用状态 | 是否启用定时提取 |

第一版定时规则只提供简单预设，例如每小时、每天和停用；不提供用户自行填写 Cron 表达式。

系统以未登录访问为默认策略。只有真实样本证明未登录状态无法满足正文及主评论完整率时，才启用甲方提供的合法登录会话。不得为了方便而默认要求用户提供账号。

确需登录时，内部验证版允许通过配置页面录入并在本地数据库保存目标平台账号和密码。为控制第一版成本，密码暂时明文持久化，但查询接口不得返回密码，配置详情只显示是否已配置；修改密码时必须重新输入完整值。密码不得进入配置列表、日志、错误信息、导出文件或 Git。

内部验证版只保存一套全局懂车帝账号，所有提取配置共用，不提供多账号创建、切换、轮换或为不同配置绑定不同账号的功能。

明文密码仅适用于受控内部验证版。正式公网版本集成前必须完成凭证加密存储和权限控制，并迁移或清除内部验证版遗留的明文凭证；该升级属于正式版必做项，不是可选优化。

### 5.2 提取批次

每次手动或定时执行均创建一个独立批次。

建议字段：

| 字段 | 说明 |
|---|---|
| 批次 ID | 数据库内部 UUIDv7 唯一标识 |
| 批次编号 | `YYYYMMDD-HHmmss-NNN` 格式的用户可见编号 |
| 配置 ID | 来源配置 |
| 触发方式 | 手动或定时 |
| 开始时间 | 实际开始时间 |
| 结束时间 | 实际结束时间 |
| 状态 | running / success / failed |
| 提取数量 | 本批次实际保存数量 |
| 错误信息 | 失败时的简要原因 |

批次数据不设置自动过期时间，持续保留到用户明确执行人工删除。删除批次时，应同时删除该批次所属的帖子、主评论及相关临时导出文件，不影响其他批次。

批次编号使用 `Asia/Shanghai` 时区，时间精度为秒；同一秒创建多个批次时，通过三位递增序号 `NNN` 区分。

### 5.3 提取链接

建议字段：

| 字段 | 说明 |
|---|---|
| 批次 ID | 所属提取批次 |
| 帖子 URL | 必需 |
| 标题 | 平台提供时保存 |
| 作者 | 平台提供时保存 |
| 发布时间 | 平台提供时保存 |
| 正文 | 详情接口或详情页可合法获取时保存 |
| 图片 URL | 正文中平台实际提供的图片地址列表 |
| 视频 URL | 正文中平台实际提供的视频地址列表 |
| 回复数 | 提取时的平台数值 |
| 点赞数 | 提取时的平台数值 |
| 版块 | 来源版块 |
| 平台帖子 ID | 平台提供时保存 |
| 可见状态 | visible / hidden / unknown |
| 原始状态 | 平台返回的原始值 |

平台未返回的非必需字段允许为空。不得为了填满表格而推断或伪造数据。

第一版只保存正文中的图片和视频 URL，不下载、转存或代理图片和视频文件。

### 5.4 提取评论

第一版需要采集目标帖子下可合法访问的主评论。主评论指直接回复帖子正文的一级评论；每个帖子按平台返回顺序最多保存十条，不采集楼中楼回复。评论属于对应提取批次和帖子快照，不在后续批次中覆盖旧数据。

建议字段：

| 字段 | 说明 |
|---|---|
| 批次 ID | 所属提取批次 |
| 平台帖子 ID | 所属帖子 |
| 平台评论 ID | 平台提供时保存 |
| 评论作者 | 平台提供时保存 |
| 评论内容 | 平台提供时保存 |
| 评论时间 | 平台提供时保存 |
| 点赞数 | 提取时的平台数值 |
第一版不要求采集楼中楼、超出十条的后续评论或平台未正常返回的折叠评论。

## 6. 功能模块

### 6.1 配置管理

- 查看配置列表；
- 新增、编辑、删除配置；
- 启用或停用定时规则；
- 测试配置是否能获取至少一条数据；
- 对指定配置执行“立即提取”。

### 6.2 手动提取

1. 用户选择配置并点击立即提取；
2. 系统创建运行中批次；
3. 调用对应平台采集器；
4. 分页获取帖子链接并标准化列表数据；
5. 逐条访问帖子详情，提取正文及约定范围内的评论；
6. 达到数量上限、没有下一页、列表为空或触发安全停止条件时结束；
7. 保存链接、正文和评论并更新批次状态。

### 6.3 定时提取

- 启用的配置按预设规则自动触发；
- 与手动提取复用同一采集流程；
- 同一配置已经运行时，不重复并发执行；
- 失败时记录原因；
- 第一版不包含邮件、短信或企业微信通知。

### 6.4 批次管理

- 按时间倒序展示批次；
- 展示配置、触发方式、执行时间、数量和状态；
- 支持查看批次详情；
- 失败批次允许人工重新执行；
- 支持用户确认后人工删除批次及其所属结果；
- 第一版不提供复杂统计图表。

### 6.5 链接结果

- 表格展示基础字段；
- 标题可点击跳转到原始帖子；
- 支持标题关键词搜索；
- 支持单条复制和批量复制链接；
- 支持查看帖子正文和评论；
- 支持从数据库中已经持久化的当前批次快照生成 XLSX；
- XLSX 至少包含帖子表和评论表：帖子一行对应一个帖子，评论一行对应一条主评论，并通过批次 ID、帖子 ID 或 URL 关联；
- 图片和视频 URL 保存在帖子表中，不下载媒体文件；
- 导出过程不重新访问目标平台，不更新或覆盖原批次数据；
- 支持按可见状态筛选时，以平台状态验证结果为前提。

## 7. 平台采集器功能契约

所有平台采集器都应具备相同的业务能力：

1. 验证配置和访问条件；
2. 根据圈子、版块和分页参数获取一页数据；
3. 判断是否存在下一页；
4. 将平台字段转换为统一字段；
5. 返回可诊断的错误类型；
6. 保留必要的原始状态；
7. 遵守统一的数量上限、超时、重试和停止规则。

公共业务只依赖统一结果，不直接读取平台私有字段。具体接口形式和代码契约留待技术路线文档确定。

## 8. 可见状态规则

- `visible`：已有样本和字段规则证明帖子正常展示；
- `hidden`：已有样本和字段规则证明帖子被隐藏、删除、审核或不可正常展示；
- `unknown`：字段缺失、新状态值或证据不足。

需求中出现的 `status`、`visible`、`audit_status`、`fold_type` 等名称只是候选线索，不是已确认字段。

第一版因正文和评论需求需要逐条访问详情接口或详情页。可见状态判断应优先复用该次详情访问结果，不为状态判断额外重复请求。

## 9. 页面范围

第一版只包含三个基础页面：

1. 配置管理页；
2. 提取批次列表页；
3. 批次链接详情页。

页面以信息清晰和操作可用为目标，不包含品牌级视觉设计、移动端专项适配和复杂动效。

## 10. 第一版验收条件

第一版至少满足：

1. 一个指定平台已经完成真实样本可行性验证；
2. 可以创建有效配置并测试连接；
3. 可以手动提取并生成独立批次；
4. 可以按至少一种固定周期自动生成批次；
5. 达到上限或没有更多数据时能正常停止；
6. 成功批次可以查看、搜索、复制并导出链接；
7. 可以逐条访问帖子并保存真实可获取的正文，以及每帖最多十条主评论；
8. 失败批次展示可理解的错误信息；
9. 不同批次互不覆盖；
10. 平台缺失字段和未知状态不会被伪造；
11. 已预留后续两个平台的接入边界；
12. 在约定的部署环境、网络条件、合法访问条件和统一测试数据集下，一小时内有效完成 2000 个帖子 URL 的访问与结果处理。
13. 连续三轮吞吐测试均满足上述条件；任何限流、验证码、挑战页、登录失效或其他平台控制导致未能完成约定结果时，该轮验收失败。

“有效完成”必须满足：系统在测试时间窗口内实际访问该 URL，正确识别平台响应，并保存通过字段校验的帖子快照或有证据支持的平台终态。排队未执行、主动跳过、超时、验证码或验证页、无法确认的空数据、测试窗口结束后的补跑以及人工修补结果均不计入完成量。

每小时有效完成 2000 个 URL 是真实交付要求，不是仅供观察的性能目标。最终验收仍需同时报告自动成功率、正文完整率和主评论完整率，不能仅以请求发出数量证明达标。

需求中所称“必须绕过风控”按上述结果门禁理解：项目不单独验收某种对抗技术名称，只验证实际访问条件下是否按时产生 2000 个完整有效结果。通过结果只证明对应版本、样本、账号、网络和测试时间窗口内达到门槛；运行条件实质变化后需要重新验证。

吞吐测试输入由甲方从已知有效链接中提供。每轮输入 2000 个不同 URL，要求 2000 个全部有效完成，最终完成率为 100%，不允许存在最终 `failed`、`partial` 或未完成结果。

必需字段完整率要求为 100%：可见帖子必须取得正文；帖子存在一级评论时，评论不足十条则全部取得，评论达到或超过十条则按平台返回顺序取得前十条。作者、发布时间、点赞数等平台本身未提供的可选字段允许为空，但系统不得因为解析失败而把已有字段静默保存为空。

平台在正文中实际提供图片或视频地址时，应保存其 URL；媒体文件本身不进入下载和吞吐验收范围。

## 11. 第一版不包含

- 应用内登录和权限系统；
- 第二、第三个平台的实际采集器；
- 自定义 Cron；
- 独立代理池管理、验证码识别服务和反风控运营后台；
- 默认使用浏览器自动化；
- 数据趋势、敏感词和高频账号分析；
- 邮件、短信和企业微信通知；
- 长期追踪帖子变化；
- 历史数据回刷；
- 平台改版后的长期免费维护。

## 12. 商务范围参考

当前首个平台基础交付范围由以下工作构成：

- 数据库、配置和批次管理；
- 手动及固定周期任务；
- 三个基础前端页面；
- 第一个平台采集器；
- XLSX 导出和错误记录；
- 联调、测试和部署说明。

报价、付款节点和维护期限属于商务约定，不作为功能或技术事实写入本设计。
