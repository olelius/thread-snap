# ThreadSnap 功能设计

## 1. 文档状态

- 状态：初版功能基线
- 目的：规定产品功能、业务边界、分阶段交付和验收口径
- 不包含：具体编程语言、前后端框架、数据库、调度组件和部署方案

具体技术路线将在 `technical-route.md` 中单独评审和确认。

## 2. 产品定位

ThreadSnap 用于按需或按固定周期提取论坛、车友圈等社区版块中的帖子链接，并按执行批次保存结果。

每次提取都是一份独立快照。系统不持续跟踪单个帖子的后续变化，不覆盖旧批次，也不把不同批次自动合并为一条长期记录。

## 3. 交付阶段

### 3.1 第一版：内部验证版

第一版只在受控内部环境中使用，以懂车帝为首个平台形成完整业务闭环：

- 配置目标圈子与版块；
- 导入已知帖子 URL 清单并手动发起提取；
- 按提取配置手动发起圈子发现提取；
- 按固定周期自动提取；
- 查看提取批次及状态；
- 逐条访问帖子链接并提取帖子正文及评论等相关内容；
- 查看、搜索、复制和导出链接及提取内容；
- 记录基础错误信息；
- 为后续平台预留统一采集器接口。

懂车帝的具体列表与详情接口、访问条件、分页规则、评论加载规则和状态字段仍须通过真实样本验证，不得因平台名称已经确定而假定接口可用。

第一版同时保留两种输入方式：“圈子发现提取”负责从圈子列表分页发现帖子 URL；“URL 清单提取”负责直接处理用户导入的已知帖子 URL。两种方式必须复用同一平台详情采集、标准化、存储和批次流程。

### 3.2 后续正式版

在不重复建设公共功能的前提下，再接入两个平台。后续平台原则上只新增平台采集器、字段映射、配置选项及相应测试。

如果后续平台必须依赖验证码处理、复杂动态签名、代理池或浏览器自动化，应重新评估范围和成本，不能默认视为普通适配。

若后续明确选择公网部署，必须增加身份认证和角色权限控制。具体管理框架暂不指定；业务接口和领域逻辑不得绑定到某个前端管理框架，以便后续替换管理界面或权限实现。

正式版集成到客户现有前后端系统中作为一个功能点：

- 正式前端在现有系统中新增业务界面；
- 正式前端只调用现有后端；
- 现有后端负责用户、角色、权限和公网访问；
- 现有后端通过仅限本机访问的内部接口调用提取功能服务；
- 提取功能服务持续拥有提取配置、定时规则、提取批次和提取链接。

## 4. 用户与访问边界

- 第一版只面向单一内部使用者或受控网络环境，不部署到公网。
- 第一版不建设应用内登录、用户、角色和权限管理。
- 第一版提供基础测试界面，用于直接验证提取功能服务的完整业务接口，不作为正式系统界面。
- 正式版部署到公网前，必须完成身份认证、角色权限控制和必要的外围访问保护。

第一版的平台人工认证入口同样只在上述受控内网中使用：客户使用现有浏览器，在基础测试界面的页面或弹窗中直接操作服务器浏览器，不安装远程桌面客户端，不接触 SSH、CDP、VNC 地址或第二层远程桌面登录。入口使用短期、一次性随机票据绑定当前认证任务，并在完成、取消、断开或超时后失效；该票据只缩小内网误用窗口，不替代公网身份认证。

公网访问属于后续可选部署增强，不是第一版交付或验收前提。只有客户以后明确需要公网部署时，才把正式前端接入客户现有身份系统，由现有后端承担用户、角色、权限、敏感操作重新认证以及 HTTPS/WSS、WAF 或等价外围保护；不得因此提前扩展第一版功能。

## 5. 核心业务对象

### 5.1 提取配置

一条配置对应一个平台、一个圈子和一个版块。

建议字段：

| 字段 | 说明 |
|---|---|
| 配置名称 | 便于识别的名称 |
| 平台 | 第一版只有一个可选平台 |
| 圈子 URL | 用户提供的目标地址 |
| 圈子标识 | 从 URL 解析或验证后保存 |
| 版块 | 最新发布或最新回复 |
| 访问模式 | 默认未登录；平台确需登录时使用甲方提供的合法会话 |
| 单次提取上限 | 默认 200 条 |
| 定时规则 | 第一版提供固定预设 |
| 启用状态 | 是否启用定时提取 |

第一版定时规则只提供简单预设，例如每小时、每天和停用；不提供用户自行填写 Cron 表达式。

系统以未登录访问为默认策略。只有真实样本证明未登录状态无法满足正文及主评论完整率时，才启用甲方提供的合法登录会话。不得为了方便而默认要求用户提供账号。

确需登录时，第一版不提供平台账号或密码输入框，也不在数据库中保存平台账号密码。配置页面提供一套全局懂车帝 Session 的状态、“登录/更新会话”和“清除会话”操作；所有提取配置共用该 Session，不提供多账号创建、切换、轮换或为不同配置绑定不同账号的功能。

浏览器进程、Profile 和 Session 位于部署提取功能服务的服务器上。第一版客户在内网客户机的普通浏览器中，通过基础测试界面提供的临时嵌入式交互入口，查看并操作服务器浏览器中的目标平台官方登录页面，自行完成密码、扫码、短信、验证码或滑块等官方认证。该入口不是把普通官方链接交给客户机本地浏览器；客户机本地登录状态也不会作为服务器 Session。系统只加密保存继续访问所需的 Cookie、LocalStorage、浏览器 Profile 或等价 Session 状态；查询接口只返回会话状态和最近验证时间，不返回任何可复用认证数据或原始浏览器控制地址。

采集前先探测 Session。识别到登录或等价身份异常时，每个失败事件先有界自动刷新一次现有浏览器 Profile；官方页面仍保持登录且刷新后的门禁通过时，从触发 URL 继续。出现登录表单、扫码、短信、验证码、滑块或刷新后门禁仍失败时，系统停止发送新请求，持久化当前索引、触发 URL 和待处理队列，把本批次转为 `waiting_for_auth` 并释放采集 Worker。用户从客户机完成服务器浏览器认证后，系统自动更新加密 Session、执行少量门禁，并在门禁通过后自动续跑同一批次，不要求人工重试。认证窗口超时或客户机断开只关闭临时远程交互，批次仍保持等待；用户可重新打开认证入口或显式取消。不保存密码自动登录，也不无限循环刷新。

### 5.2 提取批次

每次手动或定时执行均创建一个独立批次。

建议字段：

| 字段 | 说明 |
|---|---|
| 批次 ID | 数据库内部 UUIDv7 唯一标识 |
| 批次编号 | `YYYYMMDD-HHmmss-NNN` 格式的用户可见编号 |
| 配置 ID | 来源配置；URL 清单提取时可为空 |
| 输入方式 | 圈子发现或 URL 清单 |
| 触发方式 | 手动或定时 |
| 开始时间 | 实际开始时间 |
| 结束时间 | 实际结束时间 |
| 状态 | running / waiting_for_auth / success / failed |
| 提取数量 | 本批次实际保存数量 |
| 错误信息 | 失败时的简要原因 |

批次数据不设置自动过期时间，持续保留到用户明确执行人工删除。删除批次时，应同时删除该批次所属的帖子、主评论及相关临时导出文件，不影响其他批次。

批次编号使用 `Asia/Shanghai` 时区，时间精度为秒；同一秒创建多个批次时，通过三位递增序号 `NNN` 区分。

### 5.3 提取链接

建议字段：

| 字段 | 说明 |
|---|---|
| 批次 ID | 所属提取批次 |
| 帖子 URL | 必需 |
| 标题 | 优先保存平台标题；平台无标题但有正文文字时保存正文第一句话；两者都没有时为空 |
| 作者 | 平台提供时保存 |
| 发布时间 | 平台提供时保存 |
| 正文 | 详情接口或详情页可合法获取时保存 |
| 图片 URL | 正文中平台实际提供的图片地址列表 |
| 视频 URL | 正文中平台实际提供的视频地址列表 |
| 回复数 | 提取时的平台数值 |
| 点赞数 | 提取时的平台数值 |
| 版块 | 来源版块 |
| 平台帖子 ID | 平台提供时保存 |
| 可见状态 | visible / hidden / unknown |
| 原始状态 | 平台返回的原始值 |

平台未返回的非必需字段允许为空。不得为了填满表格而推断或伪造数据。纯图片或纯视频帖子在媒体 URL 已正确提取时，正文和标题为空属于平台真实内容形态，不记为字段不完整。

第一版只保存正文中的图片和视频 URL，不下载、转存或代理图片和视频文件。

### 5.4 提取评论

第一版需要采集目标帖子下可合法访问的主评论。主评论指直接回复帖子正文的一级评论；每个帖子按平台返回顺序最多保存十条，不采集楼中楼回复。评论属于对应提取批次和帖子快照，不在后续批次中覆盖旧数据。

建议字段：

| 字段 | 说明 |
|---|---|
| 批次 ID | 所属提取批次 |
| 平台帖子 ID | 所属帖子 |
| 平台评论 ID | 平台提供时保存 |
| 评论作者 | 平台提供时保存 |
| 评论内容 | 平台提供时保存 |
| 评论时间 | 平台提供时保存 |
| 点赞数 | 提取时的平台数值 |
第一版不要求采集楼中楼、超出十条的后续评论或平台未正常返回的折叠评论。

## 6. 功能模块

### 6.1 配置管理

- 查看配置列表；
- 新增、编辑、删除配置；
- 启用或停用定时规则；
- 测试配置是否能获取至少一条数据；
- 对指定配置执行“立即提取”。
- 查看全局平台 Session 状态和最近验证时间；
- 启动官方页面人工认证、更新 Session 或清除 Session。
- 查看等待认证的批次，重新打开服务器浏览器远程认证入口或取消批次。

### 6.2 手动提取

1. 用户选择提取配置，或导入已知帖子 URL 清单；
2. 系统创建运行中批次；
3. 调用对应平台采集器；
4. 圈子发现方式分页获取帖子链接；URL 清单方式直接校验、标准化并批内去重；
5. 逐条访问帖子详情，提取正文及约定范围内的评论；
6. 达到数量上限、没有下一页、列表为空或触发安全停止条件时结束；
7. 保存链接、正文和评论并更新批次状态。

### 6.3 定时提取

- 启用的配置按预设规则自动触发；
- 与手动提取复用同一采集流程；
- 同一配置已经运行时，不重复并发执行；
- 失败时记录原因；
- 自动刷新失败且需要官方认证时，批次持久化暂停为 `waiting_for_auth`；所有依赖同一全局 Session 的新任务暂不启动采集，认证和门禁通过后等待批次按原创建顺序自动续跑；
- 第一版不包含邮件、短信或企业微信通知。

### 6.4 批次管理

批次列表必须区分运行中、等待平台认证、成功和失败。`waiting_for_auth` 批次显示暂停原因、暂停时间和“继续认证”“取消批次”操作；认证成功后的恢复由系统自动完成，不提供以新批次替代原批次的默认重试流程。

- 按时间倒序展示批次；
- 展示配置、触发方式、执行时间、数量和状态；
- 支持查看批次详情；
- 失败批次允许人工重新执行；
- 支持用户确认后人工删除批次及其所属结果；
- 第一版不提供复杂统计图表。

### 6.5 链接结果

- 表格展示基础字段；
- 标题可点击跳转到原始帖子；
- 支持标题关键词搜索；
- 支持单条复制和批量复制链接；
- 支持查看帖子正文和评论；
- 支持从数据库中已经持久化的当前批次快照生成 XLSX；
- XLSX 至少包含帖子表和评论表：帖子一行对应一个帖子，评论一行对应一条主评论，并通过批次 ID、帖子 ID 或 URL 关联；
- 图片和视频 URL 保存在帖子表中，不下载媒体文件；
- 导出过程不重新访问目标平台，不更新或覆盖原批次数据；
- 支持按可见状态筛选时，以平台状态验证结果为前提。

## 7. 平台采集器功能契约

所有平台采集器都应具备相同的业务能力：

1. 验证配置和访问条件；
2. 根据圈子、版块和分页参数获取一页数据；
3. 判断是否存在下一页；
4. 将平台字段转换为统一字段；
5. 返回可诊断的错误类型；
6. 保留必要的原始状态；
7. 遵守统一的数量上限、超时、重试和停止规则。

公共业务只依赖统一结果，不直接读取平台私有字段。具体接口形式和代码契约留待技术路线文档确定。

## 8. 可见状态规则

- `visible`：已有样本和字段规则证明帖子正常展示；
- `hidden`：已有样本和字段规则证明帖子被隐藏、删除、审核或不可正常展示；
- `unknown`：字段缺失、新状态值或证据不足。

需求中出现的 `status`、`visible`、`audit_status`、`fold_type` 等名称只是候选线索，不是已确认字段。

懂车帝当前人工核对样本已经确认 `operation_status=2` 的帖子页面可正常展示，因此当前适配器将已验证的原始值 `0` 和 `2` 映射为 `visible`，同时保留原始值。该结论是样本验证规则，不等同于平台官方枚举说明；遇到其他新值仍标记为 `unknown`，直到重新取得证据。

第一版因正文和评论需求需要逐条访问详情接口或详情页。可见状态判断应优先复用该次详情访问结果，不为状态判断额外重复请求。

## 9. 页面范围

第一版只包含三个基础页面：

1. 配置管理页；
2. 提取批次列表页；
3. 批次链接详情页。

页面以信息清晰和操作可用为目标，不包含品牌级视觉设计、移动端专项适配和复杂动效。

## 10. 第一版验收条件

第一版至少满足：

1. 一个指定平台已经完成真实样本可行性验证；
2. 可以创建有效配置并测试连接；
3. 可以从圈子和版块发现帖子 URL；
4. 可以导入已知帖子 URL 清单，并生成独立手动批次；
5. 可以按至少一种固定周期自动生成批次；
6. 达到上限或没有更多数据时能正常停止；
7. 成功批次可以查看、搜索、复制并导出链接；
8. 可以逐条访问帖子并保存真实可获取的正文，以及每帖最多十条主评论；
9. 失败批次展示可理解的错误信息；
10. 不同批次互不覆盖；
11. 平台缺失字段和未知状态不会被伪造；
12. 已预留后续两个平台的接入边界；
13. 在约定的部署环境、网络条件、合法访问条件和统一测试数据集下，一小时内有效完成 2000 个帖子 URL 的访问与结果处理。
14. 连续三轮吞吐测试均满足上述条件；任何限流、验证码、挑战页、登录失效或其他平台控制导致未能完成约定结果时，该轮验收失败。

“有效完成”必须满足：系统在测试时间窗口内实际访问该 URL，正确识别平台响应，并保存通过字段校验的帖子快照或有证据支持的平台终态。排队未执行、主动跳过、超时、验证码或验证页、无法确认的空数据、测试窗口结束后的补跑以及人工修补结果均不计入完成量。

每小时有效完成 2000 个 URL 是真实交付要求，不是仅供观察的性能目标。最终验收仍需同时报告自动成功率、正文完整率和主评论完整率，不能仅以请求发出数量证明达标。

需求中所称“必须绕过风控”按上述结果门禁理解：项目不单独验收某种对抗技术名称，只验证实际访问条件下是否按时产生 2000 个完整有效结果。通过结果只证明对应版本、样本、账号、网络和测试时间窗口内达到门槛；运行条件实质变化后需要重新验证。

吞吐测试输入由甲方从已知有效链接中提供。每轮输入 2000 个不同 URL，要求 2000 个全部有效完成，最终完成率为 100%，不允许存在最终 `failed`、`partial` 或未完成结果。

必需字段完整率要求为 100%：可访问帖子必须取得正文文字或至少一个平台实际返回的图片/视频 URL；纯媒体帖子允许正文为空。标题优先采用平台标题，平台无标题时取正文第一句话，标题和正文都没有时标题为空。一级评论以评论接口本次实际返回为准，达到十条时按平台顺序保存前十条，不足十条且接口明确 `has_more=false` 时保存实际返回结果并视为本次结束。详情回复数、评论接口总数与实际返回数量不一致时保留诊断字段，不据此虚构缺失评论；`has_more=true` 但游标缺失、评论接口失败或控制响应仍属于不完整。作者、发布时间、点赞数等平台本身未提供的可选字段允许为空，但系统不得因为解析失败而把已有字段静默保存为空。

字段完整率以测试时点能够取得帖子详情的结果为分母；详情已经不存在的输入单独计入“来源缺失”和“输入解析率”，不伪装成字段解析失败。正式每轮 2000 条验收仍要求事前固定 2000 条有效输入，运行时出现来源缺失仍会使该轮 2000/2000 有效完成门失败，不能通过事后缩小分母通过吞吐验收。

上述是第一版完工验收，不等同于正式功能开发前的“采集框架 PoC”。当前优先执行的 PoC 只验证 2000 个不同真实 URL 在一小时内能否访问到对应帖子真实内容，并正确排除验证码、挑战页、登录页和异常空响应。PoC 不要求实现圈子列表、主评论、数据库、前端或导出；这些仍是第一版完工必须通过的功能。

平台在正文中实际提供图片或视频地址时，应保存其 URL；媒体文件本身不进入下载和吞吐验收范围。
