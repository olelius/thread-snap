# ThreadSnap 技术路线

## 文档状态

状态：部分确认，框架及依赖仍待单独评审。

本文件用于后续记录已经确认的技术路线，包括但不限于：

- 前端框架及工程组织；
- 后端语言、框架及接口规范；
- 数据库与数据迁移方式；
- 定时任务和任务并发控制；
- 平台采集器代码契约；
- HTTP 请求、HTML 解析或浏览器自动化的适用边界；
- 配置、凭证与日志安全；
- 测试策略；
- 本地运行、构建和部署方式。

## 已确认的系统边界

- 使用独立提取功能服务实现提取领域能力，具体实现语言尚在评审。
- 提取功能服务持续拥有提取配置、定时规则、提取批次、提取链接、持久化和任务调度。
- 内部验证版提供基础测试前端，直接调用提取功能服务的接口。
- 正式版由现有前端调用现有后端，再由现有后端调用提取功能服务。
- 现有后端负责用户、角色、权限和公网访问；提取功能服务不绑定正式管理框架。
- 提取功能服务与现有后端部署在同一台主机，只允许本机内部调用，不向网络暴露服务端口。
- 当前不考虑 Docker 部署。
- 当前开发环境不是 Linux；日常编码、单元测试、访问冒烟和中等批量预筛以当前开发环境为准。
- 目标部署环境已确认为 CentOS Stream 10（Coughlan）、x86_64、glibc 2.39；主机规格、语言运行时、浏览器系统依赖和进程管理机制仍待确认，因此尚不固化安装和服务管理命令。
- 候选方案在开发阶段必须使用同一台开发主机、相同网络出口和相同测试条件进行公平对比。
- 开发环境中的性能结果只用于预筛和调优，不能代替部署环境验收。阶段 3 的三轮 2000 URL/小时硬门禁必须直接在最终部署的 Linux 主机执行。
- 最终选定的技术栈必须在 Linux 环境完成依赖安装、浏览器运行时、路径行为、进程管理和启动方式验证；Linux 三轮硬门禁通过后，才能最终确认技术路线。
- 正式功能开发前，两个候选都必须生成最简 Linux PoC 测试包并完成部署验证；PoC 原型开发不属于正式业务功能开发。
- Linux PoC 测试包统一采用 `tar.gz`。包内包含候选原型、锁定的依赖描述、面向目标 Linux 架构生成的离线应用依赖、所需浏览器运行时、Linux 安装脚本、启动脚本、健康检查脚本、基准测试入口和简要说明。
- 测试包不得包含开发机的 `.venv`、`node_modules`、Windows 浏览器二进制、浏览器缓存、平台凭证、测试结果或其他机器相关状态。
- 为便于项目负责人直接复制，源码压缩包旁允许放置一个被 Git 忽略的本地操作目录，使用明文 `config.json` sidecar 和真实 `input-urls.txt`；部署脚本校验标准压缩包后再把 sidecar 复制到解压目录。sidecar 不属于标准测试包校验内容，也不得进入 Git、日志或结果回显。
- 不在 PoC 阶段制作 Docker 镜像、RPM/DEB 安装包或冻结为单文件可执行程序。Linux 端依据锁文件和离线依赖重新建立应用运行环境，以暴露真实的跨平台兼容问题。
- 依赖稳定性由锁文件、精确版本、SHA-256 清单和测试包版本共同保证；离线依赖用于避免测试时上游仓库变化或下载失败，不能替代版本锁定和目标平台兼容验证。
- Linux 测试机允许联网，但阶段 2.5 和阶段 3 不从公网解析或下载应用依赖及浏览器运行时。网络只用于目标平台访问、系统环境准备、诊断和重新生成测试包。
- Linux 发行版、CPU 架构和 libc 已形成初始环境基线；最终离线依赖包仍必须面向该 Linux 环境生成，不能复制 Windows 虚拟环境或依赖目录。语言运行时与浏览器系统库在打包前继续确认。
- 阶段 3 必须从测试包解压后的干净目录运行，不能直接使用开发工作区或人工修补后的目录。
- 最终 Linux 主机由项目负责人手动上传、校验、解压并运行测试脚本，Codex 不远程登录或自动操作该主机。
- 人工负责的是部署和命令触发；环境快照、测试计时、完成量、访问证明完整率、风控与错误事件和资源指标仍由测试脚本自动记录，不采用人工计数或手工修改结果。
- 目标 Linux 第一次运行时先执行 `test-connectivity.sh`：最多 3 条、并发 1，分层记录运行时/浏览器、DNS/TCP/TLS/HTTP、两个固定候选的登录和内容访问；只有汇总为 `ready_for_2000=true` 后才执行 2000 条吞吐入口。
- 短信初始化保存的两个 `profile_dir/storage-state.json` 是后续联通与吞吐进程的认证来源。联通入口为了避免测试过程改写主会话，会在每次运行前重建 `profiles/connectivity-candidate-*`，分别从候选自己的配置目录复制当前状态并保持 `0600`；不得只切换到空的隔离目录后重新走密码登录，也不得在源状态缺失时沿用旧副本。`prepare.log` 只记录每个候选是否复制成功，不输出状态内容。
- Linux 包把两个候选的浏览器统一安装到 `.runtime/browsers`；安装、健康检查、联通和吞吐入口都必须在启动候选前导出同一个 `PLAYWRIGHT_BROWSERS_PATH`，不能让运行入口回退到用户级 `~/.cache/ms-playwright`。
- 认证入口默认展示手机验证码登录；两个候选必须显式点击可见的“密码登录”，并等待账号、密码输入框可见后再填充提交，不按按钮位置或“最后一个按钮”推断登录模式。
- 登录后的验证判定只使用可见正文和可见短信码、验证码、滑块或验证容器；不能因 HTML 源码或脚本包含相关关键字直接判定。联通结果可保存脱敏截图、最终路径、查询参数名、标准化提示词和控件布尔值，但不保存完整 HTML、Cookie 值或凭证。
- 目标 Linux 的 v0.2.4 可见证据已确认：密码表单提交后页面明确提示“为保证账号安全，请使用手机验证码登录”，属于当前账号与服务器访问条件触发的二次手机验证，不是未切换密码登录。诊断结构必须单独记录该提示；候选 A 的登录入口与其吞吐请求一致丢弃图片、字体等非必要资源，避免这些资源阻塞 Scrapling 的页面 `load` 等待。
- 当前 PoC 为解决上述阶段门，只增加一次性人工认证初始化：候选 A/B 按顺序各自点击发送；出现可视验证时，由各自框架启动的原 Chromium 仅在 `127.0.0.1` 暴露独立 CDP 端口，项目负责人从 Windows 经 SSH 隧道打开 Chrome DevTools 完成人工验证；程序确认验证容器消失且发送控件进入倒计时后，才从 SSH 终端读取动态码、保存隔离的 `storage-state.json`，随后由新进程复用会话。CDP 入口不需要在服务器安装桌面或 VNC，完成初始化后随浏览器进程关闭；动态码、Cookie 和挑战数据不进入配置、日志、结果或持久状态。该做法不确定为正式项目方案；正式环境的验证码、会话续期和外部接入方式留待 PoC 后结合会话寿命与部署约束决策。
- 短信初始化不先访问帖子主文档，而是由原始帖子 URL 构造同源 `/login-required?redirect=...` 入口；这样避开 Scrapling 首次帖子导航对完整 `load` 的等待，两个候选仍在各自固定框架中运行，登录完成后继续使用原始帖子 ID 校验内容。目标 Linux 已证明登录主文档 HTTP 200 且 `DOMContentLoaded` 完成时控件可交互，但 Scrapling 的首次 `page.goto` 及随后稳定性检查仍各自固定等待 `load`；页面原生 `window.stop()` 不会释放 Playwright 已建立的生命周期等待。因此候选 A 只在短信入口的 `page_setup` 中把这两处等待映射为 `domcontentloaded`，候选 B 通过 Crawlee 原生 `gotoOptions.waitUntil` 使用同一条件。后台请求仍按资源类型报告，但不再阻塞原有页面动作；终端还必须输出登录控件就绪和发送按钮点击完成阶段，不能把脚本启动或页面到达当作短信已经请求。
- 目标 Linux 在已认证会话下再次证明 Candidate A 的普通帖子入口同样可能因页面后台资源而让 Scrapling 的 `page.goto(wait_until=load)` 满 90 秒；同轮 Candidate B 对相同3条样本全部取得帖子 ID 与内容证明。Candidate A 的登录确认和逐 URL 吞吐现统一在 Scrapling `page_setup` 中把首次导航及其固定稳定性 `load` 等待映射为 `domcontentloaded`，随后仍按原等待时间读取 DOM 并执行统一内容契约；这只调整导航完成条件，不更换 Scrapling 或放宽成功判定。
- 短信发送按钮点击完成不单独视为平台已经接受请求。两个候选均在点击前开始采集、点击后等待 5 秒，并以 `sms_send_evidence` 输出 XHR/fetch 的请求方法、响应状态和无查询参数路径，以及倒计时、附加验证和标准化可见警告；手机号、请求体、响应体和动态码不进入证据。只有结合网络响应和页面反馈，才能区分事件未触发、平台拒绝、附加验证与短信投递问题。
- 会话主动探测只以真实帖子证明判断现有资料是否可用，不再用 `storage-state.json` 修改时间代替服务端状态。目标 Linux 已确认约19.5小时未更新的 Candidate A 资料在并发1首条探测中取得文章 HTTP 200 空文档，随后同一旧浏览器资料打开登录入口也在 HTTP 200 后等待短信控件超时；这证明旧资料当前不可复用，但不单独区分自然过期和平台控制。短信重新初始化因此改为由两个固定框架分别创建不加载旧 Cookie、Local Storage、缓存或客户端资料的临时浏览器目录；登录及原始帖子证明成功后才在浏览器关闭后整体提升为候选主资料，任一步失败均保留旧资料并记录脱敏页面形态和失败阶段。
- 可视验证与短信码是两个不同阶段：检测到可视验证后，初始化状态必须进入 `manual_verification_waiting`，不得提前读取短信码；只有同时取得“可视验证已消失”和“发送控件倒计时可见”两个页面证据，才记录 `manual_verification_completed`、`sms_send_confirmed` 并进入短信码输入。等待十分钟仍未取得完整证据时，本次初始化按失败收口，不把 HTTP 200 或验证码组件消失单独解释为短信已发送。
- 资源过滤必须按场景分开：普通密码诊断与帖子吞吐可继续丢弃非必要图片以控制加载和资源占用；短信人工初始化必须放行 `image`/`imageset`，保证滑块背景、拼图和验证码素材可加载，同时仍可丢弃 `media`、`font` 等与验证无关的资源。目标 Linux 的 v0.2.11 已用 `[5202] 图片加载失败` 和页面 Logo 缺图证明短信入口沿用通用图片过滤会直接破坏可视验证。
- 当前开发电脑上的 PoC 输入、测试包和原始结果统一保存在 `artifacts/poc/`，分别使用 `inputs/`、`packages/` 和 `results/<candidate>/<round-id>/` 子目录，不允许散落到仓库其他路径。
- 采集任务采用异步任务语义：创建任务后返回批次或任务标识，再查询状态和结果，不让调用方同步等待完整采集过程。
- 内部接口采用 HTTP/JSON，只监听 `127.0.0.1`，版本化路径前缀为 `/internal/v1`。
- 内部接口不额外使用共享令牌，依赖回环地址、Linux 进程权限和现有后端的公网访问控制；接受同一主机其他进程可能调用接口的剩余风险。
- 内部接口的错误结构、幂等规则和调用追踪仍待确认。

## 技术选型前置门禁

提取功能服务的最终语言和采集框架不得在真实样本验证前直接确定。进入第一版正式功能开发前，必须使用同一批懂车帝真实 URL 对以下两个候选方案完成对比 PoC：

### 候选方案 A

- Python；
- FastAPI；
- Scrapling；
- 使用 Scrapling 的普通 HTTP 与标准动态页面采集能力完成对比验证。

### 候选方案 B

- Node.js；
- TypeScript；
- Fastify；
- Crawlee；
- Playwright；
- 使用 Crawlee 的 HTTP 与 Playwright 采集能力完成对比验证。

本轮不再把 `Scrapy + Playwright` 作为项目技术选型候选，但其仍可保留在通用技术调研中作为行业对照。

两个候选必须遵守相同的数据字段、输入 URL、访问条件、网络环境和结果判定规则。不得根据框架宣传、个人熟悉度或单个成功样本直接决定技术路线。

### 当前直接 HTTP/Spider 验证分支（尚未形成选型结论）

已确认当前吞吐入口仍以逐 URL 浏览器访问为主：Candidate A 使用 Scrapling `AsyncDynamicSession`，Candidate B 使用 Crawlee `PlaywrightCrawler` 且吞吐入口未启用 `SessionPool`。两端虽已在冒烟或诊断代码中使用 `FetcherSession`、`CheerioCrawler`，首轮 2000 条和后续 500 条结果仍不能证明直接 HTTP 路线的正确性、风控表现或吞吐。

下一轮架构预筛保持候选语言、框架和统一成功契约不变，只替换批量访问通道：

- Candidate A：使用 Scrapling `Spider` 负责队列、并发、回调和运行状态，注册 `FetcherSession(impersonate="chrome")` 作为普通 HTML/JSON 请求通道；
- Candidate B：使用 Crawlee `CheerioCrawler` 处理 HTML、`HttpCrawler` 处理 JSON，并启用 `SessionPool` 与同会话 Cookie 持久化；
- 本阶段不启动浏览器、不导入浏览器会话状态、不在直接 HTTP 失败后切换浏览器；任一 URL 只能由直接 HTTP 通道产生结果，失败按统一分类器如实结束；
- 页面主文档若已在内嵌状态中提供当前访问证明或后续正式功能所需字段，优先直接解析该状态，不为同一字段额外调用接口。

框架与平台适配器的职责必须分开：框架负责 TLS/HTTP 客户端特征、请求头、Cookie、会话池、并发、限速、重试、队列和恢复；懂车帝适配器负责帖子 ID、内嵌状态、评论接口路径、分页游标、动态参数生命周期和平台响应分类。框架默认的 HTTP 状态码阻断判定不能识别本项目已出现的 HTTP 200 空文档，两个候选必须继续调用统一分类器。

评论等接口若需要 `msToken`、`a_bogus` 或等价动态参数，不并入本轮直接 HTTP 主文档可行性预筛。当前只测页面主文档及其内嵌状态能否满足访问证明；若后续字段验证确认必须请求带动态参数的接口，再建立独立实验组，分别验证纯 HTTP 参数实现与浏览器运行时参数方案，不把两组结果拼接。Cookie、UA、请求头、客户端/TLS 特征和会话级令牌必须作为一个会话身份整体管理，请求级签名按实际 URL 与参数即时生成，不跨会话复用。这里记录的是待验证边界，不把参数名或一次成功请求写成稳定接口结论。

动态参数生成、复用和身份不一致本身都可能触发平台控制，因此后续独立实验必须记录参数来源、首次 `login`、`empty`、`captcha`、`challenge` 或限流出现的时间与已完成 URL 数、会话存活时间、令牌刷新/复用次数、同一身份并发数和恢复结果；这些指标不进入当前纯 HTTP 主文档轮次。出现控制后停止向同一会话盲目重试，隔离该会话并保留脱敏证据。令牌值、Cookie 值、完整请求体和可复用签名不得进入 Git、日志或结果报告。

开发电脑只用于确认实现可运行、字段契约正确并完成中等批量预筛；平台控制还受网络出口、账号/会话、运行时、TLS 客户端特征和并发影响，因此开发电脑结果不直接外推到 CentOS。通过本地预筛的直接 HTTP 通道仍须进入目标 Linux 的同等级测试，最终选型继续以三轮 2000 URL/小时硬门禁为准。

吞吐统一按“有效 URL/秒”统计，而不是请求发送数、队列完成数或 HTTP 200 数。当前正式门槛 2000 URL/小时约等于持续 `0.56` 个有效 URL/秒；“十万条/夜”若按 8 小时计算约需 `3.47` 个有效 URL/秒，`10` 个有效 URL/秒等于 36000 URL/小时，只作为扩展压力目标，不替代当前交付门槛。并发预算应依据“目标有效 URL/秒 × 每 URL 实际请求数 × 平均请求耗时”估算，并用 P50/P95、请求放大率和最终有效完成率校正。

2026-08-11 本机阶段 2A 已按上述隔离条件执行同一固定500条、并发1：Candidate A 原始处理速度约6.96 URL/秒但500条全部为 `login`；Candidate B 原始处理速度约6.70 URL/秒但为497条 `login`、2条 `captcha`、1条 `challenge`；两端有效链接速度均为0、统一契约错误均为0、HTTP通道均为100%。因此“匿名纯直接 HTTP 主文档”在当前条件下未通过可行性门，不继续并发2/4/8，也不进入目标 Linux 打包。该结论不外推到认证条件下的纯 HTTP、评论动态参数实验或目标 Linux；任何后续实验必须另立轮次，不与本轮拼接。

2026-08-12 的新浏览器/HTTP 对照进一步确认：全新浏览器打开两条样本均直接显示登录页；Candidate A 已使用 Chrome 模拟、隐蔽请求头、中文语言头，并在同一 HTTP 会话先访问首页取得匿名 Cookie，但文章仍由服务器302到登录入口。当前阻塞不应写成“框架没有处理指纹”，更准确的是现有指纹与匿名会话不足以满足平台访问条件；主文档重定向发生在页面运行前，评论动态参数不是该阶段的直接原因。后续认证会话试验必须与匿名轮次隔离。

2026-08-12 Candidate A 已完成独立的认证纯 HTTP 首版验证。当前日常 Chrome 只用于确认登录可见，因其未开启 CDP，项目没有直接读取或复制该浏览器的 Cookie；Scrapling `AsyncDynamicSession` 使用项目既有测试账号建立项目自有认证状态并显式导出 Playwright storage state，随后由 `Spider + FetcherSession` 对3条固定样本执行并发1、每URL一次请求。框架化复跑为3/3 `post/success`、1.169秒、约2.57个有效URL/秒、请求放大率1.0，未出现登录、验证码、挑战或限流。该结果只解锁认证主文档的下一阶段负载设计，不与匿名500条拼接，也不解锁评论动态参数或目标Linux门禁。

Candidate A 的职责边界据此固定为“框架优先”：Scrapling 负责浏览器/HTTP Session、TLS与请求头模拟、Cookie请求、Spider调度、Request/Response、CrawlStats和内置结果导出；项目适配层只保留框架没有业务语义的帖子ID/正文证明、HTTP 200控制页细分、脱敏诊断、摘要和校验清单。Spider 默认 blocked 流程在重试耗尽后不会把终态响应交给项目回调，因此首版只调用并记录框架状态码阻断证据，不启用自动重试；HTTP 200登录页、空文档和挑战仍由项目分类器补充。这不是重复实现框架功能，而是为统一结果契约保留失败证据。

同日认证HTTP继续执行固定500条、并发1：500/500均产生终态，399条HTTP 200通过帖子证明，101条为HTTP 404，有效完成率79.8%；总时长166.031秒，处理速度约3.01 URL/秒、有效速度约2.40 URL/秒，请求放大率1.0。未出现登录、空文档、验证码、挑战或限流，框架暂停未触发；404分散在全部10个连续50条区间，两条有界复查返回相同标准404正文，历史浏览器轮次的24条404全部重合。当前技术判断是认证Session没有在本轮166秒内表现出已识别风控，但固定输入的当前可访问性不满足500条100%门禁；先复核并替换404输入，再测试更高并发，不用失败分母宣告吞吐通过。

随后按用户要求执行固定2000条、并发1持续诊断。旧状态在启动前已为空，项目自有Scrapling浏览器重新登录并以3/3复检确认新状态有效后，主轮次在第708个终态、约228.635秒首次出现HTTP 200零字节空文档并暂停：此前568条有效、139条HTTP 404，剩余1292条未请求。停控后本轮刚成功的已知URL在HTTP和项目Scrapling浏览器profile中都转为空，但同电脑同网络的用户日常Chrome重新导航仍能加载完整正文；据此排除单个坏URL和纯IP全局封锁，控制范围更接近项目测试账号/会话/profile/客户端身份组合，尚不能细分账号信誉、会话绑定或客户端身份评分。不得刷新Session后续跑并把分段结果拼成同一轮。

同日等待一段时间后，使用原storage state、原profile和原HTTP配置复访本轮曾成功的已知样本，首条仍为HTTP 200零字节并暂停，说明单纯冷却没有让该项目Session身份自然恢复。认证HTTP入口已支持 `--offset` 选择未完成清单段，但只有重新认证并通过小样本阶段门后才能启动；新Session的剩余1292条只能作为独立恢复段，不得与旧Session前708条合并为2000条通过。

随后使用新的Scrapling隔离profile重新密码登录，无二次验证；新状态交给 `Spider + FetcherSession` 后先取得3/3有效门禁，再以 `offset=708` 启动1292条独立恢复段。该段在第767个终态、262.041秒再次出现HTTP 200零字节并暂停，此前640条有效、126条HTTP 404，剩余525条未请求；停控后复查门禁中已确认有效的样本也立即为空，排除单条输入异常。控制后统计中的2个过期Cookie实际在恢复段开始后数秒即到期，首控附近没有Cookie到期，因此不能把262秒处的状态切换解释为客户端Cookie自然到期。结合旧轮第708个终态、228.635秒的相近转变规模，当前应优先用独立新Session执行固定样本的速率/间隔矩阵，分别控制持续时间、请求量和请求速率；新Session/profile恢复只证明刷新身份能暂时恢复，不单独证明旧Session自然过期，也不得把两个身份的结果拼接。

认证HTTP现增加有界Session恢复控制，而不是无限重试：每个HTTP段由Scrapling `Spider + FetcherSession`执行并在首个 `empty/login` 暂停；控制器使用 `AsyncDynamicSession` 和全新隔离profile重新密码登录，新的storage state必须先通过3条固定纯HTTP门禁，随后从触发URL本身重新请求。默认最多恢复2次、配置上限5次；`captcha/challenge/rate_limited`、登录失败、门禁失败、恢复预算或一小时窗口耗尽均结束。最终结果按每个输入URL唯一终态统计，但门禁、旧Session控制尝试与新Session重试都写入请求事件并计入采集HTTP请求放大率；浏览器登录子请求不混入该指标，Session刷新次数单列。该机制符合ADR 0004“同一窗口内自动恢复才可计为完成”，但只有新的完整2000条轮次才能判定是否通过。

实现后的真实1条闭环使用无效夹具Cookie触发登录门：旧门禁首条为 `login`，Scrapling重新密码登录且无二次验证，新Session门禁3/3、触发目标重试1/1成功；总计5个HTTP请求、1次成功Session刷新、16.999秒。另有两份历史状态在约数小时后重新门禁均为3/3，说明旧状态可能自然恢复，但当前没有最短恢复时间证据；自然恢复与重新登录恢复继续分开记录。

同一实现随后完成Windows固定2000条完整轮次：全新Session及两次恢复Session的门禁均为3/3；HTTP 200空文档分别在原清单第708和第1466条出现，两次都经重新登录、门禁和触发URL重试恢复，第三个Session完成至第2000条。总时长747.120秒，采集HTTP请求2011次、放大率1.0055，最终没有未恢复控制；但只有1644条取得帖子证明，356条为标准HTTP 404，因此完整覆盖和自动恢复通过、统一100%正确性门失败。该配置的有效速度约2.20 URL/秒，超过2000/小时门槛但低于十万条/8小时约3.47 URL/秒；下一轮必须使用事先固定并哈希的当前可访问清单重新从0执行，不得从本轮事后删除404。

PoC 访问模式遵循“未登录优先”：

- 先使用未登录状态验证真实帖子内容访问和风控响应识别；
- 未登录状态能够达到当前采集框架 PoC 门槛时，不使用账号、Cookie 或登录会话；
- 只有未登录状态无法满足真实字段要求时，才由甲方提供合法登录会话；
- 同一对比轮次中两个候选必须使用相同访问模式；需要登录时必须使用同一授权条件；
- 测试轮次中途不得从未登录切换到登录后继续累计结果；访问模式变化后必须重新开始该轮测试；
- 凭证、Cookie 和会话状态不得进入前端、日志、示例文件或 Git。

正式功能确需登录时采用“客户机远程操作服务器官方登录页面 + 加密 Session + 有界自动刷新 + 原批次自动续跑”，不建立平台账号或密码字段：

- 第一版只维护一套全局懂车帝 Session；所有提取配置隐式共用，不实现多账号、账号轮换或配置绑定；
- 浏览器进程、Profile 和 Session 始终位于服务器；提取功能服务在服务器启动受控浏览器并打开平台官方登录页面，客户从客户机通过 ThreadSnap 或客户现有系统提供的临时、已鉴权远程交互通道查看和操作该浏览器，自行完成密码、扫码、短信、验证码或滑块；客户机本地浏览器形成的 Cookie 不作为服务器 Session；
- 只持久化 Cookie、LocalStorage、浏览器 Profile 或等价 Session 状态及脱敏元数据；状态必须加密保存，密钥与数据库分离，文件和运行进程采用最小访问权限；
- 查询接口只返回会话状态和最近验证时间；Cookie、LocalStorage、动态码、扫码内容、Profile 路径和其他可复用数据不得进入前端、日志、错误、导出、截图、测试报告或 Git；
- 采集前用少量真实样本探测 Session。HTTP 采集识别到 `login`、异常空响应或等价身份异常时暂停新请求，保留触发 URL，并对既有 Profile 执行一次有界自动刷新；
- 官方页面仍保持登录且新 Session 通过门禁时，从触发 URL 继续；出现登录表单、扫码、短信、验证码、滑块或门禁失败时，不再循环刷新，持久化批次当前索引、触发 URL 和待处理队列，将批次转为 `waiting_for_auth`；
- `waiting_for_auth` 是数据库中的可恢复状态，不是持续占用进程的挂起调用：状态提交后释放采集 Worker、连接和事务；所有依赖同一全局 Session 的新定时任务和手动请求在等待期间不启动采集；认证门禁通过后，等待批次按原创建顺序有界重新入队，避免同时恢复造成请求突发；
- 人工认证使用独立、短生命周期的服务器浏览器进程。客户完成认证后，服务端原子替换加密 Session、关闭远程交互通道和登录浏览器，再执行 1 至 3 条真实样本门禁；门禁通过后自动把同一批次从触发 URL 和待处理队列重新入队，不要求用户点击重试；
- 人工认证入口必须限时并仅供管理员访问；CDP、VNC 或等价控制端口不得直接暴露公网。完成、取消、断开或超时后关闭浏览器和临时入口；断开或超时只结束交互窗口，批次检查点继续保持 `waiting_for_auth`，用户可重新打开入口或显式取消；
- 认证后门禁失败时仍保持 `waiting_for_auth` 并记录脱敏原因，不自动循环创建登录浏览器或反复重登；
- 清除或更新 Session 时安全删除旧状态，并验证进程异常退出不会遗留长期可访问的控制入口。

甲方负责提供至少 2000 个不同的真实帖子 URL，作为吞吐门禁的输入池。两个候选在同一测试轮次必须使用相同的 2000 个 URL。已接收的 2694 个不同懂车帝帖子 URL 满足当前输入数量需求。

当前采集框架 PoC 使用 2000 个 URL 进行一小时目标吞吐测试，记录实际完成量、访问成功率、真实帖子内容证明完整率、风控事件和资源指标。该 PoC 只负责采集框架选型，不要求提前实现圈子列表、完整正文与主评论解析、数据库、前端或导出。

吞吐门禁必须连续执行三轮独立测试，三轮每轮都必须在一小时内有效完成 2000 个 URL；任何一轮未达标，该候选即未通过吞吐门禁。

需求中所称“必须绕过风控”在技术选型中按结果门禁执行，不作为独立技术名称或单独功能模块验收。限流、验证码、挑战页、登录失效或其他平台控制导致任一 URL 未在窗口内产生有效访问证明时，该轮失败；候选自动恢复并在同一窗口内产生通过校验的访问结果时可以计入完成。三轮通过只证明已记录的版本、样本、访问条件、网络和测试时间窗口内达标，条件实质变化后重新执行同等级验证。

甲方提供的吞吐 URL 均作为已知真实业务链接输入。每轮输入数量和有效完成数量均为 2000，要求 100% 最终完成率和零最终失败。单个 URL 只在平台返回的帖子标识与输入匹配，且至少获得标题或正文存在性证明之一，同时未将验证码、挑战页、登录页或异常空响应当作内容时，才计为有效完成。仅 HTTP 200 不构成通过证据。

PoC 对首次 `login` 和 `empty` 采用有界脱敏诊断：每个候选、每种分类最多保存 3 条，只记录 URL 哈希、最终路径类型、文档长度与哈希、DOM 形态、已知控制标记、主文档状态链以及 Cookie 数量和名称集合哈希；不保存页面正文、Cookie 名称/值、账号或完整 URL。该证据用于区分登录重定向、空壳文档和平台控制形态，不改变两个固定候选的访问技术和统一成功契约。

Linux PoC 运行器必须把每个候选放入独立进程组；候选入口退出、超过窗口或外层脚本收到终止信号时，按 TERM 后 KILL 的有界顺序清理同组 npm、tsx 和浏览器子进程。Candidate B 在 Crawlee 队列返回后显式刷新完成标记并退出，避免队列已经结束而 Node 进程继续滞留。

当两个固定候选在并发 8 下均出现约一分钟后的 HTTP 200 空文档时，已保留“全新隔离会话 + 并发1 + 固定前500条”的浏览器诊断包和执行入口，不删除或改写该证据。鉴于现有大批量路径仍为逐 URL 浏览器访问，当前优先执行上述直接 HTTP/Spider 本地预筛；其结果决定是把 HTTP 通道打包到目标 Linux，还是再执行浏览器单并发诊断。两条路径均使用原统一成功契约，短样本和500条结果都不替代正式三轮2000条硬门禁。

完整正文、主评论、媒体 URL 和其他业务字段的提取在第一版正式功能开发与完工验收中执行，不作为当前采集框架 PoC 的前置输出要求。

导出采用数据库快照生成方式：采集结果先持久化，用户发起导出时按批次查询帖子、主评论和媒体 URL，再生成 XLSX。导出过程不得重新访问目标平台。具体数据库产品和 XLSX 生成依赖仍待最终技术栈确认。

历史批次不自动过期，仅在用户明确执行人工删除后清理。删除操作必须在同一事务中处理批次、帖子和主评论等关联数据，避免残留孤立记录。

用户可见批次编号采用 `YYYYMMDD-HHmmss-NNN`，使用 `Asia/Shanghai` 时区，时间精度为秒，同一秒内通过三位递增序号区分。数据库内部批次主键采用 UUIDv7，不直接使用批次编号作为主键。

任一候选未达到该门槛时不得被选为最终方案；两个候选都未达到时，不得选择“相对更快”的失败方案进入正式开发，而应扩大候选范围、调整采集架构或重新评估数据获取方式后再次执行 PoC。
