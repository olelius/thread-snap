# ThreadSnap 技术路线

## 文档状态

状态：部分确认，框架及依赖仍待单独评审。

本文件用于后续记录已经确认的技术路线，包括但不限于：

- 前端框架及工程组织；
- 后端语言、框架及接口规范；
- 数据库与数据迁移方式；
- 定时任务和任务并发控制；
- 平台采集器代码契约；
- HTTP 请求、HTML 解析或浏览器自动化的适用边界；
- 配置、凭证与日志安全；
- 测试策略；
- 本地运行、构建和部署方式。

## 已确认的系统边界

- 使用独立提取功能服务实现提取领域能力，具体实现语言尚在评审。
- 提取功能服务持续拥有提取配置、定时规则、提取批次、提取链接、持久化和任务调度。
- 内部验证版提供基础测试前端，直接调用提取功能服务的接口。
- 正式版由现有前端调用现有后端，再由现有后端调用提取功能服务。
- 现有后端负责用户、角色、权限和公网访问；提取功能服务不绑定正式管理框架。
- 提取功能服务与现有后端部署在同一台主机，只允许本机内部调用，不向网络暴露服务端口。
- 当前不考虑 Docker 部署。
- 当前开发环境不是 Linux；日常编码、单元测试、访问冒烟和中等批量预筛以当前开发环境为准。
- 目标部署环境已确认为 CentOS Stream 10（Coughlan）、x86_64、glibc 2.39；主机规格、语言运行时、浏览器系统依赖和进程管理机制仍待确认，因此尚不固化安装和服务管理命令。
- 候选方案在开发阶段必须使用同一台开发主机、相同网络出口和相同测试条件进行公平对比。
- 开发环境中的性能结果只用于预筛和调优，不能代替部署环境验收。阶段 3 的三轮 2000 URL/小时硬门禁必须直接在最终部署的 Linux 主机执行。
- 最终选定的技术栈必须在 Linux 环境完成依赖安装、浏览器运行时、路径行为、进程管理和启动方式验证；Linux 三轮硬门禁通过后，才能最终确认技术路线。
- 正式功能开发前，两个候选都必须生成最简 Linux PoC 测试包并完成部署验证；PoC 原型开发不属于正式业务功能开发。
- Linux PoC 测试包统一采用 `tar.gz`。包内包含候选原型、锁定的依赖描述、面向目标 Linux 架构生成的离线应用依赖、所需浏览器运行时、Linux 安装脚本、启动脚本、健康检查脚本、基准测试入口和简要说明。
- 测试包不得包含开发机的 `.venv`、`node_modules`、Windows 浏览器二进制、浏览器缓存、平台凭证、测试结果或其他机器相关状态。
- 为便于项目负责人直接复制，源码压缩包旁允许放置一个被 Git 忽略的本地操作目录，使用明文 `config.json` sidecar 和真实 `input-urls.txt`；部署脚本校验标准压缩包后再把 sidecar 复制到解压目录。sidecar 不属于标准测试包校验内容，也不得进入 Git、日志或结果回显。
- 不在 PoC 阶段制作 Docker 镜像、RPM/DEB 安装包或冻结为单文件可执行程序。Linux 端依据锁文件和离线依赖重新建立应用运行环境，以暴露真实的跨平台兼容问题。
- 依赖稳定性由锁文件、精确版本、SHA-256 清单和测试包版本共同保证；离线依赖用于避免测试时上游仓库变化或下载失败，不能替代版本锁定和目标平台兼容验证。
- Linux 测试机允许联网，但阶段 2.5 和阶段 3 不从公网解析或下载应用依赖及浏览器运行时。网络只用于目标平台访问、系统环境准备、诊断和重新生成测试包。
- Linux 发行版、CPU 架构和 libc 已形成初始环境基线；最终离线依赖包仍必须面向该 Linux 环境生成，不能复制 Windows 虚拟环境或依赖目录。语言运行时与浏览器系统库在打包前继续确认。
- 阶段 3 必须从测试包解压后的干净目录运行，不能直接使用开发工作区或人工修补后的目录。
- 最终 Linux 主机由项目负责人手动上传、校验、解压并运行测试脚本，Codex 不远程登录或自动操作该主机。
- 人工负责的是部署和命令触发；环境快照、测试计时、完成量、访问证明完整率、风控与错误事件和资源指标仍由测试脚本自动记录，不采用人工计数或手工修改结果。
- 目标 Linux 第一次运行时先执行 `test-connectivity.sh`：最多 3 条、并发 1，分层记录运行时/浏览器、DNS/TCP/TLS/HTTP、两个固定候选的登录和内容访问；只有汇总为 `ready_for_2000=true` 后才执行 2000 条吞吐入口。
- 短信初始化保存的两个 `profile_dir/storage-state.json` 是后续联通与吞吐进程的认证来源。联通入口为了避免测试过程改写主会话，会在每次运行前重建 `profiles/connectivity-candidate-*`，分别从候选自己的配置目录复制当前状态并保持 `0600`；不得只切换到空的隔离目录后重新走密码登录，也不得在源状态缺失时沿用旧副本。`prepare.log` 只记录每个候选是否复制成功，不输出状态内容。
- Linux 包把两个候选的浏览器统一安装到 `.runtime/browsers`；安装、健康检查、联通和吞吐入口都必须在启动候选前导出同一个 `PLAYWRIGHT_BROWSERS_PATH`，不能让运行入口回退到用户级 `~/.cache/ms-playwright`。
- 认证入口默认展示手机验证码登录；两个候选必须显式点击可见的“密码登录”，并等待账号、密码输入框可见后再填充提交，不按按钮位置或“最后一个按钮”推断登录模式。
- 登录后的验证判定只使用可见正文和可见短信码、验证码、滑块或验证容器；不能因 HTML 源码或脚本包含相关关键字直接判定。联通结果可保存脱敏截图、最终路径、查询参数名、标准化提示词和控件布尔值，但不保存完整 HTML、Cookie 值或凭证。
- 目标 Linux 的 v0.2.4 可见证据已确认：密码表单提交后页面明确提示“为保证账号安全，请使用手机验证码登录”，属于当前账号与服务器访问条件触发的二次手机验证，不是未切换密码登录。诊断结构必须单独记录该提示；候选 A 的登录入口与其吞吐请求一致丢弃图片、字体等非必要资源，避免这些资源阻塞 Scrapling 的页面 `load` 等待。
- 当前 PoC 为解决上述阶段门，只增加一次性人工认证初始化：候选 A/B 按顺序各自点击发送；出现可视验证时，由各自框架启动的原 Chromium 仅在 `127.0.0.1` 暴露独立 CDP 端口，项目负责人从 Windows 经 SSH 隧道打开 Chrome DevTools 完成人工验证；程序确认验证容器消失且发送控件进入倒计时后，才从 SSH 终端读取动态码、保存隔离的 `storage-state.json`，随后由新进程复用会话。CDP 入口不需要在服务器安装桌面或 VNC，完成初始化后随浏览器进程关闭；动态码、Cookie 和挑战数据不进入配置、日志、结果或持久状态。该做法不确定为正式项目方案；正式环境的验证码、会话续期和外部接入方式留待 PoC 后结合会话寿命与部署约束决策。
- 短信初始化不先访问帖子主文档，而是由原始帖子 URL 构造同源 `/login-required?redirect=...` 入口；这样避开 Scrapling 首次帖子导航对完整 `load` 的等待，两个候选仍在各自固定框架中运行，登录完成后继续使用原始帖子 ID 校验内容。目标 Linux 已证明登录主文档 HTTP 200 且 `DOMContentLoaded` 完成时控件可交互，但 Scrapling 的首次 `page.goto` 及随后稳定性检查仍各自固定等待 `load`；页面原生 `window.stop()` 不会释放 Playwright 已建立的生命周期等待。因此候选 A 只在短信入口的 `page_setup` 中把这两处等待映射为 `domcontentloaded`，候选 B 通过 Crawlee 原生 `gotoOptions.waitUntil` 使用同一条件。后台请求仍按资源类型报告，但不再阻塞原有页面动作；终端还必须输出登录控件就绪和发送按钮点击完成阶段，不能把脚本启动或页面到达当作短信已经请求。
- 目标 Linux 在已认证会话下再次证明 Candidate A 的普通帖子入口同样可能因页面后台资源而让 Scrapling 的 `page.goto(wait_until=load)` 满 90 秒；同轮 Candidate B 对相同3条样本全部取得帖子 ID 与内容证明。Candidate A 的登录确认和逐 URL 吞吐现统一在 Scrapling `page_setup` 中把首次导航及其固定稳定性 `load` 等待映射为 `domcontentloaded`，随后仍按原等待时间读取 DOM 并执行统一内容契约；这只调整导航完成条件，不更换 Scrapling 或放宽成功判定。
- 短信发送按钮点击完成不单独视为平台已经接受请求。两个候选均在点击前开始采集、点击后等待 5 秒，并以 `sms_send_evidence` 输出 XHR/fetch 的请求方法、响应状态和无查询参数路径，以及倒计时、附加验证和标准化可见警告；手机号、请求体、响应体和动态码不进入证据。只有结合网络响应和页面反馈，才能区分事件未触发、平台拒绝、附加验证与短信投递问题。
- 可视验证与短信码是两个不同阶段：检测到可视验证后，初始化状态必须进入 `manual_verification_waiting`，不得提前读取短信码；只有同时取得“可视验证已消失”和“发送控件倒计时可见”两个页面证据，才记录 `manual_verification_completed`、`sms_send_confirmed` 并进入短信码输入。等待十分钟仍未取得完整证据时，本次初始化按失败收口，不把 HTTP 200 或验证码组件消失单独解释为短信已发送。
- 资源过滤必须按场景分开：普通密码诊断与帖子吞吐可继续丢弃非必要图片以控制加载和资源占用；短信人工初始化必须放行 `image`/`imageset`，保证滑块背景、拼图和验证码素材可加载，同时仍可丢弃 `media`、`font` 等与验证无关的资源。目标 Linux 的 v0.2.11 已用 `[5202] 图片加载失败` 和页面 Logo 缺图证明短信入口沿用通用图片过滤会直接破坏可视验证。
- 当前开发电脑上的 PoC 输入、测试包和原始结果统一保存在 `artifacts/poc/`，分别使用 `inputs/`、`packages/` 和 `results/<candidate>/<round-id>/` 子目录，不允许散落到仓库其他路径。
- 采集任务采用异步任务语义：创建任务后返回批次或任务标识，再查询状态和结果，不让调用方同步等待完整采集过程。
- 内部接口采用 HTTP/JSON，只监听 `127.0.0.1`，版本化路径前缀为 `/internal/v1`。
- 内部接口不额外使用共享令牌，依赖回环地址、Linux 进程权限和现有后端的公网访问控制；接受同一主机其他进程可能调用接口的剩余风险。
- 内部接口的错误结构、幂等规则和调用追踪仍待确认。

## 技术选型前置门禁

提取功能服务的最终语言和采集框架不得在真实样本验证前直接确定。进入第一版正式功能开发前，必须使用同一批懂车帝真实 URL 对以下两个候选方案完成对比 PoC：

### 候选方案 A

- Python；
- FastAPI；
- Scrapling；
- 使用 Scrapling 的普通 HTTP 与标准动态页面采集能力完成对比验证。

### 候选方案 B

- Node.js；
- TypeScript；
- Fastify；
- Crawlee；
- Playwright；
- 使用 Crawlee 的 HTTP 与 Playwright 采集能力完成对比验证。

本轮不再把 `Scrapy + Playwright` 作为项目技术选型候选，但其仍可保留在通用技术调研中作为行业对照。

两个候选必须遵守相同的数据字段、输入 URL、访问条件、网络环境和结果判定规则。不得根据框架宣传、个人熟悉度或单个成功样本直接决定技术路线。

PoC 访问模式遵循“未登录优先”：

- 先使用未登录状态验证真实帖子内容访问和风控响应识别；
- 未登录状态能够达到当前采集框架 PoC 门槛时，不使用账号、Cookie 或登录会话；
- 只有未登录状态无法满足真实字段要求时，才由甲方提供合法登录会话；
- 同一对比轮次中两个候选必须使用相同访问模式；需要登录时必须使用同一授权条件；
- 测试轮次中途不得从未登录切换到登录后继续累计结果；访问模式变化后必须重新开始该轮测试；
- 凭证、Cookie 和会话状态不得进入前端、日志、示例文件或 Git。

确需登录时，内部验证版采用极简数据库凭证方案：

- 通过配置页面录入平台账号和密码；
- 账号和密码保存到提取功能服务拥有的本地数据库；
- 内部验证版只保存一套全局懂车帝账号，所有提取配置隐式共用；
- 不实现多账号表、账号选择、账号轮换或配置与账号的多对多关联；
- 为控制内部验证版成本，密码暂时明文持久化；
- 密码是只写字段，查询接口不得返回密码，只返回是否已经配置；
- 修改密码时覆盖原值，不支持读取或复制原密码；
- 密码、Cookie 和会话状态不得进入代码仓库、列表接口、日志、错误堆栈、导出文件或测试报告；
- 未登录模式可用时不配置账号密码；
- 登录失效时由用户更新密码或重新建立会话。
- 当前 PoC 命令行运行器从本地明文 `config.json` 读取固定测试账号；候选 A/B 使用同一配置但各自保存浏览器配置，按顺序运行，避免同一账号并行登录互相影响。

该方案是受控内部验证版明确接受的安全降级。正式公网版本集成前必须：

- 将平台密码和会话秘密改为加密持久化；
- 建立独立密钥管理和凭证访问权限；
- 确保内部验证版遗留明文凭证已加密迁移或安全清除；
- 完成日志脱敏、接口回显和数据库迁移测试。

相关决策见 `docs/adr/0002-plaintext-platform-credentials-for-internal-validation.md`。

PoC Linux 测试包决策见 `docs/adr/0003-package-poc-for-linux-before-formal-development.md`。
采集框架访问 PoC 与第一版功能验收的分层决策见 `docs/adr/0006-split-collector-access-poc-from-v1-functional-acceptance.md`。

平台风控结果门禁决策见 `docs/adr/0004-treat-platform-controls-as-poc-outcome-gate.md`。

甲方负责提供至少 2000 个不同的真实帖子 URL，作为吞吐门禁的输入池。两个候选在同一测试轮次必须使用相同的 2000 个 URL。已接收的 2694 个不同懂车帝帖子 URL 满足当前输入数量需求。

当前采集框架 PoC 使用 2000 个 URL 进行一小时目标吞吐测试，记录实际完成量、访问成功率、真实帖子内容证明完整率、风控事件和资源指标。该 PoC 只负责采集框架选型，不要求提前实现圈子列表、完整正文与主评论解析、数据库、前端或导出。

吞吐门禁必须连续执行三轮独立测试，三轮每轮都必须在一小时内有效完成 2000 个 URL；任何一轮未达标，该候选即未通过吞吐门禁。

需求中所称“必须绕过风控”在技术选型中按结果门禁执行，不作为独立技术名称或单独功能模块验收。限流、验证码、挑战页、登录失效或其他平台控制导致任一 URL 未在窗口内产生有效访问证明时，该轮失败；候选自动恢复并在同一窗口内产生通过校验的访问结果时可以计入完成。三轮通过只证明已记录的版本、样本、访问条件、网络和测试时间窗口内达标，条件实质变化后重新执行同等级验证。

甲方提供的吞吐 URL 均作为已知真实业务链接输入。每轮输入数量和有效完成数量均为 2000，要求 100% 最终完成率和零最终失败。单个 URL 只在平台返回的帖子标识与输入匹配，且至少获得标题或正文存在性证明之一，同时未将验证码、挑战页、登录页或异常空响应当作内容时，才计为有效完成。仅 HTTP 200 不构成通过证据。

完整正文、主评论、媒体 URL 和其他业务字段的提取在第一版正式功能开发与完工验收中执行，不作为当前采集框架 PoC 的前置输出要求。

导出采用数据库快照生成方式：采集结果先持久化，用户发起导出时按批次查询帖子、主评论和媒体 URL，再生成 XLSX。导出过程不得重新访问目标平台。具体数据库产品和 XLSX 生成依赖仍待最终技术栈确认。

历史批次不自动过期，仅在用户明确执行人工删除后清理。删除操作必须在同一事务中处理批次、帖子和主评论等关联数据，避免残留孤立记录。

用户可见批次编号采用 `YYYYMMDD-HHmmss-NNN`，使用 `Asia/Shanghai` 时区，时间精度为秒，同一秒内通过三位递增序号区分。数据库内部批次主键采用 UUIDv7，不直接使用批次编号作为主键。

任一候选未达到该门槛时不得被选为最终方案；两个候选都未达到时，不得选择“相对更快”的失败方案进入正式开发，而应扩大候选范围、调整采集架构或重新评估数据获取方式后再次执行 PoC。

PoC 完成并评审前：

- 功能服务语言保持未确认；
- Web 框架和采集框架保持未确认；
- 不创建绑定某一候选栈的正式业务工程；
- 可以创建隔离的验证原型，但原型不得被默认视为生产代码；
- 不将估算吞吐、短样本外推、排队数量、失败请求或测试窗口结束后的补跑写成达到每小时 2000 个链接。

PoC 通过后，应将最终选择、证据和被放弃方案记录到技术路线文档，并为最终语言与采集框架形成单独 ADR。

## 仍待评审

- 测试前端框架及工程组织；
- 候选方案 A 与候选方案 B 的对比 PoC 结果；
- 功能服务最终使用 Python 还是 Node.js，以及相应 Web 框架、接口规范和运行进程；
- 数据库与数据迁移方式；
- 定时任务和并发控制组件；
- 平台采集器代码契约；
- HTTP 请求、HTML 解析或浏览器自动化的适用边界；
- Linux 主机规格、语言运行时、浏览器系统依赖和可用的进程管理机制；
- 本机内部接口的进程级保护；
- 测试策略、构建方式和本机部署脚本。

具体框架和依赖版本应在懂车帝接口可行性验证、候选方案对比 PoC 和运行环境确认后形成后续决策，并与 `product-design.md` 的功能边界保持一致。
