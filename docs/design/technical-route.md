# ThreadSnap 技术路线

## 文档状态

状态：第一版前后端实现、Windows 联调、完整离线包封装和目标 Linux 安装验证已完成；连续三轮 2000 URL 的最终吞吐门禁仍待执行。新增舆情反馈已完成真实视频 URL、视频与图文模型 PoC，并已实现数据库、独立 Worker、运行时配置、列表/详情和人工修正闭环；生产环境真实模型调用与部署升级仍按单独验收执行。

- 本地运行、构建和部署方式。

## 已确认的系统边界

- 使用独立 Python 提取功能服务实现提取领域能力。
- 提取功能服务持续拥有每周计划节点、循环计划节点、自动提取规则、平台采集配置、圈子列表来源、提取批次、提取链接、持久化和任务调度。
- 第一版自建 Web 前端和一个独立提取后端；该后端同时提供面向前端的 `/api/v1` 和面向后续后端集成的 `/internal/v1`，两套控制器共用同一应用层和领域实现。
- 第一版前端只调用 `/api/v1`，不调用 `/internal/v1`，也不接触平台接口、采集器私有结构或认证数据。
- 正式版由现有前端调用现有后端，再由现有后端调用提取功能服务。
- 现有后端负责用户、角色、权限和公网访问；提取功能服务不绑定正式管理框架。
- 后续客户现有后端继续调用原提取后端的 `/internal/v1`；第一版前端及其 `/api/v1` 入口可以停用，采集、调度、Session、数据库和批次状态不迁移。
- 当前不考虑 Docker 部署；第一版按 ADR 0017、ADR 0018 使用目标特定的完整离线 `tar.gz`、systemd、Weston 无头 Wayland 和 Nginx。

第一版远程平台认证仍遵循内部验证边界：第一版前端只在受控内网开放，客户使用普通浏览器通过页面或弹窗操作服务器浏览器，不安装专用客户端。提取后端的 `/api/v1` 负责短期、一次性认证任务票据和画面/输入通道；浏览器进程、Profile、Session 和认证状态机由同一提取后端拥有。原始 CDP、VNC 或等价控制端口只监听回环地址或内部网络，不直接暴露给客户机。该入口不新增应用用户、角色或 MFA，安全边界仍由受控内网和部署权限承担。

第一版认证入口依据 ADR 0014 采用 Patchright 服务器浏览器、进程内 `CDPSession` 与短期 WebSocket 中继：后端用 `Page.startScreencast` 输出 `1280 × 800`、JPEG 质量 85 的连续变化帧，逐帧确认并保持单帧背压；指针移动、按下、释放、拖动和滚轮通过 CDP 输入域发送，文本、组合键和粘贴继续由受控浏览器输入接口完成。前端不取得原始 CDP 地址；用户保存时只检查 storage state 结构，再加密持久化 Session 并关闭，不判断页面登录状态，也不调用采集器验证圈子、帖子或字段端点。KasmVNC、noVNC、WebRTC 媒体栈不是第一版依赖。公网部署只作为后续可选增强：届时复用客户现有身份系统和后端权限，增加敏感操作重新认证、HTTPS/WSS 网关、来源校验、连接限额、审计和 WAF 或等价保护；这些能力不进入第一版默认实现与验收。
- 当前开发环境不是 Linux；日常编码、单元测试、访问冒烟和中等批量预筛以当前开发环境为准。
- 目标部署环境已确认为 CentOS Stream 10（Coughlan）、x86_64、glibc 2.39；Python 3.11+、浏览器系统依赖、systemd、Weston 与 Nginx 已进入离线封装，CPU 型号与核心数仍须在最终主机复核。CentOS Stream 10 已移除 Xorg/Xvfb，因此完整 Chromium 通过 Weston 无头 Wayland 运行。
- 候选方案在开发阶段必须使用同一台开发主机、相同网络出口和相同测试条件进行公平对比。
- 开发环境中的性能结果只用于预筛和调优，不能代替部署环境验收。阶段 3 的三轮 2000 URL/小时硬门禁必须直接在最终部署的 Linux 主机执行。
- 第一版后端技术栈已依据 ADR 0011 进入实现；Linux 依赖安装、浏览器运行时、路径行为、进程管理和三轮硬门禁保留为最终部署验收，暂不阻塞本次后端编码。
- ADR 0003 原规定的“正式功能开发前通过”顺序已由 ADR 0011 替代；其测试包、凭证隔离和证据规则继续有效。
- Linux PoC 测试包统一采用 `tar.gz`。包内包含候选原型、锁定的依赖描述、面向目标 Linux 架构生成的离线应用依赖、所需浏览器运行时、Linux 安装脚本、启动脚本、健康检查脚本、基准测试入口和简要说明。
- 测试包不得包含开发机的 `.venv`、`node_modules`、Windows 浏览器二进制、浏览器缓存、平台凭证、测试结果或其他机器相关状态。
- 为便于项目负责人直接复制，源码压缩包旁允许放置一个被 Git 忽略的本地操作目录，使用明文 `config.json` sidecar 和真实 `input-urls.txt`；部署脚本校验标准压缩包后再把 sidecar 复制到解压目录。sidecar 不属于标准测试包校验内容，也不得进入 Git、日志或结果回显。
- 不在 PoC 阶段制作 Docker 镜像、RPM/DEB 安装包或冻结为单文件可执行程序。Linux 端依据锁文件和离线依赖重新建立应用运行环境，以暴露真实的跨平台兼容问题。
- 依赖稳定性由锁文件、精确版本、SHA-256 清单和测试包版本共同保证；离线依赖用于避免测试时上游仓库变化或下载失败，不能替代版本锁定和目标平台兼容验证。
- Linux 测试机允许联网，但阶段 2.5 和阶段 3 不从公网解析或下载应用依赖及浏览器运行时。网络只用于目标平台访问、系统环境准备、诊断和重新生成测试包。
- Linux 发行版、CPU 架构和 libc 已形成初始环境基线；最终离线依赖包仍必须面向该 Linux 环境生成，不能复制 Windows 虚拟环境或依赖目录。语言运行时与浏览器系统库在打包前继续确认。
- 阶段 3 必须从测试包解压后的干净目录运行，不能直接使用开发工作区或人工修补后的目录。
- 最终 Linux 主机由项目负责人手动上传、校验、解压并运行测试脚本，Codex 不远程登录或自动操作该主机。
- 人工负责的是部署和命令触发；环境快照、测试计时、完成量、访问证明完整率、风控与错误事件和资源指标仍由测试脚本自动记录，不采用人工计数或手工修改结果。
- 目标 Linux 第一次运行时先执行 `test-connectivity.sh`：最多 3 条、并发 1，分层记录运行时/浏览器、DNS/TCP/TLS/HTTP、两个固定候选的登录和内容访问；只有汇总为 `ready_for_2000=true` 后才执行 2000 条吞吐入口。
- 短信初始化保存的两个 `profile_dir/storage-state.json` 是后续联通与吞吐进程的认证来源。联通入口为了避免测试过程改写主会话，会在每次运行前重建 `profiles/connectivity-candidate-*`，分别从候选自己的配置目录复制当前状态并保持 `0600`；不得只切换到空的隔离目录后重新走密码登录，也不得在源状态缺失时沿用旧副本。`prepare.log` 只记录每个候选是否复制成功，不输出状态内容。
- Linux 包把两个候选的浏览器统一安装到 `.runtime/browsers`；安装、健康检查、联通和吞吐入口都必须在启动候选前导出同一个 `PLAYWRIGHT_BROWSERS_PATH`，不能让运行入口回退到用户级 `~/.cache/ms-playwright`。
- 认证入口默认展示手机验证码登录；两个候选必须显式点击可见的“密码登录”，并等待账号、密码输入框可见后再填充提交，不按按钮位置或“最后一个按钮”推断登录模式。
- 登录后的验证判定只使用可见正文和可见短信码、验证码、滑块或验证容器；不能因 HTML 源码或脚本包含相关关键字直接判定。联通结果可保存脱敏截图、最终路径、查询参数名、标准化提示词和控件布尔值，但不保存完整 HTML、Cookie 值或凭证。
- 目标 Linux 的 v0.2.4 可见证据已确认：密码表单提交后页面明确提示“为保证账号安全，请使用手机验证码登录”，属于当前账号与服务器访问条件触发的二次手机验证，不是未切换密码登录。诊断结构必须单独记录该提示；候选 A 的登录入口与其吞吐请求一致丢弃图片、字体等非必要资源，避免这些资源阻塞 Scrapling 的页面 `load` 等待。
- 当前 PoC 为解决上述阶段门，只增加一次性人工认证初始化：候选 A/B 按顺序各自点击发送；出现可视验证时，由各自框架启动的原 Chromium 仅在 `127.0.0.1` 暴露独立 CDP 端口，项目负责人从 Windows 经 SSH 隧道打开 Chrome DevTools 完成人工验证；程序确认验证容器消失且发送控件进入倒计时后，才从 SSH 终端读取动态码、保存隔离的 `storage-state.json`，随后由新进程复用会话。CDP 入口不需要在服务器安装桌面或 VNC，完成初始化后随浏览器进程关闭；动态码、Cookie 和挑战数据不进入配置、日志、结果或持久状态。该做法不确定为正式项目方案；正式环境的验证码、会话续期和外部接入方式留待 PoC 后结合会话寿命与部署约束决策。
- 短信初始化不先访问帖子主文档，而是由原始帖子 URL 构造同源 `/login-required?redirect=...` 入口；这样避开 Scrapling 首次帖子导航对完整 `load` 的等待，两个候选仍在各自固定框架中运行，登录完成后继续使用原始帖子 ID 校验内容。目标 Linux 已证明登录主文档 HTTP 200 且 `DOMContentLoaded` 完成时控件可交互，但 Scrapling 的首次 `page.goto` 及随后稳定性检查仍各自固定等待 `load`；页面原生 `window.stop()` 不会释放 Playwright 已建立的生命周期等待。因此候选 A 只在短信入口的 `page_setup` 中把这两处等待映射为 `domcontentloaded`，候选 B 通过 Crawlee 原生 `gotoOptions.waitUntil` 使用同一条件。后台请求仍按资源类型报告，但不再阻塞原有页面动作；终端还必须输出登录控件就绪和发送按钮点击完成阶段，不能把脚本启动或页面到达当作短信已经请求。
- 目标 Linux 在已认证会话下再次证明 Candidate A 的普通帖子入口同样可能因页面后台资源而让 Scrapling 的 `page.goto(wait_until=load)` 满 90 秒；同轮 Candidate B 对相同3条样本全部取得帖子 ID 与内容证明。Candidate A 的登录确认和逐 URL 吞吐现统一在 Scrapling `page_setup` 中把首次导航及其固定稳定性 `load` 等待映射为 `domcontentloaded`，随后仍按原等待时间读取 DOM 并执行统一内容契约；这只调整导航完成条件，不更换 Scrapling 或放宽成功判定。
- 短信发送按钮点击完成不单独视为平台已经接受请求。两个候选均在点击前开始采集、点击后等待 5 秒，并以 `sms_send_evidence` 输出 XHR/fetch 的请求方法、响应状态和无查询参数路径，以及倒计时、附加验证和标准化可见警告；手机号、请求体、响应体和动态码不进入证据。只有结合网络响应和页面反馈，才能区分事件未触发、平台拒绝、附加验证与短信投递问题。
- 会话主动探测只以真实帖子证明判断现有资料是否可用，不再用 `storage-state.json` 修改时间代替服务端状态。目标 Linux 已确认约19.5小时未更新的 Candidate A 资料在并发1首条探测中取得文章 HTTP 200 空文档，随后同一旧浏览器资料打开登录入口也在 HTTP 200 后等待短信控件超时；这证明旧资料当前不可复用，但不单独区分自然过期和平台控制。短信重新初始化因此改为由两个固定框架分别创建不加载旧 Cookie、Local Storage、缓存或客户端资料的临时浏览器目录；登录及原始帖子证明成功后才在浏览器关闭后整体提升为候选主资料，任一步失败均保留旧资料并记录脱敏页面形态和失败阶段。
- 可视验证与短信码是两个不同阶段：检测到可视验证后，初始化状态必须进入 `manual_verification_waiting`，不得提前读取短信码；只有同时取得“可视验证已消失”和“发送控件倒计时可见”两个页面证据，才记录 `manual_verification_completed`、`sms_send_confirmed` 并进入短信码输入。等待十分钟仍未取得完整证据时，本次初始化按失败收口，不把 HTTP 200 或验证码组件消失单独解释为短信已发送。
- 资源过滤必须按场景分开：普通密码诊断与帖子吞吐可继续丢弃非必要图片以控制加载和资源占用；短信人工初始化必须放行 `image`/`imageset`，保证滑块背景、拼图和验证码素材可加载，同时仍可丢弃 `media`、`font` 等与验证无关的资源。目标 Linux 的 v0.2.11 已用 `[5202] 图片加载失败` 和页面 Logo 缺图证明短信入口沿用通用图片过滤会直接破坏可视验证。
- 当前开发电脑上的 PoC 输入、测试包和原始结果统一保存在 `artifacts/poc/`，分别使用 `inputs/`、`packages/` 和 `results/<candidate>/<round-id>/` 子目录，不允许散落到仓库其他路径。
- 采集任务采用异步任务语义：创建任务后返回批次或任务标识，再查询状态和结果，不让调用方同步等待完整采集过程。
- 第一版页面接口采用 HTTP/JSON，版本化路径前缀为 `/api/v1`；只通过受控内网前端入口发布，负责展示模型、输入文件和远程认证通道，不成为后续集成契约。
- 集成接口采用 HTTP/JSON，只监听或仅允许 `127.0.0.1`，版本化路径前缀为 `/internal/v1`；使用调用方无关的提取业务语义，不包含第一版页面组件或展示状态。
- `/api/v1` 和 `/internal/v1` 的控制器调用同一应用层；不得为了两套接口复制采集、调度、Session、持久化或状态机。
- `/internal/v1` 不额外使用共享令牌，依赖回环地址和 Linux 进程权限；后续接入时再叠加现有后端的访问控制。接受同一主机其他进程可能调用接口的剩余风险。
- 两套接口使用一致的稳定英文错误码；`message`、`details`、`reason` 和字段级错误均由后端生成中文，前端直接展示，不维护按错误码翻译的文案表。错误响应包含 `request_id`，批量校验可以一次返回多个工作表、单元格、行和字段错误，但不得返回堆栈、内部路径或凭证。
- 数据库时间统一按 UTC 写入；SQLite 读出的无时区 `datetime` 在 ORM 边界恢复为 UTC。`/api/v1` 与 `/internal/v1` 的 JSON 时间字段必须输出带 `Z` 或 `+00:00` 的 RFC 3339 字符串，前端统一使用 `Asia/Shanghai` 格式化，不能依赖后端服务器或浏览器本地时区推断。
- 手动创建提取必须携带一次性幂等键：`/api/v1` 由前端生成，`/internal/v1` 使用 `Idempotency-Key`。同一键和同一规范化请求返回原批次并附中文“该提取任务已提交”；同一键对应不同请求时返回中文冲突错误。定时批次使用“计划节点 + 计划时间”的稳定幂等键，并把全部规则 ID 与触发时版本写入请求哈希；同一节点同一计划时刻只创建一个合并批次。

## 已确认的第一版前端技术基线

- 第一版前端采用 React、TypeScript 和 Vite 单页应用，使用 shadcn/ui、Tailwind CSS、TanStack Router、TanStack Query、TanStack Table 与 Lucide 图标；动态交互使用 CSS/Tailwind 过渡和 Motion for React。前端只消费既有 `/api/v1`，不引入服务端渲染、第二个业务后端或前端自有业务数据库。
- UI 外壳以 MIT 许可的 `satnaing/shadcn-admin` 为上游基线，固定提交为 `e16c87f213a5ba5e45964e9b67c792105ec74d26`（上游版本 `2.2.1`）。`frontend/THIRD_PARTY_NOTICES.md` 记录仓库、提交、许可证和裁剪边界，`frontend/LICENSE` 保留许可证正文。采用选择性复用：保留应用外壳、主题 Token、Sidebar、Header、导航项状态、响应式 Sheet、表格、表单、弹层、反馈和可访问性基础；按 ThreadSnap 三个页面和真实 API 重组业务模块。
- “选择性复用”只裁剪示例登录、Clerk、示例用户、示例图表、假数据页面、RTL 专项和其他无关 SaaS 功能，不重写已选中的上游 UI 原语。Sidebar 的展开/收缩状态、键盘触发、状态持久化、宽度和位置过渡、图标与文字层级、移动窄窗 Sheet 行为作为必须保留的 UI 特性。
- 导航和基础控件优先沿用上游组件的状态模型与设计 Token；项目定制通过语义 Token、组件组合和业务层样式完成，避免在页面中散落覆盖上游内部选择器。上游组件确需修改时保留最小差异，并以组件测试和视觉证据覆盖展开、收缩、焦点、悬停、选中、禁用和减少动态效果状态。

## 已确认的受控舆情模型技术契约

- 云端模型按已探测能力使用独立输出适配。`qwen3.5-omni-plus-2026-03-15` 提交文字、全部图片 URL 和全部视频 URL，保持 `stream=true`、`response_format=json_object`、正文分块聚合和完整多模态合同。`deepseek-v4-flash` 只提交判定对象、标题和正文，固定关闭 thinking，并向 `/beta/chat/completions` 提交 `strict=true` 的单一强制函数；客户端只聚合该函数的流式 `arguments`，并要求 `finish_reason=tool_calls`。两条路径的合同关系违约都只允许一次包含原始输入、候选哈希和具体错误的干净纠正，不把错误候选作为 assistant 历史再次提交。
- 本地选项代码为 `paddlenlp-local-text-nano-v1`，使用 PaddlePaddle 3.3.1、PaddleNLP 3.0.0b4、`uie-senta-nano` 和 `utc-nano`。UIE-Senta 以已配置品牌/重点产品作为评价维度抽取观点与依据；UTC 先执行负面/非负面分类，只有负面结果再将依据映射到现有六类负面代码。后端保存两个模型的原生 JSON，以固定映射生成统一 Schema 和中文模板总结。该路径只读标题和正文，媒体统一记为 `not_requested`；不解析视频地址、不调用云端 API、不产生计费 Token。两个已加载 Taskflow 实例进程内复用，配置测试与后台 Worker 的模型加载和推理全部投递到同一条专用推理线程，避免 Paddle Predictor 跨创建线程复用；Taskflow 显式使用 2 个 CPU 数学线程，取代其按主机一半核心数扩张的默认值。该预算可由进程环境在 1～4 范围内受控覆盖；本地推理固定单路，云端并发由 1～64 的运行时配置独立控制。
- 三种选项都不引入业务多轮对话、Agent 框架、RAG、联网搜索或第二模型裁决；DeepSeek 的强制函数只承载结构化返回，不执行外部动作，也不允许模型自主选择工具。一次合同纠正只修复同一候选输出，不产生新的语义裁决。本地 Nano 不是通用大模型，对未配置别名、隐含指代和复杂语境的理解不等同于两个云端模型；DeepSeek 只取得文字语境，不具备本次千问路径的媒体证据。
- “原生视频模型”在本项目中专指一次请求直接接收完整视频 URL，并在同一模型调用中处理连续画面与音频；不以封面、抽帧、字幕或单独 ASR 代替完整视频输入。PoC 服从该模型官方当前输入时长、大小、格式和 URL 可访问性限制，不在 ThreadSnap 内截断、下载、中转、转码、抽帧或语音转写。
- 模型服务改为服务器持久化的“AI 舆情”配置，而不是只读环境变量：页面可保存 API Host/Base URL、API Key 替换值、受控模型代码、云端并发、目标品牌、重点产品和选填补充说明；业务是否分析由自动提取规则或手动批次决定，不在模型配置中全局启停。千问与 DeepSeek 使用同一窄客户端但各自保存独立加密 Base URL/API Key；接口顶层连接字段始终表示当前模型，并额外返回不含明文的 `model_connections` 供下拉切换恢复对应提供方连接状态。API Key 使用现有 Fernet 能力加密落库，读接口只返回 `api_key_configured`，任何日志、SSE、错误、导出或 Git 文件都不返回明文，也不把密钥持久化到浏览器。API Key 写请求只允许同源页面发起，并要求 HTTPS 或浏览器与后端均为回环地址；当前远程纯 HTTP `8088` 入口只读显示配置状态，凭证写入须经正式 HTTPS 或 SSH 本地端口转发。目标对象保存不可变版本；任务冻结对象、提示词和模型版本，执行时从当前已验证服务配置解密凭证，不把密钥复制进任务快照。
- 配置保存不触发模型调用；`POST /api/v1/sentiment/config/test` 在云端选项下使用该模型的生产输出协议发送最小文字请求：千问验证 JSON Object，DeepSeek 验证 Beta Strict Tool 的 Schema、强制函数和流式参数；本地选项加载 UIE-Senta 与 UTC 并分别执行一次最小本地推理。API Key、Base URL 或模型变化立即清除已验证状态并暂停要求 AI 的排队任务；当前配置测试成功后恢复模型就绪状态和这些暂停任务。测试失败保留配置并保持不可用。受控目录只包含 `qwen3.5-omni-plus-2026-03-15`、`deepseek-v4-flash` 和 `paddlenlp-local-text-nano-v1`，不接受自由模型名或本地 HTTP 模型地址；不增加余额查询或费用凭证。
- `GET /api/v1/sentiment/config` 返回 `revision`、`api_base_url`、`api_key_configured`、`model_code`、`available_models`、`model_connections`、`model_name`、`model_provider`、`model_input_mode`、`cloud_concurrency`、`cloud_concurrency_range`、`validation_status`、`validated_at` 和 `subject`；`subject` 只含 `brand`、`products`、`supplement`。`PUT /api/v1/sentiment/config` 接受相同可写字段和选填 `api_key`，省略密钥或 `cloud_concurrency` 分别表示保留现值，响应始终不含密钥；本地模型不要求 URL 或 Key，切换回云端时继续使用原有加密连接配置。写请求使用 `revision` 防止覆盖。对象字段实质变化才生成新的 `subject_version`，服务连接字段变化只更新服务配置修订并使验证失效；单独修改云端并发只更新配置修订，不使既有连接验证失效。
- Base URL 接受所选提供方官方端点或实现该受控模型生产输出协议的公网 HTTPS 代理。保存与请求前拒绝 URL 内嵌凭证、query、fragment、回环、私网、链路本地和云元数据地址，连接时校验 DNS 解析结果且不跟随跨主机重定向；透明代理 Fake-IP 模式下，域名解析结果允许 RFC 2544 的 `198.18.0.0/15`，但直接填写该网段 IP 仍拒绝，连接继续依赖 HTTPS 主机证书校验。千问代理必须支持 JSON Object；DeepSeek 代理必须支持 `/beta/chat/completions`、Strict Tool Schema、固定 `tool_choice` 和流式工具参数，连接测试失败时不降级为 JSON Object。页面按当前模型提示代理实际接收范围：千问包含帖子文字和媒体 URL，DeepSeek 只有判定对象与帖子文字。该兼容边界只保证请求协议，不假设代理提供统一余额、用量或价格接口。
- 提示词、分类代码、模型专属 Schema 和版本随代码发布，不建设在线编辑器。千问 `v4-clean-correction` 继续依赖 JSON Object 加本地完整合同；DeepSeek `deepseek-text-v5-strict-tool` 使用提供方 Strict Tool Schema 降低括号、层级、必填字段、类型、枚举与额外字段偏差，但真实 420 条批次已证明 Beta Strict 仍可能返回非法 JSON，因此它不是本地信任边界。新增受控模型时必须先做能力探测并增加独立 `output_mode` 适配，不能把某个提供方的 `json_schema`、JSON Object 或 Strict Tool 能力推定给其他模型；仍复用窄客户端和统一最终结果，不提前建设通用模型平台或新微服务。
- 提取帖子快照提交后，在同一 ThreadSnap 操作系统进程中创建持久舆情任务，由独立后台 Worker 消费 SQLite 队列。云端 Worker 的“同时分析任务数”由运行时配置控制，范围 1～64、默认 8；保存配置后增加所需槽位或暂停超出新值的槽位，已经发出的请求继续完成，后续领取立即服从新值。本地模型无论已保存云端值为何都只开放一个槽位。SQLite 只在短领取事务上用进程内锁串行化，外部模型请求并发执行，避免同一任务被重复领取。Worker 在领取事务内登记当前线程持有的分析 ID，任何未预期异常都记录堆栈并把任务写为 `ANALYSIS_INTERNAL_ERROR`；五秒看门狗只处理数据库仍为运行中但已无本进程线程持有的孤儿任务，首次自动恢复排队，重复失联转为失败。云端请求复用一个线程安全的 `httpx.Client`，连接池总连接与保活连接上限均为 64；429 继续由全部槽位共享冷却窗口。提取状态和分析状态分别持久化；分析调用、重试或服务暂停不占用平台采集 FIFO，不回滚帖子快照，也不要求新增 Redis、Celery、消息总线或第二应用进程。
- SQLite 连接保持 WAL，并设置 15 秒有界 `busy_timeout`。短写事务发生竞争时由驱动等待锁释放；等待达到边界后页面 API 返回 `503 DATABASE_BUSY` 和一秒后重试提示，不把锁竞争伪装成未知内部错误。
- 批次详情的帖子查询以 `run.summary_version` 参与 React Query 缓存键，并在批次运行期间每 3 秒查询；因此首次空响应会随新帖子入库失效。批次与帖子列表查询使用 20 秒前端读取超时，并分别呈现加载、失败和真实空结果；该超时只用于页面读取，不影响显式模型测试、提取创建等写操作。
- 结构化结果至少包含 `subject_relevance`、`matched_subjects`、`sentiment`、`primary_category`、`secondary_categories`，以及 `text`、`image`、`video_visual`、`video_audio` 的覆盖状态、预期/已处理数量、逐媒体输入索引或 URL 哈希、依据和失败原因。`subject_relevance=false` 规范化为 `unrelated` 且情感、分类为空；相关内容才允许 `negative` 或 `non_negative`，负面包含一个主要类型和去重的次要类型数组。音频优先区分有语音、静音、无语音、不可辨认和不可访问；提供方只明确返回通用 `processed` 时保留该真实状态并视为已处理，不从依据文本推断更具体音频类型。后端只执行 JSON、Schema、枚举、字段关系和模态覆盖校验，不通过关键词或业务常识重判模型结论。
- 千问云端模型输入、输入指纹、模态身份校验和详情媒体使用同一稳定媒体去重：忽略签名查询、已验证的懂车帝 CDN 路径签名和同一媒体的等价懂车帝 CDN 主机后，身份相同的多个 URL 只保留首个实际 URL，真实媒体路径不同的内容仍分别提交；数据库中的原始快照不改写。DeepSeek 与本地模型的输入指纹只包含标题和正文，媒体 URL 变化不影响文字结果复用。DeepSeek 严格工具参数只含 `subject_relevance`、`matched_subjects`、`sentiment`、`primary_category`、`secondary_categories`、`evidence` 和 `summary`；本地验证通过后，后端根据标题/正文是否存在填充文字状态，并依据未发送媒体这一确定事实补齐实际媒体数量和 `not_requested`，模型不再生成这些机械字段。DeepSeek JSON 语法失败时，固定版本 `json-repair` 生成通用候选，解析错误点附近另枚举有界单结构字符编辑；候选相对原参数只允许改变 JSON 标点、引号、转义符和空白，且必须唯一通过无重复字段、精确七字段、Pydantic、业务关系和输入身份校验。含视频的千问任务在付费请求前按快照 `video_id` 复用详情的两段直接 HTTP JSON 解析，取得当前临时播放 URL 后只替换本次请求输入；刷新失败只结束该帖任务，不把模型连接配置或整条队列误判为失效。千问提示词继续要求依据数组、零基连续媒体索引、无输入模态使用 `absent` 和受控状态枚举；单条依据字符串、错误索引或哈希、字段错层、Markdown 围栏及其他偏差均视为模型违约，不做语义归一化。
- 持久化同时保留每次失败候选的原始响应、最终严格通过的结构化结果，并记录提供方请求 ID、模型快照、提示词版本、舆情判定对象版本、输入指纹、开始/结束时间、耗时、Token/媒体用量、重试次数和稳定错误码。应用不依据可能变化的价格表计算或展示单次费用。日志只记录媒体 URL 哈希和脱敏主机信息，不记录签名查询、API Key、平台 Session、Cookie 或账号凭证。
- 分析状态包含 `analysis_queued`、`analysis_running`、`analysis_completed`、`analysis_partial`、`analysis_failed`、`analysis_paused` 和 `analysis_disabled`。千问多模态路径存在图片或视频时，任何必要媒体不可访问、不可辨认或未被模型处理都会形成 `analysis_partial`；DeepSeek 与本地路径的媒体为 `not_requested`，不影响文字结果形成 `analysis_completed`。部分和失败结果保留原始证据但不更新有效舆情结论；暂停表示批次要求 AI 但模型配置不可用、配置恢复后继续，禁用只表示该批次明确关闭 AI 且不会自动恢复。
- 批次 AI 开关只作用于该批次尚未创建的帖子任务，不取消其他批次已经发出的付费请求，也不回刷历史禁用帖子。401、403、模型不存在或本地模型运行异常等配置错误使要求 AI 的既有队列进入 `analysis_paused`，配置失效期间由开启 AI 的批次继续入库的新任务也直接记录为暂停；更正配置并测试成功后恢复原任务。关闭 AI 的批次始终记录 `analysis_disabled`，不因模型配置恢复而进入队列。
- 自动重试保持有界：网络错误、超时和 5xx 最多执行三次指数退避；DeepSeek 文字流逐块读取超时为 30 秒，并以 60 秒单次绝对总时限阻止持续心跳或碎片流无限延长一次请求；千问多模态逐块读取超时为 600 秒。HTTP 429 由全部云端分析槽位共享提供方 `Retry-After` 或默认 30 秒冷却，并且每条任务最多重试一次。流式响应缺少 `[DONE]`/结束原因或以 `length`/`max_tokens` 结束时，保存该次请求 ID、用量、耗时、原始响应和原因，延迟一秒后完整重请求一次；第二次仍异常则以 `MODEL_STREAM_INCOMPLETE` 失败。千问流正常结束但 JSON 或完整合同违约时，以 `MODEL_RESPONSE_ERROR` 保存候选与具体错误并干净纠正一次；DeepSeek JSON 语法违约先执行 ADR 0030 的唯一无损结构恢复，成功时保留原始坏参数和解析错误、标记 `locally_recovered` 且不增加模型调用；无唯一候选或本地业务关系违约时才在同一强制函数和原 Schema 下纠正一次。两者的合同纠正都只执行一次，不把失败任务永久重新排队；DeepSeek 当前生产路径不再执行 ADR 0027 的字段形状专用恢复。媒体覆盖按合同明确返回但处理不完整时保存部分结果，不触发合同纠正。401、403 或模型不存在暂停整个舆情队列等待配置修复；提供方内容策略拒绝直接记录并进入人工处理；超过官方输入限制记录部分结果。预算耗尽后持久化失败，不影响提取任务。
- 同帖身份使用 `(platform_code, platform_post_id)`。千问分析输入指纹由规范化标题、正文和稳定媒体标识形成并忽略签名 URL 的时效查询噪声；DeepSeek 与本地分析输入指纹只包含标题和正文。人工判定记忆只在身份相同且内容指纹未实质变化时继承。内容变化后重新分析，并保留旧人工结果作为参考。首版上线不为现有历史快照自动建任务。
- 无人工结果时，完整 AI 反馈的精确复用键为 `(platform_code, platform_post_id, analysis_input_hash, subject_version, prompt_version, model_snapshot)`；只有 `analysis_completed` 可以命中，新快照引用原分析结果而不复制原始响应。有效结论优先级为当前快照人工修正、有效继承的人工判定记忆、当前或精确复用的完整 AI 反馈；结论来源在同一结果单元格下显示，不增加独立列。
- 人工修订使用 `POST /api/v1/runs/{run_id}/posts/{post_id}/sentiment/manual-revisions` 追加 `set_result` 或 `restore_ai` 事件。`set_result` 接收 `negative`、`non_negative` 或 `unrelated`、分类和选填备注；`restore_ai` 只在存在完整可用 AI 反馈时成立。等待、运行和暂停状态拒绝修订，完成、部分、失败和禁用允许；同一帖子最新未撤销人工事件优先，原始响应和历史事件不可覆盖或删除。第一版不提供重新分析端点。
- 现有 `GET /api/v1/runs/{run_id}/posts` 增加 `sentiment_result` 与 `analysis_status` 两个独立筛选参数，并返回有效结果、来源和分析状态；现有帖子详情端点返回规范化中文展示段、模态覆盖、人工历史和媒体 URL。前端收到现有 SSE 资源变化信号后回查权威列表或详情，不把完整 AI 原始响应放入事件。
- 帖子详情继续使用现有 Sheet；人工修正使用挂载到 viewport 的 Radix Dialog Portal，关闭后恢复 Sheet 内原焦点和滚动位置。图片以 `loading="lazy"` 直接读取保存 URL。视频不直接绑定快照里的时效地址：含视频的详情组件挂载后自动调用 `POST /api/v1/runs/{run_id}/posts/{post_id}/media/resolve`，从数据库读取该快照保存的 `video_id`，使用与平台网页一致的 `common/token` 授权接口和 VOD `GetPlayInfo` 接口完成两次直接 HTTP JSON 请求；候选地址先按码率排序，同一清晰度优先选择已验证支持浏览器连续 Range 播放的 `BackupPlayUrl`，缺失时回退 `MainPlayUrl`。查询关闭窗口聚焦自动刷新和自动重试，组件卸载后立即释放前端缓存，重新打开详情会再次调用，后端短缓存负责合并有效期内的重复解析。该链路不导航原帖页面、不启动 Chromium，也不读取媒体正文。播放器请求返回的同源 `media/play/{index}` 地址，该 GET 只对刚缓存的 URL 响应 `307`、`Referrer-Policy: no-referrer` 和 `Cache-Control: no-store`，不读取媒体正文，浏览器再以 `preload="auto"` 直连媒体主机提前缓冲并启用行内播放，仍保持用户主动开始播放。端点不接受客户端媒体 URL，不改写快照，不下载或代理媒体；进程内按帖子串行解析并最多缓存 256 个结果，缓存不超过五分钟、签名到期前一分钟或四十五分钟上限。前端显示局部加载状态，失败时保留重试和原帖入口，成功后保留显式刷新入口。正常详情只显示中文结论、总结、分模态依据、模型和时间，不显示 SSE 分块、英文 JSON、单次 Token 或预估费用；原始响应与用量仍在后端留存审计。
- 首轮 PoC 的执行规范和事实结果分别为 `docs/research/sentiment-analysis-poc-plan.md` 与 `docs/research/sentiment-analysis-poc-results.md`。PoC 已完成 30 条视频 URL 获取与公开可达性验证、一次有声视频模型调用和一次图文模型调用；这些分母不外推模型成功率。正式功能仍不设置准确率、召回率、误判率、漏判上限或人工一致性门槛。

## 已确认的页面证据与关联截图成果技术契约

- 依据 ADR 0026，圈子列表的浏览器渲染、页面清单和原始分页证据成为截图覆盖范围内唯一的列表发现事实来源。Patchright 使用当前加密平台 Session、固定桌面视口、`zh-CN` 与 `Asia/Shanghai` 打开圈子任务冻结的精确来源 URL；同一 DOM 稳定点一次性取得帖子 ID、链接、来源顺序、卡片矩形与页面尺寸并写入清单，然后生成原始无损截图。汽车之家只监听该浏览器页面自身发出的同页官方列表响应，用其中的原始论坛归属、视频 ID 和删除标志补充详情校验字段，并要求其50项身份与最终 DOM 严格同序；它不另发列表请求，也不让响应替代 DOM 决定证据条目。现有 HTTP 详情接口继续负责正文、评论和媒体字段，不重新请求列表决定截图条目。
- 正式页面证据使用资源开启的 Patchright Chromium；后台列表不再保留 `DynamicSession` 兼容回退。捕获器逐段滚动触发懒加载，等待 `document.fonts.ready` 和卡片图片终态；最终测量前只回到平台原始页首并连续取得三次稳定布局，不注入隐藏滚动条、禁用动画/过渡、改变定位或其他会改变页面像素的 CSS，再读取卡片矩形和生成全页 PNG。只对实际入库候选卡片执行完整性门禁；图片正常加载或页面明确呈现平台占位才算终态，空白、浏览器破图、仍在请求或卡片数量/身份漂移均失败；广告和非帖子侧栏资源不进入分母。
- 一个页面捕获器在同一平台内串行工作。每冻结一个物理分页就把该页清单交给现有详情采集池；同页详情按平台内部并发分批执行并按冻结顺序提交，页面捕获通道可与其他圈子任务的详情请求重叠。平台并发为 1 时保持顺序执行，不另设截图并发配置或为每个圈子常驻 Chromium。列表请求、详情请求、即时重试和浏览器捕获共同服从平台容量门禁。
- 数据模型新增页面证据、页面条目、关联成果组、成果版本和成果分片。页面证据绑定 `circle_task_id + physical_page`，保存精确 URL、捕获时间、浏览器与适配器版本、视口/DPR、文档尺寸、清单版本、状态、错误、文件路径和 SHA-256；页面条目保存平台帖子 ID、来源位置、卡片矩形、可见内容指纹以及后续 `post_snapshot_id`。关联成果组使用独立稳定 ID 绑定原始关联链和冻结来源身份，不由某一个批次物理拥有；成果版本保存结果汇总版本、有效舆情版本、贡献批次、结果数、待判定数、负面数、状态和生成原因；成果分片保存顺序、尺寸、文件路径与哈希。
- 页面条目成为证据化帖子需要同时满足：同次清单存在卡片、原始证据完整、详情快照已入库且 `(platform_code, platform_post_id)` 一致。详情失败、跨页重复和未入库候选仍保留在原始证据与诊断清单中，但不进入最终卡片集合；补足目标时后续物理分页使用相同合同。功能迁移不扫描或补拍历史批次，新字段和表只作用于迁移后新任务；历史批次返回明确的 `not_collected` 能力状态。
- 原始截图写入 `data/screenshots/evidence/<run-id>/<circle-task-id>/`，先写同目录临时文件并原子重命名；数据库同时保存浏览器/适配器/清单版本、DPR、尺寸和逐文件哈希。原始文件和清单不可变；进程重启先校验原图与清单哈希并复用冻结候选，不重新访问同一历史页面。本地拼接失败可以复用证据重试；上下文结束后的新平台访问必须形成新的关联采集和证据记录。
- 最终渲染器只读取关联结果稳定顺序、被这些结果引用的完整原始页面证据和现有有效舆情结论。渲染器 `v5-autohome-full-card-frame-boundaries` 按证据首次出现顺序复制完整原始 PNG，保持原图宽高，不裁取、缩放、重排卡片或插入标题/溯源条；`negative` 只沿完整卡片框沿用既有 5 px 红框，其他结果不框；没有负面框的成果页直接复制来源 PNG，保证字节一致。既有像素边界恢复继续在原图卡片左右背景边界附近恢复可见卡片的上、下、左、右边界，用于校正旧证据因截图重排产生的渐进式坐标漂移；汽车之家 v10 清单曾只记录占主栏 96% 的 `li`，v5 只在派生成果中按当时 DOM 的左右各 2% 列表外边距恢复完整主栏框，原始证据和数据库清单保持不可变；边界证据不足时回退到数据库矩形。校正结果只进入新成果版本和 manifest 的 `source_rect`，原始证据在渲染前校验 SHA-256 且不被修改。成果清单 `v2` 为每张页面记录来源证据、来源批次、物理页码、捕获时间和原图哈希；卡片审计项继续记录来源批次和捕获时间。渲染器版本与证据适配器版本纳入输入哈希，像素规则变化时生成新的不可变版本而不复用旧图；不执行 OCR、截图模型调用或关键词重判。渲染使用项目显式固定的 Pillow 依赖，写入 `data/screenshots/artifacts/<group-id>/<version>/` 并记录逐文件 SHA-256。
- 成果状态至少包含 `evidence_pending`、`evidence_running`、`waiting_for_sentiment`、`rendering`、`ready`、`empty` 和 `failed`，与 `CircleTask.status` 和 `PostSnapshot.analysis_status` 分离。截图开启且 AI 开启时，只有当前关联结果全部证据化帖子存在有效结论才进入渲染，分析失败、部分或暂停保持等待；截图开启且 AI 关闭时不等待舆情，按无负面框原图生成，后续人工有效结论可以触发新版本。平台明确空列表产生 `empty` 零结果成果，错误导致零条进入 `failed`。证据完整而渲染失败允许本地重新生成，证据缺失没有原批次补拍端点。
- 关联成果组按原批次关联链和同一冻结来源身份聚合，复用当前跨补提去重与稳定来源位置。补提增加结果、删除贡献批次、人工修正或恢复 AI 都提升成果输入版本并排队生成新版本；短时间连续变化可以合并到最新输入版本。前端当前指针只指向最新版，旧版本文件、生成原因、数量和哈希保留审计；删除任一贡献批次先移除其证据和输入，再从剩余贡献生成新版本，最后一个贡献批次删除后在同一清理流程删除整个成果组及文件。
- 渲染器一次只解码并输出一张被引用的原始物理分页，不把多页拼接为超长图，也不在成果阶段切割原页。PoC 在 Windows 和目标 Linux 上测定最大原页像素高度、编码内存和前端解码边界；版本清单记录页面稳定顺序、原始尺寸、卡片范围、来源哈希和成果哈希。前端用连续查看器按需加载可见页面，不通过 Canvas 合并全部像素；下载端点流式生成一个包含清单和有序完整页面的成果包。单页和多页对业务都返回同一个逻辑成果 ID。
- 页面 API 使用 `GET /runs/{run_id}/screenshots` 返回成果组、当前版本与原始证据清单，使用受控的 `/page-evidence/{id}/image|download`、`/screenshot-groups/{id}/tiles/{index}|download` 读取文件，并以 `POST /screenshot-groups/{id}/rebuild` 执行本地重建；成果分片 URL 必须带版本号与文件 SHA-256，使长期 `immutable` 缓存只复用同一不可变文件，新版本自然换 URL。响应不暴露磁盘路径或静态目录。补提批次与原批次解析到同一成果组；批次详情增加“链接结果/页面截图”标签和接近全屏的分片查看器，不增加顶级导航。
- `data/screenshots/` 与批次数据同寿命，纳入 Linux 备份、恢复、磁盘空间和逐文件哈希校验。系统不设置独立保留天数或自动清理开关；删除路径按贡献批次和成果组引用关系精确清理，失败清理保留可诊断记录，不扫描或删除目录外文件。历史成果版本体积、当前证据体积和总占用通过只读摘要暴露。
- 实现与验收按 `docs/research/circle-screenshot-poc-plan.md` 先过真实来源、卡片完整性、关联补提、版本重绘和超长分片门禁，再进入正式迁移与页面交付。该功能涉及数据库迁移、平台浏览器、持久文件和备份，验证等级按红色高风险执行；目标 Linux 必须真实触发页面捕获、分片查看、备份恢复和回滚。

## 已确认的垂媒口碑巡检技术边界

- 当前懂车帝真实口碑适配器版本为 `dongchedi-reputation-v9-scrapling`，映射验证合同仍为 `dongchedi-reputation-mapping-v1`；v9只把差评率等普通HTTP请求执行切换到ADR 0054统一Scrapling传输层，页面身份、Patchright截图和指标合同不变。输入只接受 `https://www.dongchedi.com/auto/series/<id>` 或 `/auto/series/score/<id>-x-x-x-x-x` 且URL稳定车型ID必须等于映射平台ID；导航后的落地URL再次核对同一ID。页面车型名取可见车型标题或同级车评分卡当前行并与映射展示名规范化精确匹配；口碑分和业务排名取可见 `.rank-wrapper` 的当前车型行及其一基位置，明确暂无时两者同时为空；口碑量只取页面可见“共N人评价”。正式巡检从同一评分页 `__NEXT_DATA__.props.pageProps.reviewListData.total_count` 读取口碑评价篇数，并以同一平台车型ID作为 `series_id` 请求 `api.dcarapi.com/motor/car_score/api/v1/landing_page/get_detail/`，从 `tag_info_v2.hierarchical_tag_list` 的优点、缺点计数按半入规则形成整数差评率；接口调用只使用固定客户端版本标识，不要求用户配置第二套ID、登录凭证或动态设备指纹。未开售或零评价车型只有在页面四项均为空、`seriesHomeHead.total_score=0`、`total_review_count=0`，且差评率接口评价总数也为0时，才把五项判为平台暂无；否则评价篇数缺失仍触发解析错误。这一行为扩展不改变映射验证合同，因此既有映射验证保持有效。页面顶部 `No.N` 全站榜不进入业务排名合同。
- 映射验证使用共享加密Session启动有头Patchright Chromium，按平台当前内部并发运行；同一页面上下文冻结动画后连续三次比较车型身份、三项指标文字和指标DOM矩形，整页懒加载导致的文档总高度变化不作为指标合同漂移。通过后按稳定矩形直接截取单张不可变口碑指标区域PNG并记录SHA-256，不捕获或保存完整长截图；每次操作只对暂时性不稳定项自动追加一次完整页面尝试，后续人工重试只提交失败车型ID。

- 证据摘要由后端按批次冻结的全部车型平台执行项集合聚合，返回 `required_count`、可靠指标数、截图成功数和 `complete_logical_count`；所有计数按唯一车型平台执行项ID去重。普通日检、月末、首次初始化和新映射基线都把批次全部目标持久化为要求留证集合，不在查询时依据当前角色、指标变化或平台重算。平台分组使用相同聚合并返回处理中、失败、缺失原因分布；`not_available`按截图状态计数，`unknown`不进入可靠指标数。
- 证据包生成器读取批次冻结证据清单，将每项唯一的 `region.png` 字节按安全的 `platform_code/vehicle_id/region.png` 相对路径写入ZIP，不解码重编码图片；`manifest.json` 使用 `reputation-evidence-region-v1` 记录逻辑证据ID、映射快照、URL、时间、页面尺寸、截图矩形、截图尺寸、文件相对路径、SHA-256、状态和缺失原因，`SHA256SUMS` 覆盖包内全部实际文件。生成前校验路径不得逃逸、文件哈希与记录一致，缺失或不一致项写入清单并使证据包标记不完整，不写占位图片。产物键包含批次ID、关联证据版本和manifest版本，相同输入复用同一ZIP；下载接口与TXT、XLSX分离。

- 指标序列键包含内部车型ID、平台代码和经过验证的平台稳定车型身份，而不是映射版本ID或可变URL。批次创建时逐项比较当前与前日序列键：相同则允许继续执行既有指标、排名范围和数量语义比较；不同或前日不存在时保存 `new_mapping_baseline` 比较状态，跳过全部delta与颜色，并强制把该项加入指标区域截图队列。角色、展示名或URL变化但稳定身份相同不切断序列；缺少稳定平台ID时适配器版本化的规范页面身份必须明确证明连续，否则产生新序列。序列判断结果和两侧映射快照随批次冻结，不因后续验证或改绑重算。
- 关联结果解析以车型平台执行项为原子，查询或持久化选择键不允许按指标字段分别取来源。候选版本按 `success > partial_success > failed` 排序，同一状态按采集完成时间和稳定批次ID确定最新项；选中记录携带单一贡献批次ID、执行项ID和采集时间。补跑任务输入始终是尚无成功候选的完整车型平台项，并以本次执行重新产生的五项指标与口碑页面证据作为完整结果，不跨访问时点拼字段。数据库不建立跨尝试字段级合成表。下一日基线冻结保存所选执行项ID及其完整指标快照，后续选择变化不追溯重算。
- 口碑适配器对每次浏览器页面访问施加单项90秒上限，覆盖导航、关键资源终态、三次稳定测量和指标区域截图写入。只对明确分类为暂时性的网络、平台服务端错误或页面加载错误执行一次完整目标重试，最多2次尝试；确定性身份、映射、认证或页面合同错误直接形成对应状态。批次领取时保存实际开始时间和45分钟绝对截止时间；Worker每次领取和等待外部请求时检查剩余预算，截止后不再领项，取消未完成任务并把未终态执行项原子标记为 `timeout`，随后汇总批次和触发汇报。服务重启从持久化实际开始时间恢复同一截止点，不重新获得45分钟预算；延迟批次则从自身实际开始时间首次计算。上述值是后端版本化常量，不进入前端写模型。
- 正式口碑执行器及失败项补跑使用后端常量 `REPUTATION_RUN_CONCURRENCY = 2` 建立有界浏览器页面池，并在批次创建时把2写入 `concurrency` 快照；执行入口对修复前遗留或异常写入的非终态快照再次收敛为2，终态历史批次不改写。页面内稳定测量、截图和即时重试不嵌套领取许可。帖子提取继续使用平台 `internal_concurrency` 的1至8配置，两种业务并发不相互继承；映射验证不属于巡检批次，继续冻结平台并发。批次聚合按执行项ID和冻结顺序确定性提交，不依赖完成先后。当前性能验收统一为单平台27项全量留证15分钟目标，硬截止仍为45分钟。
- 平台容量调度在既有FIFO上增加一个只用于每日正式口碑批次的非抢占优先队列。容量令牌释放时先从已到达的正式口碑队列领取，再从普通FIFO领取；已经持有令牌的帖子任务运行到自身边界，正式口碑不撤销Future、关闭其页面或修改检查点。正式口碑队列清空或批次终态后，普通任务保持进入队列时的相对顺序继续。口碑失败项补跑和映射验证写入普通FIFO。队列优先级、等待开始时间和首次取得容量时间必须持久化或可由事件恢复，服务重启不得把已入队正式口碑降级或重复入队；此规则由ADR 0035作为ADR 0009严格FIFO的窄例外。
- 适配器识别共享Session失效或明确认证页时不执行普通暂时错误重试，当前项记为 `auth_required`，同平台尚未开始项快速收敛为相同原因；未来其他平台Worker不受影响。口碑批次不进入 `waiting_for_auth`，也不提供运行中取消用例。共享配置认证成功只更新平台Session，操作者显式调用既有“重新巡检失败项”后才创建关联补跑；原批次状态、证据和截止时间不恢复。
- 排名记录除整数值外保存原始排名文字和范围身份；比较键包含内部车型ID、平台代码和排名范围身份。范围身份变化返回 `not_comparable` 及前后范围原文，不计算数值delta；重点车型在该状态下仍排队生成页面证据，汇报生成器把它归入排名口径变化而不是改善或下降。
- 指标表同时保存平台原始显示文字、单位和Decimal规范值；解析器使用显式十进制定标与单位换算，不通过float比较。变化计算读取批次冻结的当前与基线规范值，并保留两侧原文；规范值相同则无变化。隐藏接口字段不进入比较合同，除非未来以新适配器版本和独立证据口径明确替代。
- 口碑量解析器输出原始文字、原始单位、显示小数位、`Decimal`条数规范值及 `exact | rounded | lower_bound` 数量语义；千位分隔符只影响格式，万和亿分别显式乘以 `10000` 与 `100000000`，带加号或“以上”只产生下限语义而不伪造精确值。适配器必须用测试夹具列出平台实际支持的单位和下限文案，未识别单位进入 `unknown`。比较键要求前后语义相同；不同时返回 `not_comparable` 和两侧原文，汇报生成器归入展示口径变化；证据队列始终覆盖批次全部执行项，不再由指标变化决定。
- 口碑巡检XLSX由独立固定布局生成器读取批次冻结指标、变化方向和已持久化指标区域证据生成；平台分组按批次冻结平台范围确定，文件键包含批次或关联结果版本及布局版本并保存SHA-256。生成、下载与清理可以复用现有文件基础设施，但不读取帖子导出模板版本或标签注册表，也不在导出时访问平台。
- 汇报生成器先从终态冻结输入产生结构化汇报快照，再由同一快照渲染页面正文、复制文本和UTF-8 TXT字节，三者不得分别拼装业务内容。TXT文件键包含批次或关联结果版本、汇报版本和渲染版本，保存内容SHA-256并复用相同输入产物；文件名按已清理的巡检日期、普通或月末类型和批次编号生成。XLSX由独立布局生成器提供，指标区域截图继续走证据文件接口；当前不加载DOCX、PDF、HTML渲染器或汇报ZIP打包流程。
- 结构化汇报快照按批次冻结平台顺序生成不可省略的平台章节，并把章节结果显式归一为 `changed | no_change | not_comparable`：有正常变化即为 `changed`，至少存在可比较结果且没有变化即为 `no_change`，没有任何可比较结果即为 `not_comparable`。异常与缺失作为章节内独立集合保存，不被章节状态吞并；混合变化、无变化和异常时分别渲染。只有全部章节均为 `no_change` 且异常集合全空时才设置全局无变化标志，`not_comparable` 或任何异常都禁止生成全局“今日无口碑指标变化”。
- 派生产物记录分别保存 `queued | generating | success | failed`、输入哈希、生成器版本、尝试次数、文件记录ID和稳定错误码；正文快照、TXT、XLSX及证据ZIP互不以彼此成功为事务前提。生成任务对暂时文件错误最多自动重试1次，仍失败后由幂等“重新生成失败产物”用例仅领取失败类型；相同输入哈希和生成器版本命中已有成功记录时直接返回。生成器版本变化时追加新派生版本，旧成功文件和哈希继续可下载；文件先写同目录临时路径并校验后原子发布。派生任务不调用平台适配器，晚到补跑不改变已绑定输入版本或自动排队重建。
- 派生产物类型在数据库中保存唯一 `published_artifact_id`。同类型首个成功事务仅在该指针为空时原子设置；后续不同生成器版本追加 `rebuilt` 记录但不修改指针，并保存生成时间、输入版本、生成器版本、原因和SHA-256。默认下载端点解析发布指针，版本下载端点要求显式artifact ID；当前没有切换发布指针的写接口。首次成功前的失败尝试不占发布版，相同输入哈希与生成器版本的重试通过唯一键复用记录。汇报正文快照ID独立于文件版本，复制与页面渲染不读取“最新文件”。
- XLSX每个车型行的备注列只锚定一张图片。单平台直接使用指标区域图；多平台时生成器按冻结平台顺序把1至3张指标区域图横向缩放排版为单张预览图，记录引用证据ID与SHA-256后锚定到该备注单元格，避免多张浮动图片在不同表格软件中重叠。预览图是导出派生物，不写回证据表或改变逻辑证据数量。
- 口碑巡检删除以每日正式批次关联链为边界并使用持久化删除作业。作业先在数据库中冻结关联链、生成带路径和SHA-256的不可变文件清单并进入 `deleting`，再把文件逐项原子移动到同一文件系统的作业隔离目录；移动过程记录检查点且可幂等重放。任一移动失败时按清单逆序恢复已隔离文件，领域数据保持不变，作业进入 `delete_failed`；恢复也必须校验路径、哈希和目标不存在冲突，异常保持显式状态而不继续数据库删除。
- 文件全部隔离并通过清单校验后，单个数据库事务级联删除补跑批次、指标、证据、汇报、预览图和XLSX记录，同时为被后续冻结基线引用的来源写入唯一墓碑。事务失败时恢复隔离文件；事务提交后逻辑删除成立，后续批次已经持久化的基线快照与派生结果不重算。提交后的隔离目录清理是独立幂等步骤，失败进入 `storage_cleanup_pending` 并重试，只影响磁盘回收状态，不恢复业务记录。删除接口按作业幂等键返回既有作业，前端分别展示删除中、删除失败和存储清理待重试。
- 墓碑表对“巡检日期 + 普通或月末计划类型”保持与正式批次相同的唯一性，并保存原调度幂等键；调度查建必须同时检查活动批次和墓碑，命中任一即视为该日期计划事件已经消费，不因删除而重建。关联基线查询排除墓碑的已删除指标：下一批次尚未冻结时返回无前日基线，已经冻结的批次继续读取自身基线快照和来源墓碑标识。墓碑不持有可用于恢复的指标或文件地址。
- 口碑巡检范围使用草稿与已发布版本分离的单当前指针，并持久化每次版本生效时间与被替代时间。映射验证只更新草稿验证状态；发布端点在单一事务中复核当前平台全部启用车型映射、草稿revision和预期分母，再创建不可变版本并原子切换当前指针。每日调度按计划时间10:00查询发布历史并冻结该时点生效版本，而不是读取任务实际开始时的当前指针；计划时点无有效版本时只写调度错误，不创建空批次。
- 一次性口碑范围初始化命令接收UTF-8 CSV文件路径，只允许在不存在口碑车型、范围草稿或已发布版本的全新业务状态执行。解析器接受可选UTF-8 BOM，要求固定表头 `schema_version,seed_key,series_name,vehicle_name,role,role_order,platform_code,platform_vehicle_id,platform_url,platform_display_name`，同一文件所有行Schema版本一致，并按标准CSV引号规则读取中文、逗号和URL；不引入XLSX解析依赖。解析后先在内存中校验恰好27款、重点14款、竞品13款、`role`枚举、稳定初始化键和当前平台车型ID唯一、两组顺序分别从1连续无重复，以及必填URL和展示字段完整；任一错误拒绝整份输入且不写部分数据。通过后在单一数据库事务中创建不可变内部车型ID、服务端草稿、组内顺序和未验证平台映射，并保存输入Schema版本、原始文件字节SHA-256、导入时间和计数摘要，不把原CSV字节写入数据库。同一SHA重复执行幂等返回既有初始化记录，已有不同初始化状态时拒绝覆盖；命令不访问平台、不运行OCR、不把导入映射标为已验证，也不暴露长期文件上传接口。仓库只保留空CSV模板、Schema和校验规则，实际填充路径由操作者显式传入。
- 单平台映射批量粘贴端点接收草稿revision、平台代码和一至当前范围分母行的四列结构化数据，只以内部车型ID关联草稿车型。预览阶段规范化URL并检查平台已接入、行列完整、内部车型ID存在且不重复、平台车型ID在该平台内不重复、URL格式与平台适配器静态规则有效，并返回新增、修改、错误和未包含车型集合；保存请求携带预览revision与输入哈希，事务内复核无漂移后全量写入本次行集并递增草稿revision，任一错误不写部分行，未提交车型不改变。可选“保存并验证”在保存事务成功后只为实际变化项创建独立验证任务，按保存时平台内部并发快照执行；验证成功和失败逐项落库，失败不撤销草稿映射。该端点不接受多平台混合输入、不按展示名称猜测身份，也不调用发布端点。
- 范围草稿为每个车型保存角色和角色内稠密顺序，排序命令提交草稿revision、角色、完整有序车型ID列表并在事务中校验无缺失、重复、跨草稿ID或筛选子集；服务端重写该组顺序并递增revision。角色切换事务把车型追加到目标组末尾。排序和角色变更保留既有映射验证记录，发布版本复制不可变角色序与车型序；前端拖拽与键盘按钮调用同一命令，搜索或筛选激活时不提交排序。车型永久删除用例要求不存在批次、发布版本或其他引用，否则只写停用状态。
- 前端范围编辑器区分 `local_dirty`、`saving_or_validating` 和“服务端已保存未发布”三类状态。路由拦截器只在前两类状态生效：本地脏状态的站内离开弹出保存、放弃或返回编辑选择，浏览器卸载使用 `beforeunload`；进行中请求在取得明确成功或失败结果前不执行离开。成功草稿写入返回新revision并清除对应本地脏字段，失败则保留本地值和中文错误。发布入口要求无本地脏状态、无进行中请求，并以最新保存revision重新请求预览；离开保护、草稿保存和映射验证都不得调用发布端点。
- 发布预览端点以草稿revision和当前已发布版本计算新增、停用、角色变化、映射变化、预计车型平台分母、新序列执行项数量和下一计划生效时间；发布请求必须携带预览revision，事务内重新计算不一致时返回冲突而不切换指针。发布提交时间与调度冻结事务形成确定顺序：冻结事务读取到的新版本才进入当天批次，批次创建后提交的版本只供下一计划时点查询。响应返回版本ID、提交时间和下次生效时间，前端不自行根据本地时钟猜测；延迟调度仍按计划时间查询发布历史。
- 当前不存在已发布范围版本时，发布预览额外返回 `initial_publish=true`、27项有序全量复核行、角色分母、当前平台映射分母、每项验证内容哈希、验证时间和验证证据ID，以及名称差异或验证绑定失效等警示。首发事务除复核普通revision外，还要求恰好27款、角色分母为14和13、当前平台27项验证记录均绑定事务内当前映射内容、没有进行中验证，并要求请求显式携带未默认选中的 `initial_review_acknowledged=true`；任一条件变化返回冲突并要求重新预览。前端本地脏状态先按既定保存门禁收口，服务端以revision和内容哈希防止未预览数据发布。该确认只记录首发操作者动作和时间，不引入第二审批人、电子签名或新的权限模型。
- 映射验证使用单一受控浏览器页面上下文：先验证规范化URL、平台车型身份和非错误页面，再读取指标数值或平台明确暂无原文；资源终态后禁用动画并连续三次测量车型身份、指标文字与DOM矩形，三次一致才按同一矩形直接捕获指标区域图。验证记录保存适配器版本、原始文字、视口、文档尺寸、矩形、截图尺寸和文件SHA-256；任一门禁失败都保持草稿未验证并返回中文分阶段原因。
- 验证记录保存映射内容哈希和独立 `mapping_validation_contract_version`，内容哈希覆盖内部车型ID、平台代码、平台车型ID、规范化URL和平台展示名。草稿任一覆盖字段变化或合同版本提升时原子清除当前有效验证指针，但保留历史验证与证据；角色、组内顺序、共享Session和普通适配器实现版本变化不清除。验证时间只展示，不参与有效性计算。对仍绑定当前内容的已验证映射再次验证时，网络超时、`auth_required` 或其他未能证明身份变化的失败只追加尝试记录，不撤销当前有效指针；页面不存在、跨车型跳转或稳定身份不一致等确定性身份失败则清除指针、写入“映射待修复”并使未来执行项快速失败。发布事务只接受当前内容哈希和合同版本均匹配的有效验证指针。
- 映射验证运行与口碑巡检批次分表建模：运行冻结平台代码、目标映射内容哈希集合和平台内部并发快照，每个目标拥有递增尝试号及 `queued | running | success | failed` 终态。网络错误或页面超时分类为暂时错误并在同一用户操作内最多自动追加1次完整页面尝试；`auth_required`、确定性身份错误、指标合同失败和证据门禁失败不自动重试。自动或人工尝试都必须从页面访问起点重新执行身份、指标和证据三门禁，只以单次尝试全门禁成功更新有效验证指针，不跨尝试拼接。批量“重试失败项”按上一运行终态选择失败目标并创建新验证运行，成功目标不入队；单行重验只创建一个目标。身份错误目标要求草稿内容哈希已经变化，否则端点返回“请先修复映射”；认证错误允许Session更新后保持同一内容哈希重试。尝试历史和文件不可变保留，验证运行不写巡检调度幂等键、不生成口碑汇报，也不切换已发布范围。
- 口碑巡检调度器在启动和日内恢复检查时对账当日10:00计划事件。若事件因服务不可用从未执行、当前仍是同一北京时间自然日且不存在当日正式批次，则以“巡检日期 + 普通或月末计划类型”的唯一幂等键创建延迟巡检批次；唯一约束与事务内查建保证重复启动、并发检查和任务投递重试都复用同一批次。延迟创建必须按计划时间查询范围发布历史并冻结10:00生效版本，恢复前新发布版本不进入当日批次；10:00无有效范围时记录配置错误，不因恢复时已有版本而补建。跨日恢复只写漏触发事件，不创建历史批次或访问平台；下一批次按既有严格前日基线合同处理缺失。已经执行但因无已发布范围等配置门禁而未建批次的计划事件不得被恢复检查改判为服务漏触发。延迟批次终态后触发汇报生成，并持久化计划时间、实际创建时间、实际汇报时间和冻结范围版本。

## 已确认的调度、队列与状态技术契约

- 只保留一个全局调度协调器，按 `Asia/Shanghai` 加载每周计划节点与循环计划节点。每周节点保存星期、单一 `HH:mm:ss`、启用状态和规则引用；循环节点保存星期、同日开始/结束 `HH:mm:ss`、1 到 1440 的正整数分钟间隔、启用状态和规则引用，开始必须早于结束。循环触发点按“开始 + n × 间隔”展开且不超过结束，开始始终触发，结束仅在恰好命中时触发。触发时逐规则以圈子集合与平台启用、圈子验证及全局自动资格求交集，再把结果按圈子 ID 合并；重复圈子采用各规则目标数最大值，两个开关分别按任一贡献规则开启即开启。每个节点的实际触发点最多创建一个顶层计划批次；每周节点写入 `scheduled`，循环节点写入独立 `recurring` 触发类型。两类节点同秒时分别创建批次并按每周、循环的稳定顺序进入平台 FIFO，不并发占用同一平台。前端以 `/runs` 展示手动和定时批次，以 `/recurring-runs` 只展示循环批次；两个侧边栏入口及对应详情路由复用同一列表和详情组件。没有可运行圈子时不建空批次，只持久化中文调度事件；帖子提取两类节点停机错过后都不补跑，独立口碑巡检固定日程按上一节的“同日补触发、跨日记漏触发”合同执行。
- 页面与集成 API、调度器和测试夹具统一使用版本化自动提取规则与两类计划节点；既有 `schedule_nodes` 通过 `node_type` 区分 `weekly` 与 `recurring`，循环节点另存结束时刻和间隔分钟，节点—规则关联、批次与调度事件外键保持不变。API 在同一 `/extraction-plan` 合同中分别返回 `nodes` 和 `recurring_nodes`，共享全局 revision 与单事务保存。调度器以相邻轮询窗口判断到期秒、按节点与计划时刻持久化去重，停机期间不补跑。
- 每周计划与循环计划编辑器复用官方 shadcn/ui `Input`、`Command`、`Popover`、`Button`、`Badge`、`Card` 和 `Alert`：星期使用同一组可多选圆形按钮，时间使用 24 小时制并显示秒的受控输入，循环计划额外使用带可见标签的开始、结束与数字间隔输入；两类节点使用相同的规则多选器、dirty 状态、保存与空状态结构。规则区按平台使用一级可折叠面板，平台内再按 `latest_reply` 和 `latest_publish` 使用二级可折叠面板，两级都提供范围全选和已选数量，最内层只把全局启用来源排入紧凑的两列满宽网格，不再逐车型建立纵向分组或重复展示列表顺序、验证与启用状态。规则区与节点区复用统一卡片或表格原语，不引入另一套日期时间组件视觉。
- 提取计划保存时把每个启用节点展开为全部 `(node_type, weekday, HH:mm:ss)` 实际触发键并在同一事务中检查类型内唯一；任一键由多个同类型节点命中时整份计划零写入，一次返回计划类型、全部冲突节点、星期和时刻。每周与循环节点的类型键不同，允许同秒保存并各自使用“节点 + 计划时刻”幂等键创建独立批次。仅循环时间段重叠但实际触发序列不相交不算冲突。停用节点不参与冲突集合，但启用操作必须重新运行全量校验。服务端使用配置修订号防止并发编辑覆盖；调度加载时复算同类型触发键，异常同类型持久数据逐节点记录 `blocked` 事件且不创建其中任一批次，跨类型同秒节点按稳定类型顺序继续触发。
- 配置 API 按唯一 owner 切分写模型：提取计划端点原子保存规则及节点；平台配置端点只写接入允许的运行参数、启用状态和 Session 操作；来源与圈子端点只写来源名称、规范化来源、验证和自动参与资格。跨区域仅返回必要 ID 和只读摘要，不接受重复字段，避免客户端通过不同端点产生最后写入覆盖。
- 圈子记录使用不可回退的首次验证时间区分初次验证与重新验证。配置圈子首次验证成功时 Worker 在同一事务中写入首次验证时间并开启全局自动参与；后续重新验证只更新最近验证结果，保持 `auto_enabled` 当前值。批量验证端点只为全部 `unverified` 配置圈子创建或复用持久验证任务，Worker 继续按现有单任务 FIFO 处理，前端按任务 ID 回查聚合进度。三平台后台来源验证和帖子提取统一声明为 `direct_http`：懂车帝与汽车之家复用加密登录 Session 发起直连请求；易车按公开 PC v311 协议为每个请求即时生成签名，详情页只严格解析当前203 Cookie挑战且最多重试一次。后台直连不回退浏览器，响应不完整或协议变化直接失败关闭；完整 Chromium 只用于共享认证状态机的人工登录或有界Session刷新，以及用户明确开启且平台支持的页面证据。
- 自动提取规则请求中的圈子 ID 必须属于配置圈子且所属平台已接入；平台数量键必须与所选圈子涉及的平台集合完全一致，并逐平台使用对应安全最小值与最大值校验。暂未接入平台保留只读展示但禁止选择。规则只额外接受布尔型 AI 分析和圈子页面截图开关；平台内部并发、启用、Session、重试预算、评论上限、发现顺序和时间不进入规则请求模型，后端对额外字段按严格契约拒绝而不静默保存。
- 平台适配器从未接入切换为已接入后，平台记录保持停用，既有规则不自动选择该平台；平台启用命令不再要求全部规则补齐该平台数量。只有规则实际选择该平台圈子时才保存数量，取消最后一个圈子时移除数量。
- 调度触发再次逐条执行所选规则的范围与数量完整性门禁；任一规则已选且当前可执行的平台缺少数量时不创建顶层批次或部分平台子任务，只持久化包含节点、全部规则版本和缺失平台代码的中文配置事件。全局停用、未验证或平台停用的已选圈子不创建子任务；合并后全部不可执行时记录跳过事件且不建空批次。
- 自动提取规则使用稳定逻辑 ID 和单调递增的不可变版本。名称以外的范围、数量、AI 分析开关或圈子页面截图开关变化时，更新在事务中新增版本并切换该逻辑规则的当前版本指针；计划节点只保存逻辑规则 ID 集合，调度触发在同一批次创建事务中解析并冻结全部确切规则版本。存在任意启用或停用节点引用时，归档和删除返回稳定冲突错误及引用节点摘要；无引用且从未进入批次快照的规则允许物理删除，已有批次快照的规则只切换为已归档状态并可恢复，不级联修改历史快照。
- 顶层批次持久化平台与圈子子任务。定时创建时通过批次规则关联冻结全部自动提取规则 ID 与版本，通过配置快照保存规则名称、圈子范围、各平台数量、两个输出开关和解析后的圈子来源映射；重复圈子只创建一个子任务并使用来源规则中的最大目标数，两个开关分别按贡献规则并集合并后写入任务快照。配置后续修改、停用或删除不改变队列中的执行快照。来源名称是例外的可变展示属性：API 和之后生成的导出通过稳定 `circle_id` 批量读取当前名称，来源删除后才回退任务中的名称快照，避免改写历史任务并防止列表逐行查询。执行时安全上限已经降低的，后端按新上限收敛并保存中文说明。
- 每个平台维护独立的严格 FIFO，手动、定时和手动补提共用同一排队规则，不允许插队。第一版后端平台级并发固定为 1；后续全部平台接入并完成组合容量验证后，再以服务端配置确定可同时运行的平台数、各平台安全上限和全局资源预算，客户前端不控制平台级并发。
- 平台内部并发是该平台全部圈子、帖子请求和自动重试共享的总信号量，不是单圈并发。依据 ADR 0057，汽车之家固定为1；懂车帝与易车继续发布1～8的可配置范围。依据 ADR 0054，三平台采集器均以线程局部 Scrapling `FetcherSession` 配合共享有界信号量执行，跨来源并行和来源内详情并行共同占用该上限。统一传输层按目标URL选择浏览器 storage state Cookie、保留服务端 Set-Cookie，并把 Scrapling Response 收敛到平台适配器既有最小合同；框架每次只请求一次，适配器即时重试和Worker持久退避不叠加隐藏重试。前端使用后端发布的范围限制输入；后端对绕过前端或旧快照中的越界值收敛到当前范围。配置保存后只影响新批次，既有批次继续使用创建时冻结并经当前上限收敛的快照。
- `direct_http` 表示默认数据通道使用普通HTTP，不表示绕过Scrapling；依据ADR 0055，适配器已明确分类为验证码或访问验证后，可以升级到一次按需Stealthy导航。依据ADR 0058，易车只为TencentCaptcha/WAF执行该一次有界导航；复访仍受控时保留`PLATFORM_CAPTCHA_REQUIRED`或`PLATFORM_CHALLENGE`并进入持久恢复，不把Stealthy页面HTTP 200当作业务恢复。ThreadSnap继续拥有数据库批次、平台FIFO、固定候选、检查点、认证等待、限流冷却和结果提交；Scrapling拥有普通HTTP Session、TLS/请求头模拟、Cookie注入、请求执行和响应对象，不使用Spider的进程内队列复制持久领域调度。正式`src/threadsnap`不直接导入`curl_cffi`，但离线依赖仍显式锁定Scrapling所用的curl-cffi传输引擎。Patchright继续负责人工认证、Session刷新和明确开启的页面/口碑像素证据。
- Scrapling传输池现以不持久化的执行作用域键隔离资源，单用户默认键为`single-user + platform + default`；进程级浏览器预算默认只放行一个短生命周期Stealthy浏览器，容量许可不携带Cookie或账号状态。导航HTTP 200不直接表示恢复，原业务请求通过平台分类器后才确认该代次。该接口为后续多客户资源配额和外部协调预留稳定边界，但当前不新增租户、权限、数据隔离、数据库迁移或第二套调度器。
- 队列、配置快照、固定候选清单、圈子检查点、网络重试状态和认证等待状态必须持久化。服务启动时恢复已入队任务，不重新创建批次。平台认证只阻塞该平台 FIFO：原任务进入 `waiting_for_auth` 并释放 Worker，后续同平台任务继续排队，其他平台继续运行；认证通过后原任务先恢复。网络重试任务保持当前批次的平台队首，退避等待期间不领取后续同平台批次；同批次其他来源仍可服从内部并发继续，其他平台也不受影响。
- 批次状态机使用 `queued`、`running`、`waiting_for_auth`、`success`、`partial_success`、`failed`。圈子任务在详情访问前按来源顺序冻结前 N 个去重候选身份、规范 URL 和来源位置；瞬时网络错误按2秒起、最高60秒的持久退避重试同一来源或候选 URL，不向后发现替代帖子，不产生失败数或终态。URL清单任务每次领取时以任务已持久化的`PostSnapshot.platform_post_id`过滤原冻结URL，只把未完成URL交给适配器；首次没有显式`source_indexes`时由原清单顺序建立稳定位置映射，过滤和认证恢复后仍沿用该位置。终态手动补提创建新的 `manual` 批次并关联原批次。关联汇总按每个圈子剩余批次中的最新成功结果计算，不物理合并或修改任何历史快照。
- `manual retry` / 手动补提是内部领域和接口语义，用户可见操作统一为“重新提取失败项”。Worker分段提交只持久化已完成结果；候选网络错误在归类为持久重试时保持 `failed_count=0`，原 URL 成功后清除重试检查点。平台明确返回删除、身份冲突或内容不成立等终态错误时，任务才按实际固定候选结果收敛为 `partial_success` 或 `failed`。补提创建新批次并重新冻结该时点的候选和页面证据，不把新候选写入原批次；历史批次继续不可变。前端保留“成功任务派生可见失败数0”的兼容逻辑，以正确展示修复前已冻结的历史批次。确认 Dialog 从后端读取可重提失败项数量，提交仍调用现有幂等补提用例；成功后使用返回的新批次 ID 更新列表并建立原批次关联，不在前端复制失败 URL 或改写原批次。
- 第一版不取消普通 `queued` 或 `running` 批次。`waiting_for_auth` 可以经二次确认执行“结束本次提取”，按已有有效结果结束为 `partial_success` 或 `failed`，关闭认证入口并释放对应平台队列。只有终态允许二次确认后的事务级永久删除。

批量来源配置采用“先收集全部错误、后单事务写入”：格式、平台归属、圈子 ID、列表顺序和批内/库内复合重复错误必须一次返回；同一圈子的最新回复与最新发布可同时存在，复用同一校验和采集流程。任一行失败时整批零写入。网络验证与保存解耦，保存后状态可以是 `unverified`；显式测试、启用未验证来源或首次手动使用新来源时才创建异步验证任务。

## 已确认的 XLSX 模板技术契约

- 模板元数据和原始文件按不可变版本保存。同名上传创建新版本；删除只隐藏当前可选项，被历史导出记录引用的版本继续保留。配置页下载当前卡片显示的最新原始版本，使用模板 ID 与版本 ID 定位文件，响应以清理过路径保留字符的“模板名-v版本.xlsx”作为附件名；该读取操作不生成导出记录。
- 模板只生成并解析 `s.<source_key>.<field>` 稳定标签。`circles.export_key` 在来源创建时生成，由排除易混字符的字符表组成，固定 10 位，并以数据库唯一约束保证所有平台全局唯一；导出标签不编码平台代码、来源 UUID 或可修改名称。所有平台共用同一字段后缀注册表，平台暂时缺少的字段按现有导出语义留空，不新增平台专属标签格式。来源自身字段使用 `name`、`id`、`list_order` 和 `list_order_name` 短后缀，内部映射到 `source.*` 字段语义。第一版正式数据在交付前清理，因此不实现 22 位来源键、UUID 长标签、圈子标签或 `vehicle.name` 的兼容解析。标签不能使用中文名称或数据库物理字段名，也不能位于合并单元格；所有无效标签、缺失字段和冲突均一次返回中文工作表/单元格定位信息。
- 标签单元格是该圈子字段的第一条数据单元格。生成器按圈子结果顺序向下写入，一个帖子一行；同表多个圈子列组按各自第 N 条落到第 N 个数据行，短列留空，后端不从工作表名称推断车型或圈子，也不建立横向帖子关系。
- 后续单元格只克隆标签单元格的字体、填充、边框、对齐和数字格式。预计写入范围已有文字、公式或其他内容时导出失败并返回中文冲突位置；第一版不自动扩展公式，写入范围外的公式、图表、图片和说明保持原样。
- 单值时间写为 Excel 日期时间并使用 `yyyy-mm-dd hh:mm:ss`；集合文本按 `Asia/Shanghai` 使用同一格式。评论、图片和视频集合在单元格内按平台顺序编号，以中文分号和换行分隔并启用自动换行。评论默认字段包含作者、时间和正文，带点赞版本另含点赞；每帖最多十条主评论。
- 导出记录绑定“批次或补提关联汇总版本 + 模板 ID + 模板版本”，保存生成状态、时间和文件哈希。组合键未变化时复用已有文件，任一版本变化时新建导出。只从已持久化终态结果生成；删除批次时级联清理其导出记录和文件。

第一版不为该边界增加第二个业务后端，也不引入服务注册、消息总线、分布式事务或平台采集代理层。内网静态前端或反向代理只发布 `/api/v1`；`/internal/v1` 不对浏览器开放。后续替换调用方时不得把采集模块复制进客户现有后端。

第一版已由一个 Python 后端代码库承载该结构：FastAPI 提供 `/api/v1` 与 `/internal/v1` 控制器，Scrapling/curl_cffi 实现列表与详情采集，Patchright 承担服务器官方认证页面，SQLAlchemy 2 与 Alembic 管理持久结构，openpyxl 生成 XLSX，cryptography 加密 Session。第一版单进程使用 SQLite、一个全局调度线程和一个持久平台 FIFO Worker；未来多进程、多实例或多平台组合容量需要变化时，再评审 PostgreSQL、外部队列和服务端平台级并发。

## 已确认的第一版 Linux 部署基线

- Windows 开发机生成只含 ThreadSnap wheel、前端生产构建、固定配置和部署工具的制包输入包；完整离线包必须在与目标机相同的 CentOS Stream 主版本、x86_64 和 Python 次版本上组装。
- 完整离线包内置全部 Python wheels、锁定 Patchright 对应的 Linux Chromium，以及 Python、Nginx、Weston 和浏览器共享库 RPM。RPM 目录带本地仓库元数据和顶层组件清单；目标机安装固定使用 `pip --no-index` 与 `dnf --disablerepo='*'`，只由包内仓库解析缺失依赖，不把全部递归 RPM 强制升级到制包日版本。
- 程序 release 位于 `/opt/threadsnap/releases/`，配置位于 `/etc/threadsnap`，持久数据默认位于 `/var/lib/threadsnap`。安装前用 `lsblk`、`findmnt`、`df -hT` 与 `df -Pi` 核对挂载点；存在独立数据盘时把 `--data-dir` 指向其挂载点，不把 SQLite、模板、导出或加密 Profile 放入程序 release。
- systemd 只启动一个 ThreadSnap 应用进程，并由独立 Weston 服务通过 `wayland-99` socket 提供 `1280 × 800` 无头显示。专用 `threadsnap-nginx.service` 使用 `/etc/threadsnap/nginx.conf` 发布 SPA、代理页面 API/SSE/认证 WebSocket并明确屏蔽 `/internal/v1`，不接管宿主机已有的 80/443 Nginx；Uvicorn 继续只监听 `127.0.0.1:8000`，不开放 CDP，Wayland socket 仅对 `threadsnap` 用户可用。
- 既有服务器做兼容应用升级时，只有 `pyproject.toml`、前端 package/lock、`deploy/linux` 和制包脚本与当前已校验完整离线包均未变化，才允许使用应用最小包：包内只放新的 ThreadSnap wheel、前端生产构建、兼容元数据和逐文件 SHA-256，不复制 wheelhouse、浏览器、RPM、模型或 `node_modules`。目标机先校验基线 release、完整离线包和依赖清单，再以同文件系统 reflink 从当前不可变 release 建立新 release，只替换应用 wheel 与前端文件并使用 `pip --no-index --no-deps`，不得重新解析或安装依赖。切换前必须确认所有业务 Worker 空闲并在停机窗口备份 SQLite；Nginx 先于其 `Requires=` 后端停止，原子更新 `current`/`previous` 后分别等待后端与 Nginx 健康，失败时同时恢复旧 release 和数据库。
- 制包、安装、验证、备份和回滚的唯一操作说明为 `docs/deployment/linux-v1.md`，具体脚本位于 `deploy/linux/`。完整离线包的发行版、架构、Python、浏览器和逐文件 SHA-256 必须写入 manifest 与校验清单。

## 保留的部署与性能验收门禁

以下候选对比和 Linux 三轮规则保留为历史证据与最终部署验收依据。依据 ADR 0011，它们暂不再作为本次后端编码前置条件，也不表示已通过目标 CentOS 三轮。

### 候选方案 A

- Python；
- FastAPI；
- Scrapling；
- 使用 Scrapling 的普通 HTTP 与标准动态页面采集能力完成对比验证。

### 候选方案 B

- Node.js；
- TypeScript；
- Fastify；
- Crawlee；

PoC 访问模式遵循“未登录优先”：

- 先使用未登录状态验证真实帖子内容访问和风控响应识别；
- 未登录状态能够达到当前采集框架 PoC 门槛时，不使用账号、Cookie 或登录会话；
- 只有未登录状态无法满足真实字段要求时，才由甲方提供合法登录会话；
- 同一对比轮次中两个候选必须使用相同访问模式；需要登录时必须使用同一授权条件；
- 测试轮次中途不得从未登录切换到登录后继续累计结果；访问模式变化后必须重新开始该轮测试；
- 凭证、Cookie 和会话状态不得进入前端、日志、示例文件或 Git。

第一版确需登录时采用“内网客户机浏览器操作服务器官方登录页面 + 加密 Session + 有界自动刷新 + 原批次自动续跑”，不建立平台账号或密码字段：

- 第一版只维护一套全局懂车帝 Session；所有懂车帝任务隐式共用，不实现多账号、账号轮换或配置绑定；后续平台各自维护独立 Session 状态；
- 浏览器进程、Profile 和 Session 始终位于服务器；提取功能服务在服务器启动受控浏览器并打开平台官方登录页面，第一版客户从内网客户机的普通浏览器通过基础测试界面的临时嵌入式通道查看和操作该浏览器，自行完成密码、扫码、短信、验证码或滑块；客户机本地浏览器形成的 Cookie 不作为服务器 Session；
- 只持久化 Cookie、LocalStorage、浏览器 Profile 或等价 Session 状态及脱敏元数据；状态必须加密保存，密钥与数据库分离，文件和运行进程采用最小访问权限；
- 懂车帝当前会对无头认证浏览器返回 HTTP 200 零字节文档，因此人工认证入口默认使用 Patchright 随附完整 Chromium 的有头模式；Windows 使用正常桌面会话，目标 CentOS Stream 10 由 Weston 提供无头 Wayland 显示并通过 `--ozone-platform=wayland` 启动完整 Chromium。后端在开放输入前同时检查 HTTP 状态、`Content-Length` 和可交互 DOM，零字节或空 DOM 进入明确失败状态，不把 WebSocket 已连接误判为页面已加载；
- 每个认证任务先在服务端独立临时 Profile 中运行。已有正式 Profile 先解密到任务目录；浏览器导出的 Session 结构有效后关闭浏览器、重新加密归档并原子替换正式 Profile，同时更新加密 Session。保存阶段不判断页面登录状态，不创建采集器或访问真实圈子样本。浏览器导出的Cookie合同要求`name/domain/path`为非空字符串、`value`字段存在且为字符串，其中空字符串是合法Cookie值；结构检查在关闭浏览器前完成，持久化故障使用独立`AUTH_SESSION_SAVE_FAILED`错误，不归类为页面加载失败。任务关闭、过期或服务正常停止时删除临时 Profile，单进程服务启动时清理上次异常退出遗留的任务目录；接口、日志和前端始终不返回 Profile 路径或内容；
- 查询接口只返回会话状态和最近验证时间；Cookie、LocalStorage、动态码、扫码内容、Profile 路径和其他可复用数据不得进入前端、日志、错误、导出、截图、测试报告或 Git；
- 采集前用少量真实样本探测 Session。HTTP 采集识别到 `login`、异常空响应或等价身份异常时暂停新请求，保留触发 URL，并对既有 Profile 执行一次有界自动刷新；
- 官方页面仍保持登录且新 Session 通过门禁时，从触发 URL 继续；出现登录表单、扫码、短信、验证码、滑块或门禁失败时，不再循环刷新，持久化批次当前索引、触发 URL、具体控制错误和待处理队列，将批次转为 `waiting_for_auth`；后续人工入口按错误分流：真实 `AUTH_REQUIRED` 创建不继承正式 Profile 的空白隔离环境并打开官方登录页，验证码或访问验证则复制既有加密 Profile 并打开原始触发 URL，不清除已有登录态；
- `waiting_for_auth` 是数据库中的可恢复状态，不是持续占用进程的挂起调用：状态提交后释放采集 Worker、连接和事务；依赖同一平台 Session 的后续任务继续进入该平台 FIFO 但不启动采集，其他平台不受影响；验证码或访问验证页面在已观察到控制页后返回原站时，认证中继自动导出并保存更新状态、把同一任务恢复为队列头；人工保存 Session 使用同一恢复动作。恢复任务先在原 URL 执行采集访问门禁，再按该平台原创建顺序处理后续任务，避免同时恢复造成请求突发；
- 人工认证使用独立、短生命周期的服务器浏览器进程。客户完成登录后，服务端原子替换加密 Session、关闭远程交互通道和登录浏览器，自动恢复同一批次的触发 URL 和待处理队列，不创建独立重试批次；
- 第一版人工认证入口必须限时、绑定一次性认证任务，并且只在受控内网可达；CDP、VNC 或等价控制端口不得直接暴露给客户机或公网。批次详情首次观察到 `waiting_for_auth` 状态转换时自动打开一次认证 Dialog，操作者关闭后保持手动入口可用且不在同一次等待中循环弹出。完成、结束、断开或超时后关闭浏览器和临时入口；服务端投屏循环即使静止页面没有新帧或输入，也按任务到期时间主动唤醒并回收浏览器。断开或超时只结束交互窗口，批次检查点继续保持 `waiting_for_auth`，内部操作者可重新打开入口或经二次确认结束本次提取；
- 保存后的原 URL 若仍明确要求登录则重新进入 `waiting_for_auth`；访问验证、限流或内容错误保留自身分类，不在 Session 保存操作中预先判断或改写为登录失败。帖子提取的 `PLATFORM_RATE_LIMITED` 进入同一任务持久冷却：检查点保存固定剩余URL、来源位置、限流分类、重试次数和下次时间，按60、120、240、480、900秒且最高900秒退避；到期只领取FIFO队首一个限流来源并以实际并发1复访，成功后才领取下一来源，不创建补提批次；
- 清除或更新 Session 时安全删除旧状态，并验证进程异常退出不会遗留长期可访问的控制入口。

当前采集框架 PoC 使用 2000 个 URL 进行一小时目标吞吐测试，记录实际完成量、访问成功率、真实帖子内容证明完整率、风控事件和资源指标。该 PoC 只负责采集框架选型，不要求提前实现圈子列表、完整正文与主评论解析、数据库、前端或导出。

吞吐门禁必须连续执行三轮独立测试，三轮每轮都必须在一小时内有效完成 2000 个 URL；任何一轮未达标，该候选即未通过吞吐门禁。

需求中所称“必须绕过风控”在技术选型中按结果门禁执行，不作为独立技术名称或单独功能模块验收。限流、验证码、挑战页、登录失效或其他平台控制导致任一 URL 未在窗口内产生有效访问证明时，该轮失败；候选自动恢复并在同一窗口内产生通过校验的访问结果时可以计入完成。三轮通过只证明已记录的版本、样本、访问条件、网络和测试时间窗口内达标，条件实质变化后重新执行同等级验证。

甲方提供的吞吐 URL 均作为已知真实业务链接输入。每轮输入数量和有效完成数量均为 2000，要求 100% 最终完成率和零最终失败。单个 URL 只在平台返回的帖子标识与输入匹配，且至少获得标题或正文存在性证明之一，同时未将验证码、挑战页、登录页或异常空响应当作内容时，才计为有效完成。仅 HTTP 200 不构成通过证据。

PoC 对首次 `login` 和 `empty` 采用有界脱敏诊断：每个候选、每种分类最多保存 3 条，只记录 URL 哈希、最终路径类型、文档长度与哈希、DOM 形态、已知控制标记、主文档状态链以及 Cookie 数量和名称集合哈希；不保存页面正文、Cookie 名称/值、账号或完整 URL。该证据用于区分登录重定向、空壳文档和平台控制形态，不改变两个固定候选的访问技术和统一成功契约。

Linux PoC 运行器必须把每个候选放入独立进程组；候选入口退出、超过窗口或外层脚本收到终止信号时，按 TERM 后 KILL 的有界顺序清理同组 npm、tsx 和浏览器子进程。Candidate B 在 Crawlee 队列返回后显式刷新完成标记并退出，避免队列已经结束而 Node 进程继续滞留。

当两个固定候选在并发 8 下均出现约一分钟后的 HTTP 200 空文档时，已保留“全新隔离会话 + 并发1 + 固定前500条”的浏览器诊断包和执行入口，不删除或改写该证据。鉴于现有大批量路径仍为逐 URL 浏览器访问，当前优先执行上述直接 HTTP/Spider 本地预筛；其结果决定是把 HTTP 通道打包到目标 Linux，还是再执行浏览器单并发诊断。两条路径均使用原统一成功契约，短样本和500条结果都不替代正式三轮2000条硬门禁。

完整正文、主评论、媒体 URL 和其他业务字段的提取在第一版正式功能开发与完工验收中执行，不作为当前采集框架 PoC 的前置输出要求。

导出采用数据库快照生成方式：采集结果先持久化，用户发起导出时选择模板版本，按批次或补提关联汇总查询帖子、主评论和媒体 URL，再由 openpyxl 生成 XLSX。导出过程不得重新访问目标平台。第一版数据库为 SQLite，并由 SQLAlchemy 2 与 Alembic 管理迁移。

历史批次不自动过期，仅在用户明确执行人工删除后清理。删除操作必须在同一事务中处理批次、帖子和主评论等关联数据，避免残留孤立记录。

用户可见批次编号采用 `YYYYMMDD-HHmmss-NNN`，使用 `Asia/Shanghai` 时区，时间精度为秒，同一秒内通过三位递增序号区分。数据库内部批次主键采用 UUIDv7，不直接使用批次编号作为主键。

该适配器当前以 `autohome-club-v11-scrapling-page-evidence-frame` 注册为 `available`、默认停用、依据ADR 0057内部总并发固定为1；v2按ADR 0045保留平台列表中的跨论坛聚合帖并冻结发现来源与详情原始归属双重身份，v3按ADR 0046把帖子点赞数纳入认证采集合同，v4按ADR 0048移除评论完整性整帖门禁，v5按ADR 0050冻结前 N 个候选且禁止后续补位并按ADR 0049移除采集器内部固定并发1，v6按ADR 0052在详情访问前冻结本轮候选并把限流剩余URL交给Worker冷却续跑，v7按ADR 0054把普通HTTP执行切换为Scrapling FetcherSession，v8按ADR 0055增加控制页Stealthy复访，v9按ADR 0056依据固定轮次证据撤回汽车之家Stealthy恢复并改用正式认证后的单来源探针，v10复用既有页面证据与关联成果链，在同一Patchright页面冻结列表响应、最终DOM卡片和原始全页PNG，重启后从不可变manifest恢复候选；v11把 `ul.post-list` 的左右外边距纳入每条完整列表框，使框线位于主栏留白而不覆盖最右侧浏览/回复文字。人工认证只保存服务器浏览器 Session；真实采集时，适配器再用 `clubUserShow`、`autouserid` 与 `sessionlogin` 的一致非游客身份组合取得会员ID，并以页面同款点赞接口读取主帖值。详情HTML中的点赞 `0` 是加载占位；认证后的空列表保存数字0，唯一主帖项保存非负整数，401/403/430进入有界刷新/`waiting_for_auth`，无效JSON、结构、负数或冲突值以 `POST_LIKE_COUNT_INVALID` 失败关闭。Session 保存状态不替代这项采集访问门禁。普通批次遇到验证码或访问验证时，适配器保留具体分类和精确触发 URL，直接交给共享 Worker 并持久化为 `waiting_for_auth`，不再追加汽车之家Stealthy导航。批次会话入口据 `run_id` 读取该等待任务的错误码和检查点：验证码/访问验证复用既有登录 Profile 打开触发 URL，并在验证页返回原站后自动保存更新状态、原位续跑；只有 `AUTH_REQUIRED` 才使用全新环境进入官方登录页。恢复批次先只以实际并发1领取最早等待来源；该来源在原URL形成成功、部分成功或确定失败后，才释放同批次其余来源并恢复冻结并发，再次等待认证或进入持久重试时继续保持后续来源阻塞。限流保持独立分类并进入原任务冷却续跑，不转换为登录或终态失败；会话刷新后的平台控制同样保留具体错误码，不降级为 `TASK_INTERNAL_ERROR`。bootstrap以registry为发布状态唯一来源，能把既有数据库中的汽车之家从 `not_integrated` 提升为 `available`，但不替用户打开平台启用开关。实际视频URL解析、正式认证和圈子页面证据能力均已打开。固定500验收工具和汽车之家生产Provider已经落地：正式入口没有可缩小分母的参数，来源必须逐 seed 绑定两个列表顺序，冻结输入绑定认证访问模式、适配器版本、Git提交和SHA-256；认证模式下遇到登录失效、验证码、挑战或限流响应仍在首个控制响应后停止平台请求并为余项写入 `not_requested` 唯一终态。首轮匿名预检从2540个稳定候选中复核325条，按当时v1合同得到295条有效详情、7条社区身份不符、22条挑战和1条验证码；这些结果不具备可信点赞数，也不得直接外推到当前v11，后续正式验收使用认证Session从零重跑。首次控制出现在选择序号303。本地fixture已经通过正常Worker领取路径贯通持久化、详情API和XLSX，构成本地发布证据，但不替代正式500验收。上述预检不与后续轮次拼接，须在正式Session模式下重新冻结运行条件并完整运行500条；完成前不声明正式环境大样本验收通过。
