# 链档：首个平台交付

## 当前口径

- 第一版是内部验证版，只完成一个平台的基础前后端闭环；同时支持圈子列表自动发现与已知帖子 URL 清单导入，两者复用同一详情采集流程；后续两个平台通过统一采集器契约接入。
- 正式功能开发前必须完成候选采集技术栈 PoC；最终三轮吞吐门禁在目标 Linux 主机由项目负责人手动触发。
- 当前优先完成采集框架 PoC：每轮输入 2000 个不同真实帖子 URL，必须在一小时内全部产生帖子 ID 匹配且具有标题或正文存在性证明的访问结果；平台控制造成任一最终未完成即为该轮失败。
- 甲方已提供懂车帝工作表：2698 行原始 URL 经规范化得到 2694 个不同帖子 URL，这些是真实项目会使用的输入，已满足当前 PoC 数量要求；首轮已用种子 `threadsnap-poc-round-1-20260808-v1` 固定 2000 条，清单 SHA-256 为 `4558a54cbe96259c1a64d6fda02658b3b344b8a269fcd85ea32a793572ea5d70`。
- 候选 A/B 已完成 Windows 阶段 1 的四层 URL、持久匿名会话、同会话复访、内置 Chromium/正式 Chrome 与直连对照；两者及独立匿名浏览器均在挑战完成后收到服务端 `302 /login-required`。这不是结果分类器或跳转跟随错误，但当前证据也不把它解释为业务固有要求登录；下一步在目标 Linux 的不同网络出口复测同一阶段门。
- 使用同一套合法测试账号后，两个固定候选均已自动完成密码登录与 SSO 回调，并能在清除凭证环境后复用各自持久配置；四层样本结果一致为 3 条真实帖子成功、同一条服务器 404。登录访问方式已验证，当前先复核固定输入的现时有效性。
- 两个固定候选的 Linux 认证吞吐运行器已经形成：同一明文 sidecar 配置、同一 2000 条清单、候选隔离的持久会话、一小时硬截止、逐 URL 证据、资源指标和自动汇总；本机 1 条合成端到端均通过。当前只证明运行链完整，真实 2000 条结论仍以目标 Linux 轮次为准。
- 目标 Linux 首次执行改为先跑独立联通门：最多 3 条两个候选都曾成功的样本，依次验证运行时/浏览器、DNS/TCP/TLS/HTTP、Scrapling 登录访问和 Crawlee/Playwright 登录访问；服务器只需返回脚本生成的诊断压缩包，复核 `ready_for_2000=true` 后再进入 2000 条。
- 目标主机已实测为 CentOS Stream 10（Coughlan）、x86_64、glibc 2.39、Python 3.12.12；根分区可用 56G、内存可用 13GiB、Swap 可用 7.8GiB，两个候选的浏览器健康检查和网络基线均通过。首次联通因候选 A 运行入口未继承包内浏览器缓存路径而失败，属于运行脚本环境变量顺序问题，不是框架或主机资源问题；候选 B 当时只完成登录页请求，不是帖子访问成功。
- 修复浏览器路径后的 Linux 联通包已通过外层和 21/21 内部校验：两个候选均提交了表单，但3条样本均未开始帖子请求。已确认登录页默认是手机验证码模式，旧逻辑按“最后一个按钮”切换并未可靠进入密码表单；两个候选现改为显式点击可见的“密码登录”，等待账号和密码输入框可见后再提交。
- 显式密码登录修复后的 Linux 联通包再次通过外层和 21/21 内部校验：两个候选均 `password_login_selected=true`、`submitted=true`，但提交后仍为 `logged_in=false`，3 条帖子请求均未启动。说明密码模式切换已生效但不是全部阻塞；当前补充提交后可见二次验证控件、标准化提示和脱敏截图，再区分二次手机验证、验证码或账号提示。
- v0.2.4 Linux 联通包的外层 SHA-256 与 23/23 包内校验一致且零凭证匹配。候选 B 的脱敏截图明确显示密码表单提交后提示“为保证账号安全，请使用手机验证码登录”，已确认当前阻塞是服务器访问条件下的二次短信验证；候选 A 尚未到达诊断动作，原因是首个帖子导航等待 `load` 满 90 秒。源码继续保留 Scrapling，并让其登录入口像吞吐请求一样丢弃非必要资源；两个候选同时增加强制短信验证结构化标记，待目标 Linux 复跑。
- 当前 PoC 已增加独立的 SSH 手动短信初始化入口：两个候选分别触发短信、读取终端动态码并保存隔离会话；合成端到端已确认两者均能在初始化进程退出后由新进程复用状态取得 1/1 帖子成功，且完整运行目录中没有动态码残留。本入口只用于解除当前测试阶段门，不代表正式项目已选定验证码处理方案。
- v0.2.6 在目标 Linux 首次执行候选 A 时只输出启动阶段，随后停在 Scrapling 以原始帖子 URL 启动的 `goto(load)` 导航链；回溯证明“获取验证码”点击尚未发生，但不单独证明最终画面仍在文章页。短信初始化现改为由帖子地址直接构造同源登录入口，A/B 均增加主文档生命周期、页面就绪与发送点击进度；本机合成端到端确认两者没有先发起未认证帖子请求，并继续完成持久会话复访。
- v0.2.7 目标 Linux 输出已把候选 A 阻塞定位到登录页内部：登录主文档 HTTP 200、`DOMContentLoaded` 已完成，但完整 `load` 长时间未触发，说明文章重定向和登录主文档均正常，剩余加载项阻塞了 Scrapling 进入 `page_action`。两个候选现于首次登录页 DOM 就绪后等待 250ms，按资源类型输出未完成计数并调用页面原生停止加载，再继续各自框架原有短信动作；带永不完成子文档的本机夹具已覆盖该路径。
- v0.2.8 目标 Linux 进一步返回未完成资源为 `fetch:2,script:2,xhr:4`，页面原生停止加载已经执行，但 Scrapling/Playwright 的 `goto(wait_until=load)` 仍保持等待；这证明 `window.stop()` 处理层级错误。当前实现直接在两个固定框架的导航配置层使用 `domcontentloaded`：候选 A 同时覆盖 Scrapling 的首次 `goto` 与随后稳定性检查，候选 B 使用 Crawlee 原生 `gotoOptions`，后台资源只保留诊断计数。本机永不完成子文档夹具下两者均已进入短信动作并完成持久会话复访。
- v0.2.9 目标 Linux 已确认候选 A 依次到达 DOM 就绪、页面动作就绪和发送按钮点击；候选 A/B 随后均未在手机端收到动态码。现有 `sms_request_clicked` 只证明浏览器事件完成，尚未区分平台接口请求、业务拒绝、附加验证和短信投递。两个候选现同步增加点击后 5 秒的脱敏 XHR/fetch 状态、按钮倒计时和可见验证/警告证据，再按共同结果定位，不更换候选技术。
- v0.2.10 目标 Linux 已确认两个候选均请求短信接口并收到 HTTP 200，随后平台加载验证中心且页面为 `verification_visible=true`、`countdown_visible=false`；因此当前阻塞是短信发送前的可视验证，不是登录导航、发送按钮点击或某一个候选框架。PoC 现为两个固定候选分别增加回环 CDP 人工验证入口：Windows 通过 SSH 隧道操作服务器原浏览器上下文，程序取得验证消失与短信倒计时两个信号后才读取动态码并保存隔离会话；该入口仍只用于 PoC，等待目标 Linux 真实复核。
- v0.2.11 目标 Linux 已通过 SSH 隧道在 Windows DevTools 显示 Candidate A 原浏览器登录页与滑块容器，但验证码报 `[5202] 图片加载失败` 且页面 Logo 缺图；源码确认 A/B 的短信入口都拦截了 `image`。当前只为两个候选的短信人工初始化放行图片，普通诊断与吞吐过滤保持原样，待 v0.2.12 在目标 Linux 复核验证码素材、倒计时和会话保存。
- v0.2.12 目标 Linux 已分别完成 Candidate A/B 可视验证、短信登录与帖子 200 复访，两份候选状态均成功落盘。随后联通包 `connectivity-20260810T164845+0800` 的外层 SHA-256 与 23/23 内部校验一致，网络基线全部通过，但联通临时配置把会话目录切换到空的 `profiles/connectivity-candidate-*`：Candidate B 因此重新进入密码登录并触发二次短信验证，Candidate A 在同一未认证入口等待 `load` 超时。根因是 PoC 隔离目录未复制当前会话，不是候选框架失效；联通准备阶段现重建隔离目录并分别复制 A/B 的 `storage-state.json`，源状态缺失时同时清除旧副本。
- v0.2.13 目标 Linux 联通包确认 A/B 会话均已复制；Candidate B 对同一3条样本取得3/3 `post/success`，Candidate A 则在已认证首帖的 Scrapling `page.goto(wait_until=load)` 满 90 秒并于登录结果落盘前退出。账号、样本、网络及会话条件已由 B 的同轮成功对照排除，当前只把 A 的普通登录确认和逐 URL 访问改为 DOM 就绪导航；同时让联通汇总优先报告候选运行/契约错误，不再把已启动异常误报为 `runner_not_started` 或登录猜测。
- v0.2.14 目标 Linux 联通包通过外层及23/23内部校验：运行时、浏览器、网络和两份会话均正常，Candidate A/B 对同一3条样本分别取得3/3 `post/success`，完成率、帖子 ID 匹配率和内容证明率均100%，未恢复控制数与契约错误均为0。联通汇总已为 `ready_for_2000=true`，独立联通阶段门关闭，下一步按固定2000条清单执行首轮双候选吞吐。

## 决策链

| 日期 | 决定 | 为什么 |
|---|---|---|
| 2026-07-30 | 第一版只交付一个平台，后续两个平台走统一适配器 | 控制首版成本，同时避免重复开发公共调度、存储和前端能力 |
| 2026-07-30 | 第一版按内部验证版建设，正式公网权限由现有系统承担 | 当前目标是先验证采集与批次闭环，不提前建设未知集成框架 |
| 2026-07-30 | Python 与 Node.js 两候选先做真实样本和 Linux PoC | 目标接口、平台控制和吞吐尚未验证，不能凭经验直接确定技术栈 |
| 2026-07-30 | 2000 URL/小时采用三轮 100% 最终完成硬门禁 | 这是交付要求，短样本外推、重复 URL 或人工修补不能证明可交付 |
| 2026-07-30 | 采用 forged-in-prod 项目流控制并建立唯一 WORKLOG | 避免上下文压缩后丢失进度、重查已验证结论或产生平行口径 |
| 2026-08-08 | 第一版保留圈子发现与 URL 清单两种输入，当前 PoC 只先测采集框架的访问吞吐与风控表现 | 不用完整业务开发阻塞最高风险的技术选型，同时不缩减第一版最终功能 |
| 2026-08-08 | Linux 测试使用标准源码包加本地明文配置 sidecar | 允许项目负责人直接复制和运行，同时保持源码压缩包、Git、日志和结果不含凭证 |
| 2026-08-10 | 目标 Linux 先过最多 3 条的独立联通门，再启动 2000 条 | 把环境、网络、登录和内容访问问题提前分层，避免直接用完整负载定位基础连接失败 |

## 未决项

- [ ] 懂车帝列表、详情、正文和一级评论的完整业务获取方式 —— 解锁条件：采集框架 PoC 通过后，在第一版正式功能开发中完成列表与字段级验证。
- [ ] 匿名访问是否满足第一版字段完整率 —— 该项不阻塞当前采集框架 PoC；在正式功能回归时用功能样本完成字段级比对，不满足时再验证甲方提供的合法会话。
- [x] 当前采集框架 PoC 的登录访问处理 —— 两个固定候选已使用同一授权条件完成自动密码登录、候选隔离的持久会话和无凭证复访；登录模式后续轮次必须独立执行，不与匿名结果拼接。
- [ ] 固定输入的现时有效性 —— 登录后四层样本仍有同一条服务器 404；解锁条件：依据来源索引核对测试时状态，并在中等样本中统计真实 404 分母，避免把无效输入解释为框架失败。
- [x] Linux 双候选认证吞吐运行器 —— 两个候选均已完成同结构入口、本地合成端到端和源码包构建；真实轮次仍受目标主机环境及固定输入有效性约束。
- [x] Linux 独立联通门 —— v0.2.14 在目标 Linux 对 A/B 各自3条均取得帖子 ID 与内容证明，汇总 `ready_for_2000=true`；该结果只解锁2000条吞吐，不构成吞吐门禁通过。
- [ ] Python 或 Node.js 正式技术栈 —— 解锁条件：两个候选完成 Windows 预筛和目标 Linux 三轮硬门禁，形成对比报告与选型 ADR。
- [ ] Linux 主机规格、语言运行时、浏览器系统依赖和进程管理方式 —— 已确认可用内存、Swap、磁盘、Python 3.12.12 和浏览器健康检查；CPU 型号/核心数及正式进程管理方式仍待确认。
- [ ] 内部接口错误结构和进程管理方式 —— 解锁条件：正式技术栈确定并确认客户现有后端集成约束。
- [ ] 正式项目的验证码与会话续期方案 —— 当前 PoC 仅采用 SSH 手动输入完成一次性测试初始化；解锁条件：采集框架 PoC 通过后，取得真实会话寿命、失效频率、部署值守和现有系统集成约束，再比较人工续期、受控自动接码或外部会话托管。
