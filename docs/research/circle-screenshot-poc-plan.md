# 圈子页面证据与关联截图成果 PoC 计划

## 1. 目的

本 PoC 验证 ThreadSnap 能否从圈子任务实际来源页面同步冻结有序帖子清单和完整原始证据，在平台资源预算内流水线采集详情，并从不可变证据生成可追溯、可版本化的完整原页标注成果。PoC 只验证事实能力、资源边界和失败分布，不把单个成功样本外推为正式完成。

## 2. 假设

1. Patchright Chromium 可以在当前加密 Session 下，对实际执行的最新回复与最新发布来源取得稳定 DOM、完整懒加载卡片和无损分页截图。
2. 同一 DOM 稳定点冻结的帖子 ID、顺序、卡片矩形和截图可以成为详情采集与截图成果共同的身份合同。
3. 每冻结一个物理分页后启动详情采集，可以在不突破平台资源预算的前提下形成有效流水线。
4. 被关联结果引用的完整原始页面可以按稳定顺序生成同尺寸副本，并根据现有有效舆情结论准确绘制整卡红框；框外像素保持一致。
5. 2000 条等价结果涉及的多个原始物理分页可以逐页有界编码、前端连续查看并形成完整成果包，而不降低采集数量上限。

## 3. 输入与保存位置

- 真实来源输入放入 `artifacts/poc/inputs/circle-screenshot/`，只保存来源身份、规范化 URL、期望列表类型和输入校验值，不提交平台 Session。
- 每轮原始结果放入 `artifacts/poc/results/circle-screenshot/<round-id>/`，包含运行配置、环境、清单 JSONL、原始页面、完整标注页面、详情结果、资源指标、成果包、清单哈希和汇总。
- 平台 Session、Cookie、签名 URL 和可能含账号可见信息的原始截图不得进入 Git、日志示例或文档正文。
- 固定记录 Git SHA、适配器版本、Patchright/Chromium/Pillow 版本、操作系统、显示后端、视口、DPR、时区、网络、输入哈希和开始结束时间。

## 4. 设计矩阵

| 编号 | 场景 | 输入 | 主要回答 |
|---|---|---|---|
| R1 | 最新回复单页 | 已验证来源，目标约 30 条 | 清单、顺序、矩形、懒加载和原始证据是否逐项一致 |
| R2 | 最新发布单页 | 已验证来源，目标约 30 条 | 不同实际来源是否沿同一合同工作且不混用页面 |
| R3 | 跨物理分页 | 同一来源目标至少 60 条 | 冻结一页后详情流水线、翻页、去重和后续证据是否稳定 |
| R4 | 详情失败补位 | 在隔离替身中让中间候选详情失败 | 失败卡片只留原始诊断，后续分页补位且最终只含实际入库帖子 |
| R5 | 卡片媒体异常 | 延迟、失败和平台占位三类图片状态 | 卡片完整门禁能否区分未完成加载与真实平台占位 |
| R6 | 关联补提 | 原批次加两次补提，构造 40+7+3 | 成果组能否合并为 50，标明逐卡来源并保留版本 |
| R7 | 结果变化 | 人工负面/非负面修正、恢复 AI、删除贡献批次 | 当前版本、历史版本、红框数和剩余结果能否准确重建 |
| R8 | 零负面与零结果 | 全部非负面、明确空列表、错误零条 | 三种终态是否分别形成无框、零结果和失败 |
| R9 | 多原页成果 | 使用真实原页按稳定清单扩展至 2000 条等价负载 | 原页尺寸/框外像素一致、逐页峰值内存、编码时长、连续查看和成果包是否通过 |
| R10 | 备份与删除 | 含原始证据、当前/历史版本和分片的数据目录 | 备份恢复、逐文件哈希和引用清理是否准确 |

## 5. 控制变量

- 同一真实来源轮次固定 Session、网络、视口、DPR、语言、时区、浏览器版本、等待规则和平台内部并发。
- R1/R2 只改变实际来源类型；R3 只扩大目标并保持其他条件不变。
- 红框测试使用已经持久化的有效舆情结果或确定性测试夹具，不额外调用模型评价截图。
- 详情失败、图片延迟、人工修正和删除只在隔离数据库或受控替身中注入，不修改正式业务数据库。
- 2000 条负载只复用已取得的真实原始页面验证逐页渲染与查看，不向平台重复请求 2000 个页面卡片。

## 6. 测量与通过阈值

### 6.1 页面证据

- 清单帖子 ID、DOM 卡片 ID、原图卡片范围和详情输入 ID：有效范围内逐项一致率 100%。
- 清单顺序与卡片纵向顺序：100% 一致；重复平台帖子 ID 为 0。
- 每个实际入库帖子都有且只有一个对应证据条目；遗漏、错配和跨来源串联均为 0。
- 必检卡片的字体、文字、图片终态和矩形门禁全部通过；未完成加载样本必须进入明确失败而不是完整证据。
- 原始证据生成后到所有成果版本完成，文件 SHA-256 保持不变。

### 6.2 关联成果

- 当前成果卡片数等于当前关联结果中的证据化帖子数；顺序与现有关联结果顺序 100% 一致。
- 红框数等于当前有效 `negative` 数，非负面和不相关误框数为 0；红框完整覆盖卡片且不切断相邻卡片。
- 40→47→50、人工修正、恢复 AI 和删除贡献批次均生成正确新版本，当前指针唯一，历史版本哈希可复核。
- 零负面、明确零结果、错误零条和历史无证据四种界面/接口状态互不混用。

### 6.3 完整原页与资源

- 2000 条等价负载必须完成全部完整页面、清单和成果包生成；每张成果页与来源原图尺寸一致，框外像素差异为 0，卡片遗漏为 0。
- 渲染进程峰值 RSS 小于 2 GiB，失败时不遗留半成品当前版本；实际编码时长、磁盘占用和压缩比分别报告，不用请求数量代替完成结果。
- 最大原始物理分页同时通过 Windows、目标 Linux 和当前受支持浏览器的加载验证；前端只加载可视页面，连续滚动期间不一次解码全部成果。
- 备份恢复后数据库记录、文件数量、逐文件 SHA-256、当前版本和历史版本全部一致；删除路径不触及其他成果组或持久目录外文件。

## 7. 失败停止条件

- 页面清单与截图出现任一帖子身份或顺序错配；
- 实际入库帖子缺少完整卡片证据，或未完成加载被记为完整；
- 独立列表请求重新决定截图内容；
- 原始证据在事后补拍或成果生成中被改写；
- 未决舆情被当成非负面并生成最终成果；
- 补提、删除或人工修正后当前成果仍包含过期卡片或红框；
- 2000 条等价负载出现原页裁切/缩放、框外像素变化、内存阈值超限、前端全量解码或成果包清单不完整；
- 原始截图、Session、Cookie、签名 URL 或账号可见信息进入 Git。

任何停止条件命中时保留原始结果和分母，修正后创建新轮次，不覆盖失败轮或缩小分母。

## 8. 实施解锁顺序

1. R1、R2 通过后冻结平台页面证据适配器合同和定位器版本。
2. R3～R5 通过后实施页面证据数据库迁移、Worker 流水线和失败恢复。
3. R6～R8 通过后实施成果组、版本、当前指针、人工修正联动和页面状态。
4. R9 通过后冻结单原页资源边界、Pillow 依赖、连续查看器和成果包格式。
5. R10 通过后更新 Linux 离线包、备份恢复、校验与删除路径。
6. 完成后按验证阶梯在真实 Windows 页面和目标 Linux 组合路径验收，再进入 Git 自动收尾。
