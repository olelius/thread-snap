# 提取功能服务技术栈对比 PoC 计划

## 1. 文档状态

- 状态：技术选型前置计划；
- 目的：在正式功能开发前，以足量真实帖子 URL 的访问吞吐、真实内容证明和风控响应识别结果，决定提取功能服务最终使用 Python 还是 Node.js；
- 当前结论：尚未选定胜出方案；
- 前置关系：本 PoC 是第一版正式业务工程开发的强制前置门禁。

本 PoC 不是第一版完工验收。当前优先验证采集框架能否在规模访问中取得对应帖子的真实内容证明，并正确识别限流、验证码、挑战页、登录页和异常空响应。圈子列表发现、完整正文与主评论解析、数据库、前端和导出仍属于第一版正式开发与验收范围。

## 2. 对比候选

### 2.1 候选方案 A

| 层次 | 候选组件 |
|---|---|
| 语言 | Python |
| 内部 Web API | FastAPI |
| 采集框架 | Scrapling |
| 普通请求通道 | Scrapling HTTP Fetcher |

### 2.2 候选方案 B

| 层次 | 候选组件 |

### 2.3 不进入本轮候选

- Scrapy + Playwright；
- Go/Colly；
- Apache Nutch；
- 纯 Selenium；
- 仅依赖 OCR 或视觉模型的采集方案；
- 依赖动态代理池、自动验证码破解或对抗性签名破解的方案。

这些方案可以保留在通用技术调研中，但不进入本次项目决策评分。

## 3. 公平对比原则

两个方案必须满足：

1. 使用同一批真实 URL；
2. 同一测试阶段使用同一运行主机、同一网络出口和相同资源条件；
3. 使用相同且有权使用的账号、Cookie 或访问条件；
4. 使用同一字段定义和结果校验器；
5. 每个 URL 都必须核对平台返回的帖子标识，并取得标题或正文存在性证明之一；
6. 对限流、验证码、挑战页、登录失效和异常空响应使用相同分类规则；
7. 仅 HTTP 200 不计为成功，不把验证码页、登录页、挑战页或异常空数据计为真实帖子内容；
8. 不把人工修补后的结果计为自动访问成功；
9. 凭证、Cookie、令牌和原始个人数据不得进入 Git；
10. 所有时间、成功率、风控事件和资源指标由独立测试驱动记录，不能只采用框架自身日志；
11. 两个方案都要保留可复现的安装说明和版本锁定文件。

访问模式额外遵循：

- 默认先验证未登录模式；
- 未登录模式能够满足当前访问成功率和访问证明完整率时，不启用登录；
- 未登录模式不足时，由甲方提供合法登录会话，两个候选使用相同授权条件；
- 访问模式改变后重新开始测试轮次，不能把未登录和登录结果拼接成一次达标结果；
- 不在吞吐测试中为每个 URL 先匿名失败一次再切换登录，避免重复请求放大；
- 最终选型报告必须标明每轮使用的访问模式。
- 需要账号密码时通过验证版配置页面录入并保存到本地数据库；允许明文持久化，但查询接口不得回显，且不得进入日志、导出、测试报告或 Git；
- 两个候选均只使用同一套全局懂车帝账号，不测试多账号选择或轮换；

## 4. 统一输出契约

两个 PoC 至少输出：

| 字段 | 说明 |
|---|---|
| URL | 输入帖子链接 |
| 平台帖子 ID | 平台提供时保存 |
| 平台帖子 ID 匹配 | 平台响应中的帖子标识是否与输入 URL 对应 |
| 真实内容证明 | 标题存在或正文存在性证明，至少一项为真 |
| 响应分类 | post / rate_limited / captcha / challenge / login / empty / error |
| 风控命中 | 本 URL 执行过程是否出现限流、验证码或挑战页 |
| 采集通道 | http / browser-network / browser-dom |
| 状态 | success / partial / failed / blocked |
| 请求次数 | 完成该 URL 的实际请求数 |
| 开始与结束时间 | 用于计算耗时 |
| 错误分类 | 失败或不完整时记录 |

当前 PoC 可以为了完成真实内容证明而解析标题或正文特征，但不要求输出完整正文、主评论或正式业务数据结构。

## 5. 测试样本

当前采集框架 PoC 的必需输入只有真实帖子 URL 清单。甲方已确认这些 URL 是真实项目中会使用的链接；它们不是测试结果，程序运行后的逐 URL 结果写入 `url-results.jsonl`，汇总写入 `summary.json`。

每轮测试必须满足：

- 只从甲方确认的固定清单中抽取；
- 两个候选在同一轮使用完全相同的抽样结果；
- 保存随机种子、抽样时间和实际 URL 清单，保证结果可以复现；
- 不得为了让某个候选通过而删除失败样本或重新抽样；
- 不要求甲方在当前 PoC 前填写正文、评论、可见性和登录要求的人工期望值。

吞吐样本从已收到的真实 URL 输入池中形成。重复 URL 必须单独统计，不得通过重复请求少量 URL 放大完成数量。

## 6. 测试阶段

### 阶段 0：环境与样本确认

目标：

- 记录当前开发环境的操作系统、硬件、网络和运行时基线；
- 准备最终部署的 Linux 主机；该主机尚不可用时只执行开发环境预筛，不执行 Linux 硬门禁；
- 记录 Linux 发行版、CPU 架构、libc、语言运行时和浏览器系统依赖基线；
- 固化语言、浏览器和依赖版本；
- 确认网络出口；
- 确认真实 URL 输入池、规范化规则和帖子标识提取规则；
- 确认凭证提供和保存方式；
- 先验证未登录模式是否满足访问成功率与真实内容证明门槛，必要时再固化登录模式；
- 确认目标页面是否允许当前访问方式。

阶段 0 未完成时不得开始性能比较。

环境分工：

- 阶段 1 和阶段 2 可以在当前开发环境执行，用于访问验证、错误发现和候选预筛；
- 两个候选在同一阶段必须使用同一台开发主机和相同测试条件；
- 开发环境的阶段 1、阶段 2 结果不构成最终技术选型或交付性能验收；
- 进入阶段 3 前，两个候选都必须生成 Linux PoC 测试包，并在最终部署的 Linux 主机完成安装、启动和访问校验；
- 不使用 Docker 消除环境差异，必须真实验证 Linux 下的依赖、浏览器运行时、路径、文件权限和进程行为。

### 阶段 1：访问冒烟

从甲方真实 URL 清单中抽取少量样本，分别对两个候选执行单 URL 访问。

验证：

- HTTP 通道是否能访问到对应帖子响应；
- 需要时动态页面通道是否能访问到对应帖子响应；
- 记录初始文档、脚本挑战后的文档复访、服务端重定向和最终文档组成的完整主文档链，不只保存最终 URL；
- 将全新临时会话、框架原生持久匿名会话和同会话复访分开测试，不能把某一临时配置的登录跳转直接解释为业务必须登录；
- 浏览器通道至少记录 XHR/fetch 的状态和路径模板摘要，用于判断内容来自主文档还是页面接口；会话等价性诊断只允许记录 Cookie 数量和名称哈希，不得记录 Cookie 值、授权头值或请求体中的凭证；
- 阶段 1 输入必须覆盖已知的 URL 路径与帖子 ID 长度分层，不得只取清单前若干条后外推全部输入；Windows 与目标 Linux 均使用同一种子生成的分层清单；
- 若候选与独立匿名浏览器对公开基线都收到相同服务端登录重定向，先在目标 Linux 的不同网络出口复测；在普通浏览器基线取得帖子内容之前，不把该现象归为框架缺陷，也不提前进入阶段 2；
- 平台返回的帖子 ID 能否与输入 URL 对应；
- 是否至少取得标题或正文存在性证明之一；
- 登录页、验证码页、挑战页和异常空响应能否被正确识别；
- 单条失败是否会影响其他 URL。

任一方案把风控页面、登录页、空响应或错帖内容判为成功时，不进入下一阶段。

### 阶段 2：中等批量对比

从甲方固定清单中随机抽取不少于 200 条且不与冒烟样本完全重合的 URL。两个候选使用同一抽样结果和随机种子。

验证：

- 自动访问成功率；
- 帖子 ID 匹配率与真实内容证明完整率；
- HTTP 与浏览器通道占比；
- 平均耗时、P50、P95 和最大耗时；
- 每个 URL 的平均请求数；
- CPU、内存和浏览器进程数量；
- 超时、重试、403、429、验证页面和登录失效数量；
- 进程中断后的任务恢复能力；
- 重复 URL 是否被识别且不计入不同 URL 完成量。

### 阶段 2A：直接 HTTP/Spider 架构预筛（当前下一步）

首轮目标 Linux 吞吐与500条转变诊断使用的批量入口均以逐 URL 浏览器访问为主，已证明这一路线在当前并发和会话条件下会于约一分钟后大面积转为 HTTP 200 空文档，但尚未验证候选框架的直接 HTTP 批量能力。阶段 2A 不增加第三个候选，也不改变统一成功契约；它只为 A/B 分别增加可独立运行的 HTTP 批量入口：

- Candidate A：`Spider + FetcherSession(impersonate="chrome")`；
- Candidate B：HTML 使用 `CheerioCrawler`，JSON 使用 `HttpCrawler`，启用 `SessionPool` 与 `persistCookiesPerSession`；
- 本阶段禁止浏览器初始化、浏览器状态导入、运行时参数刷新和逐 URL 浏览器降级；发现任何浏览器通道事件时该轮实验无效，重新以纯直接 HTTP 条件执行；
- 两端继续复用现有帖子 ID、标题/正文存在性、登录/空文档/控制页分类器和结果文件，不以框架默认 blocked 状态或 HTTP 200 代替项目契约。

执行顺序：

1. 在当前开发电脑上，使用现有固定联通样本、并发1，分别确认直接 HTTP 能返回匹配的帖子 ID 与标题/正文存在性证明；A/B 顺序运行，不共享会话；
2. 冒烟通过后，对同一固定前500条做递进并发预筛：`1 -> 2 -> 4 -> 8`。每一级使用新的候选隔离会话；上一级出现控制、最终失败或有效速度下降时停止升并发，不用更高并发掩盖失败；
3. 每一级记录首次控制事件的时间和已完成数、持续有效 URL/秒、P50/P95、实际请求数、请求放大率、HTTP 会话年龄、会话退休原因和最终分类分布；本阶段 HTTP 通道占比必须为100%；
4. 选出满足统一正确性契约且有效速度最高的稳定配置，再以固定500条独立复跑一次；只有复跑仍稳定，才生成目标 Linux 测试包；
5. 在目标 Linux 重做联通、中等批量和阶段3门禁，不把 Windows 的速度或风控结果当作 CentOS 结论。

动态参数不进入阶段 2A：当前访问 PoC 只验证帖子 ID、标题/正文存在性以及页面内嵌状态，不为评论字段扩张验收范围。若后续功能样本证明前10条一级评论必须调用评论接口，再另立实验任务记录接口路径模板、分页游标与参数名，并把纯 HTTP 参数实现和浏览器运行时参数实现拆成互不混合的实验组。任何实验都不跨会话复用动态值，也不记录令牌值、完整查询串或请求体。

速度结论只使用有效链接速度：当前硬门槛 2000 URL/小时约为 `0.56` 个有效 URL/秒；若将“一晚上”按8小时计算，100000条约需 `3.47` 个有效 URL/秒；`10` 个有效 URL/秒是36000 URL/小时的扩展压力目标。任何数值都必须同时给出最终有效完成率、测试时长、样本量、请求放大率和首次控制时间；队列处理速度、请求发送速度和小样本瞬时峰值不构成持续吞吐结论。

阶段结果（2026-08-11）：开发电脑已完成同一固定500条、并发1的纯匿名直接 HTTP 轮次。A/B 原始处理速度分别约6.96和6.70 URL/秒，但有效结果均为0/500；A 全部为 `login`，B 为497条 `login`、2条 `captcha`、1条 `challenge`。两端HTTP通道占比100%、请求放大率1.0、统一契约错误0。依据第2步停止条件，本阶段在并发1结束，不执行并发2/4/8、不生成Linux包；后续认证纯HTTP或动态参数研究必须另立互不混合的实验轮次。

认证分支首版结果（2026-08-12）：Candidate A 先由项目自有 Scrapling 浏览器 Session 建立并导出认证状态，再由 `Spider + FetcherSession` 对3条固定样本并发1执行纯HTTP请求；3/3均通过帖子ID与正文证据，总时长1.169秒、有效速度约2.57 URL/秒、请求放大率1.0，没有登录、验证码、挑战、限流或空文档。该小样本只关闭“认证Cookie能否交接给HTTP”的最小阶段门，下一轮须另定固定中等样本、会话寿命和递增负载规则；不得直接跳到500条，也不得把小样本瞬时速度外推为夜间吞吐。

Candidate A 的实现优先复用 Scrapling：Session、TLS/请求头、Cookie请求、Spider调度、Request/Response、CrawlStats和JSONL导出均使用框架。项目代码只实现框架没有的平台业务语义：帖子ID与正文真实性、HTTP 200登录/空文档/挑战细分、敏感信息脱敏、统一摘要和校验清单。由于 Scrapling 0.4.12 对 blocked 响应在重试耗尽后不再调用 `parse()`，本阶段不启用框架自动重试；只记录框架状态码阻断结果并让项目分类器形成唯一终态，避免风控响应从分母中消失。

认证分支500条结果（2026-08-12）：同一固定清单前500条、并发1、每URL一次请求已完整执行，399条HTTP 200通过帖子证明，101条为HTTP 404；总时长166.031秒、处理速度约3.01 URL/秒、有效速度约2.40 URL/秒、请求放大率1.0。没有 `login/empty/captcha/challenge/rate_limited`，因此没有触发首控暂停。404跨全部10个连续50条区间分布，两个有界复查样本返回相同标准404正文，旧浏览器轮次的24条404全部重合。当前阶段门仍因399/500失败；先复核和替换当前不可访问输入、生成新清单哈希并重跑并发1，达到500/500后再进入并发2/4/8。

认证分支2000条持续诊断（2026-08-12）：旧认证状态在运行前首条已为空，先由项目Scrapling浏览器重新登录并以3/3复检确认状态有效；固定2000条主轮次在第708个终态、228.635秒首次出现HTTP 200零字节空文档并暂停，此前568条有效、139条HTTP 404，剩余1292条不再请求。停控后刚成功的已知URL在项目HTTP和项目浏览器profile中均转为空，同机同网络的日常Chrome重新导航仍能加载正文；后续因果实验应拆分项目测试账号/会话、profile、HTTP客户端身份和速率，不能把该结果简化为纯IP封锁，也不能刷新状态后续跑并拼接为一轮。

冷却恢复探测（2026-08-12）：等待后保持原storage state、profile和HTTP配置，对本轮曾成功的已知样本只请求1次，仍得到HTTP 200零字节并立即暂停，因此没有发送剩余1292条。入口新增 `--offset` 以保留原清单偏移和来源哈希；后续若重新认证并从偏移708执行，只计为新Session恢复段，不修改原2000条持续轮次失败结论。

新Session恢复段（2026-08-12）：Scrapling使用新的隔离profile重新密码登录且无二次验证，新的storage state先通过3/3纯HTTP门禁；随后以原固定清单 `offset=708` 执行1292条独立恢复段，在本段第767个终态、262.041秒再次出现HTTP 200零字节并暂停，此前640条有效、126条HTTP 404，剩余525条未请求。停控后复查门禁中已确认有效的样本同样为空；首控附近没有客户端Cookie到期。该结果确认刷新Session/profile组合可以暂时恢复，但不确认旧Session自然过期，也不区分账号、profile、HTTP客户端身份、请求量、持续时间和速率。下一实验改为每个实验臂使用独立新会话的固定有效样本矩阵，至少比较当前约3请求/秒、1请求/秒和分批暂停，并以首控序号和首控时间裁决；不继续拼接剩余525条。

### 阶段 2.5：打包与 Linux 部署验证

阶段 2 通过后，为每个仍在候选范围内的方案生成独立 Linux PoC 测试包。该步骤属于 PoC，不属于第一版正式业务功能开发。

最简打包方式统一为 `tar.gz`。当前开发电脑中的测试包统一放在 `artifacts/poc/packages/<candidate>/`，文件名采用：

`threadsnap-poc-<candidate>-<version>-linux.tar.gz`

测试包至少包含：

- 候选原型源代码或必要构建产物；
- 锁定的依赖描述及对应校验信息；
- `deps/`：面向目标 Linux 环境生成的离线应用依赖；Python 候选使用 wheelhouse，Node.js 候选使用完整的离线包缓存或等价 vendor 目录；
- `browsers/`：候选方案需要浏览器时，保存与框架版本匹配的 Linux 浏览器运行时；
- `SHA256SUMS`：覆盖原型、锁文件、离线依赖、浏览器运行时和脚本；
- `preflight.sh`：检查发行版、CPU 架构、libc、语言运行时和必要系统库；
- `install.sh`：在 Linux 中创建独立应用环境，并且只从包内离线依赖安装；
- `start.sh`：以前台或简单后台方式启动 PoC 服务；
- `healthcheck.sh`：验证进程和内部接口可用；
- `run-poc.sh`：执行统一访问验证和阶段 3 基准测试，并把本轮结果直接写入固定结构的结果目录；
- `test-connectivity.sh`：首次部署时以最多 3 条已验证样本、并发 1 顺序检查网络基线和两个固定候选的登录/内容访问；每次运行先把两个候选当前 `storage-state.json` 分别复制到新建的联通隔离目录，源状态缺失时清除旧副本，最后生成可复制回开发电脑的诊断压缩包；
- Candidate A 的 Scrapling 登录确认与逐 URL 访问以 `domcontentloaded` 作为导航完成条件，再经过固定短等待读取最终 DOM；不得因平台后台资源未结束而持续等待完整 `load`，也不得把 DOM 就绪单独当作帖子成功，仍须通过帖子 ID 和标题/正文存在性契约；
- `README.md`：记录支持的运行时版本、配置步骤、启动命令和已知限制；
- 测试包的 SHA-256 校验值。

为满足人工直接复制到 Linux 的操作要求，标准 `tar.gz` 旁可以生成一个本地 `copy-to-linux/` 目录：目录内包含压缩包及校验值、明文 `config.json`、真实 `input-urls.txt` 和只负责校验/解压/复制 sidecar 的 `deploy.sh`。账号密码 sidecar 不进入标准压缩包、Git、运行日志或结果文件；复制目录整体继续位于被 Git 忽略的 `artifacts/poc/packages/`。

测试包不得包含：

- Windows 虚拟环境、`.venv` 或 `node_modules`；
- Windows 浏览器二进制或开发机浏览器缓存；
- 账号、密码、Cookie、令牌或真实配置文件；
- 本地数据库、历史采集结果或预置性能测试结果；
- 与候选方案无关的开发工具和临时文件。

Linux 部署验证必须从干净目录解压测试包后执行，并确认：

1. 压缩包校验值正确；
2. `preflight.sh` 验证实际 Linux 环境与测试包目标基线匹配；
3. 在临时禁止依赖仓库访问的条件下，安装脚本仍可建立独立应用环境并安装全部应用依赖；
4. 安装过程没有从公网解析或下载应用包和浏览器运行时；
5. 浏览器运行时及原生系统依赖可以正常启动；
6. 路径、文件权限、字符编码和时区行为正确；
7. 服务启动与健康检查成功；
8. 统一访问样本通过；
9. 运行目录没有依赖开发工作区或人工复制的机器状态。

在第 7 项健康检查之后、进入统一访问样本或 2000 条轮次之前，先执行独立联通门。联通门只判断服务器是否具备继续测试的基础条件：DNS、TCP、TLS、HTTP 均可达，两个候选均完成登录，且各自至少一条样本取得帖子 ID 与内容存在性证明。其余样本中的真实 404 单独保留，不把单条失效链接误判为服务器整体不通。联通门不形成吞吐通过结论。

任一候选不能通过该阶段时，不得进入阶段 3。禁止在 Linux 主机上人工修改代码后直接继续测试；修复必须回到候选源码，重新生成带新版本号和校验值的测试包。

Linux 测试机虽然允许联网，但联网能力不作为应用依赖安装成功的组成部分。语言运行时、浏览器所需系统库等主机级前置环境可以按已记录的精确版本在线准备；PoC 应用依赖和浏览器运行时必须由测试包离线提供。若离线包缺少依赖，必须重新构建测试包，不能在验收目录中临时联网补装后继续计入结果。

若目标账号在 Linux 密码提交后被要求二次短信验证，当前 PoC 允许由项目负责人在 SSH 交互终端分别为两个候选输入一次性动态码并建立隔离持久会话。动态码不得进入配置、日志、结果包或持久状态。该测试初始化方式不自动成为正式项目的验证码与会话续期方案，正式决策留待 PoC 通过后结合真实会话寿命和部署约束形成。

若短信发送前出现可视验证，两个候选继续使用各自固定框架启动的原浏览器上下文，并分别通过只监听 `127.0.0.1` 的 CDP 端口与 Windows SSH 隧道提供一次性人工操作入口；不安装 Linux 桌面或 VNC，不共享候选浏览器资料。程序必须先确认可视验证消失及短信倒计时出现，再读取动态码；可视验证、短信码、Cookie、挑战令牌和请求体均不进入结果证据。该入口只解除 PoC 的认证初始化阶段门，不计入 2000 条计时窗口，也不构成正式功能方案。

短信人工初始化的资源路由必须放行图片与图片集，确保滑块背景、拼图和验证码素材完整加载；该例外只作用于认证初始化，不改变普通登录诊断和2000条吞吐访问对非必要图片、媒体与字体的资源控制。若验证码出现图片加载错误，应先核对候选自身路由事件，再分析外部网络，不把页面可见或验证容器存在单独视为可操作验证。

部署执行边界：

- 阶段 2.5 和阶段 3 直接使用最终部署的 Linux 主机，不使用临时等价主机代替；
- 项目负责人手动上传测试包、核对 SHA-256、解压并执行文档中的脚本；
- Codex 不远程登录、不上传文件，也不自动操作最终 Linux 主机；
- 人工只负责环境准备和命令触发，不人工统计完成量、不编辑指标文件、不补齐失败结果；
- `run-poc.sh` 自动保存包版本、Git 提交、`SHA256SUMS`、环境快照、开始/结束时间、输入清单哈希、逐 URL 状态、帖子标识与内容证明、风控事件和资源指标；
- 每个候选对 `login` 和 `empty` 各最多保存 3 条脱敏访问形态，只含 URL 哈希、页面形态、已知控制标记、主文档状态链及 Cookie 数量/名称集合哈希，不含完整 URL、页面正文或 Cookie 内容；
- 每个候选由 `setsid` 启动为独立进程组；候选入口结束、硬截止或外层终止时，以 TERM/KILL 有界清理同组 npm、tsx 和浏览器子进程；
- `run-poc.sh` 只写入本次测试产生的数据，不扫描或收集服务器上的其他文件；
- Linux 测试包内每轮结果目录固定为 `results/<candidate>/<round>-<timestamp>/`，至少包含环境信息、输入 URL 清单、摘要、逐 URL 结果、请求事件、脱敏访问诊断、资源指标、运行日志和校验值；
- `input-urls.txt` 和逐 URL 结果必须保留实际完整 URL，不以哈希值替代；输入清单哈希仅用于确认两个候选和各轮使用了约定清单；
- 测试结束后由项目负责人把完整轮次目录复制到当前开发电脑的 `artifacts/poc/results/<candidate>/<round>-<timestamp>/`；
- 从最终 Linux 主机复制回来的范围只包含本次测试结果，不包含程序、离线依赖、运行环境、浏览器目录或数据库；
- 结果不执行额外内容脱敏。结果数据结构本身不定义账号、密码、Cookie 或令牌字段，日志也不得写入这些内容。

每轮结果目录采用固定文件名和格式：

| 文件 | 格式 | 用途 |
|---|---|---|
| `environment.json` | JSON | Linux、硬件、运行时、依赖、浏览器和测试包环境快照 |
| `summary.json` | JSON | 轮次、起止时间、输入数、完成数、访问成功率、访问证明完整率、风控事件和最终结论 |
| `input-urls.txt` | UTF-8 纯文本 | 按实际测试顺序每行保存一个完整 URL |
| `url-results.jsonl` | JSONL | 每行保存一个 URL 的最终状态、耗时、帖子标识匹配、真实内容证明和错误分类 |
| `request-events.jsonl` | JSONL | 每行保存一次请求、重试、恢复或异常事件 |
| `access-diagnostics.jsonl` | JSONL | 有界保存 `login/empty` 的脱敏页面形态、主文档状态链和 Cookie 形态 |
| `resource-metrics.csv` | CSV | 按时间采样保存 CPU、内存和浏览器进程数量 |
| `run.log` | UTF-8 纯文本 | 保存测试运行日志，不写入凭证 |
| `SHA256SUMS` | UTF-8 纯文本 | 校验该轮目录中上述结果文件 |

JSON、JSONL、CSV 和日志统一使用 UTF-8；时间使用带时区的 ISO 8601 格式。两个候选必须生成相同文件结构和字段定义。

首轮 2000 条出现大面积 `login/empty` 后，先运行 `test-access-transition.sh`：按原输入顺序固定取前 500 条，保持两个候选原并发、资源路由和会话方式，每个候选使用 1200 秒诊断窗口。该运行只复核分类转变、会话形态和进程退出，不计为阶段 3 的 2000 条正式轮次；诊断完成后复制其压缩包和外层 SHA-256 回开发机复核。

转变诊断已确认两个候选在持续并发后均收到 HTTP 200 空文档；现有 `test-single-concurrency.sh candidate-a|candidate-b`、全新隔离会话初始化和 v0.2.18 包继续保留为浏览器路径历史证据，但不作为阶段 2A 的失败兜底。当前直接 HTTP/Spider 本地预筛必须先独立形成“通过或失败”结论；直接 HTTP 冒烟失败或稳定配置不能满足正确性门槛时，本阶段即失败，不通过切换浏览器补齐结果。浏览器单并发诊断如需继续，必须作为后续独立任务和独立轮次执行。

### 阶段 3：目标吞吐验证

候选方案只有在阶段 2 达到访问正确性门槛后，才能进入目标吞吐测试。两个候选分别判定，不能因为另一方案失败而降低本方案门槛。

阶段 3 必须使用阶段 2.5 生成并通过校验的测试包，直接在最终部署的 Linux 主机执行。最终主机尚不可用时，阶段 3 保持待执行，不以临时主机、开发环境结果或估算值代替。当前开发环境中的吞吐结果只能作为预筛数据，不得替代本阶段的三轮硬门禁。

目标工作负载：

- 以 2000 个帖子 URL 为一个完整测试批次；
- 测试时间窗口为一小时；
- 记录一小时内实际完成数量；
- 记录自动访问成功率、帖子 ID 匹配率、真实内容证明完整率和风控事件；
- 未完成任务必须保留真实状态，不能删除或计为成功；
- 不以无限重试换取表面成功率；
- 实际访问条件必须与未来内部部署条件一致；
- 三轮测试必须使用相同且已记录的 Linux 环境基线，环境发生实质变化后应重新执行三轮。

每小时有效访问 2000 个 URL 是当前采集框架 PoC 的硬性淘汰门槛。达到门槛的候选才有资格进入最终工程评分和第一版正式功能开发。

每轮输入 2000 个已知真实 URL，必须全部有效完成，最终完成率为 100%。任何 `failed`、`partial`、未完成、仍待重试或未确认结果都会使该轮测试失败。

访问证明完整率为 100%：

- 平台响应中的帖子 ID 或等价平台帖子标识与输入 URL 对应；
- 标题存在或正文存在性证明至少一项为真；
- 响应分类为真实帖子内容，不是限流、验证码、挑战页、登录页或异常空响应；
- 对应证据写入本轮 `url-results.jsonl`，而不是只在控制台输出成功字样。

“有效完成”必须满足：

- 在一小时测试窗口内实际访问该 URL；
- 正确识别对应帖子标识和真实内容证明；
- 保存通过统一访问结果校验器的逐 URL 证据；
- 没有将登录页、验证码页、挑战页或无法确认的空响应作为有效结果。

以下数量不得计入完成量：

- 仅进入任务队列但尚未执行；
- 主动跳过或延迟到测试窗口外；
- 测试窗口结束后补跑；
- 超时、无限重试或仍待重试；
- 验证码、登录失效或未确认的风控响应；
- 使用预置缓存代替本轮真实访问；
- 人工修改或补齐后的结果；
- 重复请求少量 URL 放大数量；
- 根据小样本速度外推得到的估算数量。

瞬时网络错误、连接重置或单次请求失败必须保留在原始指标中。候选方案只要在一小时测试窗口内自动恢复，并最终为该 URL 产生通过校验的访问结果，即可把该 URL 计入有效完成，不计为最终失败。

为验证结果可重复，阶段 3 连续执行三轮独立随机测试。每轮都从甲方固定清单中形成满足相同构成规则的 2000 个真实输入，并保存随机种子和实际清单。三轮每轮都必须在一小时内有效完成 2000 个 URL；任何一轮未达标，该候选即未通过吞吐门禁。

如果平台允许的访问条件不足以完成该测试，应记录为外部约束，不能将估算值写成实测值。

需求中所称“必须绕过风控”统一解释为本节的结果门禁，而不是单独指定某种实现技术：

- 限流、验证码、挑战页、登录失效或其他平台控制导致任一 URL 未在一小时内产生有效访问证明时，该轮失败；
- 自动恢复只有在同一小时窗口内产生通过统一校验的访问结果时才计为完成；
- 三轮均通过后，该候选才满足当前实测条件下的风控结果门禁；
- 通过结论绑定候选版本、测试包、URL 清单、账号或未登录模式、网络出口、最终 Linux 主机和测试时间；
- 上述条件实质变化后，原结果不直接外推，重新执行同等级测试；
- 不以某种“绕过”技术名称、框架宣传或临时人工操作代替结果证据。

## 7. 指标与门槛

### 7.1 硬门槛

任一候选出现以下情况时不能胜出：

- 存在无法识别的静默错误数据；
- 将验证码、登录页或挑战页保存为帖子正文；
- 无法稳定核对帖子标识并取得真实内容证明；
- 凭证会进入日志、前端或 Git；
- 任务中断后无法识别已完成与未完成 URL；
- 无法输出统一业务数据结构；
- 必须依赖未进入项目范围的基础设施或服务才能运行。

### 7.2 定量指标

| 指标 | 计算方式 | 当前门槛 |
|---|---|---|
| 自动访问成功率 | 自动产生有效访问证明的 URL / 有效输入 URL | 每轮 100% |
| 帖子 ID 匹配率 | 平台帖子标识与输入对应的 URL / 有效输入 URL | 每轮 100% |
| 内容证明完整率 | 具有标题或正文存在性证明的 URL / 有效输入 URL | 每轮 100% |
| 未恢复风控数 | 窗口结束时仍为限流、验证码、挑战或登录失效的 URL 数 | 0 |
| 吞吐量 | 一小时有效完成并通过访问校验的 URL 数 | 每轮 2000，硬门槛 |
| P95 耗时 | 95% URL 的完成时间上界 | 对比项 |
| 请求放大率 | 实际请求总数 / 完成 URL 数 | 越低越好 |
| 持续有效速度 | 稳定窗口内通过统一校验的 URL 数 / 稳定窗口秒数 | 至少支撑当前2000 URL/小时门槛；扩展目标单列 |
| 首次控制时间 | 从本级开始到首次 login/empty/captcha/challenge/rate_limited 的时间与已完成数 | 越晚越好；出现后不得只报平均速度 |
| 会话稳定性 | 会话寿命、退休原因、令牌刷新/复用次数和控制后恢复结果 | 对比项；不得泄露令牌值 |
| 峰值内存 | 进程及子浏览器峰值总和 | 待主机规格确认 |
| 恢复正确率 | 中断恢复后无丢失、无重复的任务比例 | 必须通过 |

### 7.3 工程评分

硬门槛通过后，再按以下维度评审：

| 维度 | 建议权重 |
|---|---:|
| 访问正确性与风控识别 | 30% |
| 连续运行稳定性 | 25% |
| 目标吞吐和资源效率 | 20% |
| 开发及维护复杂度 | 15% |
| 部署、日志与现有后端集成 | 10% |

权重用于区分两个均通过硬门槛的方案，不能用总分掩盖硬门槛失败。

### Git 存储边界

- 当前开发电脑上的所有本地 PoC 产物统一放在 `artifacts/poc/`，不得散落到仓库其他路径；
- 甲方填写后的真实清单放在 `artifacts/poc/inputs/`；
- 包含离线依赖、浏览器运行时的 Linux PoC 测试包放在 `artifacts/poc/packages/<candidate>/`；
- 从 Linux 复制回来的各轮结果放在 `artifacts/poc/results/<candidate>/<round>-<timestamp>/`，同一轮的环境、URL 明细、逐 URL 结果、请求事件、资源指标、日志和校验值都保存在该轮目录内；
- 整个 `artifacts/poc/` 只保存在本地，不提交 Git；
- 完整 URL 只保存在本地原始结果中；进入 Git 的汇总报告仅记录样本数量、构成、清单哈希和结论，不列出完整 URL 清单；
- Git 只提交 `docs/research/collector-stack-poc-results.md` 汇总报告、最终技术选型 ADR、必要的汇总表和用于关联本地原始结果的 SHA-256；
- 汇总报告必须记录候选版本、测试包 SHA-256、各轮结果目录的 `SHA256SUMS`、三轮结论和失败原因，使本地原始证据可以被定位；
- Linux PoC 测试包和原始测试结果至少保留到第一版验收完成，之后由项目负责人手动决定继续保留或删除，不自动清理；
- 仓库通过 `.gitignore` 统一忽略 `artifacts/poc/`。

## 10. 决策规则

1. 只有一个候选通过全部硬门槛：选择通过者；
2. 两个候选均通过：根据定量指标和工程评分选择；
3. 两个候选均未通过：保持技术路线未确认，扩大候选范围、调整采集架构或重新评估数据获取方式，然后重新执行同等级 PoC；
4. 任一候选只有单次成功、无法复现：视为未通过；
5. 框架文档中的性能或隐蔽性宣传不能代替本项目实测；
6. 最终决定必须能够回溯到样本、版本、指标和失败记录。
