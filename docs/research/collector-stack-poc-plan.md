# 提取功能服务技术栈对比 PoC 计划

## 1. 文档状态

- 状态：技术选型前置计划；
- 目的：在正式功能开发前，以可复现证据决定提取功能服务最终使用 Python 还是 Node.js；
- 当前结论：尚未选定胜出方案；
- 前置关系：本 PoC 是第一版正式业务工程开发的强制前置门禁。

## 2. 对比候选

### 2.1 候选方案 A

| 层次 | 候选组件 |
|---|---|
| 语言 | Python |
| 内部 Web API | FastAPI |
| 采集框架 | Scrapling |
| 普通请求通道 | Scrapling HTTP Fetcher |
| 动态页面通道 | Scrapling 标准动态页面采集能力 |

### 2.2 候选方案 B

| 层次 | 候选组件 |
|---|---|
| 语言 | Node.js + TypeScript |
| 内部 Web API | Fastify |
| 采集框架 | Crawlee |
| 普通请求通道 | Crawlee HTTP/Cheerio Crawler |
| 动态页面通道 | Crawlee PlaywrightCrawler + Playwright |

### 2.3 不进入本轮候选

- Scrapy + Playwright；
- Go/Colly；
- Apache Nutch；
- 纯 Selenium；
- 仅依赖 OCR 或视觉模型的采集方案；
- 依赖动态代理池、自动验证码破解或对抗性签名破解的方案。

这些方案可以保留在通用技术调研中，但不进入本次项目决策评分。

## 3. 公平对比原则

两个方案必须满足：

1. 使用同一批真实 URL；
2. 同一测试阶段使用同一运行主机、同一网络出口和相同资源条件；
3. 使用相同且有权使用的账号、Cookie 或访问条件；
4. 使用同一字段定义和结果校验器；
5. 每个帖子提取正文及平台实际返回的最多十条一级评论；
6. 不采集楼中楼；
7. 对不可见、删除、登录失效和验证页面使用相同分类规则；
8. 不把验证码页、登录页或异常空数据计为成功；
9. 不把人工修补后的数据计为自动采集成功；
10. 凭证、Cookie、令牌和原始个人数据不得进入 Git；
11. 所有时间、成功率和资源指标由独立测试驱动记录，不能只采用框架自身日志；
12. 两个方案都要保留可复现的安装说明和版本锁定文件。

访问模式额外遵循：

- 默认先验证未登录模式；
- 未登录模式能够满足正文和主评论 100% 完整率时，不启用登录；
- 未登录模式不足时，由甲方提供合法登录会话，两个候选使用相同授权条件；
- 访问模式改变后重新开始测试轮次，不能把未登录和登录结果拼接成一次达标结果；
- 不在吞吐测试中为每个 URL 先匿名失败一次再切换登录，避免重复请求放大；
- 最终选型报告必须标明每轮使用的访问模式。
- 需要账号密码时通过验证版配置页面录入并保存到本地数据库；允许明文持久化，但查询接口不得回显，且不得进入日志、导出、测试报告或 Git；
- 两个候选均只使用同一套全局懂车帝账号，不测试多账号选择或轮换；

## 4. 统一输出契约

两个 PoC 至少输出：

| 字段 | 说明 |
|---|---|
| URL | 输入帖子链接 |
| 平台帖子 ID | 平台提供时保存 |
| 标题 | 真实可获取时保存 |
| 作者 | 真实可获取时保存 |
| 发布时间 | 真实可获取时保存 |
| 正文 | 详情内容 |
| 图片 URL | 正文中平台实际提供的图片地址列表 |
| 视频 URL | 正文中平台实际提供的视频地址列表 |
| 点赞数 | 提取时数值 |
| 回复数 | 提取时数值 |
| 主评论 | 最多十条一级评论 |
| 可见状态 | visible / hidden / unknown |
| 采集通道 | http / browser-network / browser-dom |
| 状态 | success / partial / failed / blocked |
| 请求次数 | 完成该 URL 的实际请求数 |
| 开始与结束时间 | 用于计算耗时 |
| 错误分类 | 失败或不完整时记录 |

任何平台未提供的字段允许为空，不得推断或伪造。

## 5. 测试样本

正式测试前由甲方提供固定清单模板。清单应按功能模块或样本类型分组，并尽量覆盖：

- 正常可访问帖子；
- 评论少于十条的帖子；
- 评论不少于十条的帖子；
- 已删除、审核中、仅登录可见或异常帖子；
- 包含长正文、图片或特殊字符的帖子；
- 重复 URL 和不同形式但指向同一帖子的 URL；
- 必要的合法登录条件。

部分功能模块允许暂时只有一条样本，但该样本只能证明该条数据可以被处理，不能单独证明该模块在不同数据上的普遍稳定性。

样本应包含人工确认的期望结果，作为正确性判定基准。随机测试必须满足：

- 只从甲方确认的固定清单中抽取；
- 两个候选在同一轮使用完全相同的抽样结果；
- 保存随机种子、抽样时间和实际 URL 清单，保证结果可以复现；
- 不得为了让某个候选通过而删除失败样本或重新抽样；
- 固定功能覆盖样本与吞吐样本分开管理。

功能覆盖样本用于验证不同模块、数据状态和字段正确性。甲方已确认可以提供至少 2000 个不同、且在测试开始前已知有效的真实帖子 URL；吞吐样本从该输入池中形成。重复 URL 必须单独统计，不得通过重复请求少量 URL 放大完成数量。

甲方填写模板已经固定：

- `docs/templates/poc/throughput-urls-template.txt`：每行一个完整 URL，甲方删除占位内容后提供至少 2000 个不同且有效的 URL；
- `docs/templates/poc/functional-samples-template.csv`：按模块填写功能样本、预期可见状态、正文预期、评论档位、登录要求和人工确认时间；
- `docs/templates/poc/README.md`：字段解释、示例和返回前检查规则。
- `docs/templates/poc/threadsnap-poc-client-input-templates-v1.0.zip`：包含上述三份文件，可直接发送给甲方。

模板文件本身进入 Git；甲方填写后的真实清单属于本地 PoC 输入，固定保存为 `artifacts/poc/inputs/throughput-urls.txt` 和 `artifacts/poc/inputs/functional-samples.csv`，不覆盖模板，不提交 Git。

## 6. 测试阶段

### 阶段 0：环境与样本确认

目标：

- 记录当前开发环境的操作系统、硬件、网络和运行时基线；
- 准备最终部署的 Linux 主机；该主机尚不可用时只执行开发环境预筛，不执行 Linux 硬门禁；
- 记录 Linux 发行版、CPU 架构、libc、语言运行时和浏览器系统依赖基线；
- 固化语言、浏览器和依赖版本；
- 确认网络出口；
- 确认样本 URL 与期望字段；
- 确认凭证提供和保存方式；
- 先验证未登录模式是否满足完整性门槛，必要时再固化登录模式；
- 确认目标页面是否允许当前访问方式。

阶段 0 未完成时不得开始性能比较。

环境分工：

- 阶段 1 和阶段 2 可以在当前开发环境执行，用于功能验证、错误发现和候选预筛；
- 两个候选在同一阶段必须使用同一台开发主机和相同测试条件；
- 开发环境的阶段 1、阶段 2 结果不构成最终技术选型或交付性能验收；
- 进入阶段 3 前，两个候选都必须生成 Linux PoC 测试包，并在最终部署的 Linux 主机完成安装、启动和功能校验；
- 不使用 Docker 消除环境差异，必须真实验证 Linux 下的依赖、浏览器运行时、路径、文件权限和进程行为。

### 阶段 1：功能冒烟

从甲方固定清单中抽取覆盖各功能模块和不同状态的样本。只有一条样本的模块必须纳入，但应在报告中标记其覆盖有限。

验证：

- HTTP 通道是否能获取数据；
- 动态页面通道是否能获取数据；
- 正文及前十条一级评论是否正确；
- 登录页、验证码页和异常空数据能否被正确识别；
- 字段标准化是否一致；
- 单条失败是否会影响其他 URL。

任一方案出现静默错误数据时，不进入下一阶段。

### 阶段 2：中等批量对比

从甲方固定清单中随机抽取不少于 200 条且不与冒烟样本完全重合的 URL。两个候选使用同一抽样结果和随机种子。

验证：

- 自动成功率；
- 完整率；
- HTTP 与浏览器通道占比；
- 平均耗时、P50、P95 和最大耗时；
- 每个 URL 的平均请求数；
- CPU、内存和浏览器进程数量；
- 超时、重试、403、429、验证页面和登录失效数量；
- 进程中断后的任务恢复能力；
- 重复 URL 是否产生重复数据。

### 阶段 2.5：打包与 Linux 部署验证

阶段 2 通过后，为每个仍在候选范围内的方案生成独立 Linux PoC 测试包。该步骤属于 PoC，不属于第一版正式业务功能开发。

最简打包方式统一为 `tar.gz`。当前开发电脑中的测试包统一放在 `artifacts/poc/packages/<candidate>/`，文件名采用：

`threadsnap-poc-<candidate>-<version>-linux.tar.gz`

测试包至少包含：

- 候选原型源代码或必要构建产物；
- 锁定的依赖描述及对应校验信息；
- `deps/`：面向目标 Linux 环境生成的离线应用依赖；Python 候选使用 wheelhouse，Node.js 候选使用完整的离线包缓存或等价 vendor 目录；
- `browsers/`：候选方案需要浏览器时，保存与框架版本匹配的 Linux 浏览器运行时；
- `SHA256SUMS`：覆盖原型、锁文件、离线依赖、浏览器运行时和脚本；
- `preflight.sh`：检查发行版、CPU 架构、libc、语言运行时和必要系统库；
- `install.sh`：在 Linux 中创建独立应用环境，并且只从包内离线依赖安装；
- `start.sh`：以前台或简单后台方式启动 PoC 服务；
- `healthcheck.sh`：验证进程和内部接口可用；
- `run-poc.sh`：执行统一样本验证和阶段 3 基准测试，并把本轮结果直接写入固定结构的结果目录；
- `README.md`：记录支持的运行时版本、配置步骤、启动命令和已知限制；
- 测试包的 SHA-256 校验值。

测试包不得包含：

- Windows 虚拟环境、`.venv` 或 `node_modules`；
- Windows 浏览器二进制或开发机浏览器缓存；
- 账号、密码、Cookie、令牌或真实配置文件；
- 本地数据库、历史采集结果或预置性能测试结果；
- 与候选方案无关的开发工具和临时文件。

Linux 部署验证必须从干净目录解压测试包后执行，并确认：

1. 压缩包校验值正确；
2. `preflight.sh` 验证实际 Linux 环境与测试包目标基线匹配；
3. 在临时禁止依赖仓库访问的条件下，安装脚本仍可建立独立应用环境并安装全部应用依赖；
4. 安装过程没有从公网解析或下载应用包和浏览器运行时；
5. 浏览器运行时及原生系统依赖可以正常启动；
6. 路径、文件权限、字符编码和时区行为正确；
7. 服务启动与健康检查成功；
8. 统一功能样本通过；
9. 运行目录没有依赖开发工作区或人工复制的机器状态。

任一候选不能通过该阶段时，不得进入阶段 3。禁止在 Linux 主机上人工修改代码后直接继续测试；修复必须回到候选源码，重新生成带新版本号和校验值的测试包。

Linux 测试机虽然允许联网，但联网能力不作为应用依赖安装成功的组成部分。语言运行时、浏览器所需系统库等主机级前置环境可以按已记录的精确版本在线准备；PoC 应用依赖和浏览器运行时必须由测试包离线提供。若离线包缺少依赖，必须重新构建测试包，不能在验收目录中临时联网补装后继续计入结果。

部署执行边界：

- 阶段 2.5 和阶段 3 直接使用最终部署的 Linux 主机，不使用临时等价主机代替；
- 项目负责人手动上传测试包、核对 SHA-256、解压并执行文档中的脚本；
- Codex 不远程登录、不上传文件，也不自动操作最终 Linux 主机；
- 人工只负责环境准备和命令触发，不人工统计完成量、不编辑指标文件、不补齐失败结果；
- `run-poc.sh` 自动保存包版本、Git 提交、`SHA256SUMS`、环境快照、开始/结束时间、输入清单哈希、逐 URL 状态、请求事件、完整率和资源指标；
- `run-poc.sh` 只写入本次测试产生的数据，不扫描或收集服务器上的其他文件；
- Linux 测试包内每轮结果目录固定为 `results/<candidate>/<round>-<timestamp>/`，至少包含环境信息、输入 URL 清单、摘要、逐 URL 结果、请求事件、资源指标、运行日志和校验值；
- `input-urls.txt` 和逐 URL 结果必须保留实际完整 URL，不以哈希值替代；输入清单哈希仅用于确认两个候选和各轮使用了约定清单；
- 测试结束后由项目负责人把完整轮次目录复制到当前开发电脑的 `artifacts/poc/results/<candidate>/<round>-<timestamp>/`；
- 从最终 Linux 主机复制回来的范围只包含本次测试结果，不包含程序、离线依赖、运行环境、浏览器目录或数据库；
- 结果不执行额外内容脱敏。结果数据结构本身不定义账号、密码、Cookie 或令牌字段，日志也不得写入这些内容。

每轮结果目录采用固定文件名和格式：

| 文件 | 格式 | 用途 |
|---|---|---|
| `environment.json` | JSON | Linux、硬件、运行时、依赖、浏览器和测试包环境快照 |
| `summary.json` | JSON | 轮次、起止时间、输入数、完成数、成功率、完整率和最终结论 |
| `input-urls.txt` | UTF-8 纯文本 | 按实际测试顺序每行保存一个完整 URL |
| `url-results.jsonl` | JSONL | 每行保存一个 URL 的最终状态、耗时、完整性和错误分类 |
| `request-events.jsonl` | JSONL | 每行保存一次请求、重试、恢复或异常事件 |
| `resource-metrics.csv` | CSV | 按时间采样保存 CPU、内存和浏览器进程数量 |
| `run.log` | UTF-8 纯文本 | 保存测试运行日志，不写入凭证 |
| `SHA256SUMS` | UTF-8 纯文本 | 校验该轮目录中上述结果文件 |

JSON、JSONL、CSV 和日志统一使用 UTF-8；时间使用带时区的 ISO 8601 格式。两个候选必须生成相同文件结构和字段定义。

### 阶段 3：目标吞吐验证

候选方案只有在阶段 2 达到数据正确性门槛后，才能进入目标吞吐测试。两个候选分别判定，不能因为另一方案失败而降低本方案门槛。

阶段 3 必须使用阶段 2.5 生成并通过校验的测试包，直接在最终部署的 Linux 主机执行。最终主机尚不可用时，阶段 3 保持待执行，不以临时主机、开发环境结果或估算值代替。当前开发环境中的吞吐结果只能作为预筛数据，不得替代本阶段的三轮硬门禁。

目标工作负载：

- 以 2000 个帖子 URL 为一个完整测试批次；
- 测试时间窗口为一小时；
- 每帖最多十条一级评论；
- 记录一小时内实际完成数量；
- 记录自动成功率和正文、主评论的数据完整率；
- 未完成任务必须保留真实状态，不能删除或计为成功；
- 不以无限重试换取表面成功率；
- 实际访问条件必须与未来内部部署条件一致；
- 三轮测试必须使用相同且已记录的 Linux 环境基线，环境发生实质变化后应重新执行三轮。

每小时有效完成 2000 个 URL 是真实交付硬要求，也是候选方案的硬性淘汰门槛。达到门槛的候选才有资格进入最终工程评分。

每轮输入 2000 个已知有效 URL，必须全部有效完成，最终完成率为 100%。任何 `failed`、`partial`、未完成、仍待重试或未确认结果都会使该轮测试失败。

必需字段完整率为 100%：

- 可见帖子必须取得正文；
- 一级评论少于十条时全部取得；
- 一级评论达到或超过十条时，按平台返回顺序取得前十条；
- 平台本身未提供的可选字段允许为空；
- 实际存在但因解析失败而缺失的字段不能按“平台未提供”处理。
- 平台在正文中实际提供图片或视频地址时保存其 URL，不下载媒体文件。

“有效完成”必须满足：

- 在一小时测试窗口内实际访问该 URL；
- 正确识别真实帖子、隐藏、删除或其他有证据支持的平台状态；
- 保存通过统一字段校验器的数据或平台终态；
- 没有将登录页、验证码页、挑战页或无法确认的空响应作为有效结果。

以下数量不得计入完成量：

- 仅进入任务队列但尚未执行；
- 主动跳过或延迟到测试窗口外；
- 测试窗口结束后补跑；
- 超时、无限重试或仍待重试；
- 验证码、登录失效或未确认的风控响应；
- 使用预置缓存代替本轮真实访问；
- 人工修改或补齐后的结果；
- 重复请求少量 URL 放大数量；
- 根据小样本速度外推得到的估算数量。

瞬时网络错误、连接重置或单次请求失败必须保留在原始指标中。候选方案只要在一小时测试窗口内自动恢复，并最终为该 URL 产生通过校验的完整结果，即可把该 URL 计入有效完成，不计为最终失败。

为验证结果可重复，阶段 3 连续执行三轮独立随机测试。每轮都从甲方固定清单中形成满足相同构成规则的 2000 个真实输入，并保存随机种子和实际清单。三轮每轮都必须在一小时内有效完成 2000 个 URL；任何一轮未达标，该候选即未通过吞吐门禁。

如果平台允许的访问条件不足以完成该测试，应记录为外部约束，不能将估算值写成实测值。

需求中所称“必须绕过风控”统一解释为本节的结果门禁，而不是单独指定某种实现技术：

- 限流、验证码、挑战页、登录失效或其他平台控制导致任一 URL 未在一小时内完整完成时，该轮失败；
- 自动恢复只有在同一小时窗口内产生通过统一校验的完整结果时才计为完成；
- 三轮均通过后，该候选才满足当前实测条件下的风控结果门禁；
- 通过结论绑定候选版本、测试包、URL 清单、账号或未登录模式、网络出口、最终 Linux 主机和测试时间；
- 上述条件实质变化后，原结果不直接外推，重新执行同等级测试；
- 不以某种“绕过”技术名称、框架宣传或临时人工操作代替结果证据。

## 7. 指标与门槛

### 7.1 硬门槛

任一候选出现以下情况时不能胜出：

- 存在无法识别的静默错误数据；
- 将验证码、登录页或挑战页保存为帖子正文；
- 无法稳定取得约定范围内的正文和主评论；
- 凭证会进入日志、前端或 Git；
- 任务中断后无法识别已完成与未完成 URL；
- 无法输出统一业务数据结构；
- 必须依赖未进入项目范围的基础设施或服务才能运行。

### 7.2 定量指标

| 指标 | 计算方式 | 当前门槛 |
|---|---|---|
| 自动成功率 | 自动成功 URL / 有效输入 URL | 每轮 100% |
| 正文完整率 | 正文与人工样本一致的 URL / 可见 URL | 100% |
| 评论完整率 | 约定范围内主评论正确的 URL / 应有评论 URL | 100% |
| 吞吐量 | 一小时有效完成并通过校验的 URL 数 | 每轮至少 2000，硬门槛 |
| P95 耗时 | 95% URL 的完成时间上界 | 对比项 |
| 请求放大率 | 实际请求总数 / 完成 URL 数 | 越低越好 |
| 峰值内存 | 进程及子浏览器峰值总和 | 待主机规格确认 |
| 恢复正确率 | 中断恢复后无丢失、无重复的任务比例 | 必须通过 |

### 7.3 工程评分

硬门槛通过后，再按以下维度评审：

| 维度 | 建议权重 |
|---|---:|
| 数据正确性与完整性 | 30% |
| 连续运行稳定性 | 25% |
| 目标吞吐和资源效率 | 20% |
| 开发及维护复杂度 | 15% |
| 部署、日志与现有后端集成 | 10% |

权重用于区分两个均通过硬门槛的方案，不能用总分掩盖硬门槛失败。

## 8. 需要记录的实现成本

- 完成统一输出契约的工时；

## 9. 测试产物

PoC 完成后至少产生：

1. 两个隔离的候选原型；
2. 两套锁定的依赖清单；
3. 两个候选包含离线应用依赖和浏览器运行时的 Linux PoC `tar.gz` 测试包及 `SHA256SUMS`；
4. Linux 安装、启动、健康检查和基准测试脚本；
5. 统一样本清单；
6. 统一结果校验器；
7. 按固定结果结构生成的原始指标文件；
8. Linux 部署与运行验证记录；
9. 每轮由 `run-poc.sh` 生成的固定结果目录及 `SHA256SUMS`；
10. `docs/research/collector-stack-poc-results.md` 对比报告；
11. 更新后的 `docs/design/technical-route.md`；
12. 最终技术选型 ADR。

PoC 原型默认是验证代码。只有经代码审查、测试和结构评估后，胜出方案的代码才可以进入正式业务工程。

### Git 存储边界

- 当前开发电脑上的所有本地 PoC 产物统一放在 `artifacts/poc/`，不得散落到仓库其他路径；
- 甲方填写后的真实清单放在 `artifacts/poc/inputs/`；
- 包含离线依赖、浏览器运行时的 Linux PoC 测试包放在 `artifacts/poc/packages/<candidate>/`；
- 从 Linux 复制回来的各轮结果放在 `artifacts/poc/results/<candidate>/<round>-<timestamp>/`，同一轮的环境、URL 明细、逐 URL 结果、请求事件、资源指标、日志和校验值都保存在该轮目录内；
- 整个 `artifacts/poc/` 只保存在本地，不提交 Git；
- 完整 URL 只保存在本地原始结果中；进入 Git 的汇总报告仅记录样本数量、构成、清单哈希和结论，不列出完整 URL 清单；
- Git 只提交 `docs/research/collector-stack-poc-results.md` 汇总报告、最终技术选型 ADR、必要的汇总表和用于关联本地原始结果的 SHA-256；
- 汇总报告必须记录候选版本、测试包 SHA-256、各轮结果目录的 `SHA256SUMS`、三轮结论和失败原因，使本地原始证据可以被定位；
- Linux PoC 测试包和原始测试结果至少保留到第一版验收完成，之后由项目负责人手动决定继续保留或删除，不自动清理；
- 仓库通过 `.gitignore` 统一忽略 `artifacts/poc/`。

## 10. 决策规则

1. 只有一个候选通过全部硬门槛：选择通过者；
2. 两个候选均通过：根据定量指标和工程评分选择；
3. 两个候选均未通过：保持技术路线未确认，扩大候选范围、调整采集架构或重新评估数据获取方式，然后重新执行同等级 PoC；
4. 任一候选只有单次成功、无法复现：视为未通过；
5. 框架文档中的性能或隐蔽性宣传不能代替本项目实测；
6. 最终决定必须能够回溯到样本、版本、指标和失败记录。

## 11. 环境输入与待确认事项

### 11.1 已确认

- 甲方已确认可在目标 Linux 主机提供 `cat /etc/os-release`、`uname -m` 和 `ldd --version` 的完整输出，无需为采集这些信息额外安装工具；具体值待主机确定后记录；
- PoC 部署人员具有 `sudo` 或 root 权限，可以安装语言运行时、浏览器系统库等主机级依赖；
- Linux 测试完成后由项目负责人只把完整轮次结果目录复制到当前开发电脑的 `artifacts/poc/results/<candidate>/<round>-<timestamp>/`，用于复核和技术选型；
- 每轮结果统一使用 `environment.json`、`summary.json`、`input-urls.txt`、`url-results.jsonl`、`request-events.jsonl`、`resource-metrics.csv`、`run.log` 和 `SHA256SUMS`；

### 11.2 待确认

- 目标 Linux 的发行版、版本和主机规格；
- 目标 Linux 的 CPU 架构、libc、语言运行时及可预装的浏览器系统依赖；
- 甲方固定清单的模板字段和模块分组；
- 如果未登录模式不足，合法登录会话的具体提供方式；
